# HTTP-сервис oncl-server

Для кого: для тех, кто хочет подписывать и проверять документы по HTTP из своих систем, без десктопной программы. Здесь написано, как запустить `oncl-server`, выдать токен, подключить ключи и не ошибиться с безопасностью. Формат запросов — в [http-api.md](http-api.md).

Сервис не зависит от десктопной программы: у него свои настройки, свои ключи и свой журнал. По умолчанию он ничего не слушает: нужен файл настроек и явное включение.

## Быстрый старт

1. Создайте закрытый каталог и токен:

   ```text
   oncl-server token-create --directory /private/oncl-operator --name client.token
   ```

   Команда создаёт каталог (если его нет), записывает в `client.token` новый 256-битный токен и печатает только **верификатор** (по нему сервис проверяет токен). Существующий файл токена она не перезаписывает.

2. Запишите `server.toml` в тот же каталог (подставьте свой верификатор и каталог журнала):

   ```toml
   enabled = true
   bind = "127.0.0.1:13579"
   audit_directory = "/private/oncl-audit"

   [[tokens]]
   id = "accounting-service"
   verifier = "<64 строчных шестнадцатеричных знака верификатора>"
   actions = ["hash"]
   keys = []
   ```

3. Запустите:

   ```text
   oncl-server serve --config /private/oncl-operator/server.toml --enable-api
   ```

4. Вызовите сервис: `Authorization: Bearer <содержимое файла токена>`. Хеш трёх байт `abc`:

   ```json
   {"operation_id":1,"algorithm":"sha256","digest":"ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad","bytes_in":3}
   ```

Важно знать:

- Запуск без подкоманды сокет не открывает. `serve` без файла настроек не работает.
- При `enabled = false` процесс сразу завершается: журнал, TLS-ключи и слушатель не открываются.
- Остановка: Ctrl-C (SIGINT). С флагом `--shutdown-stdin` сервис останавливает перевод строки или конец ввода в его stdin (для супервизора); Ctrl-C при этом флаге не обрабатывается. Сервис дожидается уже начатых операций. Файлы аудита при остановке сохраняются.

### Закрытый каталог и токены

Каталог оператора должен принадлежать только учётной записи сервиса. Настройки, файл токена и файлы с ключами и PIN — обычные файлы с одной жёсткой ссылкой в таком каталоге. Сервис проверяет права (или ACL), отказывает при ссылках и чужих файлах и никогда не исправляет права сам. Каталог данных десктопа для этого не используйте.

Токен — это пароль:

- передавайте его через средство секретного ввода клиента, а не через аргументы командной строки или журналы;
- в настройках хранится только идентификатор токена, верификатор и права, но не сам токен;
- ни токены, ни ключи, PIN и пароли не попадают в отладочный вывод.

## Настройки server.toml

Конфигурация строгая: неизвестные поля и небезопасные значения отвергаются. Файл не больше 64 КиБ.

```toml
enabled = false
bind = "127.0.0.1:13579"
audit_directory = "/private/oncl-audit"
recover_audit = false
max_in_flight = 2
# max_uploads = 8
blocking_workers = 2
queue_capacity = 2
admission_wait_ms = 1000
operation_timeout_ms = 300000
upload_idle_timeout_ms = 30000
upload_min_bytes_per_second = 1024
max_connections = 32
header_timeout_ms = 5000
input_bytes = 1073741824
container_bytes = 1073741824
memory_per_operation = 268435456
total_memory = 536870912
temp_per_operation = 8589934592
total_temp = 17179869184
framing_bytes = 67108864
metadata_bytes = 67108864
# scratch_directory = "/private/oncl-scratch"
inline_pkcs12 = false

[[tokens]]
id = "accounting-service"
verifier = "<64 строчных шестнадцатеричных знака верификатора>"
actions = ["hash"]
keys = []
```

| Ключ | Что делает | Значение по умолчанию и границы |
|---|---|---|
| `enabled` | включает HTTP (или флаг `--enable-api`) | `false` |
| `bind` | адрес и порт; для IPv6 loopback нужен явный IPv6-адрес | — |
| `hosts` | допустимые значения заголовка `Host` | без него — ровно адрес `bind` с портом |
| `audit_directory` | каталог журнала аудита (абсолютный путь) | — |
| `recover_audit` | открыть существующий журнал заново (см. «Журнал аудита») | `false` |
| `max_in_flight` | сколько операций выполняется одновременно | 1..256 |
| `max_uploads` | сколько тел запросов принимается одновременно | 1..256; см. «Загрузки» |
| `blocking_workers` | рабочие потоки для тяжёлых операций | 1..64 |
| `queue_capacity` | очередь рабочих потоков | не больше 256 |
| `admission_wait_ms` | сколько запрос ждёт свободный слот | не больше `operation_timeout_ms` |
| `operation_timeout_ms` | общий срок операции, включая загрузку | 300 000; 1..86 400 000 |
| `upload_idle_timeout_ms` | сколько ждать следующий кусок тела | 30 000; 1 000..86 400 000 |
| `upload_min_bytes_per_second` | минимальная скорость загрузки, `0` — выключено | 1 024; не больше 1 ГиБ/с |
| `max_connections` | одновременные соединения | 1..1024 |
| `header_timeout_ms` | срок на заголовки | 5 000; не больше `operation_timeout_ms` |
| `input_bytes` | предельный размер документа | 1 ГиБ |
| `container_bytes` | запас на подпись или конверт у уже подписанного входа | 1 ГиБ; уменьшайте вместе с `input_bytes` |
| `memory_per_operation` / `total_memory` | память на операцию / на весь сервис | 256 МиБ / 512 МиБ |
| `temp_per_operation` / `total_temp` | временные файлы на операцию / всего | 8 ГиБ / 16 ГиБ |
| `framing_bytes` | запас на служебные байты multipart | 64 МиБ |
| `metadata_bytes` | память под отчёты проверки XML/PDF | 64 МиБ; не меньше 32 КиБ; для пакетов подписей XML/PDF увеличьте |
| `scratch_directory` | каталог временных файлов (нужен для multipart с документами) | необязательно |
| `inline_pkcs12` | разрешить ключи PKCS#12 прямо в запросе | `false` |
| `audit_segment_bytes` | размер сегмента журнала | 1 048 576 |
| `audit_quota_bytes` | квота журнала | 67 108 864, больше 64 МиБ нельзя |

Ещё ограничения: не больше 256 токенов, 64 ключей, 16 плагинов и 32 записей `hosts`.

Права токена (`actions`): `hash`, `verify`, `extract`, `inspect`, `extend`, `stamp`, `verify_stamp`, `sign`, `sign_digest`. Отдельное право `batch` нужно для `POST /v1/batch`.

### Заголовок Host

Без `hosts` сервис принимает в `Host` ровно свой адрес сокета вместе с портом. Если клиенты обращаются по имени, задайте `hosts = ["localhost:13579"]`. Шаблонов (`*`) нет. Заголовок `Origin` никаких прав не даёт.

## Маршруты

Других маршрутов нет:

| Маршрут | Что делает |
|---|---|
| `POST /v1/hash` | SHA-256 от сырого тела запроса. Нужно право `hash` |
| `POST /v1/operations` | хеш, проверка, подпись, извлечение и другие операции. См. [http-api.md](http-api.md) |
| `POST /v1/batch` | упорядоченный пакет операций. Нужно право `batch` |
| `GET /v1/openapi.json` | описание API. Нужен действительный токен, право `hash` не нужно |
| `GET /health` | состояние сервиса и журнала аудита. Нужно право `hash` |

Правила запросов:

- Content-Length необязателен. Тело неизвестной длины (chunked) тоже считается по лимитам.
- Тело документа для хеша не накапливается в памяти и не пишется на диск.
- Отвергаются: параметры запроса (query), селекторы ключей, заголовки подмены метода, несовпадающий `X-Oncl-Operation`, трейлеры, абсолютные URL.
- Методы точные: POST для хеша, GET для health. HEAD не заменяет GET.
- Искажённое или обрезанное тело никогда не даёт успешный хеш.
- HTTP-синтаксис, который Hyper не может разобрать, может быть отвергнут без JSON-ответа.

Ошибки содержат `code` и `applied`. Для хеша `applied` всегда `NotApplied` (закрытый ключ не используется).

| Ситуация | Ответ |
|---|---|
| неверная авторизация | 403 |
| искажённый запрос | 400 |
| неизвестный путь, неверный метод | 404 / 405 (`InvalidRequest`, `NotApplied`) |
| превышен лимит байт | 413 |
| нет свободного слота или очередь полна (`CapacityExceeded`) | 503 |
| вышел срок (`DeadlineExceeded`) | 504 |

Скрытых повторов и долговременной очереди документов нет. Шифрования, расшифрования и административных маршрутов нет (шифрование ждёт ГОСТ-бэкенд).

## Явный доступ из локальной сети

Адрес не loopback требует явного режима доступа и точных `hosts`. Есть два варианта.

**1. TLS на самом сервисе.** Сертификат и закрытый ключ ваши (PEM). Ключ должен лежать в закрытом каталоге. Сервис не создаёт CA и не устанавливает сертификаты. Клиентам нужно явно настроить доверие, проверку сертификата отключать нельзя.

```toml
bind = "0.0.0.0:13579"
hosts = ["signing.internal:13579"]
exposure = { mode = "tls", certificate = "/operator/server.crt", private_key = { directory = "/private/oncl-operator", name = "server.key" } }
```

**2. Обратный прокси с TLS в защищённой сети.**

```toml
bind = "0.0.0.0:13579"
hosts = ["signing.internal"]
exposure = { mode = "trusted_proxy", peers = ["192.0.2.10"] }
```

- Подключаться могут только пиры из списка `peers`; проверяется настоящий IP сокета.
- `Forwarded`, `X-Forwarded-For`, `Origin` ничего не доверяют и не заменяют токен.
- Между прокси и сервисом TLS нет: защитите этот участок сетью или правилами хоста.
- Адреса вида `::ffff:a.b.c.d` приравниваются к IPv4. Нативный IPv6 — отдельный адрес. Неопределённые адреса (`0.0.0.0`, `::`) в списке недопустимы.

## Именованные ключи оператора

Оператор привязывает к именам файлы PKCS#12/JKS или токены. Клиент в запросе называет только имя, пути к файлам клиент передать не может.

```toml
[[keys]]
source = "file"
name = "corporate-signing"
path = "/operator/corporate.p12"
# alias = "signing" # опускайте только для контейнера с одной записью
secret = { directory = "/private/oncl-operator", name = "container.password" }

# Вариант с токеном:
# [[keys]]
# source = "token"
# name = "card-signing"
# reader = "Operator PCSC Reader"
# kind = "AKKaztokenStore"
# alias = "signing"
# secret = { directory = "/private/oncl-operator", name = "card.pin" }
```

Для подписи клиенту нужны оба: действие (`sign` и т. д.) и точное право на это имя ключа в `keys` токена.

Ключи PKCS#12 прямо в запросе (inline) работают только при двойном согласии: `inline_pkcs12 = true` в настройках сервиса и `inline_pkcs12 = true` у токена. Оба выключены по умолчанию. Подробнее — «Ключи и роли секретов» в [http-api.md](http-api.md).

Проверка подписи по умолчанию идёт с пустым набором доверия и без доступа к сети PKI. Подписывающие операции — отдельные маршруты со своими правами, через запрос проверки они недоступны.

## Журнал аудита

Перед каждым использованием закрытого ключа сервис пишет в журнал запись `BEGIN` и ждёт, пока она попадёт на диск. После операции пишется `FINAL`. Если записать `BEGIN` не удалось, ключ не используется. Если не удалось записать `FINAL` после использования, исход считается неизвестным, новые закрытые операции блокируются, а результат не выдаётся как успех. Второго журнала и режима «разрешить всё» нет.

Новый журнал создаётся сам. Существующий журнал открывается только при `recover_audit = true`. Полностью повреждённый, чужой, старый или занятый другим процессом журнал отвергается. Сервис никогда не чинит и не мигрирует журнал молча. Если сервис перезапускается после первого запуска (`Restart=on-failure`, перезагрузка), держите `recover_audit = true`. Первому запуску он не нужен.

### Код ошибки в записи FINAL

`FINAL` неудачной операции хранит число-код причины в байте 127 кадра. `0` — кода нет: операция удалась или причина неизвестна (например, запись сделало восстановление после перезапуска). У успеха код всегда `0`.

| Число | Код | Число | Код |
|---|---|---|---|
| 1 | `PermissionDenied` | 11 | `TempLimit` |
| 2 | `InteractionRequired` | 12 | `MetadataLimit` |
| 3 | `InvalidRequest` | 13 | `OutputLimit` |
| 4 | `CapacityExceeded` | 14 | `AuditUnavailable` |
| 5 | `DeadlineExceeded` | 15 | `MissingConfiguration` |
| 6 | `Cancelled` | 16 | `KeyNotFound` |
| 7 | `InputLimit` | 17 | `ValidationFailed` |
| 8 | `FramingLimit` | 18 | `OperationFailed` |
| 9 | `MissingTemporaryStore` | 19 | `Internal` |
| 10 | `MemoryLimit` | 255 | число, которого читатель не знает |

Числа не меняются. Новый код получает следующее число. Неизвестное число читатель читает как `255`. Журнал, записанный прежней версией, читается без изменений.

**Откат на прежнюю версию.** Старый сервер считает такой байт повреждением и не запустится над журналом, где есть `FINAL` с кодом. Перед откатом переместите весь каталог аудита в архив, чтобы старый сервер начал новый журнал. То же верно для журнала с записями плагинов (ниже).

### Свидетельства и CRL

Часть запроса со свидетельством (`certificate`, `ocsp`, `crl`) не больше 1 МиБ. Предел движка 2 МиБ на CRL относится к свидетельствам, которые уже лежат внутри проверяемого контейнера. Полный CRL НУЦ (около 20 МБ) сервис не принимает. XAdES-LT/LTA подписываются с CRL не больше примерно 190 КиБ.

### Записи плагинов в журнале

Формат журнала — `ONCLAU02`, кадры по 160 байт. Журнал без плагинов совпадает побайтно с тем, что писали прежние версии (кроме байта 127 в `FINAL`). Плагин, который объявляет использование ключа (`[[operations]]` в манифесте), добавляет два вида кадров.

- **Разрешённое использование ключа.** Перед `BEGIN` пишутся кадры `PluginDetail`: идентификатор плагина, хеш пакета, версия, имя операции, дайджест билета, SHA-256 одобрения (если одобрял пользователь), SHA-256 и длина содержимого, было ли содержимое готовым дайджестом, SHA-256 параметров, вид вызывающего (`browser` / `local-operator` / `service-client`), `declared` и грант оператора. Всё это пишется вместе с `BEGIN` одной записью. Сбой между ними оставляет детали без `BEGIN`: ключ не использовался.
- **Отказ.** Отклонённое использование пишет те же `PluginDetail` и кадр `PluginRefusal` с подкодом (например, `content-mismatch`, `not-granted`, `no-consent-guard`). `BEGIN` не пишется. На операцию попадает не больше четырёх отказов, все они также идут в события `warn` (target `oncl::plugin_audit`). Вызывающий получает `PermissionDenied`. Подкод предназначен оператору, а при необходимости и клиенту API, но не самому плагину.

Плагины без объявлений ничего нового не пишут (`declared=false`). Байты документов, параметры, секреты и одноразовые значения в журнал не попадают. Записи читает `DurableAuditGuard::plugin_records()`.

Что знать оператору:

- **Запись отказов — по возможности.** Она пропускается (отказ лишь логируется), если журнал нездоров, сегмент заполнен, достигнута квота, операция не привязана, это пятый отказ операции или факты нельзя закодировать. Ответ клиенту это не меняет. Использование, факты которого не помещаются (версия плагина или id гранта длиннее 255 байт), отклоняется как `audit-fact-too-long` без использования ключа. Версия в манифесте — до 64 знаков, id плагина, токен гранта и операция — до 64 байт, поэтому на сервере эта проверка скорее страховочная.
- **Дайджест содержимого в журнале.** Он позволяет узнать документ тому, кто читает журнал и может угадать содержимое. Защищайте каталог аудита так же, как каталог с секретами ключей. В лог дайджест попадает только на уровне `debug`.
- **Оборванная запись.** При потере питания файловая система может сохранить поздние кадры без ранних. Тогда журнал повреждён: сервис не запустится и не прочитает `BEGIN` неверно. Чисто обрезанный хвост повреждением не считается: его чинит `recover_audit = true`.
- **Откат.** См. выше: перед запуском старого сервера уберите каталог аудита.
- **Подкоды.** Полный перечень и их соответствие прежним названиям — в [руководстве по ручному окну](manual-plugins.md) и руководстве по SDK. В журнале подкоды записаны в kebab-case (`not-declared`, `package-changed`, `options-mismatch`, `approval-expired`, `key-use-spent` и другие). Всего 49 идентификаторов.

Встроенные ключи PKCS#12 в запросе принимаются в ограниченную память, но не пишутся в каталог временных файлов документа.

## Плагины

WASM-плагин устанавливает оператор. Блок `[[plugins]]` только делает код доступным. Доступ даёт отдельный блок `[[plugins.permissions]]` на пару (токен, операция). Вызывающий плагин определяется токеном. Полный справочник — в [http-api.md](http-api.md), «Справочник по настройке плагинов». Образец: `deploy/server/server.example.toml`.

```toml
[[plugins]]
id = "vendor.sign"
manifest = "/private/plugins/sign.toml"
wasm = "/private/plugins/sign.wasm"

[[plugins.permissions]]
token = "accounting-service"
operation = "sign-file"            # объявленная операция с `server = true`
imports = ["keys_sign_cms_ex"]     # из объявленных импортов; пусто = все объявленные
keys = ["corporate-signing"]       # именованные ключи оператора, они же в `keys` токена
plugin_bytes = true                # плагин или его клиент выбирает, что подписывает ключ
```

**Плагины, которые объявляют операции** (`[[operations]]` в `plugin.toml`):

- Грант должен укладываться в объявление: операция с `server = true`, импорты из объявленных, ключи только для объявленного использования ключа, `pki_endpoints` только для `network = "pki"`. Более широкий грант пропускается со строкой `oncl-server: error:`, остальной сервис работает.
- Объявленные параметры подписи сервис применяет на каждом вызове сам.
- Использование ключа требует `plugin_bytes = true` в гранте: сервер не может связать подписываемые байты с документом. Без него использование отклоняется до `BEGIN` и до ключа (`PermissionDenied`, подкод `not-granted`, `NotApplied`). Грант с ключами без `plugin_bytes` запускается с предупреждением: каждое использование ключа будет отклонено. То же для гранта, чей профиль ключа называет `param:`. Каждая пропущенная строка и предупреждение — также событие `tracing` (target `oncl::plugin_grants`), а итоговая строка говорит, сколько грантов пропущено.
- Если `plugin_bytes = true` есть хотя бы у одного гранта, `audit_segment_bytes` должен быть не меньше 4640 (29 кадров по 160 байт). Иначе это ошибка настроек. Одиночное использование, которое всё же не помещается, отклоняется как `audit-fact-too-long`.
- Один запрос (один идентификатор операции) может использовать ключ один раз. Второй элемент плагина или подпись в нём падает с `key-use-spent`. Использование считается потраченным, только когда журнал его принял.
- Операции, чей профиль называет `param:`, не могут использовать ключи на сервере (`options-mismatch`).

**Плагины без объявлений** (старые и сторонние): ничего не меняется. Грант — это метки оператора, параметры сервис не навязывает, в журнале `declared=false`, и при каждом старте в лог идёт `oncl-server: warning: grant without declaration ...`. `plugin_bytes` там ничего не делает (с предупреждением).

`plugin_bytes = true` без `keys` отвергается проверкой настроек.

### Рекомендации по грантам плагинов

- **Сегодня выдавать нечего.** Поставляемые плагины объявляют 30 операций, все с `manual = true` и ни одной с `server = true` (см. [руководство по ручному окну](manual-plugins.md)). Серверный грант на них пропускается с `oncl-server: error:`. Гранты нужны для сторонних плагинов с `server = true` и для плагинов без объявлений.
- **Что значит `plugin_bytes = true`.** Вы соглашаетесь, что клиент и плагин выбирают байты, которые подписывает именованный ключ. Объявленный профиль всё равно действует: вид, параметры, одно использование на запрос, токен гранта как вызывающий, ключ из `keys` гранта, установленный пакет. Сам запрос тоже проходит права токена: элемент `plugin` с ключами требует право `sign` и каждый ключ в `keys` токена, иначе 403. Давайте `plugin_bytes` только токену, клиенту которого вы доверяете этот ключ.
- **Смотрите журнал запуска.** Пропущенный грант (`grant skipped`), грант с ключами без `plugin_bytes` и грант без объявлений дают по одной строке. Пропущенный грант сервис не останавливает, поэтому проверяйте журнал после каждого изменения настроек или плагина.
- **Нет `FINAL` — значит `Unknown`.** Считайте, что ключ мог быть использован.
- **Ручное окно десктопа в этом журнале не пишет.** Его использования и отказы идут в `tracing`, target `oncl::plugin_audit`.
- **Пределы.** Не больше 16 плагинов, 256 грантов на плагин, 8 ключей и 16 PKI-адресов на грант, идентификаторы по 64 байта. По умолчанию `max_memory` 1 МиБ, `max_transfer` 256 КиБ. Подробнее — [http-api.md](http-api.md).

## Лимиты и ожидание

Изменения настроек и прав вступают в силу при перезапуске. Сетевой запрос отозвать права не может. Уже начатая операция сохраняет свои права и честный исход: отзыв не откатывает её.

### Как запрос проходит через сервис

1. **Загрузка.** Запрос с телом занимает слот загрузки (`max_uploads`) и пишет документы во временный каталог. Пока клиент молчит, занят только этот слот, но не `max_in_flight` и не рабочий поток.
2. **Ожидание слота операции.** Когда тело принято, запрос ждёт слот `max_in_flight` до `admission_wait_ms`. Если слот не освободился, ответ `503 CapacityExceeded`/`NotApplied`, spool удаляется.
3. **Выполнение.** Операция идёт в рабочем потоке (не больше `blocking_workers` одновременно). Срок один на всю операцию (`operation_timeout_ms`): он начинается с приёма запроса и покрывает загрузку, очередь, работу и доставку ответа. `admission_wait_ms` в срок не входит, но срок идёт.

Запросы без тела (`GET /health`, `GET /v1/openapi.json`) слот загрузки не занимают. Если все слоты заняты, запрос ждёт до `admission_wait_ms` и получает `503`. Клиент с `Expect: 100-continue` видит отказ до того, как отправил тело. Эта предварительная проверка делается по возможности: слот могут занять между проверкой и концом тела, и тогда отказ придёт после тела.

После заголовков ответа срок, отмена или сбой могут только оборвать соединение, нового JSON-ответа уже не будет.

### Загрузки: max_uploads

`max_uploads` — от 1 до 256 и не больше `total_temp / (input_bytes + container_bytes)` (целочисленное деление; по умолчанию 16 ГиБ / 2 ГиБ = 8). Так каждая загрузка может зарезервировать самый большой spool.

- **Не задан (по умолчанию):** `min(8, max(1, total_temp / (input_bytes + container_bytes)))`. Если бюджет снижает значение ниже 8, сервис один раз при старте пишет в stderr: ``oncl-server: `max_uploads` is not set; lowered from 8 to N because total_temp holds M spool(s) of input_bytes + container_bytes``. Если в `total_temp` не помещается даже один spool, значение 1, а более крупная загрузка получает `TempLimit`.
- **Задан явно:** `0`, больше 256 или выше границы отвергается при старте, а сообщение называет ключ и границу (`` `max_uploads` must be 1..=256 and at most N ``).

Для старых `server.toml` без `max_uploads` ничего не ломается. Меняется только значение по умолчанию: при малом `total_temp` оно может быть ниже 8.

Загрузка идёт кусками по 256 КиБ: они собираются в память (учитывается один раз на запрос) и записываются на диск короткими блокирующими записями. Маршрут `/v1/hash` хеширует тело на лету, без записи на диск, но и он занимает слот загрузки.

### Зависшие и медленные загрузки

Остановившаяся загрузка не должна держать слот все 5 минут. Каждое ожидание следующего куска тела подчиняется двум правилам. Считается только время ожидания клиента, а не работа сервера.

- `upload_idle_timeout_ms` (по умолчанию 30 000): если за это время не пришло ни байта, запрос завершается.
- `upload_min_bytes_per_second` (по умолчанию 1 024, `0` — выключено): каждое окно длиной в таймаут простоя должно принести не меньше этого числа байт в секунду. 1 КиБ/с — это около 8 кбит/с, ниже любого канала, способного законно передать документ. Клиент, шлющий 64 КиБ каждые 25 с, проходит, а один байт в секунду нет. При TLS на самом сервисе запись (до 16 КиБ) должна прийти целиком, поэтому держите таймаут простоя выше «16 КиБ / скорость самого медленного законного канала».

Нарушение любого правила даёт `504 DeadlineExceeded`/`NotApplied`. Это происходит при приёме, до использования ключа: `BEGIN` не пишется, spool удаляется, слот освобождается. Новых кодов ошибок нет. Для больших файлов по медленному каналу увеличивайте `operation_timeout_ms`, а не эти два значения.

Чем рискует сервис:

- Зависший клиент занимает один слот загрузки до таймаута простоя. Если `max_uploads` клиентов зависли одновременно, остальные запросы с телом получают `503`, а `/health` остаётся доступным.
- Зависшие загрузки держат spool (до `input_bytes + container_bytes` каждый) и буфер 256 КиБ. Они могут занять весь `total_temp`, и работающая операция получит `TempLimit`.
- Лимита загрузок на токен нет: один (в том числе утёкший) токен может занять все слоты.
- Клиент, который присылает ровно минимальную скорость, держит слот весь `operation_timeout_ms`. В локальной сети поднимите `upload_min_bytes_per_second` до десятков КиБ/с.
- Клиент, который не читает большой ответ, держит свой слот выполнения до конца срока.

Чтобы расширить запас: уменьшайте `upload_idle_timeout_ms` (но не ниже самого медленного законного канала) и увеличивайте `max_uploads`, пока позволяет `total_temp`.

### Прерванные потоки ответов

Если сбой обрывает уже начавшийся ответ (статус `200` отправлен), сервис обрезает ответ без завершающей записи. Клиент видит только потерянный ответ (`ResponseLost`) и не может отличить причины: **причина видна только на сервере**. Сервис пишет ровно одну строку в stderr (и событие `tracing`, target `oncl::stream_abort`, уровень `error`):

```
oncl-server: stream aborted: operation=1 route=operations item=0 kind=sign code=metadata_limit cause=MetadataLimit applied=not_applied elapsed_ms=6 bytes_in=0 bytes_out=218
```

| Поле | Значение |
|---|---|
| `operation` | идентификатор операции (совпадает с `operation_id` в кадрах прогресса и в журнале аудита) |
| `route` | `operations` или `batch` |
| `item`, `kind` | индекс и вид выполнявшегося элемента; `none` до первого элемента |
| `code` | код ошибки (`metadata_limit`, `output_limit`, `memory_limit`, `temp_limit`, `capacity_exceeded`, `deadline_exceeded`, `cancelled`, `invalid_request`, …) |
| `cause` | имя варианта сбоя (`MetadataLimit`, `OutputLimit`, …) |
| `applied` | `not_applied`, `applied` или `unknown`: был ли применён ключ у элементов, завершившихся до обрыва |
| `elapsed_ms` | миллисекунды от начала потока ответа |
| `bytes_in`, `bytes_out` | счётчики байт по последнему снимку прогресса |

В строке только числа и закрытые имена. Никогда не пишутся текст ошибки, идентификатор элемента, имена файлов, содержимое документов, ключи, пароли, токены, URL и пути. Обрыв увеличивает счётчик `oncl.stream.aborted`.

Не охвачены: клиент, который отключился после заголовков, и обрыв по таймеру срока соединения.

Журнал аудита обрыв не меняет. Сбой до использования ключа `BEGIN` не создаёт. Сбой после использования ключа оставляет `BEGIN` и `FINAL` самого применения (`applied`, `succeeded`), а в строке лога `applied=applied`. Причину обрыва потока `FINAL` не называет: её называет строка лога.

### Запросы, прерванные до ответа

Каждый такой запрос тоже оставляет одну строку в stderr (событие `tracing`, target `oncl::request_abort`; уровень `warn` для срока, `info` для остального):

```
oncl-server: request aborted: route=hash reason=deadline_exceeded elapsed_ms=1500
```

| Поле | Значение |
|---|---|
| `route` | `hash`, `operations` или `batch` |
| `reason` | `deadline_exceeded` — вышел срок или сработало правило простоя или минимальной скорости (клиент получает `504`); `cancelled` — операция отменена; `client_disconnected` — клиент закрыл соединение во время чтения тела; `abandoned` — запрос сброшен до ответа (соединение исчезло или сервис останавливался) |
| `elapsed_ms` | миллисекунды от начала запроса |

Запрос, закончившийся ответом без срока и отмены, строк не пишет. Причины `deadline_exceeded` и `client_disconnected` проверены тестами с настоящим процессом; `cancelled` и `abandoned` — нет.

### Соединения

До аутентификации действуют пределы соединений, заголовков и TLS-рукопожатия: не больше 64 заголовков HTTP/1, буфер разбора соединения 32 КиБ. Они учитываются отдельно от памяти документов, поэтому счётчики ресурсов не говорят об общем потреблении памяти (RSS) процессом.

После ответа соединение держит своё разрешение `max_connections` до закрытия клиентом или не дольше секунды (ступенчатое закрытие, см. [http-api.md](http-api.md)). Если `max_connections` клиентов держат сокеты открытыми после ответа, новое соединение не принимается до конца этой секунды.

Серверная часть необязательна: SDK, CLI и десктоп не зависят от Axum и Hyper. Гейт 1 ГиБ (`cargo xtask platform-proof`) пройден 70/70 на Windows x64 (подробности — `docs/dev/platform-acceptance.md`). На Linux, macOS и Windows 7 этот гейт не запускали: там проверялся только запуск распакованных архивов.

## Корни PKI и закреплённые адреса

У проверки нет неявного хранилища доверия, а исходящий PKI-трафик по умолчанию запрещён. Доверенные сертификаты и точные адреса источников задаёт оператор в настройках, а не клиент в запросе:

```toml
[pki]
anchors = ["/operator/roots/root.der"]
intermediates = ["/operator/roots/intermediate.der"]

[[pki.endpoints]]
origin = "https://ca.example:443"
addresses = ["203.0.113.10:443"]
```

- Каждый файл — один сертификат DER или PEM, не больше 1 МиБ. Всего не больше 16 МиБ, 256 якорей и 256 промежуточных.
- У источника не больше 16 явных адресов, всего не больше 128 источников. Литеральный хост нельзя молча перенаправить на другой IP или порт.
- Никакой URL из запроса, корень из сертификата или флаг JSON-политики доверия не устанавливает.
- Сертификат TLS-слушателя и корни проверки документов — разные настройки. Сервис не добавляет сертификаты в хранилища ОС и браузера.
- Защищайте файлы доверия от изменения.

## Телеметрия OTLP (необязательно)

Сервис может отправлять **метрики и трассы** в ваш OTLP-коллектор. По умолчанию это выключено: без таблицы `[telemetry]` или при `enabled = false` процесс не создаёт поток экспорта и не соединяется ни с каким коллектором. OTLP-логов нет, журнал аудита — отдельный механизм. Код телеметрии есть только в сервисе, но не в SDK, CLI и десктопе.

```toml
[telemetry]
enabled = true
endpoint = "http://127.0.0.1:4318"   # базовый URL OTLP/HTTP; /v1/traces и /v1/metrics дописываются
service_name = "oncl-server"
metrics = true
traces = true
trace_sample_ratio = 1.0             # только трассы; метрики не семплируются
export_interval_ms = 10000           # 100 .. 3 600 000
export_timeout_ms = 3000             # 100 .. 60 000
connect_timeout_ms = 1000            # не больше export_timeout_ms
queue_size = 2048                    # 16 .. 65 536
batch_size = 512                     # не больше queue_size
shutdown_timeout_ms = 5000           # 100 .. 60 000
# headers = { authorization = "Bearer <учётные данные коллектора>" }   # не больше 8; только https или loopback
# ca_file = "/private/oncl-operator/collector-ca.pem"                  # только https: CA коллектора (PEM)
```

Проверки при старте:

- URL `http` или `https`, без user info, query и fragment;
- включён хотя бы один из `metrics` и `traces`;
- имена заголовков допустимы (не `host`, `content-*`, `connection` и т. п.), значения — печатаемый ASCII;
- `headers` отвергаются, если endpoint не `https` и хост не loopback (`localhost`, `127.0.0.0/8`, `::1`): учётные данные не идут по сети открытым текстом;
- `ca_file` требует `https`;
- неизвестные ключи отвергаются. Ошибка настроек не повторяет значения заголовков.

### Как работает экспорт

- OTLP/HTTP с protobuf, один POST на экспорт. Без gRPC, сжатия, перенаправлений и прокси из окружения. Переменные `OTEL_*` настройками не считаются.
- `https` проверяется по встроенным корням web PKI или, если задан `ca_file`, только по CA из этого файла (не больше 8, по 1 МиБ). Набор доверия PKI оператора для этого не используется.
- Адрес коллектора — исходящий трафик, которому вы доверяете. Закрепление `[[pki.endpoints]]` на него не распространяется.
- Не больше двух потоков экспорта (`oncl-otlp-traces`, `OpenTelemetry.Metrics.PeriodicReader`) и короткий поток `oncl-otlp-shutdown` при остановке. Потоки операций сеть не трогают и никогда не ждут: данные кладутся в очередь фиксированного размера.
- При полной очереди или сбое экспорта данные отбрасываются и считаются (`Telemetry::stats()`, метрика `oncl.telemetry.dropped{oncl.signal=spans|metrics}`). Метрики агрегируются на месте, так что память не растёт.
- Одна попытка на пакет, повторов нет. После сбоя экспортёр делает паузу `export_interval_ms · 2^n` (не больше 30 с).
- Остановка сбрасывает данные не дольше `shutdown_timeout_ms`.
- Телеметрия никак не влияет на аудит: потери, семплирование и недоступный коллектор не убирают и не задерживают запись аудита. OTLP не доказывает, что аудит записан. Здоровье аудита видно в `/health`.

### Что может покинуть процесс

Все атрибуты — значения небольшого закрытого набора. Идентификаторов запросов, клиентов, ключей и токенов, текста ошибок, путей и метрик с неограниченным набором значений нет. Атрибуты ресурса: только `service.name` и `service.version`. У спанов нет событий и ссылок.

| Атрибут | Значения |
|---|---|
| `oncl.route` | `hash`, `operations`, `batch` |
| `oncl.operation.kind` | `hash`, `verify`, `extract`, `sign`, `extend`, `jws_sign`, `jws_add`, `jws_verify`, `jwt_encode`, `jwt_decode`, `jwt_verify`, `plugin`, `inspect`, `stamp`, `verify_stamp` |
| `oncl.operation.family` | (только sign) `cms`, `cades`, `pdf`, `pades`, `xml`, `xades`, `wsse`, `xml_legacy`, `xades_legacy` |
| `oncl.outcome` | `ok`, `rejected` (отказ до работы), `failed`, `aborted` |
| `oncl.error.code` | стабильные коды ошибок (`permission_denied`, `invalid_request`, `capacity_exceeded`, `deadline_exceeded`, `audit_unavailable`, `validation_failed`, `operation_failed`, …) |
| `oncl.key.applied` | `not_applied`, `applied`, `unknown` |
| `http.response.status_code` | `200`, `400`, `403`, `404`, `408`, `413`, `422`, `500`, `503`, `504` |
| `oncl.delivery` | `complete`, `aborted` |
| `oncl.stage` | `wait`, `run` |
| `oncl.signal` | `spans`, `metrics` |

Спаны: `oncl.request` (корневой), `oncl.admission` (от начала запроса до передачи исполнителю; для запросов с телом сюда входят загрузка и ожидание слотов, поэтому в нём доминирует время клиента), `oncl.executor.wait`, `oncl.executor.run`, `oncl.operation` (на каждый выполненный элемент), `oncl.delivery`.

Метрики:

- счётчики: `oncl.requests`, `oncl.operations`, `oncl.key.uses` (операции, которые применили или могли применить закрытый ключ, без идентичности ключа), `oncl.stream.aborted`, `oncl.executor.rejected`, `oncl.telemetry.dropped`;
- гистограммы: `oncl.request.duration`, `oncl.admission.duration` (с учётом загрузки), `oncl.executor.duration`, `oncl.operation.duration`, `oncl.delivery.duration` (секунды), `oncl.response.size` (байты);
- датчики: `oncl.requests.in_flight`, `oncl.executor.running`, `oncl.executor.queued`.

### Пределы гарантий

- Не наблюдаются запросы health и OpenAPI и сбои до маршрута (искажённый HTTP, пределы соединений).
- Статус потокового ответа — `200`, даже если элемент позже упал. Исходы элементов видны в спанах `oncl.operation` и счётчике `oncl.operations`. Исход запроса — `failed`, если упал любой элемент. У элементов `/v1/batch` нет спанов и своей длительности: они видны только в счётчиках и в исходе запроса.
- Длительности и размеры ответов могут показать оператору коллектора грубую картину активности. Идентификаторы трасс случайны. Считайте коллектор частью границы доверия и защищайте `headers`.
- Потери при медленном или недоступном коллекторе ожидаемы. Телеметрия — не гарантия доставки и не запись аудита.
- TLS к коллектору всегда проверяет сертификат. Проверки отзыва и клиентских сертификатов (mTLS) нет.
- Входящие `traceparent` и `tracestate` игнорируются: клиент не может присоединиться к трассе или влиять на семплирование.

## Установка и эксплуатация

`oncl-server` поставляется отдельным архивом `oncl-server-<version>-<flavor>.zip` (Windows: `win-x64`, `win-x86`, `win7-x64`, `win7-x86`) или `.tar.gz` (`linux-x64`, собран против glibc 2.28; `osx`, универсальный). Рядом идёт архив командной строки `oncl-<version>-<flavor>`. Эти архивы собирает только workflow выпуска, как артефакты запуска. К релизу они не приложены (см. «Не сделано и не проверено»). В десктопную программу они не входят.

В архиве нет ни установщика, ни автозапуска, ни самообновления и ни токена, ключа или сертификата. Внутри лежат:

- программа и `README.md`;
- `server.example.toml` (API **выключен**);
- `docs/`;
- `THIRD-PARTY.txt` (лицензии стороннего кода; в Unix-версии добавлен AWS-LC);
- `LICENSE` и `NOTICE`;
- на Linux ещё `deploy/openncalayer-server.service` и `deploy/Dockerfile`.

Мейнтейнер собирает и проверяет архивы командой `cargo xtask package platform` (справка: `cargo xtask package platform --help`); она ничего не публикует.

**Обновление.** Распакуйте новый архив, замените программу и перезапустите сервис (или пересоберите образ). Программа сама никогда не ходит за обновлениями. Настройки, контейнеры ключей и журнал аудита замена не затрагивает.

### Что проверено у упакованных программ

`cargo xtask package platform` распаковывает свежие архивы в пустой каталог и запускает программы без GUI:

- `oncl --version`, `oncl hash` (файл и stdin) с независимой сверкой SHA-256, `oncl verify` на файле, который не является подписью (должен отказать);
- `oncl-server` без подкоманды и `serve` с примерной конфигурацией: оба завершаются сами, слушателя на порту нет;
- явное включение на loopback (токен из `token-create`, ключ RSA, OCSP/CRL синтетического PKI, `--enable-api`): ровно один loopback-слушатель, `oncl --endpoint … sign` делает подпись CMS, которую `oncl verify` признаёт `Valid`, `extract` возвращает документ, журнал аудита существует, перевод строки в `--shutdown-stdin` останавливает сервис и закрывает порт.

`cargo xtask package platform-smoke` повторяет только эту часть на готовых архивах.

### Linux и systemd

Юнит — обычный файл. Его копирование сервис не включает и не запускает, а `ConditionPathExists` не даёт стартовать, пока нет настроек.

```sh
tar -xzf oncl-server-<version>-linux-x64.tar.gz
cd oncl-server-<version>-linux-x64
sudo useradd --system --user-group --home-dir /var/lib/oncl-server --no-create-home --shell /usr/sbin/nologin oncl-server
sudo install -m 0755 oncl-server /usr/local/bin/oncl-server
sudo install -d -m 0700 -o oncl-server -g oncl-server /etc/oncl-server
sudo install -m 0600 -o oncl-server -g oncl-server server.example.toml /etc/oncl-server/server.toml
sudo install -m 0644 deploy/openncalayer-server.service /etc/systemd/system/openncalayer-server.service
sudo systemctl daemon-reload
```

Что делает юнит:

- запускает сервис от пользователя `oncl-server` с `NoNewPrivileges`, пустым набором capabilities, `ProtectSystem=strict` (запись только в `/var/lib/oncl-server` и `/etc/oncl-server`), `PrivateTmp`, `PrivateDevices`, `PrivateUsers`, фильтром системных вызовов, без дампов памяти и с `UMask=0077`;
- разрешает только семейства адресов IPv4/IPv6;
- ограничивает память (`MemoryMax=1G`, примерно вдвое больше `total_memory`: HTTP-стек лежит вне бюджета документов) и число задач (`TasksMax`);
- задаёт `KillSignal=SIGINT`, потому что сервис дожидается начатых операций только по SIGINT (`TimeoutStopSec=330` — больше 300 с `operation_timeout_ms` по умолчанию). SIGTERM завершает его сразу (код 143).

Оценка `systemd-analyze security --offline=true` — 1.1 (OK), проверено на systemd 255.

С примерной конфигурацией (`enabled = false`) `systemctl start openncalayer-server` сразу завершается, в журнале пишет `disabled: no listener` и ничего не слушает. Слушать он начнёт, только когда вы настроите токен, включите API и сами выполните `sudo systemctl enable --now openncalayer-server`.

### Выдача токена на сервере

Выполните команду от учётной записи сервиса:

```sh
sudo -u oncl-server /usr/local/bin/oncl-server token-create --directory /etc/oncl-server --name accounting.token
# verifier=<64 шестнадцатеричных знака>
```

В `server.toml` кладите верификатор, не токен. Записывайте файл от учётной записи сервиса с `umask 077`: настройки, которые может прочитать или заменить кто-то ещё, отвергаются.

```sh
sudo -u oncl-server sh -c 'umask 077 && cat > /etc/oncl-server/server.toml' <<'EOF'
enabled = true
bind = "127.0.0.1:13579"
audit_directory = "/var/lib/oncl-server/audit"
recover_audit = true
scratch_directory = "/var/lib/oncl-server/scratch"

[[tokens]]
id = "accounting"
verifier = "<верификатор, напечатанный выше>"
actions = ["hash", "verify"]
keys = []
EOF
```

Дальше:

1. Передайте `accounting.token` клиенту по надёжному каналу и положите в каталог только для владельца (`install -d -m 0700 ~/.oncl`, файл записывайте с `umask 077`; клиент отвергает читаемый другими файл токена). Используйте `--token-file`.
2. Удалите токен с сервера (`sudo -u oncl-server rm /etc/oncl-server/accounting.token`): сервису нужен только верификатор.
3. Ротация токена: создайте новый, замените верификатор в настройках и перезапустите сервис.

Клиент `oncl` складывает загружаемое (OCSP, CRL) в рабочий каталог, если не указан `--temporary-directory`. В Unix он отвергает каталог, доступный другим пользователям. Если проверка идёт по онлайн-PKI, запускайте `oncl` из каталога только для владельца.

### Windows

Проверка закрытых файлов требует файлов с защищённым ACL и ровно одной наследуемой записью для владельца. `icacls` и PowerShell `Set-Acl` такой ACL создать не могут (измерено). Используйте саму программу: она создаёт такие файлы, никогда не перезаписывает существующие и печатает только имя и размер.

```bat
oncl-server install-file --directory %ProgramData%\oncl-operator --name server.toml --input server.toml
oncl-server install-file --directory %ProgramData%\oncl-operator --name corporate.p12 --input corporate.p12
type corporate.password | oncl-server install-file --directory %ProgramData%\oncl-operator --name corporate.password
oncl-server token-create --directory %ProgramData%\oncl-operator --name accounting.token
oncl-server serve --config %ProgramData%\oncl-operator\server.toml --enable-api
```

Правила `install-file`:

- `--directory` создаётся только для владельца, если его нет, либо уже должен быть закрытым.
- `--name` — простое имя файла: только латинские буквы, цифры и `-`, `_`, `.`, не больше 64 знаков; без пути, диска, потока и зарезервированных имён устройств вроде `NUL`.
- Ввод не больше 16 МиБ.
- Отклонённое имя или слишком большой ввод ничего не создают, даже каталога. Если запись файла не удалась, файл удаляется, а созданный каталог остаётся пустым. Сбой финальной синхронизации каталога оставляет готовый файл на месте.
- Та же команда работает на Linux вместо `install -m 0600`.
- Обычные исходные файлы после этого удалите.

### TLS для доступа из сети

Адрес не loopback требует `hosts` и либо TLS, либо доверенный прокси (см. [Явный доступ из локальной сети](#явный-доступ-из-локальной-сети)). Сервис не создаёт CA и не ставит сертификат. Создайте закрытый ключ от учётной записи сервиса и запрос, который подпишет ваш CA:

```sh
sudo -u oncl-server sh -c 'umask 077 && install -d -m 0700 /etc/oncl-server/tls && cd /etc/oncl-server/tls && openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out server.key && openssl req -new -key server.key -subj "/CN=signing.internal" -addext "subjectAltName=DNS:signing.internal" -out server.csr'
```

Положите цепочку сертификатов от CA (PEM, сертификат сервера первым) в `/etc/oncl-server/tls/server.crt`.

Для лаборатории без CA подойдёт самоподписанный сертификат **конечного субъекта** (`CA:FALSE`). Сертификат `openssl req -x509` по умолчанию получается с `CA:TRUE`, и клиент отвергает его как сертификат сервера (`TlsFailed`). Клиенты должны явно ему доверять. Это не производственный сертификат:

```sh
sudo -u oncl-server sh -c 'umask 077 && cd /etc/oncl-server/tls && openssl req -x509 -key server.key -days 365 -subj "/CN=signing.internal" -addext "subjectAltName=DNS:signing.internal,IP:127.0.0.1" -addext "basicConstraints=critical,CA:FALSE" -addext "keyUsage=critical,digitalSignature" -addext "extendedKeyUsage=serverAuth" -out server.crt'
```

```toml
bind = "0.0.0.0:13579"
hosts = ["signing.internal:13579"]
exposure = { mode = "tls", certificate = "/etc/oncl-server/tls/server.crt", private_key = { directory = "/etc/oncl-server/tls", name = "server.key" } }
```

Клиент доверяет ровно этому сертификату:

```sh
oncl --endpoint https://signing.internal:13579 --ca-file server.crt --token-file ~/.oncl/accounting.token hash --algorithm sha256 --input document.bin
```

Без `--ca-file` клиент завершается ошибкой `TlsFailed`. Флага, который пропускает проверку, нет.

### Контейнер

`deploy/Dockerfile` собирает образ **из архива выпуска** (без исходников и без загрузок) на Debian 12 slim, закреплённом по дайджесту. Работает от непривилегированного пользователя (uid/gid 10001), настроек внутри образа нет. Собирайте из каталога, где лежит архив:

```sh
tar -xzf oncl-server-<version>-linux-x64.tar.gz
docker build -f oncl-server-<version>-linux-x64/deploy/Dockerfile --build-arg VERSION=<version> -t oncl-server:<version> .
```

Тома подключаются явно:

| Путь в контейнере | Что там лежит |
|---|---|
| `/etc/oncl-server` | закрытые настройки, контейнеры ключей, ключ TLS |
| `/var/lib/oncl-server` | журнал `audit/` и `scratch/`. Сервис создаёт их сам при первом старте. Смонтируйте **том**, чтобы журнал пережил контейнер, и не создавайте `audit/` сами: существующий пустой каталог отвергается |
| `/run/oncl-secrets` (необязательно) | пароли, ключ TLS, файлы токенов |

Правила закрытых файлов действуют и внутри контейнера. Готовьте тома от пользователя образа (uid 10001, режим 0700) и никогда не монтируйте домашний каталог.

```sh
docker volume create oncl-config
docker volume create oncl-state
docker run --rm -i --user 10001:10001 -v oncl-config:/etc/oncl-server --entrypoint sh oncl-server:<version> -c 'umask 077 && cat > /etc/oncl-server/server.toml' < server.toml
docker run --rm --user 10001:10001 -v oncl-config:/etc/oncl-server oncl-server:<version> token-create --directory /etc/oncl-server --name accounting.token
docker run -d --name oncl-server --read-only --cap-drop ALL --security-opt no-new-privileges \
  --memory 1g --memory-swap 1g --pids-limit 256 --tmpfs /tmp:rw,size=64m,mode=1777,noexec,nosuid \
  -v oncl-config:/etc/oncl-server -v oncl-state:/var/lib/oncl-server \
  -p 127.0.0.1:13579:13579 oncl-server:<version>
```

Ключ TLS кладут в том так же: `… --entrypoint sh … -c 'umask 077 && mkdir -p /etc/oncl-server/tls && cat > /etc/oncl-server/tls/server.key' < server.key`. Токен читают через `--entrypoint cat`.

Что учесть:

- Внутри контейнера `bind` должен быть `0.0.0.0:13579`, `hosts` — равным адресу, которым пользуются клиенты, и нужен TLS или `trusted_proxy`. Ключ `-p 127.0.0.1:…` публикует порт только на loopback хоста.
- С примерной конфигурацией контейнер печатает `disabled: no listener` и завершается с кодом 0.
- Никогда не используйте `--privileged`.
- Образ задаёт `STOPSIGNAL SIGINT`, поэтому `docker stop` дожидается начатых операций. Задайте `--time` больше `operation_timeout_ms` (по умолчанию Docker ждёт 10 с).
- `--memory 1g` — бюджет контейнера для `total_memory` из примера. Временные файлы ограничены `total_temp`: подберите под него размер тома `oncl-state` или уменьшите `temp_per_operation` и `total_temp`. Уменьшение `total_temp` уменьшает и число одновременных загрузок (см. «Загрузки: max_uploads»).
- `HEALTHCHECK` образа только проверяет, что порт (`ONCL_HEALTH_PORT`, по умолчанию 13579) принимает TCP-соединение изнутри контейнера. Для аутентифицированного `GET /health` нужен токен с правом `hash`, а в образе токена быть не должно: опрашивайте `/health` из своего мониторинга.
