# HTTP-запросы к oncl-server

Для кого: для разработчика, который вызывает [oncl-server](server.md) из своей системы. Здесь описано, как собрать запрос на хеш, проверку, подпись и другие операции, и как читать ответы и ошибки.

Все запросы идут на `POST /v1/operations` (или на `POST /v1/hash` для простого хеша). Нужны токен в заголовке `Authorization: Bearer …` и правильный заголовок `Host` — см. [server.md](server.md). Совместимости с NCANode, путей к файлам, корней доверия, лимитов, подмены метода, административных действий, повторов и сохраняемых заданий в запросах нет: всё это задаёт оператор в настройках.

## Первый запрос: хеш

Самый простой вариант — JSON. Он годится для небольших текстовых документов.

```json
{
  "metadata": {
    "items": [
      {"id":"invoice","operation":{"kind":"hash","algorithm":"sha256","input":"source"}}
    ],
    "parts": [
      {"name":"source","item_id":"invoice","role":"document"}
    ]
  },
  "documents": {"source":"abc"}
}
```

Ответ:

```json
{"type":"final","operation_id":1,"status":"completed","results":[{"item_id":"invoice","applied":"NotApplied","result":{"kind":"hash","algorithm":"sha256","digest":"ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad","bytes_in":3}}]}
```

- `operation_id` каждый раз новый.
- `item_id` повторяет идентификатор из запроса.
- `bytes_in` — сколько байт документа реально обработано.
- Успех — только полный ответ с `type: "final"`.

Как устроен запрос: в `items` перечислены операции, в `parts` — части документа, а `documents` — их содержимое. Каждая часть привязана к элементу через `item_id`.

## Формат запроса

Есть два формата. Метаданные (`items` и `parts`) в обоих одинаковые.

### JSON (небольшие документы)

`Content-Type: application/json`. Весь запрос не больше 65 536 байт, независимо от лимита документа. Значения документов — текст UTF-8, не base64.

Ошибкой считаются: повторяющиеся имена документов, неизвестные поля, неиспользованные части, повторяющиеся идентификаторы, часть, не принадлежащая своему элементу. Идентификаторы элементов и частей — 1–128 ASCII-букв, цифр, `_` или `-`.

### multipart/form-data (любые документы)

`Content-Type: multipart/form-data; boundary=<boundary>`. Граница — 1–70 ASCII-символов из допустимого для multipart алфавита.

1. Первое поле — `name="metadata"`, без имени файла. Оно содержит только объект `metadata` из примера выше, не больше 65 536 байт. Сервис разбирает его до документов и по нему решает, какие права нужны. Дублировать метаданные не нужно.
2. Затем каждую объявленную часть отправьте один раз под её именем.

```text
--example-boundary\r\n
Content-Disposition: form-data; name="metadata"\r\n
\r\n
{"items":[{"id":"invoice","operation":{"kind":"hash","algorithm":"sha256","input":"source"}}],"parts":[{"name":"source","item_id":"invoice","role":"document"}]}\r\n
--example-boundary\r\n
Content-Disposition: form-data; name="source"; filename="invoice.bin"\r\n
Content-Type: application/octet-stream\r\n
\r\n
<actual binary document bytes>\r\n
--example-boundary--\r\n
```

`\r\n` здесь — настоящие байты CRLF, а не четыре печатных символа.

Правила:

- Лишние, повторяющиеся, пропущенные и объявленные позже поля отклоняются.
- Роль части — `document` или `secret`. Секрет нельзя выдать за документ, какое бы имя файла и тип содержимого ни были у части.
- Имя файла в `Content-Disposition` — только текст для показа, не имя файла на диске.
- Документы сохраняются в закрытый каталог `scratch_directory` оператора под случайными именами и удаляются, когда ими никто не пользуется. Каталог должен быть закрытым, если он уже существует. Это не архив и не очередь.
- Content-Length необязателен. Считаются фактические байты, включая chunked-загрузки неизвестной длины. Разбивка на куски любая: раздел или CRLF могут оказаться на границе кусков.
- У байтов документов и служебных байт multipart (границ, заголовков) отдельные квоты. Слишком большие хвост или заголовки отклоняются, даже если сами документы не были отправлены.
- Ошибки: заголовок части больше бюджета — `FramingLimit`/413; исчерпан отдельный предел заголовков — `MetadataLimit`/413; искажённое или обрезанное тело — `InvalidRequest`/400. Первая зафиксированная причина (сеть, ресурсы, отмена) остаётся окончательной, её не подменяет позднейшая отмена.

## Что можно делать: виды операций

Каждому токену нужно соответствующее действие (`actions` в настройках, см. [server.md](server.md)).

| `kind` | Действие токена | Результат |
|---|---|---|
| `hash` | `hash` | JSON |
| `verify` (`cms`, `cades_*`, `pdf`, `pades_*`, `xml`, `xml_kalkan`, `xades_*`, `wsse`) | `verify` | JSON; подпись `Invalid` — завершённый отчёт HTTP 200 |
| `extract` | `extract` | `multipart/mixed` с артефактом |
| `sign` (см. ниже) | `sign` плюс право на ключ | `multipart/mixed` с артефактом |
| `extend` (`cades_t/lt/lta`, `pades_t/lt/lta`, `xades_lt/lta`) | `extend` (ключ не нужен) | `multipart/mixed` с артефактом |
| `jws_sign`, `jws_add`, `jwt_encode` | `sign` плюс право на ключ | `multipart/mixed` с артефактом |
| `jws_verify`, `jwt_verify` | `verify` | JSON; подпись, доверие и claims — отдельно |
| `jwt_decode` | `extract` | JSON; `verified` всегда `false` |
| `inspect` (`certificate`, `cms`, `container`, `named`) | `inspect` (для `named` ещё право на ключ) | JSON |
| `plugin` | точный грант оператора на (токен, плагин, операция) | JSON |
| `stamp` | `stamp` | токен штампа в `multipart/mixed` |
| `verify_stamp` | `verify_stamp` | JSON |

`GET /v1/openapi.json` требует токен, но никакого действия, и публикует описание OpenAPI 3.1 с проверенными примерами запросов и ответов. `GET /health` требует действие `hash`.

Несколько элементов на `/v1/operations` выполняются по порядку, с одним сроком и одним бюджетом; результат один, «всё или ничего». Для пакета с отдельным одобрением и записью по элементам используйте `POST /v1/batch` (ниже).

Шифрования и расшифрования нет: для них нужен внешний ГОСТ-бэкенд.

### hash

Алгоритм указывается явно: `sha1`, `sha256`, `sha512`, `gost34311`, `streebog256`, `streebog512`. Он не определяется по имени файла или содержимому. Нужно действие `hash`, ключ выбрать нельзя. Право на хеш (даже SHA-1) не даёт права подписывать.

### verify

Нужно отдельное действие `verify` (проверяется до приёма документа). Метаданные: `{"kind":"verify","profile":"cms","input":"signature"}`. Необязательное поле `detached` называет вторую часть-документ с отсоединённой полезной нагрузкой.

Профили: `cms`, `cades_b`, `cades_t`, `cades_lt`, `cades_lta`, `pdf`, `pades_b`, `pades_t`, `pades_lt`, `pades_lta`, `xml`, `xml_kalkan`, `xades_b`, `xades_t`, `xades_lt`, `xades_lta`, `wsse`. Профиль выбирает настоящий проверяющий код, а не угадывает по имени файла.

Корни доверия, режим проверки и права на сеть в запросе не передаются. Набор доверия сервиса по умолчанию пуст, а сеть PKI запрещена. Криптографически верная подпись от этого не становится «доверенной».

Как читать результат:

- Неверная подпись — это нормальный ответ HTTP 200 с `kind:"verification"` и `verdict:"Invalid"`, а не ошибка 500.
- Результат содержит проверки по каждому подписанту (подпись, цепочка, срок действия, отзыв, штамп времени, использование ключа), политику хоста, проверенное время и его основание.
- Причины в диагностике — пояснительный текст. Это не разрешение и не замена типизированным полям.
- Подпись может быть криптографически целой, но нарушать правила baseline CAdES/PAdES. Пример: атрибут signing-time, который Kalkan пишет в CMS PAdES, а EN 319 142-1 запрещает. Тогда все проверки `Passed` или `Unavailable`, причина `Profile(...)`, вердикт `Invalid`. Читайте вердикт и причины вместе, а не только шесть проверок.

### extract

Извлекает содержимое CMS-контейнера. Это не проверка подписи. Метаданные: `{"kind":"extract","input":"container"}`. Нужны действие `extract` и настроенный `scratch_directory`.

### sign

Профили подписи: `cms`, `cades_b/t/lt/lta`, `pdf`, `pades_b/t/lt/lta`, `xml`, `xades_b/t`, `wsse`, `xml_legacy`, `xades_legacy_b/t`. Профилей подписи `xades_lt/lta` нет (см. «Профили ресурсов и материалов»).

- Для CMS и CAdES `mode` — `create` или `add`.
- XML принимает необязательные идентификаторы `target`, `parent`, `signature_id`.
- `wsse` подписывает тело SOAP: `soap` = `soap11` или `soap12`, необязательный `body_id`.
- `xml_legacy` — раскладка Kalkan: XPath `element` и `xpath_parent`, URI `signature_method` и `digest_method` (должны подходить ключу; значение Kalkan по умолчанию следует алгоритму подписи сертификата).
- `xades_legacy_t` подписывает через TSA оператора (нужен policy OID).
- Недопустимые сочетания полей и профилей отклоняются по одним метаданным (400), до обращения к ключу, секрету или документу.

Ключ, секреты и свидетельства — в разделах ниже.

### plugin

Вызывает операцию плагина, установленного оператором. Установка плагина — ещё не разрешение: нужен грант `[[plugins.permissions]]` на (токен, плагин, операцию) со списком импортов, именованных ключей и точных GET-URL статуса PKI. Вызывающий определяется токеном, а не полем `origin` из запроса.

- Плагин, который **объявляет** операции (`[[operations]]` в манифесте), связан объявлением: сервис сам применяет объявленные параметры подписи (в запрос нельзя добавить атрибуты или свой TSA), `cosign` невозможен, а для использования ключа нужен `plugin_bytes = true` в гранте (см. «Справочник по настройке плагинов»). Допущенное использование попадает в аудит вместе с билетом.
- Плагин **без** объявлений работает как раньше.
- Обязательные диалоги завершаются `InteractionRequired` (403). Отклонённый вложенный импорт — `PermissionDenied`. Использование ключа записывается в аудит и сообщается как `Applied`/`Unknown`.
- Ключи токенов (PC/SC) — именованные ключи оператора. Без считывателя или карты запрос отклоняется (`NotApplied`, без `BEGIN`). Операции с картой на одном устройстве не пересекаются.

## Ключи и роли секретов

Элемент подписи называет ключ одним из двух способов:

- `{"source":"named","name":"..."}` — имя, настроенное оператором. Токен должен перечислять это точное имя в `keys`.
- `{"source":"inline","container":"<part>","password":"<part>","alias":"..."}` — контейнер и пароль в самом запросе. Нужны оба согласия: `inline_pkcs12 = true` в настройках сервиса и у токена. Права выдаются только на точную идентичность, вычисленную по полученному контейнеру и псевдониму.

Выбрать ключ по пути к файлу клиента, считывателю токена, отпечатку сертификата или кешу PIN нельзя.

Части с `role:"secret"` (контейнер до 4 МиБ, пароль до 4096 байт) хранятся в ограниченной памяти, которая затирается после использования. Правила:

- Секреты объявляются первыми и отправляются раньше любой части `document`.
- Они никогда не попадают в spool документов и в ответ.
- В JSON-запросе секреты отклоняются.
- Сетевые буферы и буферы разборщика вне владельца секрета сервис не затирает.

Инспекция контейнера использует те же роли секретов и показывает только те псевдонимы, которые перечислены в `metadata_aliases` токена.

## Порядок проверки прав

Права проверяются в таком порядке:

1. действие токена;
2. право на ключ, глобальное и токена право inline, грант `metadata_aliases` (до резервирования или чтения любого байта секрета);
3. inline-ключ без части `password` отклоняется (400) до любой привязки или захвата документа;
4. точная идентичность inline-ключа проверяется после чтения ограниченного контейнера.

Ещё раз права проверяются, когда всё тело принято и до начала закрытой операции. Отозванный токен, снятое право на ключ или изменившаяся политика за время долгой загрузки дают 403 без `BEGIN` и без использования ключа. Изменение после этой проверки не наблюдается: остаточное окно — само исполнение, которое фиксируют `BEGIN` и `FINAL` в аудите.

## Свидетельства

`sign` и `extend` принимают `evidence`:

```json
"evidence": [{"kind":"certificate|ocsp|crl","input":"<document part>"}]
```

- Не больше 64 частей, каждая DER не больше 1 МиБ. Больше 64 — `InvalidRequest` до чтения любой части.
- Для уровней LT/LTA нужен материал OCSP/CRL, полученный вызывающим. Иначе `PAdES extension requires acquired status material` (`InvalidRequest`).
- Свидетельство никогда не становится якорем доверия.
- Части-свидетельства не считаются документами и не списываются с лимита документа.
- Полный CRL НУЦ (около 20 МБ) через HTTP не поддерживается: часть не больше 1 МиБ, а встроенный в подпись XAdES-LT/LTA CRL не больше примерно 190 КиБ.

## Размеры и лимиты

### Что ограничивает документ

- `input_bytes` ограничивает документ. Документ на байт больше — `InputLimit`/413.
- Часть `input` у `verify`, `extend`, `extract` или `sign` может быть уже подписанным результатом (документ плюс подпись, ревизии или конверт). Тогда она может превышать `input_bytes` только на байты контейнера, и не больше чем на `container_bytes` (по умолчанию 1 ГиБ) или на границу самого формата (например, около 188 МиБ добавленных ревизий PDF).
- Подписанный результат документа размером `input_bytes` снова принимается сервисом, который его создал. Разбираемый документ на байт больше `input_bytes` — по-прежнему `InputLimit`. Неразбираемый мусор в этой роли — `InvalidRequest`/400.
- Любая другая часть-документ (отсоединённая полезная нагрузка, проверяемый контейнер, вход JOSE) целиком укладывается в `input_bytes`. Для CAdES: присоединённая подпись — это документ плюс подпись, а отсоединённая (часть `input`) — только контейнер; её полезная нагрузка — отдельный документ до `input_bytes`.
- Отказ из-за слишком большого подписанного входа движок находит уже после выбора статуса ответа. Поэтому потоковый запрос сообщает о нём завершающей записью с ошибкой `InputLimit` и `NotApplied`, а не обрывом.

Потолок всего запроса:

| Запрос | Потолок |
|---|---|
| вход может быть подписанным результатом | `input_bytes + container_bytes + framing_bytes + 64 КиБ` |
| другой multipart | `input_bytes + framing_bytes + 64 КиБ` |
| `/v1/hash` | `input_bytes` (сырое тело) |

Запрос, объявивший длину выше потолка, сразу отклоняется с `InputLimit`. Загрузка без объявленной длины отклоняется с `FramingLimit`, когда фактические байты переходят потолок.

### Временные файлы (scratch)

Если уменьшаете `input_bytes`, уменьшайте и `container_bytes`. Чем больше документ, тем больше временных файлов:

- Одна часть `input` у verify, extend, extract или sign сначала целиком складывается в spool, до `input_bytes + container_bytes` (2 ГиБ по умолчанию), и только потом движок решает, поддерживает ли он документ.
- Затем движок копирует примерно `input_bytes`. Verify, extend и `add` для CAdES копируют ещё раз, пока разбирают: до `input_bytes + container_bytes` плюс один кусок 256 КиБ. При значениях по умолчанию вместе со spool загрузки это около 4 ГиБ.
- Поэтому враждебная загрузка может записать в scratch несколько ГиБ, прежде чем её отклонят. Это ограничено `temp_per_operation`, `total_temp`, `max_uploads` и `max_in_flight`.
- Измеренные пики: подпись документа на пределе держит в scratch около 3× `input_bytes`, проверка подписанного результата — около 2×.
- Правило: `temp_per_operation >= 3 * (input_bytes + container_bytes)`. Настройки это правило не проверяют. Проверяется только то, что явный `max_uploads` не превышает `total_temp / (input_bytes + container_bytes)`. Не заданный `max_uploads` равен `min(8, max(1, эта граница))`.
- Элемент sign или extend принимает не больше 64 ссылок на свидетельства.
- `container_bytes` должен быть положительным, а `input_bytes + container_bytes + framing_bytes + 64 КиБ` должен помещаться в 64 бита.

### Разбор multipart

Используется закреплённая версия `multer` 3.1.0. Разборщик принимает не больше 8 192 новых байт при разборе заголовков или преамбулы неизвестной роли (плюс один предыдущий блок данных до 4 096 байт и суффикс границы) и принудительно уступает управление, чтобы всегда готовая загрузка не копилась в нём. Число заголовков ограничено. Буфер чтения Hyper — 32 768 байт. Память транспорта HTTP/TLS отдельно от рабочих буферов SDK. Память на запрос (разборщик, метаданные, входящие байты) резервируется заранее. Это не заявление о приёмке XML/PDF на 1 ГиБ.

## Ответы и ошибки

### Обычный ответ

Хеш, проверка и другие операции с JSON-результатом возвращают `Content-Type: application/json` и запись `final` (пример выше). Успех — только полный результат. Повторное чтение загруженных снимков второй раз лимит не списывает.

### Потоковые ответы с артефактами

Запросы с `extract`, подписью, продлением, штампом и JWS/JWT возвращают `multipart/mixed` со случайной границей. В нём:

- части JSON `progress` — идентификатор операции и счётчики байт (это не подтверждение успеха);
- бинарные части `artifact` — с серверным `Content-ID` и точным `Content-Length`;
- часть JSON `final` — связывает идентификатор `artifact` с этими байтами; это единственный источник истины о завершённом результате.

Адресов обратного вызова, сохраняемых заданий и путей к артефактам потом нет.

Как это работает:

- Сервис сначала принимает и записывает весь вход, и только потом начинает отвечать. Клиенту не нужно читать ответ во время загрузки.
- Рабочий поток собирает выход и освобождает слот. Медленный клиент не держит рабочий поток PKI.
- Ответ отдаётся областями по 256 КиБ через тот же ограниченный исполнитель. Исходный контекст, файлы выхода и резервы остаются привязанными к байтам ответа, пока их кто-то держит.
- `progress` и `final` и служебные байты MIME считаются как выход. Байты артефактов, созданные SDK, диск второй раз не списывает.
- Дисковый адаптер резервирует место до роста файла, ограничивает размер записи, проверяет flush/sync и размер файла и только после этого делает артефакт читаемым. Неполный или неудачный выход не публикуется.
- Сообщения `progress` объединяются: не больше одного кадра на наблюдаемое изменение. Длинная операция не создаёт неограниченный трафик.

**Что обязан делать клиент:** складывать байты артефакта во временное хранилище и публиковать их, только когда получены завершающая запись `final`, закрывающий разделитель MIME **и** успешное завершение HTTP-ответа. Корректное начало ответа или часть `progress` — не частичный успех. Нет `final` — нет публикации. Это не значит, что прежнее использование ключа откатилось.

### Статусы до начала ответа

Сбои до заголовков ответа — это JSON `{"code": ..., "applied": ...}`:

| Статус | Когда |
|---|---|
| 400 | `InvalidRequest` |
| 403 | `PermissionDenied` |
| 404 | неизвестный маршрут (`InvalidRequest`, `NotApplied`; маршрутов плагинов, шифрования и NCANode нет, `/v1/batch` есть) или `KeyNotFound` (ключ из прав токена не найден) |
| 405 | неверный метод, с заголовком `Allow` |
| 408 | `Cancelled` |
| 413 | лимиты ресурсов |
| 422 | `ValidationFailed`, `OperationFailed` |
| 500 | `Internal` |
| 503 | `CapacityExceeded`, `AuditUnavailable`, `MissingConfiguration`, `MissingTemporaryStore` |
| 504 | `DeadlineExceeded` (в том числе загрузка, которая застряла или идёт медленнее минимальной скорости, см. [server.md](server.md)) |

Право токена на ключ проверяется раньше поиска, поэтому имя ключа вне `keys` токена даёт 403, а не 404. Две причины 404 различаются полем `code`.

После заголовков о сбое сообщает только завершающая запись `final` или обрыв соединения. Обрыв не несёт клиенту причины: её пишет сервер (см. «Прерванные потоки ответов» в [server.md](server.md)).

### Завершающая запись final

`status` — `completed` или `failed`. Запись `failed` несёт `error: {code, applied}` и не содержит ни одного артефакта запроса (частичного успеха нет). Значения `applied` прежних элементов видны в `results`. Сбои ресурсов, срока и отмены, которые ни разу не применили ключ, по-прежнему обрывают соединение. Поток без `final` со статусом `completed` результатом не считается. Причину обрыва клиент не получает (только `ResponseLost`), а сервер пишет её в журнал и считает в `oncl.stream.aborted`.

### Приём тела и отказ по занятости

Аутентификация проходит до приёма тела. Приём тела — отдельная фаза со своим пределом `max_uploads`: запрос занимает слот загрузки до чтения первого байта. Ожидание медленного клиента и запись документов не занимают слот `max_in_flight`, рабочий поток и привязку аудита. Поэтому зависшая загрузка мешает только тем, кто хочет занять тот же слот загрузки.

`503 CapacityExceeded` означает, что за `admission_wait_ms` не освободился слот загрузки или операции, и ничего не применено. Сервис проверяет оба слота до чтения тела и отказывает, не принимая тело. Клиенту с `Expect: 100-continue` отправлять тело не разрешают. Эта проверка делается по возможности: слот могут занять до конца тела, и тогда отказ придёт после тела.

Если клиент всё ещё отправляет большое тело, а сервис уже отказал (решение по метаданным), немедленное закрытие сокета могло бы стереть ответ: клиент увидел бы сброс соединения вместо типизированной ошибки (особенно в Windows). Поэтому сервис закрывается поэтапно (RFC 9112, раздел 9.6):

1. отправляет ответ и закрывает свою сторону;
2. читает и отбрасывает то, что клиент ещё присылает, не дольше одной секунды и около 8 МиБ (оба предела фиксированные, не настраиваются);
3. закрывает соединение.

Пока это идёт, соединение держит разрешение `max_connections`, но ничего от своей операции (слот, scratch и бюджеты освобождены при отправке ответа). Если `max_connections` клиентов держат сокеты открытыми после ответа, следующее соединение не принимается до конца этой секунды. Клиент, который успевает закончить тело в этих пределах, читает типизированный отказ. Кто шлёт больше — получает сброс, как и без поэтапного закрытия.

Клиенту СЛЕДУЕТ читать ответ во время отправки или отправить `Expect: 100-continue` и дождаться ответа до тела (эталонный клиент так и делает).

Срок операции и общие бюджеты сохраняются на всех шагах: очередь, работа SDK, ответ и запись в сеть. Сброшенный ответ не освобождает ещё работающий рабочий поток, а удерживаемые байты ответа сохраняют свой резерв до последнего освобождения.

## Подкоды ошибок

Ответ с ошибкой (HTTP-ошибка до заголовков, `error` неудачной записи `final`, `error` неудачного элемента пакета) — это `{"code": ..., "applied": ...}`. **Только когда у отказа есть точная причина**, добавляется `"subcode": "<id>"`:

```json
{"code":"PermissionDenied","applied":"NotApplied","subcode":"not-granted"}
```

- Поле необязательное. 19 стабильных кодов и статусы не меняются, а ошибка без причины выглядит как раньше. Схема OpenAPI перечисляет `subcode`.
- Клиент на Rust (`oncl_api`) игнорирует неизвестные поля и отбрасывает не-строковый подкод. Клиент, собранный до этого изменения и отвергающий неизвестные поля, не сможет разобрать отказ плагина с подкодом (потеряет и код, и `applied`). Обновляйте клиентов вместе с сервером.
- Идентификатор соответствует `^[A-Za-z][A-Za-z0-9_-]{0,63}$` (сервер выдаёт kebab-case в нижнем регистре). У `InteractionRequired` подкода нет.
- Подкод — причина, а не сообщение. В нём нет байтов документа, ключа или параметров. Могут появляться новые идентификаторы: неизвестный трактуйте как простой `code`. Значение вне шаблона клиент отбрасывает.
- Сегодня подкод несут только отказы плагинов. Отказ — всегда `NotApplied`, кроме `key-use-spent` (второе использование ключа в одном запросе: первое было настоящим и остаётся `Applied`).

Идентификаторы, которые сервер реально присылает для операции плагина:

| `subcode` | `code` | Значение |
|---|---|---|
| `not-granted` | `PermissionDenied` | операция объявляет использование ключа, а в гранте нет `plugin_bytes = true`; либо ни один грант не покрывает использование по билету |
| `options-mismatch` | `PermissionDenied` | плагин запросил параметры подписи не из объявленного профиля (или профиль называет параметр, который сервер не может сопоставить) |
| `package-changed` | `PermissionDenied` | пакет плагина не тот, что установлен |
| `key-mismatch` | `PermissionDenied` | ключ не из названных в гранте |
| `kind-mismatch` | `PermissionDenied` | вид подписи не входит в объявленные использования ключа |
| `caller-mismatch` | `PermissionDenied` | вызывающий в билете — не токен клиента (по HTTP недостижимо: токен без подходящего гранта получает `not-granted`) |
| `ticket-uses` | `PermissionDenied` | билет допускает не ровно одно использование |
| `key-use-spent` | `PermissionDenied` | один запрос попытался использовать ключ дважды (`applied` — `Applied`) |
| `not-declared` | `PermissionDenied` | операция не объявлена плагином (серверный грант на неё пропускается при запуске, поэтому запрос обычно получает простой 403; этот идентификатор показывает CLI `oncl plugin`) |

Остальные идентификаторы семейства (всего 49) относятся в основном к ручному окну десктопа. Полный список — в [руководстве по ручному окну](manual-plugins.md#отказы-как-читать-код-на-странице) и в руководстве по SDK.

Клиент на Rust (`oncl_api::client::ClientError`) отдаёт подкод как `server_subcode` (`Option<String>`, уже проверен и безопасен для вывода). Его `describe()` даёт `PermissionDenied; subcode=not-granted`. CLI `oncl` печатает `oncl: PermissionDenied; subcode=not-granted; applied=NotApplied` и добавляет `subcode` в строку ошибки отчёта `batch --json`. Без причины строка прежняя.

## Аудит и состояние Applied

Перед использованием ключа сервис записывает в журнал `BEGIN`, привязанный к аутентифицированному субъекту и точной метке ключа, затем `FINAL`.

- Сбой аудита до использования ключа — `AuditUnavailable`/`NotApplied`.
- Сбой после возможного использования ключа: завершающая запись сообщает `Applied` или `Unknown`. Отката, повтора и гарантии «ровно один раз» нет.
- Привязка закрытой операции остаётся «надгробием» (идентификатор операции нельзя привязать заново) до исходного срока или пока каждый владелец операции (контекст, рабочий поток, ответ, артефакт) не освободится. Поэтому завершённые запросы не засоряют таблицу привязок.

## Профили ресурсов и материалов (отказ до использования ключа)

- `cades_lt/lta` и `pades_lt/lta` (sign и `extend`), а также `xades_lt/lta` (extend) требуют материал статуса, полученный вызывающим: `evidence` как минимум с одной частью `ocsp` или `crl`. Иначе 400 до обращения к секрету, ключу или документу.
- **XAdES LT/LTA** доступны только цепочкой: sign `xades_t`, затем `extend` (без ключа) до `xades_lt`, затем `xades_lta`. Профиля подписи `xades_lt/lta` нет, потому что запрос подписи XML в SDK не несёт материала статуса. Цепочка проверена по HTTP независимым средством lxml. Продление ключ не использует.
- **PAdES LT/LTA** требуют памяти и метаданных для плана обновления. Потребность считается по `oncl_pdf::budget::plan_memory` и `plan_metadata` и по входным данным, известным до открытия ключа: существующим подписям PDF, размерам частей-свидетельств и набору доверия оператора. Плюс именованные резервы хоста (4 буфера ввода-вывода, 64 КиБ метаданных, одна копия свидетельств). Проверка идёт по исходной области запроса после приёма тела. Если не помещается: 413 `MemoryLimit` или `MetadataLimit`, `NotApplied`, до `BEGIN`.
  - При лимитах по умолчанию и малых свидетельствах порог около 380 МиБ, поэтому `memory_per_operation` по умолчанию (256 МиБ) отклоняет PAdES LT/LTA. Несколько МиБ свидетельств CRL требуют порядка 600 МиБ и 72 МиБ метаданных.
  - Эти оценки **эмпирически достаточны для проверенных образцов и форм свидетельств** (прогоны с шагом 1 МиБ около порога ни разу не дали `BEGIN` с последующим сбоем по ресурсам). Это не доказательство для любого PDF. Если другие запросы исчерпают общий бюджет во время работы или форма входа нестандартна, сбой после использования ключа всё ещё возможен; он будет сообщён с настоящим состоянием `Applied` или `Unknown`.
  - PDF, который слой PDF не может прочитать (искажённый или с подписью не PAdES), — 400 `InvalidRequest` до `BEGIN`. Документ, который превысил бы лимит числа подписей, — 413 `InputLimit`. Срок, отмена и ёмкость сохраняют свои коды.
- PAdES B/T/LT/LTA поверх PDF, уже несущего действительные подписи, поддерживается: старые ревизии остаются байт в байт теми же, а новая подпись достигает запрошенного уровня. LT/LTA поднимают и прежних подписантов, поэтому свидетельства должны подтверждать и их. PDF с уже недействительной подписью отклоняется 400 до использования ключа.
- `xades_t` и `xades_legacy_t` требуют TSA оператора с policy OID (`[pki.tsa] policy`): SDK привязывает политику TSA для XAdES T/LT/LTA. Без него: 503 `MissingConfiguration`, `NotApplied`, без `BEGIN`. CAdES/PAdES T принимают TSA без политики.

## Справочник по настройке плагинов

```toml
[[plugins]]
id = "vendor.example"            # должен совпадать с id манифеста
manifest = "/private/plugins/vendor.example.toml"   # не больше 64 КиБ
wasm = "/private/plugins/vendor.example.wasm"       # не больше 16 МиБ
max_memory = 1048576             # не больше MAX_MEMORY из oncl-plugin; по умолчанию 1 МиБ
max_transfer = 262144            # не больше MAX_TRANSFER из oncl-plugin; по умолчанию 256 КиБ

[[plugins.permissions]]          # по одному на (токен, операцию); дубликаты отвергаются
token = "accounting-service"     # вызывающий: id настроенного токена
operation = "run"
imports = ["hash", "keys_sign_raw"]   # точные импорты хоста (Import::name())
keys = ["ops-key"]                    # именованные ключи оператора, они же в keys токена
pki_endpoints = ["http://pki.example/ocsp"]   # точные GET-URL для вложенной проверки
plugin_bytes = false                  # по умолчанию; см. ниже
```

### plugin_bytes

`plugin_bytes = true` — явное согласие оператора: **плагин (или его клиент) выбирает байты, которые подписывает выданный ключ**. Сервис не может связать содержимое с документом (`args` — свободный JSON). Поэтому использование ключа в *объявленной* операции отклоняется без этого флага (`PermissionDenied`, подкод `not-granted`, `NotApplied`, до `BEGIN` и до ключа; запись об отказе может быть сделана).

- Нужна хотя бы одна запись в `keys` (`plugin_bytes = true` без ключа отвергается).
- Для плагина без объявлений флаг ничего не делает (сервис пишет предупреждение).
- Использование должно точно соответствовать объявлению: плагин, хеш пакета, операция, токен как вызывающий из билета, именованный ключ из гранта, объявленный вид и параметры (иначе `options-mismatch`). Оно должно быть единственным использованием ключа в запросе (второе — `key-use-spent`).

**Ограничение.** Операция, чей объявленный профиль называет параметр (источники `param:`, например элемент XML, который вводит пользователь), не может использовать ключ на сервере: значения для сопоставления нет, поэтому использование всегда отклоняется как `options-mismatch`. Поставляемые в `plugins/` плагины объявляют 30 операций, но ни одна не объявляет `server = true`. Ни одну из них нельзя выдать на сервере или запустить через `oncl plugin call`: сервис пропускает такой грант с ошибкой в журнале, а CLI отказывает с `not-declared`.

### Что проверяется при запуске

Грант объявленного плагина сверяется с манифестом. Сервис **пропускает его с ошибкой в журнале** (остальные гранты и сам сервис работают), если грант шире объявления:

- операция, которую плагин не объявляет (в ошибке перечислены объявленные), или объявляет без `server = true`, или с содержимым `derived` (не запускается);
- импорт вне `uses.imports` (пустой `imports` означает все объявленные импорты);
- `keys` или `plugin_bytes` для операции без использования ключа;
- `pki_endpoints` без `network = "pki"`.

Грант с несуществующим импортом, неизвестным токеном или дубликатом (токен, операция) приводит к сбою настроек. Грант плагина без объявлений сохраняется как раньше, с предупреждением при запуске, что параметры подписи не навязываются.

### Пределы

Нарушение приводит к сбою настроек.

- Не больше 16 `[[plugins]]` и 256 разрешений на плагин.
- `id` плагина, `token` и `operation` гранта — не больше 64 байт. `id` плагина должен совпадать с `id` манифеста, дубликат `id` отклоняется.
- `imports` — не больше 72, `keys` — не больше 8, `pki_endpoints` — не больше 16 по не более 2048 байт. На сервере `pki_endpoints` — только GET (CLI принимает и `POST=`).

Выходы плагинов (файлы `take_output`) и привязанные входные файлы по HTTP **не раскрываются**: контракт привязки запроса к файлу не проектировался, поэтому импорты `file_*` никогда не выдаются. Импорты диалогов всегда завершаются `InteractionRequired`.

## Контейнеры ключей

Inline- и именованные контейнеры ключей проверены только как PKCS#12. Контейнеры JKS в проекте только читаются (писателя нет), поэтому подпись JKS по HTTP со строгой проверкой не подтверждена.

## Закрытый пакет (POST /v1/batch)

Запрос — тот же конверт, что у `/v1/operations` (multipart с метаданными первыми или JSON): `items` (1..1024, уникальные идентификаторы, порядок манифеста — порядок выполнения) и `parts` (сначала секреты, затем документы). Принимается любой вид элемента из таблицы выше, **кроме `plugin`** (400). Метаданные не несут одобрения, гранта или флага полномочий: неизвестные поля отклоняются.

Полномочия определяет только политика оператора:

1. **До чтения любого байта документа или секрета:** токену нужно отдельное право `batch` (`actions = [..., "batch"]`) **и** для каждого элемента — действие его операции, право на именованный ключ, право inline или `metadata_aliases`. Если не выдано хотя бы одно, весь пакет отклоняется (403, ничего не запускается, ключи и секреты не читаются).
2. После приёма тела та же проверка выполняется ещё раз (отзыв, поколение политики), затем каждый источник захватывается как неизменяемый снимок. Ключи разрешаются до lease и сертификата, но **закрытый ключ не применяется**.
3. Одобрение хоста (`BatchApproval`) выдаётся, только если захваченный план совпадает по каждому элементу с тем, что разрешила политика оператора: идентификаторы и порядок, действие, профиль подписи, разрешённые ключи, размеры источников. Другой план отклоняется (403) до любого закрытого использования. Одобрение одноразовое и привязано к исходной операции.
4. Выполнение идёт в исходном допущенном контексте. Каждое использование ключа пишется в аудит с порядковым номером элемента (`BEGIN`/`FINAL` на каждый элемент).

### Ответ

Всегда `multipart/mixed`. Отказы до этого — обычные JSON-ошибки с `NotApplied`. В ответе:

- объединённые части `progress` с позицией в пакете (`items`: `total`, `finished`, `current` `{index,item_id}`);
- по одной части `artifact` на каждый **завершённый** результат;
- последняя часть `final` с `type = "batch_final"`.

В `final`:

- `status`: `completed` (завершён каждый элемент; проверка с `Invalid` — завершённый элемент с `verdict = "Invalid"`), `partial` (какой-то элемент не удался или не запускался) или `failed` (ничего не удалось запустить);
- `items[]` в порядке манифеста; у каждого `item_id`, `index`, `outcome` (`completed`, `failed`, `not_run`), `applied` (`NotApplied`/`Applied`/`Unknown`), `verdict`, `error {code, applied}` для неудавшихся, `result` для завершённых (те же семейства результатов, что у `/v1/operations`, `artifact` — Content-ID завершённого выхода) и `sources` (SHA-256 и длина захваченных байт).

Правила:

- Неудавшийся элемент не стирает результаты, артефакты и `applied` завершённых.
- Локальные сбои элемента (нечитаемый источник, нет ключа) не мешают следующим элементам.
- После завершающей остановки (квота, сбой аудита, срок или отмена посреди элемента) следующие элементы получают `not_run`, а `stop` объясняет причину (`kind` — `item` или `control`, `code`, `item_index`).
- Повторов, ключей идемпотентности и отката нет.
- Байты выхода учитываются один раз. Сервис копирует каждый завершённый выход в своё хранилище артефактов (на время этого элемента временный диск ненадолго держит два экземпляра). Артефакт сохраняет исходный корень, срок и учёт scratch, пока не освободится его последний сетевой срез.
- Отчёты XML и PDF держат свой резерв метаданных до конца пакета (у `/v1/operations` он освобождается по элементам). Пакету с несколькими подписями XML или PDF нужен пропорционально больший `metadata_bytes`. Измерено: три обычные подписи XML плюс одна XAdES-B помещаются в 96 МиБ, одна подпись XML и ещё одна — не помещаются в 64 МиБ. Когда резерв исчерпан, элемент завершается `MetadataLimit` (с честным `applied`), следующие получают `not_run`, прежние артефакты остаются.
- Срок покрывает загрузку, очередь, каждый элемент и доставку. Если он истекает (или клиент отключается) посреди пакета, ответ **обрывается без `final`**: это неизвестный исход, не успех. Журнал аудита хранит факты по элементам. Срок, истёкший пока клиент загружает, — типизированный `504 DeadlineExceeded` (`NotApplied`) до любых заголовков. Обрыв самого транспорта строку журнала не пишет, а обрыв с типизированным сбоем пишет (см. «Прерванные потоки ответов» в [server.md](server.md)).

## Настройка оператора (кратко)

Оператор задаёт в настройках:

- `[pki]`: `anchors`, `intermediates`, `endpoints` с привязкой адресов;
- `[pki.tsa]`: `url`, необязательные `policy`, `timeout_ms`, `skew_ms`. Обязателен для подписи `*_t/lt/lta` и для `stamp`;
- `[pki.jwt]`: `expected_issuer`, `expected_audience`;
- токенам — действия `extend`, `inspect`, `stamp`, `verify_stamp`, `batch` и список `metadata_aliases`.

Ничто из этого нельзя передать в запросе. Закрытые операции проверяют строго: им нужны настроенные якоря и доступные свидетельства отзыва, иначе они завершаются сбоем до использования ключа.

## Тесты на настоящих сокетах

Тестам нужны `openssl` в `PATH` и отдельное окружение Python для независимых проверок. Как их поставить — в [`docs/dev/development.md`](../dev/development.md), раздел «Что нужно для тестов». Без них тесты падают с пояснением, а не пропускаются.

## Эталонный клиент

`oncl_api::client::ApiClient` (feature `client` крейта `oncl-api`, только `ureq` и `rustls`) — эталонный клиент этого контракта и транспорт для `oncl --endpoint` ([cli.md](cli.md#удалённый-режим---endpoint)). Он:

- пишет multipart с метаданными первыми как ограниченный поток (сначала секреты, тела документов потоком с точной длиной или chunked);
- отправляет `Expect: 100-continue` и никогда не следует перенаправлениям;
- читает `multipart/mixed` по `Content-Length` части ограниченным читателем;
- считает ответ результатом, только когда получены `final`, закрывающий разделитель и конец HTTP-ответа. Иначе исход — `ResponseLost` с `Unknown` (ключ мог быть использован) или `NotApplied`, без повтора.

Зеркало ответа клиента (`client::wire`) сверяется с каждым опубликованным примером OpenAPI (`tests/client.rs`). Длины артефактов клиент проверяет только там, где их навязывает сервер (извлечение, токен штампа времени, создание JWS/JWT; элементы пакета — никогда). Его `ExecuteOptions.control` опрашивается каждые 50 мс, поэтому остановка сообщает `Unknown` только тогда, когда тело, способное использовать ключ, уже отправлено полностью.
