# Сторонние издатели плагинов

Статус: проект, кода нет. Документ описывает, как сторонний издатель (вендор) выпускает плагины в каталог OpenNCALayer своей подписью, без подписи владельца на каждом выпуске. Механизм: делегированные роли TUF ([спецификация 1.0.37](https://theupdateframework.github.io/specification/latest/), разделы 4.5, 5.6 и 5.7). Опирается на [`tuf.md`](tuf.md), [`update-index.md`](update-index.md) и [`plugins.md`](plugins.md) (жизненный цикл и каталог). Задача в плане: P15b ([`tuf.md`](tuf.md), раздел «Почему нет делегирований»).

Места, которые не удалось проверить по коду или по документации, помечены «Открытый вопрос» и собраны в конце.

## Решения владельца

Р1. Издатель подписывает свою делегированную роль TUF (`targets`): записи каталога и хеши пакетов. Владелец делегирует один раз, дальше издатель выпускает без подписи владельца.

Р2. Издатель появляется только после одобрения владельца: PR с ключом, именем и пространством имён издателя, слияние делает владелец.

Р3. Издатель владеет префиксом идентификаторов плагинов (обратный домен, например `kz.ecc.`) и явным списком имён `module`, одобренным при подключении.

Р4. Издатель сам выбирает для каждой версии `beta` или `stable`. Сверка с оригиналом (`conformance`) к плагинам издателей не применяется.

Р5. Окно установки и окно «Плагины» показывают «Издатель: <имя>», наши порты: «Издатель: OpenNCALayer».

Р6. Отзыв издателя (снятие делегирования) выключает все его плагины у клиентов при следующей проверке каталога, как отзыв версии.

Р7. Сайт показывает плагины издателей с именем издателя.

Р8. Ключ `snapshot` уходит в CI (отдельное окружение GitHub и секрет, как у `timestamp`); `root` и верхний `targets` остаются офлайн.

Р9. Выпуск: издатель открывает PR в наш репозиторий со своим подписанным файлом роли. Если PR трогает только файлы этого издателя и проверки CI зелёные (подпись, префикс, модули, хеши, доступность пакета, лимиты), бот сливает его сам.

Р10. Пакеты лежат по любому HTTPS-адресу издателя; длина и sha256 подписаны в его роли.

Р11. Если издатель просит модули, которые обслуживает наш порт, решает владелец при подключении. Если одобрил, порт уходит из каталога, а клиентам с портом плагин издателя предлагается как обновление, с окном разрешений.

Р12. По умолчанию у издателя один ключ; несколько ключей и порог допускаются.

Р13. Инструменты издателя: `cargo xtask vendor …` в клоне нашего репозитория (ключ, сборка пакета, подпись роли, проверка).

Р14. Отдельный репозиторий `tuf/v2` со своим офлайн-корнем (новая церемония), онлайн-ключами `snapshot` и `timestamp` в CI и общим с `tuf/v1` ключом `targets`.

Р15. Плагины издателей видны начиная со следующего выпуска 0.1.x, `0.1.2`. Ниже X означает `0.1.2`.

Р16. `tuf/v1` остаётся без срока, его публикует тот же CI, снимок `tuf/v1` подписывается офлайн, как сейчас. Удаление `tuf/v1` решается отдельно и позже.

Р17. Владение доменом префикса владелец проверяет вручную при одобрении подключения, без автоматики `.well-known` или DNS.

Р18. Владелец может отозвать отдельную версию издателя своей записью в `publishers.json`, не только издателя целиком.

Р19. Не больше одного выпуска издателя в час; CI проверяет это по истории git файлов издателя.

Р20. Разрешения плагина хранятся в подписанной записи каталога (`custom.oncl.capabilities`); сайт пакеты не скачивает.

Р21. CI скачивает каждый новый пакет PR (не больше `length` и `MAX_PACKAGE`, с тайм-аутом) и сверяет длину, sha256, манифест (`id`, версия, модули, `min_core`) и равенство `custom.oncl.capabilities` разрешениям манифеста. Если хоть один пакет не скачался с раннера GitHub, PR целиком не сливается автоматически: издатель должен положить пакет туда, откуда его видно. Клиент сверяет то же самое ещё раз при установке.

Р23. Версии крейтов отвязаны от версии программы: крейты SDK выходят как `0.2.0` (ломающие изменения API в `oncl-update` и других), программа выходит как `0.1.2`.

Р22. Казахская строка для «Издатель»: «Жариялаушы».

Дополнительное требование владельца к коду: каждое решение по API, типам, ошибкам и тестам Rust следует навыку `rust-skills` (раздел «Типы и ошибки Rust» ниже).

## Что есть сейчас

Эти факты определяют форму решения; пути от корня репозитория.

- Клиент TUF отвергает любой `targets` с членом `delegations`, даже пустым: `Targets::from_signed` возвращает `TufError::Unsupported("delegations in targets metadata")` (`crates/oncl-update/src/tuf/model.rs:434-440`). Отказ случается на шаге 5.6 (`client.rs:534`) и обрывает весь `refresh`. Шаг 5.6.7 сведён к верхнему `targets` (`client.rs:33`, `:561-562`).
- Один и тот же `refresh` нужен и апдейтеру ядра (`crates/openncalayer/src/update.rs`), и каталогу плагинов (`crates/openncalayer/src/repository.rs:232`). Значит, `targets` с делегированиями в `tuf/v1` оставит каждый выпущенный клиент без обновлений ядра навсегда: новая версия ядра приходит через тот же `targets`. Это главное ограничение миграции.
- `snapshot` уже переносит версии любых метафайлов, а пропавшая из нового снимка запись считается откатом (`client.rs:478-498`). Делегированные файлы клиент не скачивает.
- Состояние TUF: `<data>/update/tuf/state.json`, `#[serde(deny_unknown_fields)]`, схема 1 (`crates/oncl-update/src/tuf/store.rs:22`, `:29-66`, `:251-252`). Версий делегированных ролей там нет.
- Пакеты плагинов целями TUF не являются: клиент берёт `url`, `size` и `sha256` из записи индекса (`crates/openncalayer/src/plugins.rs:1191` и дальше), затем сверяет манифест.
- `choose_plugin` не трогает плагин, версии которого нет в индексе: «An unlisted current version alone never causes a downgrade or removal» (`crates/oncl-update/src/plugins.rs:104-139`). Пропажа записи не отзыв, поэтому отзыв издателя нужно распознавать явно.
- Запись установленного плагина: `Installed { version, sha256, source, enabled, withdrawn }`, `Source` только `Catalog | Local` (`crates/oncl-plugin/src/store.rs:47-67`). У структур нет `deny_unknown_fields`.
- Путь отзыва уже есть: `PluginChoice::Withdrawn` выгружает плагин, пишет `withdrawn` и сообщает `PluginNotice::Withdrawn` (`crates/openncalayer/src/plugins.rs:983-998`).
- Проверка подписи `count_valid` принимает произвольный набор ключей и пару `keyids`/`threshold` (`crates/oncl-update/src/tuf/ed25519.rs:29-54`), её можно звать с ключами делегирования. Канонический разбор отвергает повтор ключа в объекте (`canonical.rs:287`).
- `cargo xtask tuf update` подписывает `targets` и `snapshot` ключами владельца (`xtask/src/tuf/update.rs:223-245`). `tuf root` выпускает онлайн-ключ (строку `oncl-tuf-ed25519-seed-v1:`) только для `timestamp`; новый ключ `snapshot` шифруется паролем (`xtask/src/tuf/root.rs:128-132`). `repo::classify` знает только `root`, `targets`, `snapshot`, `timestamp` и `targets/indexes/…` (`xtask/src/tuf/repo.rs:37-66`).
- Право на модули проверяет только `xtask` при сборке индекса (`xtask/src/index.rs:134`, `:230`); клиент разрешает конфликт при загрузке: первый зарегистрированный модуль выигрывает (`LoadError::ModuleTaken`). Префиксы идентификаторов не проверяет никто, кроме запрета `io.github.arynyklas.openncalayer.builtin.` (`crates/oncl-plugin/src/builtins.rs:43`).
- `pages.yml` подписывает `timestamp` в job окружения `tuf-timestamp`, собирает xtask до появления секрета и не использует кэш сборки рядом с ключом. Запуск других workflow токеном `GITHUB_TOKEN` через `gh workflow run` уже используется (job `dispatch`).

## Обзор схемы

Два репозитория TUF публикуются рядом на Pages:

```
tuf/v1/   как сейчас: без делегирований, для клиентов младше X
tuf/v2/   новый: верхний targets с делегированиями, для клиентов X и новее
```

`tuf/v1` не меняется по форме: старые клиенты продолжают получать индексы и новые версии ядра, в том числе версию X. Клиент X и новее читает только `tuf/v2`. Индексы `updates/v1/<канал>.json` одни и те же байты в обоих репозиториях.

У `tuf/v2` своя цепочка корней и свои ключи `root`, `snapshot` и `timestamp`; ключ верхнего `targets` общий с `tuf/v1` (обоснование в разделе «Почему отдельная цепочка корней»).

Цепочка доверия клиента X:

```
встроенный root v2 (версия 1)
  → корни v2 N+1, N+2, …
    → timestamp v2 (CI) → snapshot v2 (CI) → верхний targets (офлайн, владелец)
         ├─ indexes/<канал>.json  → индекс владельца → пакеты портов (sha256 + size из индекса)
         ├─ publishers.json       → правила издателей (префиксы, модули, имена, отзыв)
         └─ delegations: pub-<издатель> (ключи издателя, paths plugins/<издатель>/*/*)
              → роль pub-<издатель> (подпись издателя) → пакет (length + sha256 цели) по custom.oncl.url
```

## Раскладка TUF

### Файлы `tuf/v2`

| Путь | Что | Кто подписывает | В git |
|---|---|---|---|
| `metadata/<N>.root.json` | корень v2, все версии | `root` v2, офлайн | да |
| `metadata/<N>.targets.json` | верхний `targets` | `targets`, офлайн | да |
| `metadata/<N>.pub-<издатель>.json` | делегированная роль издателя, все версии | ключи издателя | да |
| `metadata/<N>.snapshot.json` | снимок; `N` равен Unix-времени подписи | `snapshot` v2, CI | нет, только артефакт Pages |
| `metadata/timestamp.json` | как сейчас | `timestamp` v2, CI | нет |
| `targets/indexes/<sha256>.<канал>.json` | индекс владельца, те же байты, что в `tuf/v1` | | да |
| `targets/<sha256>.publishers.json` | правила издателей | | да |

Имя делегированного файла `<версия>.<роль>.json` следует разделу 3.1.2.1 и правилу согласованных снимков (6.2). Новая функция `layout::delegated_path(version, &RoleName)` рядом с `targets_path` (`crates/oncl-update/src/tuf/layout.rs:28-31`).

Пакеты издателей в репозитории не лежат: цели `plugins/…` описывают байты пакета, а скачиваются они с адреса из `custom.oncl.url` (Р10). Поэтому в `targets/plugins/` файлов нет, и `tuf check` не требует их там (сейчас он требует файл для каждой цели, `check.rs`, шаг 4).

### Роли и имена

- Имя издателя (`PublisherName`): `^[a-z0-9][a-z0-9-]{1,30}[a-z0-9]$`. Зарезервированы `openncalayer`, `oncl`, `owner`, `builtin`, `port`, `ports`, `root`, `targets`, `snapshot`, `timestamp`.
- Имя роли (`RoleName`): ровно `pub-<имя издателя>`. Строится только из `PublisherName`, разбирается обратно в него. Совпасть с именем верхней роли не может.
- Делегирования одного уровня: роль издателя дальше не делегирует (клиент отвергает `delegations` в роли издателя).

### Делегирование в верхнем `targets` v2

```json
"delegations": {
  "keys": {
    "<keyid>": {"keytype": "ed25519", "scheme": "ed25519", "keyval": {"public": "<64 hex>"}}
  },
  "roles": [
    {
      "name": "pub-ecc",
      "keyids": ["<keyid>"],
      "threshold": 1,
      "paths": ["plugins/ecc/*/*"],
      "terminating": true
    }
  ]
}
```

Правила профиля v2 (клиент проверяет, xtask не даёт записать иное):

- `delegations` в верхнем `targets` v2 есть всегда, при нуле издателей это `{"keys": {}, "roles": []}`. Если члена нет или он испорчен, клиент отвергает весь верхний `targets` (`DelegationsMissing` или ошибка разбора): обновление v2 не проходит целиком, включая ядро и индекс владельца, до исправленного файла. Отзывом это не считается, установленные плагины не трогаются. Такой файл подписывает только владелец офлайн, и xtask его не запишет.
- Онлайн-подпись снимка в CI проверяет, что снимок перечисляет каждую роль издателя, когда-либо бывшую в `delegations`, с версией не ниже прошлой. Иначе клиент отвергнет снимок как откат (шаг 5.5.5), и обновление v2 остановится у всех.
- `paths` ровно `["plugins/<имя>/*/*"]`, где `<имя>` берётся из имени роли. Шаблон в смысле раздела 4.5: `*` не пересекает `/`. `path_hash_prefixes` отвергается. Другие формы шаблона клиент не разбирает: роль с ними недоступна.
- `terminating: true` у каждой роли. Пути ролей не пересекаются по построению (разные `<имя>`), поэтому порядок ролей в массиве не важен, и обход шага 5.6.7 сводится к одной роли на путь.
- `keyid` каждого ключа пересчитывается из ключа, как в корне. Ключ издателя не совпадает ни с одним ключом корня v2 и v1, ни с ключом другого издателя (то же правило «один ключ на одну роль», что в корне).
- `threshold` от 1 до числа `keyids` (Р12); дубликаты `keyids` отвергаются.
- Имена ролей уникальны (раздел 4.5 требует того же).
- Не больше 32 ролей (`Limits::max_delegations`).

### Цели издателя

Путь цели: `plugins/<издатель>/<id>/<версия>.onclp`. `<id>` и `<версия>` взяты из пути однозначно: разделитель `/` в них невозможен (`id` из `[a-z0-9.-]`, semver из `[0-9A-Za-z.+-]`), а грамматика пути клиента уже допускает эти символы (`model.rs:471-480`).

```json
"plugins/ecc/kz.ecc.market/1.2.0.onclp": {
  "length": 123456,
  "hashes": {"sha256": "<64 hex>"},
  "custom": {
    "oncl": {
      "schema": 1,
      "id": "kz.ecc.market",
      "version": "1.2.0",
      "url": "https://downloads.ecc.kz/oncl/kz.ecc.market-1.2.0.onclp",
      "channel": "stable",
      "min_core": "0.1.2",
      "modules": ["kz.ecc.market.Signer"],
      "replaces": {"symname": "kz.ecc.market", "version": "1.2.0"},
      "name": {"ru": "…", "kk": "…", "en": "…"},
      "capabilities": {"keys": true, "http": ["https://api.ecc.kz/"]},
      "rollout": 100,
      "revoked": false
    }
  }
}
```

Поля `custom.oncl` повторяют запись `plugins[]` индекса ([`update-index.md`](update-index.md), таблица полей), с отличиями:

- `size` и `sha256` не повторяются: это `length` и `hashes.sha256` самой цели (Р10).
- `id` и `version` обязаны совпасть с путём цели.
- `channel`: `beta` или `stable` (Р4). `stable` предлагается клиентам обоих каналов, `beta` только каналу `beta`, как у выпусков владельца (релиз без суффикса идёт и в `stable`, и в `beta`). Предварительная версия semver с `stable` отвергается.
- `revoked` один на версию, не на канал.
- `capabilities` (Р20): таблица `[capabilities]` манифеста пакета в JSON, те же ключи и правила, что в `plugin.toml` ([`plugins.md`](plugins.md), раздел «Capabilities»). Её заполняет `vendor add` из манифеста. CI скачивает пакет и требует, чтобы поле было равно разрешениям манифеста (Р21). Клиент сверяет то же при установке и обновлении, рядом с `check_manifest` (`crates/openncalayer/src/plugins.rs:1448`): пакет, чьи разрешения не равны записи каталога, отвергается, и версия помечается плохой.
- Незнакомые поля внутри `oncl` клиент пропускает (как незнакомые поля индекса, `update-index.md:91`), CI их отвергает. `schema` выше 1 клиент не читает: такая запись пропускается.

### `publishers.json`

Цель верхнего `targets`, подписана владельцем. Нужна потому, что `paths` не выражают права на модули и бандлы, а у отозванного издателя нет делегирования, по которому его можно узнать (`tuf.md:158` называет тот же реестр).

```json
{
  "schema": 1,
  "publishers": [
    {
      "name": "ecc",
      "state": "active",
      "display": {"ru": "ТОО «…»", "kk": "…", "en": "…"},
      "id_prefix": "kz.ecc.",
      "modules": ["kz.ecc.market.Signer"],
      "bundles": ["kz.ecc.market"],
      "supersedes": {"io.github.arynyklas.openncalayer.port.market": "kz.ecc.market"},
      "revoked_versions": [{"id": "kz.ecc.market", "version": "1.1.0", "date": "2027-02-10"}],
      "homepage": "https://ecc.kz/"
    },
    {
      "name": "old",
      "state": "revoked",
      "display": {"ru": "…", "kk": "…", "en": "…"},
      "id_prefix": "kz.old.",
      "revoked": "2027-03-01"
    }
  ]
}
```

- `state: "revoked"` с префиксом остаётся навсегда: по нему клиент узнаёт плагины отозванного издателя, даже если запись установки потеряла имя издателя, а владелец не выдаст тот же префикс другому по ошибке.
- `bundles`: разрешённые `replaces.symname` (по аналогии с модулями Р3; список может быть пустым).
- `supersedes`: порты, которые заменяет издатель (Р11), порт → идентификатор плагина издателя под его префиксом.
- `revoked_versions` (Р18): версии издателя, которые отозвал владелец. Для клиента такая версия отозвана, что бы ни писал издатель в своей роли; запись под чужим префиксом делает файл недействительным.
- Не больше 128 записей (вместе с отозванными), файл до 64 КиБ.

Клиент проверяет файл целиком: префиксы не вложены друг в друга и не лежат под `io.github.arynyklas.openncalayer.`; модули и бандлы двух издателей не пересекаются; ни один модуль не встроенный; активные издатели ровно те, у кого есть роль в `delegations`. Нарушение означает «каталог издателей недоступен» (см. «Недоступен и отозван»), индекс владельца работает дальше.

### Сроки и лимиты

| Что | Срок | Размер |
|---|---|---|
| root v2 | 365 дней, офлайн | 64 КиБ |
| верхний `targets` v2 | 30 дней, офлайн | 256 КиБ |
| `snapshot` v2 | 7 дней, CI на каждой публикации Pages | 128 КиБ |
| `timestamp` v2 | 7 дней, CI | 16 КиБ |
| роль издателя | выбирает издатель: не дальше 180 дней от подписи и не меньше 14 дней в запасе при слиянии | 128 КиБ, не больше 256 целей |
| `publishers.json` | срок верхнего `targets` | 64 КиБ |
| пакет | | `MAX_PACKAGE`, 32 МиБ (`crates/oncl-plugin/src/package.rs:17`) |

### Снимок v2

`snapshot` v2 перечисляет `targets.json` и каждую роль `pub-*`, файл которой хоть раз был в git, с `version`, `length` и `hashes.sha256`. Длину и хеш клиент v2 требует у каждой записи (сейчас они необязательны, `client.rs:705-731`): так один и тот же ключ `targets` в двух репозиториях не даёт подставить файл одного вместо другого.

Роль отозванного издателя остаётся в `snapshot` навсегда с последней версией: раздел 5.5.5 и наш клиент (`client.rs:478-498`) считают пропавшую запись откатом. Клиент эту роль не скачивает, потому что её нет в `delegations`.

## Почему отдельная цепочка корней

Нельзя положить делегирования в `tuf/v1`: каждый клиент младше X получит отказ на шаге 5.6 и больше никогда не обновится (раздел «Что есть сейчас»). Нужен второй репозиторий. Вопрос в том, делить ли с `tuf/v1` ключи.

Если `tuf/v2` делит с `tuf/v1` ключи `timestamp` и `snapshot`, то тот, кто подменяет ответы Pages, может подать клиенту v2 снимок v1 (и наоборот). Подпись сойдётся, клиент сохранит снимок (шаг 5.5.7 до шага 5.6), а затем каждый настоящий снимок будет для него откатом: в снимке v1 нет записей `pub-*`, а версия `targets.json` другая. Старый клиент, получив снимок v2 с записями `pub-*`, застрянет так же. Это долгая поломка, а не заморозка до срока, и лечится она только ротацией ключей. Если общий ключ `root`, цепочки сливаются: корень v1 версии N+1 подписан тем же ключом и подходит клиенту v2 по правилу «ровно N+1».

Поэтому (Р14):

- `root` v2: новый офлайн-ключ владельца, корень v2 версии 1 встраивается в клиент X как `crates/oncl-update/keys/root.json` (анкер v1 переезжает в `tuf/v1/metadata/1.root.json`, откуда xtask и так может его читать).
- `timestamp` v2 и `snapshot` v2: новые онлайн-ключи в CI.
- `targets`: общий офлайн-ключ. Это безопасно: файл `targets` клиент берёт только по хешу из снимка своей цепочки, а снимки подписаны разными ключами.

Подложенный чужой файл теперь отвергается по подписи на шаге 5.3, 5.4 или 5.5, до сохранения.

`tuf/v1` остаётся без срока (Р16): тот же CI публикует его рядом с `tuf/v2`, снимок `tuf/v1` подписывает владелец офлайн, как сейчас, делегирований там нет, и выпуск издателя его не трогает. Р8 относится к `tuf/v2`.

## Каталог

### Как он собирается

Каталог клиента X: индекс владельца канала плюс записи издателей, приведённые к `PluginRelease` (`crates/oncl-update/src/plugins.rs:12-35`).

| `custom.oncl` / цель | `PluginRelease` |
|---|---|
| `id`, `version` (равны пути) | `id`, `version` |
| `url`, `length`, `hashes.sha256` | `package.url`, `package.size`, `package.sha256` |
| `min_core`, `modules`, `replaces`, `name`, `rollout`, `revoked` | одноимённые поля; `revoked` ещё и `true`, если версия есть в `revoked_versions` издателя |
| `channel` | фильтр: запись входит, если `stable`, или если канал клиента `beta` |
| имя роли | новое поле `publisher: Option<PublisherName>` с `#[serde(skip)]`: из JSON индекса его не прочесть, так что индекс владельца не может выдать порт за плагин издателя |
| `capabilities` | новое поле `capabilities: Option<DeclaredCapabilities>` с `#[serde(skip)]`; у портов `None`, у плагинов издателей обязательно. `DeclaredCapabilities` в `oncl-update` держит JSON-объект как есть (крейт не зависит от `oncl-plugin`), а разбирает его в `oncl_plugin::Capabilities` код каталога в `openncalayer` при сборке каталога; не разобралось: запись отбрасывается |

Порядок старшинства, если источники расходятся. Слово владельца сильнее слова издателя, как в предпорядковом обходе шага 5.6.7, где верхний `targets` идёт раньше делегированных ролей.

1. Отзыв версии владельцем (Р18): версия из `revoked_versions` в `publishers.json` отозвана, даже если роль издателя пишет `revoked: false`. Владелец пишет её из `[[revoked_versions]]` в `publishers/<имя>/publisher.toml` и подписывает новый верхний `targets`. Снять отзыв может только владелец. Целей `plugins/…` в верхнем `targets` нет: xtask их не пишет, а клиент v2, встретив такую цель, считает профиль нарушенным, и все издатели становятся недоступны (индекс владельца работает).
2. Тот же `id` в индексе владельца и у издателя: выигрывает индекс владельца, записи издателя с этим `id` отбрасываются (журнал, `warn`). xtask не даёт владельцу добавить в индекс `id` под префиксом издателя, так что это защита от ошибки.
3. Модуль или `replaces.symname` у записи владельца и у записи издателя: выигрывает владелец. Исключение: порт, заменённый издателем (`supersedes` активного издателя), см. «Замена порта».
4. Между издателями конфликтов нет по построению: префиксы, модули и бандлы в `publishers.json` не пересекаются, а запись издателя вне его префикса, модулей или бандлов отбрасывается.

Запись издателя отбрасывается (журнал `warn`, остальные записи роли живут), если `id` не под префиксом издателя, модуль не из его списка, `replaces.symname` не из `bundles`, модуль встроенный, `id` под `io.github.arynyklas.openncalayer.`, `id`/`version` не совпали с путём, `url` не `https://`, `rollout` больше 100, модулей нет или больше 32, `stable` у предварительной версии, `capabilities` нет или они не разбираются по правилам манифеста.

### Недоступен и отозван

Для каждого издателя каталог знает одно из трёх состояний:

- активен: роль скачана и проверена, записи в каталоге;
- недоступен: не скачалась или не прошла проверку роль издателя, `publishers.json`, или `delegations` нарушают профиль. Плагины издателя не обновляются и не отзываются (`Keep`), пока это не пройдёт;
- отозван: проверенный `publishers.json` называет издателя `revoked`, или не называет его вовсе, или у него нет роли в проверенных `delegations`.

Отзыв решается только по проверенным верхнему `targets` и `publishers.json` (свежим или сохранённым и проверенным заново офлайн). Ошибка сети или подписи никогда не отзывает.

## Клиент

### Профиль репозитория

`TufClient` получает профиль `Profile::{Legacy, Delegating}`:

- `Legacy` (как сейчас): `delegations` в `targets` отвергаются. Им пользуется xtask для `tuf/v1`.
- `Delegating`: в верхнем `targets` член `delegations` обязателен и разбирается в типизированную модель; длина и хеш обязательны у каждой записи `snapshot.meta`. Клиент X работает только так.

### Шаги

Шаги 5.1–5.6.6 не меняются, кроме разбора `delegations` на шаге 5.6.3. Апдейтер ядра делает только их (`refresh`) и делегированные роли не скачивает.

Новый шаг для каталога плагинов, `TufClient::delegated(&self, trusted: &Trusted, now) -> Result<Delegated, TufError>`, его зовёт `Repository` каталога после `refresh`:

1. Скачать цель `publishers.json` из верхнего `targets` (`download_target`, лимит 64 КиБ) и разобрать её в `PublisherPolicy`. Ошибка: все издатели недоступны.
2. Обойти `delegations.roles` по порядку (раздел 5.6.7: предпорядок, верхний `targets` уже пройден). Для каждой роли, не больше `max_delegations` (32):
   1. Роль с уже встреченным именем пропускается (защита от циклов из 5.6.7.1; при уникальных именах это невозможно, но шаг оставлен).
   2. Профиль роли: имя `pub-<имя>`, `paths`, `terminating`, ключи (раздел «Делегирование»). Нарушение: роль недоступна.
   3. Запись `pub-<имя>.json` в проверенном `snapshot` обязательна. Нет: роль недоступна.
   4. Скачать `metadata/<версия>.pub-<имя>.json` не длиннее указанной в снимке длины (и не длиннее `Limits::delegated`, 128 КиБ), сверить длину и sha256 до подписи (как 5.6.2).
   5. Подпись: порог `threshold` различных `keyid` из `keyids` роли, ключи из `delegations.keys` (`count_valid`).
   6. `_type` равен `targets`; `version` равна версии из снимка (5.6.4) и не меньше сохранённой; срок не истёк (5.6.5); члена `delegations` нет (глубина 1).
   7. Каждая цель роли подходит под её `paths` (раздел 4.5: «Clients MUST check that a target is in one of the trusted paths of all roles in a delegation chain»). Цель вне путей: роль недоступна целиком. Спецификация лишь не доверяет такой цели; мы строже, потому что CI такой файл не сольёт, и его появление означает ошибку или атаку.
   8. Сохранить версию роли (5.6.6) и вернуть проверенную роль.
3. Ошибка одной роли не трогает другие и не трогает индекс владельца. Ошибка записи состояния (`TufError::Store`) обрывает весь шаг.

Отличие от спецификации, записанное в комментарий модуля `client.rs`: шаг 5.6.7 ищет одну цель, а каталогу нужен список всех целей всех издателей. Клиент проходит все делегированные роли с теми же ограничениями (порядок, посещённые роли, лимит числа ролей, проверка путей); при непересекающихся терминальных делегированиях это даёт для любого пути тот же ответ, что поиск 5.6.7. Мультиролевых делегирований в 1.0.37 нет.

5.7 для пакетов издателей делает приложение, как сегодня для пакетов индекса: HTTPS по `custom.oncl.url`, длина и sha256 из цели TUF, затем `Package::read`, `check_manifest` (`crates/openncalayer/src/plugins.rs:1448`) и новая сверка `capabilities` записи с манифестом. CI уже проверил всё это при слиянии (Р21), клиент повторяет проверку на случай подмены хостинга после слияния. Сбой скачивания у клиента обрабатывается как сегодня: ошибка сети (`Download::Unreachable`) оставляет всё как было и повторяется при следующей проверке каталога, а несовпавшие длина, sha256, манифест или разрешения помечают версию плохой (`Download::Bad`, `plugins.rs:1037-1042`). Пользователь видит обычное сообщение о неудачной установке.

### Состояние

- TUF v2: `<data>/update/tuf/v2/state.json` и `lock`, отдельно от `tuf/v1`. Отдельный каталог обязателен: у v2 своя цепочка корней и своя нумерация версий, а клиент, откаченный проверкой здоровья на версию младше X, продолжает читать `<data>/update/tuf/state.json` и не должен увидеть там чужих версий. `TrustState` v2 получает `delegated: BTreeMap<RoleName, u64>`, версии ролей. Слияние под блокировкой, как сейчас: версия никогда не понижается. Ротация ключей `snapshot`/`timestamp`/`targets` корнем забывает и `delegated` (те же правила, что `client.rs:296-302`).
- Сохраняются не файлы ролей в состоянии (32 роли по 128 КиБ больше лимита состояния 2 МиБ, `store.rs:26`), а их байты в хранилище плагинов, как индекс: `<data>/plugins/catalog/publishers.json` и `<data>/plugins/catalog/roles/pub-<имя>.json`.
- Проверка сохранённого без сети: `verify_cached_target` для `publishers.json` (уже есть, `client.rs:635-675`) и новая `TufClient::verify_cached_role(&RoleName, bytes, now)`: цепочка корней от встроенного, сохранённый верхний `targets`, делегирование роли в нём, подпись ключами делегирования, версия равна сохранённой, срок, пути. Срок действия сохранённого каталога: для индекса владельца как сейчас (корень и `targets`), для издателя ещё и срок его роли; после него издатель недоступен, не отозван.
- Хранилище плагинов: `Installed.publisher: Option<PublisherName>` с `#[serde(default, skip_serializing_if = "Option::is_none")]`; `StoreState.declined_replacements: BTreeMap<String, String>` (порт → плагин издателя, от которого пользователь отказался), так же с `default`. Новый вариант `Source` не нужен: версия младше X, откаченная проверкой здоровья, не прочла бы состояние с незнакомым вариантом.

### Отзыв

В `apply_index` (`crates/openncalayer/src/plugins.rs:944-1004`), до `choose_plugin`, для каждого плагина `Source::Catalog`:

1. Издатель плагина: `Installed.publisher`, а если поля нет, издатель, чей `id_prefix` (в том числе у отозванных) покрывает `id`. Найденное без поля записывается в `Installed.publisher`.
2. Издатель недоступен: плагин пропускается (`Keep`, ожидающее обновление остаётся).
3. Издатель отозван и плагин не `withdrawn`: тот же путь, что `PluginChoice::Withdrawn` (выгрузить, `set_withdrawn(true)`, удалить ожидающее обновление), с новым уведомлением `PluginNotice::PublisherRevoked { name, publisher }`.
4. Издатель снова активен (владелец вернул делегирование) и версия плагина в каталоге не отозвана: существующая ветка «the plugin's version is no longer revoked» (`plugins.rs:960-979`) снимает `withdrawn`.

### Замена порта (Р11)

Порт `P` из индекса владельца считается заменённым, если активный издатель называет его в `supersedes`, и в каталоге этого клиента (канал, `min_core`, раскатка, не плохая) есть версия плагина издателя `Q`. Пока такой версии нет, порт остаётся в каталоге как был: пользователь не теряет плагин из-за того, что издатель ещё не выпустил замену в его канал.

- Заменённый порт не предлагается для новой установки, `missing(module)` и `installBundle` выбирают `Q`.
- Установленный `P` (`Source::Catalog`): `apply_index` скачивает и проверяет `Q` и показывает окно замены (всегда, даже без новых разрешений: другой `id`, другой издатель). Согласие: под `changing` выгрузить `P`, загрузить `Q`; если `Q` не загрузился, загрузить `P` обратно и пометить версию `Q` плохой; если загрузился, записать `Q` (`publisher` задан) и удалить `P` с его пакетом и настройками. Отказ: `declined_replacements[P] = Q`, `P` работает дальше без обновлений каталога, окно «Плагины» показывает «Доступна замена от издателя …» с кнопкой, повторного уведомления нет.
- Издатель отозван: `supersedes` перестаёт действовать, `P` (если он ещё в индексе владельца) снова обычный порт.
- Клиенты младше X `publishers.json` не видят и продолжают обновлять `P` из того же индекса.

### Типы и ошибки Rust

Все решения в коде по навыку `rust-skills`: типизированные ошибки (`err-custom-type`, `err-thiserror-lib`), новые типы для имён и путей (`api-newtype-safety`, `type-no-stringly`), разбор на границе TUF (`api-parse-dont-validate`, `serde-try-from-validate`), без `unwrap`/`expect` вне тестов (`err-no-unwrap-prod`), явные `match` по своим перечислениям (`pat-exhaustive-enum`), точечные регрессионные тесты с описательными именами (`test-descriptive-names`).

Новые типы в `oncl-update` (часть публичного API опубликованного крейта, `publish = true`). Изменение `Targets` и `PluginRelease` ломает API, поэтому крейты SDK выходят как `0.2.0`, а программа как `0.1.2` (Р23):

| Тип | Инвариант, который держит конструктор |
|---|---|
| `PublisherName` | грамматика и зарезервированные имена |
| `RoleName` | ровно `pub-<PublisherName>`; `RoleName::of(&PublisherName)`, `RoleName::publisher()` |
| `TargetPath` | сегодняшняя `valid_target_path` (`model.rs:471`); `Targets.targets` становится `BTreeMap<TargetPath, Target>` |
| `PathPattern` | только форма `plugins/<имя>/*/*`; `matches(&TargetPath) -> bool` |
| `PublisherTarget` | разобранный `plugins/<издатель>/<id>/<версия>.onclp`: `PublisherName`, `PluginId`, `Version` |
| `PluginId`, `IdPrefix`, `ModuleName`, `BundleName` | грамматики манифеста (`manifest.rs`) и префикса; `IdPrefix::covers(&PluginId)` |
| `Delegations`, `DelegatedRole` | разобраны из `signed` вместе с `Targets`: ключи с пересчитанными `keyid`, порог, уникальные имена |
| `VerifiedRole` | конструктор приватный, создаёт только `TufClient::delegated`/`verify_cached_role` после подписи, версии, срока и путей |
| `PublisherPolicy` | `publishers.json` через `#[serde(try_from = "RawPublishers")]`: непересекающиеся префиксы, модули, бандлы |
| `PublisherRelease` | `custom.oncl` через `try_from`, совпадение с `PublisherTarget` |
| `DeclaredCapabilities` | JSON-объект `custom.oncl.capabilities` не больше 16 КиБ; разбор в `oncl_plugin::Capabilities` через `TryFrom<&DeclaredCapabilities>` в `oncl-plugin`, теми же правилами, что `[capabilities]` манифеста |
| `Catalog` | индекс владельца, `PublisherPolicy`, состояния издателей; `offer`/`choose_plugin` принимают `&Catalog` вместо `&Index` |

Ошибки:

- `TufError` получает `Delegation { role: RoleName, error: DelegationError }` и `DelegationsMissing`; `DelegationError` (`thiserror`, `#[non_exhaustive]`) различает `NotInSnapshot`, `Nested`, `PathOutside { path }`, `Pattern`, `KeyReused { keyid }`, `Threshold`, `TooMany { max }` и обёртки уже существующих причин (подпись, версия, срок, длина, хеш).
- Каталог: `CatalogError` для `publishers.json` и `EntryRejected { path: TargetPath, reason: EntryRejection }` для отброшенных записей, `EntryRejection` перечисляет причины из раздела «Как он собирается».
- Сообщения строчные, без точки; причина сохраняется в `source` (`err-source-chain`); журнал пишет структурные поля `publisher`, `role`, `path` (`obs-structured-fields`), каждую ошибку один раз.

## Онлайн-снимок v2 (Р8)

- Ключ: `tuf init --repo v2` создаёт `root` v2 (зашифрован) и онлайн-ключи `snapshot` и `timestamp` v2 строкой `oncl-tuf-ed25519-seed-v1:<64 hex>`; ключ `targets` берётся существующий. `tuf root --repo v2 --rotate-snapshot` тоже пишет онлайн-ключ (сейчас онлайн-формат только у `timestamp`, `root.rs:128-132`).
- Окружения GitHub: `tuf-snapshot` с секретом `TUF_V2_SNAPSHOT_KEY` и `tuf-timestamp` с новым секретом `TUF_V2_TIMESTAMP_KEY` рядом с `TUF_TIMESTAMP_KEY`; ветки развёртывания только `main`.
- `pages.yml`: новый job `snapshot` (окружение `tuf-snapshot`) до `timestamp`, устроен как нынешний `timestamp`: xtask собирается до появления секрета, кэша нет, подпись последним шагом, файл уходит выходом job.
- `cargo xtask tuf snapshot --dir <копия tuf/v2> --previous <URL опубликованного tuf/v2>`: проверяет клиентским кодом корни, верхний `targets` и каждую роль `pub-*` (последняя версия активного издателя подписана его ключами; у отозванного файл только перечисляется), строит `meta` (все роли, хоть раз бывшие в git), подписывает версию `max(Unix-время, предыдущая + 1)` на 7 дней. Подписать снимок над непроверенным файлом CI не может.
- Предыдущий снимок: `--previous` читает опубликованный `timestamp.json`, скачивает названный им снимок, проверяет и кладёт в артефакт рядом с новым. Клиент, у которого в кэше Pages (`max-age=600`) ещё старый `timestamp.json`, найдёт названный им снимок. Без этого он получит 404 и ошибку с повтором через 30–120 минут (открытый вопрос 2).
- `timestamp` v2 подписывается в job `timestamp` после проверки снимка v2; `tuf/v1` как сейчас.

## xtask

### Команды владельца

- `tuf update`: пишет `tuf/v1/metadata/<N+1>.targets.json` и `.snapshot.json` как сейчас (снимок `tuf/v1` остаётся офлайн, Р16) и `tuf/v2/metadata/<M+1>.targets.json` (индексы, `publishers.json` с отзывами версий владельцем, `delegations`); снимок v2 не пишет. Источник делегирований и `publishers.json`: `publishers/<имя>/publisher.toml` (раздел «Подключение»). Проверка после записи: `tuf check` обоих репозиториев, при отказе написанное удаляется (как `update.rs:280-313`).
- `tuf check`: оба репозитория. `repo::classify` узнаёт `metadata/<N>.pub-<имя>.json` и `targets/<sha256>.publishers.json`. Новые проверки: корни v1 и v2 не делят ключей; индексы в обоих одинаковы; в `tuf/v1` нет `delegations` и целей кроме индексов; `delegations` и `publishers.json` v2 совпадают с тем, что собрал бы `tuf update` из `publishers/`; каждая версия каждой роли издателя на месте, версии подряд, история не переписана (как сейчас для корней); последняя роль активного издателя проходит правила PR издателя (раздел «Проверки»); снимок в git для v2 не ожидается.
- `tuf verify-published --url …/tuf/v2/`: клиент по HTTPS, профиль `Delegating`, `delegated` по всем ролям. Пакеты издателей он не скачивает: их проверил CI при слиянии.
- `tuf timestamp`, `tuf snapshot`: см. выше.
- `index add-plugin`, `index check`: при проверке модулей и бандлов учитывают последние роли издателей и `supersedes` (модули заменённого порта могут совпадать с модулями `Q`); `id` под префиксом издателя в индекс владельца не пускают.
- `registry …`: сайт (раздел «Сайт»).

### Команды издателя (Р13)

Работают в клоне нашего репозитория; ключи вне рабочего дерева git, как у `tuf init`.

| Команда | Что делает |
|---|---|
| `vendor keygen --name <имя> --out <каталог>` | ключ Ed25519, зашифрован паролем (формат `keystore.rs`), печатает открытый ключ и `keyid` |
| `vendor onboard --name … --prefix … --module … [--bundle …] --display-ru/kk/en … --github <логин>… --key <hex>… [--threshold N] [--homepage URL] [--contact …]` | пишет `publishers/<имя>/publisher.toml` и проверяет его (`vendor check-onboarding`) |
| `vendor pack <крейт>` | `plugin pack` (детерминированная сборка) плюс проверка `id` и модулей по `publisher.toml` |
| `vendor add --name … --package <файл.onclp> --url <https> --channel beta\|stable [--rollout N]` | добавляет цель в черновик `target/vendor/<имя>/role.json` (от последней роли из git): длина и sha256 из файла, `id`, версия, `min_core`, модули, `replaces`, название и `capabilities` из манифеста пакета |
| `vendor set --name … --id … --version … [--channel stable] [--rollout N] [--revoke\|--unrevoke] [--url …]` | меняет изменяемые поля записи |
| `vendor prune --name … --id … --version …` | убирает запись, если разрешено (см. «Проверки») |
| `vendor sign --name … --keys <каталог> [--expires-days 90]` | пишет `tuf/v2/metadata/<N+1>.pub-<имя>.json`, подписанный ключами из каталога |
| `vendor cosign <файл> --keys <каталог>` | добавляет подписи для порога больше 1 (`build::add_signatures`) |
| `vendor check --name … [--offline]` | те же проверки, что CI, против `origin/main` |
| `vendor check-pr --base <rev> --head <rev> --author <логин>` | вход CI (раздел «Автослияние») |

Все проверки живут в одной функции `vendor::check_pr`, ей пользуются `vendor check`, `vendor check-pr` и `tuf check` (для последних ролей).

## Автослияние PR издателя (Р9)

### Проверки

PR сливается ботом, только если выполнено всё:

1. Изменён ровно один путь, и это новый обычный файл `tuf/v2/metadata/<V>.pub-<имя>.json`: не правка, не удаление, не переименование, не симлинк, не смена режима, до 128 КиБ. Издатель `<имя>` активен в последнем верхнем `targets` v2 на `main`.
2. Автор PR есть в списке `github` из `publishers/<имя>/publisher.toml` на `main`. Это защита от спама, не от подделки: подделку ловит подпись.
3. `V` ровно на 1 больше последней версии этой роли на `main` (1 для первой).
4. Файл разбирается клиентским кодом (канонический JSON, повтор ключей отвергается), подпись набирает порог ключами делегирования, `_type` равен `targets`, `delegations` нет.
5. `expires` от `now + 14 дней` до `now + 180 дней`, где `now` берётся в момент проверки CI, а не из файла.
6. Каждая цель: путь `plugins/<имя>/<id>/<версия>.onclp`, `custom.oncl` проходит строгий разбор (незнакомые поля отвергаются), все правила раздела «Как он собирается»; `url` синтаксически `https://` без учётных данных, запроса и фрагмента, не длиннее 2048 байт; `capabilities` разбираются по правилам манифеста; `min_core` не ниже X; не больше 256 целей.
7. Каталог после слияния: модули и бандлы уникальны среди индексов владельца (кроме заменённых портов) и всех последних ролей издателей.
8. История роли: запись, которая уже была в прошлой версии, сохраняет `length`, `hashes`, `id`, `version`, `modules`, `replaces`, `min_core`, `capabilities` (байты выпущенной версии неизменны); менять можно `url`, `rollout`, `name`, `revoked`, `channel` из `beta` в `stable`. Убрать запись можно, только если она не `revoked`, её нет в `revoked_versions` владельца и у того же `id` есть более новая неотозванная версия в том же или более широком канале; отозванные записи не убираются (иначе отзыв не дойдёт до установок, `plugins.rs:104-139`).
9. Частота (Р19): последний коммит `main`, который трогал `tuf/v2/metadata/*.pub-<имя>.json`, сделан не меньше часа назад. Время берётся как время коммитера этого коммита в `main` (`git log -1 --format=%ct -- <пути издателя>`): коммит слияния создаёт GitHub, и издатель его время не задаёт. Первый выпуск проходит всегда. Два PR одного издателя, проверенные в один час до слияния, обойти правило не могут: по проверке 3 у них одно имя файла `<N+1>`, второй после слияния первого придётся пересобрать как `<N+2>`, и новая проверка увидит свежий коммит.
10. Пакеты (Р21): каждый пакет новой записи и записи с новым `url` скачивается по `url` в job `publisher-check`: только `https`, без перенаправления на `http://`, не больше `length` байт (и не больше `MAX_PACKAGE`), тайм-аут 120 с на пакет и 10 минут на PR. Сверяются длина и sha256 с целью, `Package::read` с его лимитами, манифест (`id`, версия, модули, `min_core`, `replaces`, название) с `custom.oncl`, и `custom.oncl.capabilities` равно разрешениям манифеста. Пакет, который не скачался с раннера GitHub по любой причине (сеть, геоблокировка, 404), отвергает весь PR. Издатель, чей хост закрыт для раннеров, кладёт пакет на зеркало, доступное отовсюду (например, в релиз своего репозитория на GitHub), и пишет этот адрес в `url`: выбор адреса остаётся за ним.
11. `tuf check` дерева `main` плюс этот файл проходит.

### Workflow и права

`.github/workflows/publisher-pr.yml`:

```yaml
on:
  pull_request_target:
    types: [opened, synchronize, reopened, ready_for_review]
    branches: [main]
permissions: {}
concurrency:
  group: publisher-pr-${{ github.event.pull_request.number }}
  cancel-in-progress: true
jobs:
  publisher-check:  # contents: read, pull-requests: read; секретов нет
  merge:            # needs: publisher-check; contents: write, pull-requests: write, actions: write
```

- `publisher-check` выгружает только `main` (`persist-credentials: false`), собирает xtask из `main` без кэша сборки (кэш может отравить тот, кто запускал код в контексте `main`), затем `git fetch origin pull/<n>/head` без выгрузки. Файлы PR читаются как данные через `git cat-file` после проверки списка путей; код из PR не собирается и не запускается. Пакеты скачивает здесь же `xtask vendor check-pr`: секретов в job нет, пакет разбирается как данные (`Package::read`), модуль не выполняется. Выход job: `verdict`, `head_sha`, `publisher`, `version`. Имя job не `check`, чтобы не путать с обязательной проверкой.
- Одобрение запусков из форков в репозитории `first_time_contributors`: первый PR издателя ждёт, пока владелец одобрит запуск Actions, следующие запускаются сами. `gh` 2.86 на раннере умеет `pr checks --required --watch` и `pr merge --match-head-commit`.
- Правила `main`: защиты ветки нет; один ruleset требует статус `check`, обход только у роли Admin, обязательного ревью нет. На PR статус `check` даёт job `check` из `index-check.yml` (`plugins.yml` с тем же именем job запускается только тегом). Он выполняется на `pull_request` и для PR, меняющего `tuf/`, запускает `tuf check`, так что новый файл роли проверяется и там.
- `merge` не выгружает репозиторий и не запускает cargo. Он ждёт обязательные проверки головы PR (`gh pr checks <n> --required --watch`, не дольше 30 минут), затем `gh pr merge <n> --squash --match-head-commit <head_sha> --subject "publisher <имя>: role version <V>"`. `GITHUB_TOKEN` с `contents: write` может слить PR, когда `check` зелёный: ревью не требуется, обходить правила не нужно. Затем `gh workflow run pages.yml --ref main` (слияние токеном `GITHUB_TOKEN` не запускает `push`-события, поэтому Pages вызывается явно, как в job `dispatch` `pages.yml`).
- `pull_request_target` берёт описание workflow из `main`, а не из PR: PR, который правит этот файл или xtask, проверяется старым кодом и отвергается проверкой 1.
- Pages после слияния: `snapshot` v2 включает новую версию роли, `timestamp` v2, проверка, `oracle`, развёртывание, `verify`. Клиенты увидят выпуск на следующей проверке каталога (6–24 часа) или по «Проверить сейчас».

### Что может попробовать вредный PR

| Попытка | Почему не выйдет |
|---|---|
| Поправить workflow, xtask, `publishers/`, индекс или чужую роль вместе с файлом роли | проверка 1: ровно один новый путь своей роли; описание workflow и код берутся из `main` |
| Подписать роль чужим ключом или ключом другого издателя | проверка 4: ключи берутся из делегирования этой роли в верхнем `targets`, подписанном владельцем |
| Выпустить `id`, модуль или бандл вне одобренного | проверки 6 и 7; клиент отбрасывает такую запись и сам |
| Путь вида `../`, `pub-other`, лишнее расширение | строгий разбор пути файла и имени роли (`RoleName`) |
| Огромный файл роли или пакет, zip-бомба | 128 КиБ на роль, 256 целей; CI и клиент читают пакет не больше `length` и `MAX_PACKAGE` с лимитами `Package::read` |
| Дописать коммит после проверки | `--match-head-commit` |
| Повтор старого файла, прыжок версии | проверка 3: ровно `N+1` |
| Срок 2099 года, чтобы пережить отзыв | проверка 5; отзыв идёт через делегирование, срок роли его не задерживает |
| Подменить байты уже выпущенной версии | проверка 8; клиент сверяет sha256 и пометит версию плохой |
| Указать в записи меньше разрешений, чем просит пакет | проверка 10; клиент сверяет ещё раз |
| Указать URL, по которому пакета нет или он закрыт для раннеров | проверка 10: PR не сливается |
| URL на внутренние адреса раннера | в `publisher-check` нет секретов и прав записи; ответ только сверяется с хешем |
| Код в пакете, который выполнится в CI | пакет разбирается как данные, модуль не выполняется |
| Убрать отозванную версию, чтобы установки на ней остались | проверка 8 |
| Поток PR, частые выпуски | `concurrency`, список авторов (проверка 2), не больше выпуска в час (проверка 9) |
| Два PR одного издателя с одной версией | второй не сольётся: файл с тем же именем уже есть |
| Слияние сразу после отзыва издателя | новый файл роли отозванного издателя никто не скачивает: делегирования нет |

## Подключение издателя (Р2)

PR издателя (сливает только владелец):

`publishers/<имя>/publisher.toml`:

```toml
name = "ecc"
display = { ru = "ТОО «…»", kk = "…", en = "…" }
id_prefix = "kz.ecc."
modules = ["kz.ecc.market.Signer"]
bundles = ["kz.ecc.market"]
github = ["ecc-release"]
homepage = "https://ecc.kz/"
contact = "security@ecc.kz"
threshold = 1

[[keys]]
public = "<64 hex>"

# Только с одобрения владельца (Р11):
# supersedes = { "io.github.arynyklas.openncalayer.port.market" = "kz.ecc.market" }

# Пишет только владелец (Р18), не издатель:
# [[revoked_versions]]
# id = "kz.ecc.market"
# version = "1.1.0"
# date = "2027-02-10"
```

Схема строгая (`deny_unknown_fields`). Правила: имя и префикс по грамматикам выше, префикс не вложен в чужой и не под `io.github.arynyklas.openncalayer.`; модули и бандлы не встроенные, не чужие и не обслуживаются портом, кроме портов из `supersedes`; ключи различны между собой и с ключами корней и других издателей; `display` не содержит «OpenNCALayer» и управляющих символов.

Владение доменом префикса владелец проверяет вручную при одобрении (Р17), автоматической проверки `.well-known` или DNS нет. Для этого PR подключения открывается по шаблону `.github/PULL_REQUEST_TEMPLATE/publisher.md`, который просит издателя указать:

- юридическое название и регистрационный номер (БИН для Казахстана), страну;
- домен, из которого получен префикс (`kz.ecc.` → `ecc.kz`), и ссылку на страницу официального сайта на этом домене, где издатель называет свой аккаунт GitHub из `github` и `keyid` своих ключей;
- адрес почты на этом домене, на который владелец пришлёт одноразовую фразу; издатель повторяет её комментарием к PR от аккаунта из `github`;
- контакт для сообщений о безопасности (может совпадать с предыдущим);
- какие плагины издатель собирается выпускать, какие модули и бандлы оригинала они обслуживают и зачем каждый модуль;
- нужна ли замена порта (`supersedes`) и почему;
- кто держит ключи, сколько их и где они хранятся, нужен ли порог больше 1;
- согласие с правилами: автослияние только своих файлов, отзыв версии или издателя владельцем, не больше выпуска в час.

Владелец сверяет страницу на домене и ответ с фразой, решает по `supersedes` и отмечает проверку в PR. Ничего из этого xtask не проверяет.

`ci.yml` на PR запускает `vendor check-onboarding` (без прав, как обычные проверки). Активация: владелец на ветке PR выполняет `cargo xtask tuf update` (новый верхний `targets` v2 с делегированием и `publishers.json`), коммитит, сливает. Первый выпуск издатель делает следующим PR.

Ротация ключа издателя: PR с новым `[[keys]]` (старый остаётся или уходит), владелец подписывает верхний `targets`, затем издатель подписывает новую версию роли новым ключом. Номер версии роли продолжается: правило «ровно N+1» не даёт укравшему ключ задрать номер, так что отдельная эпоха версий не нужна.

Отзыв издателя (Р6): владелец ставит в `publisher.toml` `state = "revoked"` и дату, выполняет `tuf update` (делегирование уходит, в `publishers.json` остаётся запись `revoked`), сливает. Pages публикует, клиенты выключают плагины при следующей проверке каталога.

Отзыв одной версии (Р18): владелец добавляет `[[revoked_versions]]` в `publisher.toml` издателя, выполняет `tuf update`, сливает. Клиенты на этой версии уходят на лучшую неотозванную версию издателя (в том числе вниз), а если такой нет, плагин выключается, как при отзыве версии в индексе. PR издателя, который трогает `publishers/`, автоматически не сливается (проверка 1), так что снять такой отзыв издатель не может.

## Интерфейс (Р5)

- `InstallRequest` (`crates/openncalayer/src/plugins.rs:85-100`) и `InstallPluginRequest` (`crates/oncl-ui/src/install_plugin.rs:53`) получают `origin_kind: PluginOrigin` вместо `local: bool`: `Project`, `Publisher(Localized)`, `LocalFile`. Явное перечисление вместо пары флагов.
- Окно установки (`install_plugin.slint`): новое свойство `publisher`. Строки ru/kk/en (Р22: «Издатель» по-казахски «Жариялаушы»; остальные казахские строки пишет переводчик, открытый вопрос 4):
  - порт: «Издатель: OpenNCALayer» / «Жариялаушы: OpenNCALayer» / «Publisher: OpenNCALayer»;
  - издатель: «Издатель: {name}» / «Жариялаушы: {name}» / «Publisher: {name}» и под ней «Плагин подписан издателем. OpenNCALayer подключил издателя, но этот выпуск не проверял.» / «The publisher signed this plugin. OpenNCALayer approved the publisher but did not review this release.»;
  - из файла: прежнее предупреждение `local`, строки издателя нет.
- Строка замены «Заменит установленную версию {v} ({source})» получает третий источник «от издателя {name}».
- Окно замены порта: «Порт «{port}» заменяет плагин «{name}», издатель: {publisher}. Разрешения нового плагина: …» и кнопки «Заменить» и «Не сейчас».

## Миграция и порядок выкладки

Как сегодняшний клиент встречает `targets` с делегированиями: `TufError::Unsupported` на шаге 5.6, `refresh` проваливается, апдейтер пишет ошибку и пробует в обычный срок; каталог плагинов остаётся на сохранённом индексе до срока `targets`, потом без каталога. Новую версию ядра такой клиент уже не получит никогда. Поэтому делегирования появляются только в новом репозитории и только для клиента, который его читает.

Порядок:

1. Библиотека и xtask (шаги плана 1–6): без изменения поведения выпущенных клиентов.
2. Церемония v2: `tuf init --repo v2`, секреты и окружения, первый `tuf update` создаёт `tuf/v2` с нулём издателей. `pages.yml` публикует `tuf/v2`, `verify` и `oracle` зелёные на опубликованных байтах. `tuf/v1` не изменился ни в одном байте.
3. Выпуск X, `0.1.2` (Р15): клиент с анкером v2, `INDEX_BASE` `…/tuf/v2`, состояние `update/tuf/v2/`. X попадает в индексы обычным порядком и доходит до старых клиентов через `tuf/v1`. Гейт как у rc.2 (`docs/dev/release.md`, 7г): обновление младшей версии до X через `tuf/v1` и X до следующей версии через `tuf/v2` пройдены в лаборатории на опубликованных байтах.
4. Подключение первого издателя: только когда X в `stable`. `min_core` плагинов издателей не ниже `0.1.2` (проверка 6).
5. `tuf/v1` поддерживается без срока (Р16): тот же `pages.yml` публикует оба репозитория, ежемесячное `tuf update --refresh` подписывает оба `targets` и офлайн-снимок `tuf/v1`. Удаление `tuf/v1` решается отдельно. Клиенты младше X плагинов издателей не видят, порт с `supersedes` продолжают обновлять, а X получают обычным обновлением.

Откат X проверкой здоровья на младшую версию: та читает `update/tuf/` и `tuf/v1`, обновляется как раньше. Установленные плагины издателей у неё `Source::Catalog` без записи в индексе: они работают дальше, не обновляются и не отзываются, пока не вернётся X. Младшая версия, переписав `plugins/state.json`, теряет поле `publisher` (serde не сохраняет незнакомые поля); X восстановит его по префиксу из `publishers.json`, включая отозванных издателей.

## Угрозы

| Угроза | Что получает атакующий | Что ограничивает |
|---|---|---|
| Утёк ключ издателя | вредную версию плагина в пределах префикса и модулей издателя; автообновление без окна, если разрешения не растут | список авторов PR; не больше выпуска в час; порог больше 1 (Р12); окно разрешений при росте; отзыв версии издателем или владельцем (`revoked_versions`), отзыв издателя; песочница плагинов |
| Издатель сам вредный | то же | одобрение при подключении, ручная проверка домена владельцем, отзыв версии и издателя |
| Взломан или пропал хостинг пакетов издателя после слияния | только отказ: sha256 не сойдётся и версия станет плохой, либо скачивание не удастся и клиент сообщит о сбое установки | sha256 и длина в роли; недоступный при выпуске пакет ловит CI |
| Запись каталога показывает меньше разрешений, чем просит пакет | ничего | CI при слиянии и клиент при установке сверяют `capabilities` с манифестом |
| Чужой PR с файлом роли | ничего | подпись ключами делегирования; список авторов |
| Вредный PR правит workflow или xtask | ничего | `pull_request_target` из `main`, проверка 1 |
| Утёк онлайн-ключ `snapshot` v2 | смесь действующих версий ролей и `targets`: например, удержать старую версию роли без отзыва версии до срока этой роли | версия ролей не ниже сохранённой у клиента; срок `timestamp` 7 дней; ротация корнем v2 |
| Утекли оба онлайн-ключа v2 и контроль над Pages | заморозка каталога до срока верхнего `targets` (до 30 дней), в том числе отзыва издателя у клиентов, не видевших новый `targets` | срок верхнего `targets`; клиенты, уже видевшие отзыв, не откатываются |
| Утёк ключ `targets` | всё, как сегодня: делегирование самому себе или подмена индекса | офлайн, ротация корнем |
| Скомпрометирован токен бота или `main` | слияние чего угодно, но без офлайн-подписей: ни делегирования, ни индекса; снимок не может перечислить непроверенный файл | офлайн-ключи; проверка в job `snapshot` |
| Файлы v1 подаются клиенту v2 и наоборот | ничего: другой ключ подписи | отдельная цепочка корней v2 |
| Подложен `targets` без `delegations` | отказ каталога, не отзыв | `DelegationsMissing` |
| Сломанная или просроченная роль издателя | этот издатель недоступен | изоляция ролей; ядро и порты не затронуты |
| Много ролей и целей, большие файлы | ничего | 32 роли, 128 КиБ, 256 целей, лимиты `Package::read` |
| Издатель выдаёт себя за OpenNCALayer | ничего | `display` одобряет владелец, запрет имени |
| Издатель занимает модуль встроенного или чужого плагина | ничего | `publishers.json` и проверка записей клиентом; запрет встроенных модулей |
| Откат X проверкой здоровья | плагины издателей у младшей версии не отзываются, пока не вернётся X | X восстанавливает издателя по префиксу и отзывает |
| Клиент долго офлайн | отзыв доходит при первой проверке онлайн | срок сохранённого каталога: корень, `targets`, роль |
