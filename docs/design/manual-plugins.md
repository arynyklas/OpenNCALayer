# Плагины в окне ручных инструментов: как разрешаем подпись

Документ для разработчиков и авторов плагинов. Он объясняет, как плагин из каталога может подписать документ в окне ручных инструментов (где пользователь сам выбирает файл и ключ) и почему это безопасно. Что видит пользователь и как читать отказы, написано в [руководстве пользователя](../user/manual-plugins.md). Список портов, которые в этом окне работают, — в [инвентаризации](manual-plugins-inventory.md). Общие правила плагинов — в [plugins.md](plugins.md), про сервис и CLI — в [platform.md](platform.md).

## 1. Идея в одном абзаце

Плагин сам не решает, что и как подписывать. Операцию описывает **манифест плагина**: какой запрос отправить, какие параметры ввести, какие функции ядра разрешены и **как именно** разрешено применить ключ (вид подписи, фиксированные опции, откуда берётся содержимое). Запрос по шаблону строит программа, а не плагин. Прежде чем ключ будет применён, ядро сверяет, что плагин подписывает именно то, что пользователь одобрил, и именно так, как показано на странице подтверждения.

## 2. Что было не так

Окно ручных инструментов должно показать человеку, **что** и **как** подписывается. Для плагинов этого не хватало:

- Разрешение выдавалось вслепую: проверялось, какая функция вызывается и каким ключом, но не что подписывается.
- Опции подписи (дополнительные атрибуты, тип содержимого, свой сервер меток времени, «со-подпись» вложенного CMS, расположение подписи в XML, уровень XAdES) выбирал сам плагин. Показанное человеку могло не совпадать с реально подписанным.
- Манифест не знал, какие операции у плагина вообще есть.
- Ядро не различало, какой плагин применил ключ и с каким содержимым.
- Ручной вызов не имеет Origin (сайта). Порты, которые проверяют сайт, на такой запрос отвечают отказом. Программа не имеет права подставлять Origin.
- В «безоконном» режиме запрещены диалоги, поэтому многие порты в нём не работают.

Ещё одна причина осторожности: в ручном окне, на сервере и в CLI человек или оператор подтверждает **действие**, а название операции — лишь метка. Поэтому защита построена не на имени, а на трёх вещах: запрос строит программа, плагину доступны только объявленные функции, а применение ключа проверяется отдельно.

## 3. Принципы

1. **Ключ применяет человек.** Манифест задаёт верхнюю границу возможного, а решение принимается заново при каждом вызове.
2. **Доверенная часть страницы** состоит только из полей, которые плагин не контролирует: идентификатор плагина, контрольная сумма пакета (SHA-256), версия, данные ключа и сертификата, имена и SHA-256 документов, профиль подписи от ядра, объявленные сетевые адреса. Поля `name`, `description` и `label` из манифеста принадлежат автору плагина. Они показываются только в рамке «от плагина»: простой текст до 80 символов, управляющие символы и символы смены направления письма экранированы.
3. **Согласие привязано** к виду подписи, содержимому и опциям. Проверка идёт до применения ключа.
4. **Согласие одноразовое:** действует для одного вызова и ограничено по времени (120 секунд).
5. **Серверу и CLI человек не нужен**, но автоматического ответа «да» нет. Права оператора точные.
6. **WASM не получает дополнительного доверия.** Остаются лимиты памяти, топлива и бюджеты ядра.
7. **Произвольного окна плагина нет.** Диалоги плагина в ручном окне запрещены.

## 4. Как это устроено

### 4.1 Три варианта и выбранный

- **Вариант A.** Манифест объявляет операции. Программа строит запрос и сверяет применение ключа с одобрением (содержимое и опции). Интерфейс плагинов (ABI) не меняется.
- **Вариант B.** Плагин не подписывает сам, а возвращает типизированный запрос, который подписывает программа. Это самое безопасное, но требует нового ABI и переписывания всех 34 портов (25 из них вызывают подпись посреди своей логики). Сейчас неприемлемо.
- **Вариант C (выбран).** За основу взят A. Где это дёшево, взято из B: структуру и профиль подписи CMS, XML и XAdES строит ядро, а описание согласия рисуется из профиля, как у встроенных инструментов. Подпись «сырых» байт и подпись готового хеша допускаются только над документом, который передан параметром (а не вычислен плагином). Манифест можно позже перевести на вариант B без изменения окна.

ABI плагинов (`ABI_VERSION = 1`) и WASM-файлы портов не меняются. Меняются их `plugin.toml`.

### 4.2 Операция в манифесте

Новая таблица `[[operations]]`. Старые версии ядра её отвергают (разбор манифеста строгий), поэтому `min_core` пакета повышается. Плагин без `[[operations]]` в ручном окне **не виден**. Через WSS он работает как прежде. Объявления ограничивают только ручное окно, сервер и CLI, а путь страницы через WSS сохраняет собственные диалоги.

Пример ниже вымышленный (плагин `example.sign`, не настоящий порт):

```toml
min_core = "0.1.0-alpha.7"

[[operations]]
name    = "sign-file"                       # ^[a-z][a-z0-9-]{0,31}$, уникально
module  = "example.sign"                    # одно из имён из `modules`
manual  = true                              # показывать в ручном окне
server  = false                             # разрешать права сервера и CLI
request = '{"module":"example.sign","method":"signFile","args":["{file:base64}"]}'
label   = { ru = "Подписать файл", kk = "Файлға қол қою", en = "Sign a file" }   # только в рамке «от плагина»

[[operations.params]]
name = "file"
kind = "document"                           # document | text | choice | flag | locale
max_bytes = 16777216

[operations.uses]
imports = ["keys_select", "keys_describe", "keys_sign_cms_ex", "hash"]   # подмножество функций, которые плагин реально импортирует
network = "pki"                             # none | pki | [точные URL]
interactive = ["keys_select"]               # только выбор ключа

[[operations.uses.key]]
kind     = "cms_ex"                         # raw | cms | cms_ex | xml | xml_ex | xades
content  = "param:file"                     # содержимое — параметр, переданный пользователем
max_uses = 1                                # в ручном окне допустимо только 1
[operations.uses.key.profile]               # профиль опций, который принуждает ядро
encapsulate = false
cosign      = "never"
timestamp   = "basics"                      # none | basics | kalkan   (свой сервер запрещён)
certificates = "signer"
output      = "der"
```

**Профиль опций.** Ядро принуждает объявленный профиль, а не разбирает каждый вызов отдельно. Правила:

- Профиль — типизированная структура нужного вида подписи. Опасные поля (`attrs.extra`, произвольный `econtent_type`, `timestamp = Custom`, чужой алгоритм хеша, неизвестный `signature_method`) в профиль вообще не входят. Значения опций в реальном вызове плагина обязаны совпасть с профилем (канонический вид опций даёт `options_sha256`), иначе отказ до применения ключа (`options-mismatch`). Не заданное в профиле поле означает значение ядра по умолчанию, и отклонение от него — тоже отказ.
- Поле профиля бывает фиксированным или берётся из параметра (например, XPath `element` и `parent` у XML — текст, который ввёл пользователь и который показан в согласии).
- `cosign` в профиле только `never`. Если плагин просит `Auto`, ядро подставляет `Never`. Ручное окно подписывает байты выбранного файла как есть, даже если это CMS. Это осознанное отличие от прежнего поведения, зато нельзя подписать не то, что показано.
- `max_uses = 1`. Операции с несколькими подписями в ручном окне не поддерживаются.
- **Подпись готового хеша (`Digest`).** Допустима только над документом-параметром. Ядро само считает хеш замороженного документа алгоритмом ключа (ГОСТ 34.311, «Стрибог» или SHA-2 по сертификату) и требует побайтового совпадения с тем, что передал плагин. Показываются имя документа и этот хеш.

**Проверки при разборе:**

- `request` — JSON-объект со строгими пределами. Плейсхолдеры — только целые строковые значения, и только объявленных параметров. Размер после подстановки не больше `max_transfer`, иначе честный отказ «превышен лимит».
- Запрос может быть любым JSON-объектом: массив `args`, объект `args` или ключи прямо в корне (как у реальных портов). `module` и `method` (или `type`) фиксированы.
- Содержимое типа `text` допустимо для любого вида подписи (подписываются UTF-8-байты). Ядро отвергает в тексте любые управляющие символы, символы смены направления письма и невидимые символы, кроме `\n` и `\t`. Окно приводит CRLF к LF.
- Функции из `uses.imports` должны входить в реально импортируемые плагином (проверяет установка). Любая ключевая функция требует строки `[[uses.key]]` соответствующего вида и разрешения `keys = true`.
- Операция с ключом обязана объявить `network = "pki"`: без сети проверка подписанта и метка времени невозможны, и вызов отказал бы до применения ключа.
- `content = "param:x"` — параметр `x` типа `document` или `text`. Строк `[[uses.key]]` не больше 8. `network = "pki"` — только PKI-адреса ядра.

### 4.3 Проверка перед применением ключа

Главная проверка одна: перед применением ключа. Ядро выписывает «билет» из тех же данных, которые идут в движок подписи, и сверяет его с одобрением.

Как это работает:

1. Код, обслуживающий плагин, один раз разбирает запрос в типизированную структуру. Из **неё же** считает вид подписи, SHA-256 содержимого (уже после принудительного `cosign=Never`; для `Digest` — сам хеш) и `options_sha256`, сверяет опции с профилем.
2. Кладёт билет в контекст и передаёт ту же структуру в движок. В момент применения ключа билет забирается (одноразово) и уходит вместе с событием применения.
3. Страж применения (в десктопе `PluginConsentGuard`, на сервере свой) разрешает применение, только если билет совпадает с одобренным: не исчерпано число применений, не истёк срок, тот же идентификатор операции, та же контрольная сумма пакета. Событие без билета в плагинном движке — отказ. Событие с билетом в страже обычных документов — тоже отказ. Согласие на документ не покрывает плагин, а согласие на плагин — документ.
4. Предварительная проверка в коде плагинов — лишь быстрый отказ без побочных эффектов. Решает страж.

Новый вид «действия подписи для плагина» не вводился: он сломал бы токены доступа. Вместо этого билет передаётся в контексте, а страж у плагина отдельный.

**Какой ключ можно.** При установке плагина фиксируется политика из объявления: проверяются плагин, операция и кто вызывает, объявлены ли функции и вид применения. Конкретный ключ политика не проверяет. Ключ проверяется отдельно, при каждом вызове: пользователь выбрал ключ, и разрешён только он. Обе проверки обязательны.

**Контрольная сумма пакета.** Реестр запоминает SHA-256 установленного пакета. При вызове она сверяется с той, что была в одобрении. Если между согласием и вызовом подменили файлы плагина, отказ `package-changed`.

### 4.4 Реальный вызов

Документ замораживается до построения запроса: его читают один раз и считают SHA-256. Сравнение идёт по хешу замороженных байт, а не по пути, поэтому подмена файла между согласием и вызовом ничего не даёт. Значение подставляется в шаблон из замороженных байт. Сертификат ключа сверяется по отпечатку.

### 4.5 Что показывает страница подтверждения

Текст строит программа (на русском, казахском и английском):

```text
Плагин id: example.sign   версия 1.0.0   пакет SHA-256 9f3c…a1          ← доверенные поля
Операция: sign-file       [от плагина: «Подписать файл»]                ← рамка «от плагина»
Ключ: Иванов И. · серийный 5c… · отпечаток 8e… (до 2027-02-01)
Файл «акт.pdf» · 1 482 311 байт · SHA-256 3a7d…
Применение ключа: 1 раз
  CMS (CAdES): отсоединённая; метка времени НУЦ; со-подписи нет; доп. атрибутов нет      ← из профиля ядра
  Подписывается файл «акт.pdf» как есть (SHA-256 совпадает)
Сеть: ocsp.pki.gov.kz, tsp.pki.gov.kz. Плагин может передать данные только по этим адресам; документ может быть отправлен на разрешённые хосты.
[Отмена]  [Подписать]
```

Страница работает с клавиатуры (порядок фокуса, Enter не подтверждает подпись, пока фокус не на «Подписать», масштаб, экранные дикторы). Ответ плагина показывается простым текстом в рамке «от плагина».

Сохраняется только ответ успешно выполненного вызова, целиком и как есть, в файл `.json`. Подпись из ответа программа не извлекает. Имя файла предлагает программа (операция и идентификатор плагина, никогда не текст плагина), место выбирает пользователь, запись атомарна и ничего не заменяет.

### 4.6 Совместимость с портами

- ABI и WASM не меняются. Меняются `plugins/*/plugin.toml` (и `min_core`), хеши в `registry.toml`, а новые версии пакетов выходят через подписанный индекс обновлений.
- Объявления нужны только портам, у которых есть пригодные для окна методы (сейчас 9 из 34). Остальные порты в окне показываются как «не поддерживается» с причиной ([инвентаризация](manual-plugins-inventory.md)). Origin ради них не подставляется.
- **Старые установленные версии** без `[[operations]]` по WSS работают как раньше, в ручном окне у них операций нет.
- **Обновление из каталога.** Появление или изменение `[[operations]]` с применением ключа, расширение функций или сети, смена профиля считаются добавленной возможностью. Такое обновление требует явного согласия при установке и не ставится тихо.

### 4.7 Сервер и CLI

Для плагинов с объявлениями:

- Право оператора (`PluginGrant`) должно называть объявленную операцию с `server = true`. Список функций не шире объявленного (пустой список — все объявленные). Права на ключи — только если операция объявляет применение ключа.
- Профиль опций ядро принуждает так же, как в ручном окне: клиент не может добавить `attrs.extra`, свой сервер меток времени и т. п. Запреты `cosign=never` и `Digest` — те же.
- Привязать содержимое к документу сервер не может (у него нет типизированных параметров: `args` — свободный JSON клиента). Поэтому для любого применения ключа оператор обязан явно поставить `plugin_bytes = true`: он принимает, что содержимое выбирает клиент и плагин. Билет попадает в журнал.
- Права на операцию, которой в новой версии плагина нет, пропускаются с записью в журнал, остальные работают.
- Токены не меняются.
- CLI: `--operation` и `--allow-import` проверяются по объявлению, есть `--plugin-bytes`, а `--profile` не принимается (профиль берётся из манифеста). Команда `oncl plugin operations --manifest [--wasm]` перечисляет объявленные операции словами. Если у операции нет `--args-file`, запрос строится по шаблону из `--param`, `--param-file` и `--param-flag`. CLI согласия не спрашивает: его даёт оператор флагом `--plugin-bytes`, а в stderr до применения ключа печатается строка `plugin_use` с проверенными фактами билета. Подробности — [`docs/user/cli.md`](../user/cli.md).

Для плагинов **без** объявлений поведение сервера и CLI не меняется: права по меткам оператора, в журнале `declared=false`, при старте предупреждение «права без объявления: профиль опций не принуждается».

### 4.8 Отказы

Каждый отказ приходит **до** применения ключа и имеет код ошибки плюс подкод (поле рядом с кодом, сам набор кодов API стабилен). Так как применение ключа ровно одно, состояния «первая подпись есть, вторая отклонена» не бывает.

| Причина | Код | Подкод | Ключ применён? |
|---|---|---|---|
| Операция не объявлена | `PermissionDenied` | `not-declared` | нет |
| Операция не для ручного окна | `PermissionDenied` | `not-manual` | нет |
| Пакет изменился | `PermissionDenied` | `package-changed` | нет |
| Опции не по профилю | `PermissionDenied` | `options-mismatch` | нет |
| Срок одобрения истёк | `PermissionDenied` | `approval-expired` | нет |
| Билет не совпадает с одобрением | `PermissionDenied` | см. список ниже | нет |
| Нужно взаимодействие вне выбора ключа | `InteractionRequired` | имя функции | нет |
| Плагин требует Origin | ответ самого плагина | — | нет |
| Ошибка **после** применения (метка времени, сеть) | как раньше | — | `Applied` или `Unknown`, честно |

Подкоды несовпадения билета: `approval-missing`, `ticket-missing`, `ticket-uses`, `key-use-spent`, `key-mismatch`, `operation-mismatch`, `kind-mismatch`, `action-mismatch`, `content-mismatch`, `caller-mismatch`, `operation-id-mismatch`, `certificate-changed`, `approval-replayed`, `busy`. Есть и другие: `not-granted`, `no-consent-guard`, `audit-fact-too-long`, `resource-budget`, `no-temporary-store`, `content-binding-unavailable`. Полный список (49 кодов) и их смысл — в [руководстве пользователя](../user/manual-plugins.md).

### 4.9 Выбор ключа и диалоги в ручном окне

Порты вызывают `keys::select` (24 порта) и `keys::choose` (4 порта). Это выбор ключа, а не «окно плагина». В ручном окне ключ уже выбрал пользователь, поэтому:

- Выбор ключа (`KeysSelect`, `KeysChoose`, `KeysFlowOpen`, `KeysFlowPick`): ядро проверяет фильтр плагина по сертификату выбранного ключа. Подходит — плагин получает ссылку на единственный привязанный ключ (секрет и путь к хранилищу не передаются). Не подходит — «ничего не выбрано».
- `KeysTerminals` возвращает пустой список, `TokensScan` — «токены выключены». Порты, которым нужен непустой список считывателей, не поддерживаются.
- `KeysOpen` и прочее, что в безоконном режиме запрещено, — порт не поддерживается (причина в инвентаризации).
- **`Dialog*`, `File*`, `CoreOpenWindow`, `Keystore*` запрещены** (`InteractionRequired`). Порту, которому они нужны, остаётся «не поддерживается» с причиной.
- Освобождение буфера ответа (`reply_drop`, его импортируют 33 порта) разрешено и безвредно. Между вызовами плагин состояния не сохраняет: каждый вызов получает свежий экземпляр.

## 5. Журнал

На каждое применение ключа пишется начало: плагин, контрольная сумма пакета, версия, операция, кто вызвал, вид подписи, SHA-256 содержимого (или хеш для `Digest`), `options_sha256`, откуда содержимое, идентификатор согласия (ручное окно) или права и признак `declared` (сервер), ключ. Потом итог: применён ли ключ, успех, код. Нет итога — исход «неизвестен». Байты документа и превью в журнал не пишутся.

## 6. Атаки и защита

| Что пробует злоумышленник (плагин или клиент) | Защита | Остаточный риск |
|---|---|---|
| Подписать байты, выбранные плагином | Билет сверяется с одобрением по SHA-256 содержимого. Подпись «сырых» байт и готового хеша — только над документом-параметром. | — |
| Опции подписи вне показанного | Профиль принуждается ядром, `options_sha256` входит в билет, `cosign=never` | — |
| `Digest`, содержимое которого хосту неизвестно | Ядро само считает хеш документа алгоритмом ключа | — |
| Со-подпись вложенного CMS: показанное ≠ подписанное | `cosign` принудительно `never`, билет считается по эффективному содержимому | — |
| Подмена операции (плагин «проверить» подписывает) | Запрос строит программа; функции и вид подписи — подмножество объявленного; билет | Лживый `label` виден лишь в рамке «от плагина» |
| Имя плагина выдаёт себя за доверенную часть | Доверенны только идентификатор, контрольная сумма и версия; `name`, `label`, `description` — в рамке | Социальная инженерия внутри рамки |
| Путаница между операциями одного плагина | Права привязаны к плагину, операции и тому, кто вызывает | — |
| Подмена между согласием и вызовом (файл, пакет, сертификат, время) | Заморозка документа, сверка по хешу, контрольная сумма пакета, отпечаток сертификата, срок 120 с | Подмена «A→B→A» закрыта сверкой байт, а не пути |
| Тихое обновление добавляет операцию с ключом | Такое обновление требует явного согласия при установке | — |
| Повтор или подмена одобрения | Одобрение одноразовое, привязано к операции и ограничено по времени | — |
| Подмена ключа; `keys::terminals`, `keys_open` | Один привязанный ключ; терминалы — пусто; `keys_open` — порт не поддерживается | — |
| Диалоги плагина как «согласие» | Диалоги запрещены, выбор ключа отвечает ядро | — |
| Отправка документа плагином по сети | В согласии показаны адреса и фраза «документ может быть отправлен на разрешённые хосты». Адреса — точный список или PKI-адреса | Разрешённый хост (например, `*.gov.kz`) получит данные; решает пользователь, читая согласие |
| Подмена текста страницы (`label`, ответ) | Простой текст, ограниченная длина, управляющие символы экранированы, ответ в рамке | — |
| Исчерпание ресурсов | Лимит размера запроса, лимиты WASM, бюджет ядра | Ограниченная нагрузка на процессор |
| Плагин навязывает путь или имя результата | Имя строит программа, место выбирает пользователь, существующее не заменяется | Сохранённый ответ — текст плагина, хост его не проверяет |
| Серверный клиент подсовывает опции или метод в свободный `args` | Профиль принуждается ядром; нужен `plugin_bytes`; метод в `args` оператор принимает на доверии | Оператор принял «содержимое выбирает клиент» |
| Права оператора шире объявления | Проверка при загрузке, лишние права пропускаются | — |

## 7. Принятые решения

- ABI не меняется. Вариант с хост-подписью (новый ABI) отложен.
- Согласие не хранится: каждый вызов подтверждается заново.
- Плагин без `[[operations]]` в ручном окне не виден. Права сервера и CLI для плагинов без объявлений не меняются.
- Подпись «сырых» байт и готового хеша — только над документом-параметром (содержимое задаёт пользователь).
- **Содержимое, вычисленное самим плагином, не поддерживается.** Запуск предварительного «пробного» вызова с полным превью не делали. Единственный метод, которому это нужно, — `fhs.signFile`, который скачивает файл по адресу, присланному страницей. Сеть ручного окна — только PKI-адреса, а тот же результат даёт `fhs.sign-text` с файлом как документом. Пересмотр — только по новому решению.
- Origin не подставляется. Порты, которым он нужен, не поддерживаются.
- Диалоги запрещены.
- Охват — все порты, которые могут работать. Остальные показаны с причиной.
- Нового вида действия для плагинов нет: токены не меняются.
- `max_uses = 1` во всех операциях ручного окна.
- Опции — профиль из манифеста, `cosign=never`, свой сервер меток времени и `attrs.extra` запрещены.
- Единственная главная проверка — перед применением ключа, по билету.
- Обновление из каталога с изменёнными `[[operations]]` требует повторного согласия.
- Сервер принимает свободный `args`, но профиль принуждается и нужен `plugin_bytes=true`. Типизированные параметры для сервера — отдельный будущий этап.
- `esf-osdkz.auth` (подпись вызова для входа) в первый выпуск не входит: вход — не «подписать документ», кнопка должна называть действие, и нужна своя модель согласия. Профили для ESEDO (5 методов) — позже, отдельным решением.
- Объявления нужны только 9 портам: `rating1c`, `dogovor24`, `efactoring`, `market`, `energy`, `eproc`, `esf-osdkz` (без `auth`), `fhs`, `qiwi`.

## 8. Что сделано

Работа велась по этапам. Состояние:

**Готово:**

- Таблица `[[operations]]` в манифесте с профилем, проверками разбора и обобщённым шаблоном запроса (текст как содержимое).
- Реестр плагинов с контрольной суммой пакета, запрет по умолчанию, построение запроса и вызов с одобрением.
- Билет применения ключа, страж применения в десктопе и на сервере, отказ обычного стража на билет плагина.
- Одобрение: принуждение профиля, `cosign=never`, подпись готового хеша над документом, срок, одно применение.
- Подкоды отказов и журнал.
- Ключевой выбор по привязанному ключу, запрет диалогов в ручном окне.
- Страница «Плагины» в десктопе: список операций (в том числе неподдерживаемых с причиной), параметры, запуск, отчёт; страница согласия с доступностью; показ операций и повторное согласие при установке.
- Объявления для портов (сейчас 30 операций в 9 портах).
- Пределы ручного окна: документ до 4 МиБ (на 32-битных — 512 КиБ), отказ до применения ключа при нехватке бюджета.
- API, сервер и CLI: подкоды, `plugin_bytes`, проверка по объявлению, `oncl plugin operations`.
- Проверка объявлений: `cargo xtask plugin-ops-check`.
- Пользовательская документация.

**Не сделано:**

- Выпуск новых версий пакетов портов через подписанный индекс (нужен ключ подписи обновлений — действие владельца).
- Проверка с настоящей подписью в окне на реальной системе. Проверка доступности: фокус проверен при 100 % масштаба, а при 200 % и с экранным диктором нет.
- Типизированные параметры и документы для серверной операции плагина.
- Новый ABI с хост-подписью.
- Независимая проверка части портов.

## 9. Риски

- В первом выпуске пригодных портов мало (9 из 34). Решение «все, которые могут работать» не сужается.
- Подкоды ошибок меняют публичный контракт `oncl-api` (поле, а не новый код), поэтому обновляются OpenAPI и клиент.
- `cosign=never` для простого CMS — осознанное отличие от прежней семантики `Auto`.
