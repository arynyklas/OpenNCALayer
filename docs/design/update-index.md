# Индекс обновлений

Для тех, кто хочет понять, как OpenNCALayer узнаёт о новых версиях, и для мейнтейнера, который выпускает релизы. Здесь: что лежит в индексе, как клиент выбирает версию и откатывается при сбое, и как мейнтейнер готовит и публикует индекс.

Индекс канала — это JSON-файл со списком версий OpenNCALayer, расширения и плагинов и со ссылками на их файлы. Его читает и проверяет крейт `oncl-update`. Подлинность индекса обеспечивает TUF ([`tuf.md`](tuf.md)): индекс — «цель» TUF, а его формат от этого не менялся.

## Где лежит

- Индекс: `updates/v1/<channel>.json`, где `<channel>` — `stable` или `beta`. Он публикуется на GitHub Pages байт в байт, рядом со страницами сайта проекта (`site/`). У сайта нет своего пути `updates`: `pages.yml` копирует каталог `updates/` в артефакт после сборки сайта и сверяет копию с репозиторием.
- Проверка подлинности: метаданные TUF в `tuf/v1/` (корни, `timestamp`, `snapshot`, `targets`). Клиент берёт индекс как цель `indexes/<channel>.json` по пути `tuf/v1/targets/indexes/<sha256>.<channel>.json`. Это те же байты, что в `updates/v1/<channel>.json` (раскладка — в [`tuf.md`](tuf.md)).
- Сами файлы (пакеты Velopack, расширение, плагины) лежат в неизменяемых GitHub Releases. Индекс ссылается на них по URL и sha256.

Клиент скачивает метаданные и индекс только по HTTPS; перенаправление на `http://` отвергается. Индекс больше 1 МиБ отвергается.

## Формат

```json
{
  "schema": 1,
  "channel": "beta",
  "seq": 42,
  "generated": "2026-10-01T00:00:00Z",
  "expires": "2026-10-31T00:00:00Z",
  "core": [
    {
      "version": "0.1.0-alpha.2",
      "flavors": {
        "win-x64": {
          "url": "https://github.com/arynyklas/OpenNCALayer/releases/download/v0.1.0-alpha.2/OpenNCALayer-0.1.0-alpha.2-win-x64-full.nupkg",
          "sha256": "<64 hex>",
          "size": 123,
          "contents_sha256": "<64 hex>",
          "delta_from": {
            "0.1.0-alpha.1": {"url": "https://…-delta.nupkg", "sha256": "<64 hex>", "size": 45}
          }
        }
      },
      "rollout": 100,
      "revoked": false,
      "notes_url": "https://github.com/arynyklas/OpenNCALayer/releases/tag/v0.1.0-alpha.2"
    }
  ],
  "extension": {
    "version": "0.1.0-alpha.2",
    "chromium_zip": {"url": "https://…", "sha256": "<64 hex>"},
    "firefox_xpi": {"url": "https://…", "sha256": "<64 hex>"}
  },
  "plugins": [
    {
      "id": "kz.example.echo",
      "version": "1.0.0",
      "url": "https://github.com/arynyklas/OpenNCALayer/releases/download/plugins-20261029/kz.example.echo-1.0.0.onclp",
      "sha256": "<64 hex>",
      "size": 12345,
      "min_core": "0.2.0",
      "modules": ["kz.example.Echo"],
      "replaces": {"symname": "kz.example.echo", "version": "1.2.1"},
      "name": {"ru": "…", "kk": "…", "en": "…"},
      "rollout": 100,
      "revoked": false
    }
  ]
}
```

Общие поля:

| Поле | Смысл |
|---|---|
| `schema` | Версия формата, сейчас `1`. Индекс другой схемы клиент не читает. |
| `channel` | `stable` или `beta`. Должен совпадать с каналом клиента. |
| `seq` | Номер индекса канала, растёт с каждой публикацией. Клиент не принимает `seq` ниже последнего принятого. |
| `generated` | Когда индекс собран, RFC 3339. |
| `expires` | Срок индекса, RFC 3339. `cargo xtask index` ставит `generated` + 30 дней. Клиент по этому полю индекс не отвергает: свежесть задают сроки ролей TUF. Поле остаётся частью формата. |

Версии ядра (`core`):

| Поле | Смысл |
|---|---|
| `core` | Версии ядра. Каждая версия встречается один раз. |
| `core[].version` | Версия semver (тег `v<version>`). |
| `core[].flavors` | Пакеты по вариантам сборки (flavor): `win-x64`, `win-x86`, `win7-x64`, `win7-x86`, `osx`, `linux-x64`. Незнакомые ключи клиент пропускает, поэтому новые варианты не ломают старых клиентов. |
| `…flavors.<flavor>.url`, `sha256`, `size` | Полный пакет: URL, sha256 (64 строчные hex-цифры) и размер в байтах. |
| `…flavors.<flavor>.delta_from` | Необязательно. Дельта-пакеты (только изменения): ключ — версия, от которой применяется дельта. |
| `…flavors.<flavor>.contents_sha256` | Обязательно, если есть `delta_from`. Сумма sha256 списка файлов полного пакета (`oncl_update::contents_sha256`): число записей zip, затем по каждой записи по имени — длина имени (8 байт, little-endian), имя и sha256 распакованных данных. Нужна потому, что Velopack собирает полный пакет из дельты как другой zip с теми же файлами (другой порядок и сжатие); его sha256 не совпадает с `sha256`, и клиент сверяет его по этой сумме. |
| `core[].rollout` | Процент установок, которым версия предлагается, от 0 до 100. |
| `core[].revoked` | Необязательно, по умолчанию `false`. Отозванная версия больше не предлагается. Клиент читает только индекс своего канала, поэтому релиз, который есть и в `stable`, и в `beta`, отзывается в обоих. |
| `core[].notes_url` | Необязательно. Ссылка на описание релиза. |

Расширение браузера (`extension`, необязательно): версия совпадает с версией ядра, файлы для Chromium (`.zip`) и Firefox (`.xpi`).

Плагины (`plugins`, необязательно; про сами плагины — [`plugins.md`](plugins.md)):

| Поле | Смысл |
|---|---|
| `plugins` | Версии плагинов. Каждая пара `id` + `version` встречается один раз. Каждое имя модуля и каждый заменяемый бандл (`replaces.symname`) принадлежат одному `id` во всём индексе. Зарезервировано за ядром и отвергается: `id` с префиксом `io.github.arynyklas.openncalayer.builtin.`, имена модулей встроенных модулей (`crates/oncl-builtin-*/plugin.toml`) и `replaces.symname` бандлов оригинала, которые ядро реализует само (`oncl_builtin_accessory::CORE_BUNDLES`). |
| `plugins[].id`, `version` | Идентификатор плагина и semver его порта (не версия бандла оригинала). |
| `plugins[].url`, `sha256`, `size` | Пакет `.onclp`: URL, sha256 и размер в байтах. |
| `plugins[].min_core` | Самая старая версия ядра, на которой плагин работает. Более старое ядро эту версию не ставит. |
| `plugins[].modules` | Имена модулей протокола, которые обслуживает плагин: от 1 до 32, без повторов. |
| `plugins[].replaces` | Необязательно. Бандл оригинала, который заменяет плагин: `symname` и его версия в формате оригинала. По нему работает `accessory.installBundle`, а `getBundles` показывает его, пока плагин установлен и включён. |
| `plugins[].name` | Название на русском, казахском и английском, для менеджера плагинов и подсказок. |
| `plugins[].rollout` | Процент установок, которым версия предлагается. Бакет — `sha256(install_id ‖ id ‖ 0x00 ‖ version)[0] * 100 / 256`, свой у каждого плагина и версии. |
| `plugins[].revoked` | Необязательно, по умолчанию `false`. Отозванная версия не предлагается. Установки на ней переходят на самую новую неотозванную (раскатка при этом не учитывается, допускается откат на старую версию); если такой нет, плагин выключается. |

Все URL в индексе должны начинаться с `https://`. Незнакомые поля внутри схемы 1 клиент пропускает, поэтому в формат можно добавлять поля без смены схемы.

## Как клиент проверяет индекс

`oncl_update` принимает индекс, только если выполнено всё:

1. Цепочка TUF проверена целиком (корни, `timestamp`, `snapshot`, `targets`, цель с длиной и sha256). Правила и отказы — в [`tuf.md`](tuf.md).
2. Индекс не больше 1 МиБ.
3. Индекс разобран и соблюдает правила формата: схема 1, URL только `https://`, `rollout` не больше 100, версии не повторяются.
4. `channel` индекса совпадает с каналом клиента.
5. `seq` не меньше последнего принятого для этого канала. Тот же `seq` — тот же индекс, скачанный повторно; так клиент может повторить обновление, которое не скачалось. Каждый новый индекс канала получает новый `seq`.

JSON индекса разбирается только после проверки подписей и sha256.

Правила «меньше 30 дней с `generated`» нет. Клиент отвергает метаданные с истёкшим сроком роли, а не индекс по возрасту. Метаданные TUF общие для обоих каналов: срок `targets` и `snapshot` продлевается подписью владельца (не реже раза в 30 дней), а срок `timestamp` — ежедневной подписью при публикации Pages ([`tuf.md`](tuf.md)).

Корень доверия клиента — `crates/oncl-update/keys/root.json`. `build.rs` встраивает его в сборку. Без файла обновления в сборке выключены, а повреждённый файл ломает сборку.

## Выбор версии

`oncl_update::choose` выбирает версию ядра для установки. Версия предлагается, если выполнено всё:

- она не отозвана;
- она не помечена локально как плохая, то есть не провалила проверку здоровья на этой установке;
- в ней есть пакет для варианта сборки этой установки;
- установка попала в раскатку: бакет `sha256(install_id ‖ version)[0] * 100 / 256` меньше `rollout`.

`install_id` — 16 случайных байт установки, `version` — строка версии. У каждой версии свой бакет, поэтому первыми обновляются не всегда одни и те же установки.

Из предложенных версий берётся самая новая. Если она новее текущей — это обновление. Если нет — ничего не делается.

**Если индекс отзывает текущую версию**, важнее уйти с неё, чем соблюсти поэтапную раскатку. Тогда `rollout` не учитывается: берётся самая новая версия, которая не отозвана, не помечена как плохая и имеет пакет для варианта сборки. Установка на отозванной версии получает исправление, даже если оно раскатано не на всех (в том числе при `rollout: 0`). Если эта версия новее текущей — это обновление, если старше — откат (даунгрейд). Только в этом случае клиент откатывается на старую версию.

Если версия ядра вообще не упомянута в индексе (локальная сборка или версия, убранная из индекса), на старую версию клиент не откатывается.

Скачанный пакет сверяется с `size` и `sha256` из индекса (`Package::check_file`). Пакет, который не сошёлся, не применяется.

## Что клиент хранит

Файл `<данные>/update/state.json` записывается атомарно:

```json
{
  "last_seq": {"stable": 7, "beta": 42},
  "install_id": "<32 hex>",
  "bad": ["0.2.0-beta.1"],
  "pending_health": {"from": "0.1.0", "to": "0.2.0", "applied": "2026-10-27T10:00:00Z", "started": "2026-10-27T10:00:20Z"}
}
```

| Поле | Смысл |
|---|---|
| `last_seq` | Последний принятый `seq` по каналам. |
| `install_id` | Случайный идентификатор установки, нужен только для бакета раскатки. Никуда не отправляется. |
| `bad` | Версии, которые на этой установке не прошли проверку здоровья. Они больше не предлагаются. |
| `pending_health` | Обновление применено, но новая версия ещё не подтвердила, что работает. Поле есть только в это время. `started` — начало текущего запуска новой версии; при чистом завершении поле стирается. `crashes` — сколько запусков подряд упали или зависли. `rollback: true` — это откат с версии, не прошедшей проверку. `attempts` — сколько раз откат передавался Velopack. |

Если файл повреждён (не читается как состояние), программа записывает вместо него новый: с новым `install_id` и без `last_seq`. Обновления от этого не останавливаются.

Если файл не читается по другой причине (нет прав, его держит другая программа), он не трогается. В этом запуске программа не проверяет здоровье и не откатывает, проверка обновлений повторяется через 30–120 минут, а изменение, которое не удалось сохранить, не применяется.

Все записи в файл идут под одной блокировкой: каждая перечитывает файл и меняет только своё поле.

## Обновление в программе

Сама себя обновляет только копия, установленная через Velopack и собранная с корнем доверия `crates/oncl-update/keys/root.json`. Корень встраивается при сборке, если файл есть. Без него, а также в архиве из Releases или в своей сборке обновления выключены; об этом пишется в журнал и в окно настроек.

Настройки в `settings.json`: `"updates": {"enabled": true, "channel": "stable"}`, канал `stable` или `beta`. Если канал не записан, сборка предварительной версии (`-alpha.1`, `-rc.1`) читает `beta`, а релиз — `stable`: предварительные версии попадают только в `beta`. Записанный канал не меняется. В окне настроек есть флажок «Обновлять автоматически», выбор канала и кнопка «Проверить сейчас». В меню значка есть пункт «Проверить обновления».

Порядок работы:

1. Первая проверка идёт через 2–10 минут после запуска, следующие — раз в 6–24 часа. Время каждый раз выбирается случайно.
2. Метаданные TUF и индекс канала скачиваются с `https://arynyklas.github.io/OpenNCALayer/tuf/v1/` через прокси из настроек и проверяются, как описано выше. Затем `choose` выбирает версию.
3. Если индекс не скачался, следующая попытка — через 30–120 минут. Если индекс отвергнут, следующая попытка — в обычный срок. Уведомлений в обоих случаях нет, ошибку видно в журнале и в окне настроек.
   - Если индекса канала ещё нет, в окне настроек пишется «В канале пока нет выпусков», уведомления нет, следующая проверка в обычный срок. Это значит: клиент ещё не принял ни одного `timestamp`, а репозиторий отвечает на него 404, или в принятых `targets` нет записи канала.
   - 404 после первой принятой публикации — ошибка проверки, повтор через 30–120 минут.
4. О новой версии программа сообщает уведомлением «Доступна версия X», один раз на версию.
5. Velopack получает список из одной выбранной версии: полный пакет и дельту от текущей версии, если она есть в индексе. Файлы скачиваются только по HTTPS и перед передачей Velopack сверяются с `size` и `sha256` из индекса.
   - Полный пакет, который Velopack собрал из дельты или нашёл на диске, принимается, только если он совпадает с полным пакетом индекса по `sha256` и размеру или содержит те же файлы (`contents_sha256`). Эта проверка идёт до того, как пакет встаёт на место и из него извлекается `Update.exe`.
   - Пакет на диске, не прошедший проверку, удаляется и скачивается заново. Собранный из дельты заменяется скачиванием полного пакета.
   - Для этого Velopack собирается из нашего форка (см. `docs/dev/development.md`, «Форки сторонних крейтов»).
6. Программа ждёт, пока не останется открытых окон и запросов страниц в работе, и после последнего запроса ещё 30 секунд. Затем индекс проверяется ещё раз: если версию за это время отозвали или обновления выключили, она не ставится. Новые запросы страниц задерживаются до выхода программы.
7. В состояние записывается `pending_health`. Velopack ставит новую версию после выхода программы и запускает её с теми же аргументами.

### Проверка здоровья и откат

Новая версия должна доказать, что работает, иначе программа вернёт предыдущую.

- При каждом запуске новая версия записывает в `pending_health` время `started`. Проверка идёт в отдельном потоке и не зависит от цикла окон.
- Если серверы и цикл окон проработали 5 секунд подряд, версия удаляет `pending_health` и показывает «Обновлено до X».
- Если этого не случилось за 60 секунд после запуска, версия считается плохой. Она попадает в `bad`, а программа, дождавшись простоя, ставит предыдущую версию из её полного пакета в индексе. После запуска предыдущая версия показывает «Обновление откачено».

Что считается сбоем:

- Запуск, после которого при следующем старте `started` всё ещё стоит: прошлый запуск упал или завис, и `crashes` растёт на 1. После двух таких запусков подряд версия попадает в `bad`, и откат делается сразу, до запуска серверов и окон. Один сбой, после которого версия проработала нормально, к откату не ведёт.
- Учёт запусков начинается сразу после проверки, что программа запущена одна, ещё до проверки TLS и порта. Поэтому запуск, который упал при настройке или вышел с кодом 1, тоже считается сбоем.
- Неудавшийся цикл окон — не чистое завершение, даже если программа выходит с кодом 2 или 3.
- Обработчика завершения сеанса (выход из системы, выключение) нет. Если сеанс закончился, пока новая версия ещё не подтвердила здоровье (обычно первые 5–7 секунд запуска), этот запуск считается сбоем. Два таких запуска подряд без подтверждённого запуска между ними откатят исправную версию и отметят её в `bad` на этой машине; следующие версии предлагаются как обычно.

Что сбоем не считается: чистое завершение до подтверждения. Это «Выход» в меню значка, остановка для обновления или выход с кодом 2 или 3 (TLS не настроен, порт занят). При нём `started` стирается, а `crashes` обнуляется.

Если откат не получается:

- Velopack не применил откат и снова запустил плохую версию: откат повторяется, но не больше трёх раз. Если Velopack сразу отказался применять откат, повторов нет. В обоих случаях плохая версия остаётся в `bad` и продолжает работать, программа один раз сообщает «Версия X работает с ошибками», а обычные проверки продолжаются.
- Индекс не скачался, пакет не загрузился или скачанный пакет пропал до передачи Velopack (его может удалить очистка Velopack при другом запуске программы): откат повторяется через 30–120 минут, тоже не больше трёх раз. Этот счётчик живёт в пределах запуска. Пока откат не отменён, следующий запуск плохой версии снова пробует скачать его, прежде чем начать работать, и только потом возвращается к расписанию. Если за запуск не удались все три попытки, откат отменяется, как при отказе Velopack: плохая версия остаётся в `bad`, программа один раз сообщает «Версия X работает с ошибками», и следующие запуски откат уже не скачивают. При запуске плохой версии на скачивание индекса и пакета отводится не больше 15 секунд: дальше программа запускается как обычно, а откат повторяется в фоне с обычным временем на загрузку.
- В индексе нет пакета предыдущей версии: плохая версия остаётся в `bad`, программа один раз сообщает об этом. Обычные проверки продолжаются, и исправленная версия установится, когда выйдет.
- Предыдущая версия тоже в `bad`: отката нет.

## Для мейнтейнера: подготовка индекса

Индексы лежат в репозитории в `updates/v1/` и публикуются байт в байт. `.gitattributes` запрещает git менять в них концы строк, иначе подпись не сойдётся. Здесь — правила и команды; порядок действий от первого ключа до выпуска — в [`../dev/release.md`](../dev/release.md).

Подпись индекса — это TUF ([`tuf.md`](tuf.md)). Команды `cargo xtask tuf …` заменяют `sign` и часть `index check` (в них остались следы прежней подписи minisign), актуальный порядок — в `release.md`.

### Какие URL допустимы

Все файлы лежат в релизах проекта. URL каждой записи должен быть ровно `https://github.com/arynyklas/OpenNCALayer/releases/download/v<версия>/<файл>`, где `<версия>` — версия самой записи, а `<файл>` — имя файла этого вида:

- полный пакет — `OpenNCALayer-<версия>-<flavor>-full.nupkg`;
- дельта — `OpenNCALayer-<версия>-<flavor>-delta.nupkg`;
- расширение — `openncalayer-chromium-<версия>.zip` и `openncalayer-firefox-<версия>.xpi`;
- плагин — `<id>-<версия>.onclp` в релизе с тегом `plugins-ГГГГММДД[.N]` (а не `v<версия>`): `https://github.com/arynyklas/OpenNCALayer/releases/download/plugins-ГГГГММДД[.N]/<id>-<версия>.onclp`. Предварительная версия плагина в `stable` не допускается.

`notes_url` — `https://github.com/arynyklas/OpenNCALayer/releases/tag/v<версия>`. Запросы (`?…`), фрагменты (`#…`) и незнакомые варианты сборки не допускаются.

Это правило проверяют `index add`, `index refresh`, `sign` и `index check` (`index add` и `index refresh` — и для индекса, который они читают, и для того, который записывают). Клиент его не проверяет: подписывается только индекс, который прошёл эту проверку.

### Команды

**Ключ мейнтейнера.** `cargo xtask sign keygen --out <каталог>` создаёт пару ключей: `oncl-index.key` (зашифрован паролем, пароль вводится без эха) и `oncl-index.pub`.
- Команда отвергает каталог внутри рабочего дерева git, если он не указан в `.gitignore`. Отвергается и файл, который уже отслеживается git.
- Перед проверкой существующая часть пути разрешается: символические ссылки, junction и `..`. Рабочее дерево ищется по ближайшему каталогу-предку с `.git`, а не поиском самого git. Если git не может открыть репозиторий (например, у связанного рабочего дерева пропал основной), команда отказывается писать ключ, а не считает каталог посторонним.
- Открытый ключ кладётся в `crates/oncl-update/keys/current.pub` (или в `next.pub` для ротации).

**Добавить версию ядра.** `cargo xtask index add --channel beta --tag v<версия> --release-assets <каталог>` дописывает версию в индекс по скачанным ассетам релиза:
- полные пакеты по вариантам сборки;
- дельты; версия, от которой применяется дельта, — самый новый полный пакет старше новой версии в `releases.<flavor>.json` Velopack из тех же ассетов;
- расширение, только оба файла вместе.

sha256 и размеры берутся из файлов. `seq` растёт на 1, `generated` — текущее время, `expires` — через 30 дней. `--rollout` задаёт процент раскатки (по умолчанию 100). Подпись прежнего индекса удаляется: к новому она не подходит.

**Собрать плагин.** `cargo xtask plugin pack <каталог крейта>` собирает плагин под `wasm32-unknown-unknown` и пишет `target/plugins/<id>-<версия>.onclp`.
- Версия в `plugin.toml` должна совпадать с версией крейта; модуль проходит ту же проверку ABI, что и в программе.
- Пути машины сборки (домашний каталог, тулчейн, рабочее дерево) в модуль не попадают: сборка заменяет их на `/cargo`, `/rustc`, `/workspace` и `/plugin`.
- Архив детерминирован: те же исходники тем же тулчейном дают те же байты.

**Добавить плагин.** `cargo xtask index add-plugin --channel <channel> --tag plugins-ГГГГММДД[.N] --package <файл.onclp>…` дописывает версии плагинов в индекс.
- `id`, версия, `min_core`, модули, `replaces` и название берутся из манифеста пакета, sha256 и размер — из файла.
- Повтор `id` + версии, модуль или бандл оригинала (`replaces.symname`), который уже у другого плагина, и предварительная версия в `stable` отвергаются.
- Индекс с новыми пакетами проходит проверку URL и владельцев до записи, поэтому при отказе файл не меняется.
- `seq`, `generated`, `expires` и подпись — как у `index add`; `--rollout` задаёт раскатку.
- В `stable` попадает только порт, чей `registry.toml` в каталоге портов (`--plugins`, по умолчанию `plugins/`) говорит `conformance = "confirmed"`, то есть совместимость проверена на работающем оригинале. Порт с `computed` и пакет, `id` которого нет ни у одного порта, в `stable` не добавятся. Для `beta` каталог портов не читается.

**Продлить индекс.** `cargo xtask index refresh --channel <channel>` продлевает индекс, не меняя содержимое: `seq` растёт на 1, `generated` — текущее время, `expires` — через 30 дней. Индекс нужно продлевать и подписывать заново, пока не прошли 30 дней с `generated`.

**Подписать индекс (minisign).** `cargo xtask sign updates/v1/<channel>.json --key <секретный ключ>` пишет `.minisig` с доверенным комментарием `channel=…;seq=…`.
- Перед записью подпись проверяется открытым ключом той же пары: так ловится испорченный ключ или файл. Подпись не тем ключом ловит `index check`.
- Неверный или истёкший индекс не подписывается, как и индекс с URL не на релизы проекта.

**Проверить перед публикацией.** `cargo xtask index check updates/v1` проверяет:
- Каждый индекс проходит проверку клиента подписью ключом `crates/oncl-update/keys/current.pub` (не `next.pub`: следующий ключ нужен клиентам, подписывать им рано). Его URL и владельцы модулей и бандлов проверяются по правилам выше. Подписи без индекса быть не должно.
- Тег `v<версия>` каждой версии, новой относительно базы или с заменёнными пакетами (если в базе нет индекса канала — каждой), содержит `crates/oncl-update/keys/current.pub`, и это `current.pub` или `next.pub` проверяемого дерева.
  - Без базы (`--no-base`: ручной запуск Pages) теги не проверяются: версии, опубликованные до ротации ключа, хранят в тегах старый ключ.
  - Если каталога `updates/v1` ещё нет (ключи закоммичены раньше первого индекса), проверка проходит, прочитав только ключи, а Pages ничего не публикует.
  - Сборка без ключа не обновляет себя, и переводить на неё установки нельзя. `index add` проверяет то же до записи, а job `index` для тега без ключа PR не открывает и пишет уведомление.
- Относительно базовой ветки (`--base`, по умолчанию `origin/main`) у изменённого индекса `seq` больше, и ни один индекс не удалён.
- Без `--offline` каждый URL пакета ядра, расширения и плагина отвечает на `HEAD` кодом 200.
- С `--vm-smoke` на теге каждой новой версии должен стоять статус коммита `vm-smoke = success`: установщики прошли проверку на чистых системах лаборатории.
- С `--conformance` на теге каждой новой версии в `stable` должен стоять статус коммита `conformance = success`: сборка тега сверена с оригиналом в лаборатории. В `beta` этот гейт не действует: релиз без суффикса проверяется на `conformance` в индексе `stable`, а предварительной версии хватает `vm-smoke`.

Гейты ключа в теге, `vm-smoke` и `conformance` относятся только к версиям ядра. Оба статуса ставит агент лаборатории на коммит тега: сначала `vm-smoke`, затем для того же тега `conformance`. `index-check.yml` запускает проверку с `--vm-smoke --conformance` и читает статусы через API GitHub своим токеном (право `statuses: read`). Эти флаги несовместимы с `--offline`. «Новая» значит новая относительно базы; без базы (`--no-base`) новой считается каждая версия индекса.

## Публикация

Тег `v<версия>` запускает `.github/workflows/release.yml`:

1. **Сборка.** Для каждого варианта сборки собираются архив, установщик и пакеты Velopack (`cargo xtask package windows|macos|linux`, внутри `vpk pack --packId OpenNCALayer --channel <flavor>`). Собираются `win-x64`, `win-x86`, `win7-x64`, `win7-x86`, `linux-x64` и `osx`.
   - Дельта строится от полного пакета того же варианта из релиза с наибольшей версией ниже текущей: для релиза — среди релизов, для пререлиза — среди версий любого вида. Этот пакет скачивается прямо из того релиза (`gh release download`; `vpk download github` видит только 10 последних релизов) и сверяется с его `SHA256SUMS`. Если такого релиза нет, дельты нет; любая другая ошибка останавливает сборку.
   - В релиз попадают `OpenNCALayer-<версия>-<flavor>-full.nupkg`, `-delta.nupkg` (если есть предыдущий пакет), `releases.<flavor>.json` (список Velopack: эта версия и полный пакет, от которого построена дельта) и на Windows `RELEASES-<flavor>`. Установщики: `openncalayer-<версия>-<flavor>-setup.exe` для четырёх вариантов Windows, `openncalayer-<версия>-osx.pkg` и `openncalayer-<версия>-osx.zip`, `openncalayer-<версия>-linux-x64.AppImage`.
   - Варианты `win7-*` собирает `cargo xtask win7` (с app-local DLL рядом с exe). Их исполняемые файлы, `Squirrel.exe`, заглушка Velopack и `Setup.exe` проходят проверку импортов Windows 7. Linux собирается в контейнере с glibc 2.28 (`cargo xtask package linux-build`).
2. **Приложения к релизу.** Рядом ложатся расширение, SBOM `openncalayer-<версия>.cdx.json` (CycloneDX, `cargo cyclonedx`) и `SHA256SUMS`. На каждый файл релиза выпускается аттестация происхождения сборки (`actions/attest-build-provenance`); проверить её можно командой `gh attestation verify <файл> --repo arynyklas/OpenNCALayer`.
3. **Подпись кода.** Идёт, только если заданы её секреты; иначе шаг пропускается с уведомлением в журнале.
   - Authenticode через SignPath: секрет `SIGNPATH_API_TOKEN`, переменные `SIGNPATH_ORGANIZATION_ID`, `SIGNPATH_PROJECT_SLUG`, `SIGNPATH_SIGNING_POLICY_SLUG`. Подписываются `openncalayer.exe` и `nmhost.exe` до упаковки и каждый `Setup.exe` после неё (app-local DLL сборок Windows 7 не подписываются).
   - Подпись и нотаризация Apple: секреты `APPLE_CERTIFICATE_P12` (base64), `APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGN_IDENTITY`, `APPLE_ID`, `APPLE_TEAM_ID`, `APPLE_APP_PASSWORD`. `.app` (пакет обновления, `.zip` и содержимое `.pkg`) подписывает и нотаризует `vpk pack`. Сам `.pkg` подписывается и нотаризуется, только если задан ещё секрет `APPLE_INSTALL_IDENTITY` («Developer ID Installer»). Архив macOS остаётся неподписанным.
4. **Индекс.** После публикации релиза job `index` скачивает его ассеты, выполняет `cargo xtask index add` для каждого канала версии и открывает PR в `main` с неподписанными индексами. Пререлиз идёт только в `beta`, релиз без суффикса — в `stable` и в `beta`. У каждого индекса свой следующий `seq`, прежние записи сохраняются, индекс другого канала пререлиз не трогает. Вариант `osx` добавляется вместе с остальными: универсальную сборку проверяет workflow `mac-smoke.yml` на Mac с Apple Silicon и с Intel.

Дальше мейнтейнер на ветке PR при необходимости меняет `rollout`, подписывает каждый индекс PR (`cargo xtask sign`; для релиза — оба), коммитит индексы с их `.minisig` и пушит. Неподписанный индекс `index check` отвергает. PR, открытый workflow, сам проверки не запускает, поэтому `index-check.yml` (`cargo xtask index check updates/v1 --base origin/main --vm-smoke --conformance`) срабатывает на этот пуш.

После слияния `pages.yml` ещё раз проверяет индексы и публикует `updates/` на GitHub Pages под `/updates/`. Весь сайт Pages — один артефакт: другие страницы сайта лежат в нём рядом с `updates/`.

Настройки репозитория меняет только мейнтейнер:

- Pages: Settings → Pages → Source: GitHub Actions;
- PR от workflow: Settings → Actions → General → Allow GitHub Actions to create and approve pull requests.
