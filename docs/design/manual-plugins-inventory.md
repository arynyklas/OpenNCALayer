# Какие плагины работают в окне ручных инструментов

Документ для тех, кто хочет узнать, какие из 34 портов можно запустить в окне ручных инструментов и почему остальные нельзя. Здесь: короткий итог, причины отказа простыми словами, вердикт по каждому порту, подробности про те порты, которые работают, и способ проверить выводы самому. Как устроена защита этого окна — в [manual-plugins.md](manual-plugins.md). Пользовательский взгляд — в [руководстве](../user/manual-plugins.md).

## 1. Итог в цифрах

- Портов (WASM-пакетов): **34**. Имён модулей 35, потому что у `documentolog` их два. Методов, видимых вызывающему сайту: **166**.
- **Работают в окне:** 15 методов в **9** портах — `dogovor24`, `efactoring`, `energy`, `eproc`, `esf-osdkz`, `fhs`, `market`, `qiwi`, `rating1c`. Для 13 из них нужны условия (например, фиксированное значение параметра, которое выбирает программа).
- **Не работают:** 59 методов, потому что их блокирует одна или несколько причин из раздела 3.
- **Ничего не подписывают:** 92 метода (справочные: версия, список ключей, проверка и т. п.). В окне они не предлагаются.
- В 25 портах из 34 нет ни одного подходящего метода.

Выводы получены не из документации, а из разбора самих портов:

- по секции импортов каждого из 34 собранных WASM-файлов: какие функции ядра порт может вызвать;
- по чтению исходников пути каждого метода;
- по существующим тестам портов (они проходят);
- по графу вызовов — слабое доказательство, использовалось только для методов, которые ничего не подписывают.

Реальный «ручной» вызов с синтетическим ключом в момент инвентаризации не запускали (самого пути ещё не существовало). Поэтому вердикты — «по коду метода»: они проверены позднее на настоящем WASM для портов, которые получили объявления (раздел 6).

## 2. Как ведёт себя ручной вызов

Это факты о том, что делает программа сейчас. Они объясняют многие отказы.

- **Каждый вызов получает новый экземпляр плагина.** Всё, что порт запомнил в памяти между вызовами (например, «выбранный ключ» после `selectKey`), теряется. По WSS экземпляр живёт на всё соединение, поэтому порты «сначала выбрать ключ, потом подписать» там работают, а в ручном окне нет. Это главная причина отказа для многих портов.
- **Диалоги и файлы запрещены:** `Dialog*`, `File*`, `CoreOpenWindow`, `Keystore*` дают `InteractionRequired`. Выбор ключа (`keys_select`, `keys_choose` и др.) отвечает ядро для единственного привязанного ключа.
- **Прочие функции ядра** для безоконного режима недоступны (`keys_open`, `core_*`, `tokens_*` и др.) и дают `PermissionDenied`. Освобождение буфера ответа (`reply_drop`, его линкуют 33 порта) разрешено.
- **Файлы страницы.** `page_file_read` отдаёт только заранее привязанный вход, `page_file_write` принимает имя без разделителей путей. Порты, которым нужен «диск страницы» с буквой диска (`arta.signFilePath`, `ezsigner.signFilePath`), отвергаются уже после применения ключа, поэтому честного отказа до ключа для них нет.
- **У ручного вызова нет Origin.** Порты, которые читают `request.origin`, — ровно 7 из 34 (`buhta`, `k2sign`, `knp`, `nursign`, `qoltanba`, `taxtech`, `xdox`). Из них только `taxtech` терпит пустое значение. Остальные поступают по-разному: `qoltanba` отвечает `INVALID_ORIGIN` на любой метод, `buhta`, `k2sign`, `knp`, `nursign` обрывают соединение, `xdox` отвечает, что модуль работает только на своём сайте.
- **Язык окон плагина в этом режиме всегда `ru`.** Для подходящих методов это не важно.

Как ведут себя группы функций ядра в окне:

| Группа | Функции | Что в окне |
|---|---|---|
| Выбор ключа | `keys_select`, `keys_choose`, `keys_release`, `keys_describe`, `keys_chain` | Разрешены. Ядро отвечает для единственного привязанного ключа. |
| Терминалы | `keys_terminals` | Пустой список. Порт, которому для успеха нужен непустой список считывателей, не поддерживается. |
| Подпись | `keys_sign_raw`, `keys_sign_cms_ex`, `keys_sign_xml`, `keys_sign_xml_ex`, `keys_sign_xades` (и `keys_sign_cms`, которого никто не линкует) | Одно применение ключа, профиль принуждает ядро. |
| Запрещённые | `dialog_*`, `file_*`, `keys_open`, `page_file_*` | Если нужны на успешном пути, метод не поддерживается. |
| Сеть | `ocsp_fetch`, `tsp_stamp`, `tsp_request`, `crl_fetch`, `ca_*`, `pkix_path` (PKI); `http_request_ex` (любой http/https) | В согласии показывается сеть. Произвольный `http_request_ex` не разрешён. |
| Состояние | `shared_*`, `settings_*` | Между вызовами недоступно. |
| Проверка | `cms_verify`, `xml_verify` | Локальная проверка. |
| Нейтральные | `log`, `now`, `random`, `cert_info`, `cert_details`, `hash`, `local_time`, `platform`, `reply_drop` | Разрешены. |

Сколько портов импортируют: `keys_release`, `log`, `random` — все 34, `reply_drop` — 33, `keys_sign_cms_ex` — 27, `keys_select` — 24, `cert_info` — 23, `cert_details` — 22, `keys_terminals` — 17, `now` и `ocsp_fetch` — по 15, `keys_open` и `keys_sign_xml_ex` — по 11, `local_time` — 8, `dialog_choice`, `file_choose`, `http_request_ex` и `keys_sign_raw` — по 7, `ca_issuer`, `cms_verify`, `tsp_stamp` — по 6, `dialog_message`, `dialog_password`, `keys_sign_xml` — по 5, `keys_choose` и `platform` — по 4, `file_open_ex`, `hash`, `page_file_read`, `page_file_write` — по 3, `ca_list`, `keys_chain`, `xml_verify` — по 2, остальные — по одному.

Виды подписи у портов: 7 портов используют подпись «сырых» байт (`acbank`, `arta`, `devart`, `esf-osdkz`, `rating1c`, `taxtech`, `uchet-esf`), один — XAdES (`skf`), остальные — CMS и XML.

## 3. Причины, по которым метод не работает

| Код | Что это значит |
|---|---|
| `ORIGIN` | Порту нужен адрес сайта-инициатора. В ручном окне его нет, и подставлять его нельзя. |
| `DIALOG` | На успешном пути порт показывает свой диалог. Диалоги запрещены. |
| `KEYS_OPEN` | Порт сам открывает файл ключа по пути и паролю из запроса. В окне ключ выбирает пользователь, а пароль страницы не принимается. |
| `STATE` | Порту нужно состояние, оставшееся от прошлого вызова (например, выбранный ключ). Каждый ручной вызов — новый экземпляр. |
| `OPTIONS` | Порт просит опции подписи вне разрешённого профиля: дополнительные атрибуты (ESEDO), собственный тип содержимого, свой сервер меток времени. |
| `MULTI` | За один вызов нужно больше одной подписи. В ручном окне допускается одна. |
| `FILE` | Нужны файловые диалоги или файлы страницы. |
| `DERIVED` | Подписываемые байты вычисляет или скачивает сам плагин, а не передаёт пользователь. |
| `COSIGN` | Нужна со-подпись чужого CMS из запроса. |
| `HTTP` | Для успеха нужен произвольный http-запрос вне PKI (сервер лицензий вендора). |
| `TERMINALS` | Ветка хранилища токенов упирается в пустой список считывателей. |

Сколько методов блокирует каждая причина (по строкам «не работает»; «главная» — самая жёсткая причина метода, «только она» — метод заблокирован только ею, снять её — и метод заработает):

| Причина | Главная | Упомянута всего | Только она |
|---|---|---|---|
| `ORIGIN` | 15 | 15 | 6 |
| `DIALOG` | 9 | 12 | 0 |
| `KEYS_OPEN` | 13 | 21 | 6 |
| `STATE` | 8 | 10 | 3 |
| `OPTIONS` | 6 | 14 | 5 |
| `MULTI` | 5 | 14 | 5 |
| `FILE` | 1 | 7 | 0 |
| `DERIVED` | 1 | 16 | 1 |
| `COSIGN` | 0 | 1 | 0 |
| `HTTP` | 0 | 2 | 0 |
| `TERMINALS` | 1 | 1 | 1 |

Главное наблюдение: портов, которые подходят, мало **не из-за Origin**. Основные причины — `STATE`, `KEYS_OPEN`, `DIALOG` и `OPTIONS`.

## 5. Порты, подходящие для окна

Порядок — от простого к сложному.

| Порт | Методы | Вид подписи | Условия и оговорки |
|---|---|---|---|
| `rating1c` | `signXml`, `createCmsFromBase64`, `createRawSignFromBase64` | XML, CMS, «сырая» | Параметры хранилища и типа ключа программа подставляет сама (`PKCS12`, `SIGNATURE`). Сертификат должен пройти проверку срока самого плагина. Для подписи элемента у него должен быть атрибут `Id`. |
| `dogovor24` | `signCMS` | CMS | Ключ выбирается до разбора имени метода. В сертификате должно быть расширенное назначение без `clientAuth`. |
| `efactoring` | `text`, `xml` | CMS, XML | XPath подписываемого элемента и родителя вводит пользователь. Диалог повтора при ошибке недоступен: ошибка подписи завершает вызов ошибкой. |
| `market` | `text`, `xml` | CMS, XML | То же, что у `efactoring`. |
| `energy` | `sign` | CMS | Диалог только на ошибке. `alias` не передаётся, число документов 1, `isDigested=false`. |
| `eproc` | `signXml` | XML | Хранилище `PKCS12`, ключ типа `SIGNATURE`. Подписывается весь документ или элемент. |
| `esf-osdkz` | `signPlainData` | «сырая» | Подписывает текст, поэтому согласие должно показывать сам текст. |
| `fhs` | `signXml`, `signText` (V1) | XML, CMS | Диалог повтора только на ошибке. |
| `qiwi` | `signXml` | XML | Адреса алгоритмов зависят от ключа, поэтому объявлены две операции: для ключа RSA-SHA256 и для ГОСТ 2004. |

Общие условия для всех строк со значком «с условиями»:

1. Программа строит запрос с фиксированными необязательными параметрами (`storageName=PKCS12`, `keyType=SIGNATURE`, пустое `BINControl`).
2. Привязанный пользователем ключ должен подходить под фильтр плагина (тип ключа, назначение сертификата). Иначе выбор ключа вернёт «ничего», и порт ответит «отмена».
3. `cosign=Auto` приводится к `Never` (см. [manual-plugins.md](manual-plugins.md)).
4. Параметры-тексты (XPath, текст для текстовых методов) показываются в согласии как параметры, а не как «содержимое».

## 6. Как порты объявлены на деле

Объявление операции должно выразить форму запроса порта. Формы разные:

| Порт | Форма запроса |
|---|---|
| `rating1c`, `dogovor24`, `qiwi` | `args` — массив (у `rating1c` из 6 элементов, строки и булевы). |
| `fhs` (V1), `energy` | `args` — объект (у `energy` вложен массив объектов `{id,name,base64}`). |
| `eproc`, `esf-osdkz` | Поля прямо в корне запроса, `args` нет. |
| `efactoring`, `market` | Вместо `method` ключ `type`, поля в корне. |

Поэтому шаблон запроса может быть любым JSON-объектом, плейсхолдеры допускаются на любой глубине, а текстовый параметр может быть содержимым «сырой» подписи.

Что выяснилось на настоящем WASM при объявлении операций:

- `fhs.signXml` и `fhs.signText` объявлены с `"args":{...}`. Окно повтора есть у порта только при ошибке, а в ручном окне диалогов нет.
- `esf-osdkz.signPlainData` объявлен как `sign-plain-data` с текстовым параметром. Подпись проверена независимым RSA-проверяющим. Ядро отвергает в тексте управляющие и невидимые символы.
- У `rating1c` документ для XML — текстовый параметр (не более 65536 знаков), а не base64. `attached` и `withTSA` — поля профиля, а не параметры, поэтому для CMS объявлено четыре операции (`create-cms`, `-attached`, `-timestamp`, `-attached-timestamp`), а для XML две (весь документ и элемент в родителя с XPath-параметрами). Плагин вызывает несколько функций ядра, без любой из которых вызов отказывает, поэтому объявлены все реально вызываемые.
- `qiwi.signXml` потребовал в профиле XML поле `transforms`. Объявлены `sign-xml-rsa` и `sign-xml-gost2004`.
- У `efactoring` добавлена операция `sign-xml-element` (оба XPath — введённые пользователем параметры, видны на странице подтверждения). Если `parent` пустой или не абсолютный, отказ до запуска плагина. Если `parent` равен элементу, отказ порта до применения ключа.
- `energy`, `efactoring`, `market`: `attach` или `encapsulate` и `has_timestamp` или `tsaProfile` — поля профиля, поэтому четыре CMS-операции (`…-attached-timestamp`, `-attached`, `-detached-timestamp`, `-detached`). У `dogovor24.signCMS` одна форма (прикреплённая, метка времени Kalkan). У `eproc.signXml` две операции (документ целиком и элемент).
- **Сеть.** Операция с применением ключа обязана объявить `network = "pki"`. Любое применение ключа в окне проверяет подписанта у OCSP-ответчика из сертификата, а метка времени идёт на `tsp.pki.gov.kz`. Метка времени Kalkan запрашивается методом GET, поэтому для OCSP и TSA разрешены и GET, и POST. При `network = "none"` вызов отказывает до применения ключа.

Настройки ресурсов ручного окна (одно определение `ManualLimits::desktop()`, обоснование и измерения — в [`docs/dev/plugins-manual-tests.md`](../dev/plugins-manual-tests.md)): на 64-битной системе документ до 4 МиБ, передача 9 МиБ, память плагина 112 МиБ, бюджеты 704 и 896 МиБ. При нехватке бюджета отказ до ключа (`resource-budget`). XML-подписи нужно временное хранилище, иначе отказ `no-temporary-store`.

При проверке были исправлены ещё две вещи: настройки по умолчанию для лимитов плагина были несовместимы с бюджетом памяти (любой порт отказывал), а подача «топлива» кусочками приводила к невозобновляемой ошибке перевода функции WASM и обрыву вызова любого порта.

## 7. Нужно ли поддерживать вычисляемое содержимое

**Нет, и сейчас не планируется.** Доводы:

- Строк с причиной `DERIVED` 16, но заблокирован **только** ею один метод — `fhs.signFile`. Остальные заблокированы ещё и более жёсткой причиной (`ORIGIN`, `DIALOG`, `KEYS_OPEN`, `STATE`, `FILE`), так что снятие `DERIVED` им не поможет.
- `fhs.signFile{url}` подписывает документ, скачанный по адресу страницы, то есть двоичные данные любого размера. Пользователь в ручном окне и так владеет файлом: тот же результат даёт `fhs.signText{base64data}` с этим файлом.
- Вычисляемая «сырая» подпись (`acbank`, JWS) заблокирована ещё `DIALOG` и `MULTI`.
- Цена («пробный» вызов, список разрешённых функций, заморозка часов и случайных чисел, полное превью) несоразмерна одному методу.

## 8. Что изменится, если снять отдельные причины

Это не предложение менять дизайн, а оценка. Метод считается разблокированным, если все его причины входят в снимаемый набор.

| Сценарий | Сколько методов заработает | Какие |
|---|---|---|
| Снять `OPTIONS`: профиль ESEDO, где ядро само строит атрибуты по именам файлов и ответу OCSP | 5 | `bas.sign`, `dogovor24.signEsedo`, `eot.signCmsWithSignedAttrs`, `eup.sign`, `idocs.sign` |

Оговорки:

1. Снятие `OPTIONS` даёт не один профиль, а набор разных вариантов ESEDO (разные формы времени, имена, ответы OCSP, типы содержимого).
2. «`keys_open` привязанным ключом» меняет смысл ввода пароля: порт ждёт пароль от страницы, а в ручном окне страницы нет.
3. Сохранение экземпляра противоречит правилу «согласие не переживает вызов».
4. `MULTI` даёт только списочные варианты уже поддерживаемых методов.

## 9. Принятые решения по итогам инвентаризации

- `cosign=Auto` у `keys_sign_cms_ex` (так вызывают шесть подходящих портов) приводится к `Never`. Иначе правило «опции равны профилю» отвергло бы все CMS-методы. На странице согласия показан фактический профиль.
- Хранилище для подходящих операций задаётся шаблоном (`PKCS12`), поэтому пустой список считывателей им не мешает.
- `esf-osdkz.auth` не включён: для входа нужна своя модель согласия.
- ESEDO-профили (`bas`, `dogovor24.signEsedo`, `eot`, `eup`, `idocs`) отложены до отдельного решения.
- `reply_drop` разрешён как безвредный.

## 10. Как это проверить самому

```text
cd plugins
cargo build --release --locked --target wasm32-unknown-unknown --workspace      # 34 модуля
python ../scripts/mp0_wasm_imports.py <CARGO_TARGET_DIR>/wasm32-unknown-unknown/release          # импорты по портам
python ../scripts/mp0_wasm_imports.py <CARGO_TARGET_DIR>/wasm32-unknown-unknown/release --json   # то же, JSON
cargo test -p oncl-port-tests --test clones --test ecc --test medium            # существующие тесты портов (из корня репозитория)
```

Скрипт читает секцию импортов каждого WASM-файла: это то, что возвращает `Compiled::imports()`. Все 34 модуля импортируют только из пространства `oncl`, и все имена известны ABI. Для проверки конкретного вердикта откройте исходник порта и убедитесь, что диспетчер ведёт к нужной функции, а перечисленные импорты есть в секции импортов.
