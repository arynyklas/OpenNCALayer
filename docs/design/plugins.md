# Плагины

Для тех, кто пишет или переносит плагин, и для тех, кто хочет понять, что плагин может и чего не может. Здесь: как устроен пакет, что писать в манифесте, какие функции даёт программа и какие у них лимиты.

**Плагин** — модуль WebAssembly, который отвечает на запросы сайтов к одному или нескольким `module`-именам протокола NCALayer. Обычно это порт стороннего плагина оригинала: он отвечает тем же JSON, что и оригинал. Плагин работает в песочнице и получает только те возможности программы, которые заявил в манифесте. Общая модель — в [дорожной карте](roadmap.md), разделы «Плагины и порты» и «Как устроены плагины».

Пакет и манифест читает и проверяет крейт `oncl-plugin`; он же исполняет плагины (интерпретатор WebAssembly [Wasmi](https://github.com/wasmi-labs/wasmi), без JIT). Интерфейс плагина с программой (ABI) и гостевой SDK — крейт `oncl-pdk`.

Быстрый путь для автора плагина на Rust: возьмите пример `crates/oncl-pdk/example` (раздел [«SDK»](#sdk)), напишите `plugin.toml` ([«Манифест»](#манифест)), соберите пакет командой `cargo xtask plugin pack <каталог крейта>` и установите его через окно «Плагины» → «Установить из файла…».

## Пакет

Пакет плагина — zip-архив с расширением `.onclp`. Сжатие — `deflate` или без сжатия. Правила:

- файл пакета — не больше 32 МиБ;
- в корне архива ровно два файла:
  - `plugin.toml` — манифест, не больше 64 КиБ, в UTF-8;
  - `plugin.wasm` — модуль WebAssembly, не больше 16 МиБ; начинается с `\0asm` и версии 1 (байты `00 61 73 6D 01 00 00 00`);
- имена сравниваются побайтно, с учётом регистра;
- пакет отвергается, если в нём есть:
  - каталоги, в том числе пустые;
  - файлы с другими именами, в подкаталогах, с `..`, с абсолютным путём или с `\`;
  - два файла с одним именем;
  - символические ссылки;
  - зашифрованные файлы;
- размеры считаются по байтам, которые фактически получились при распаковке. Размерам из заголовков zip не доверяем: файл, который распаковывается больше заявленного или больше лимита, отвергается;
- sha256 пакета считается от байтов всего файла `.onclp`. Его сверяют с записью в индексе обновлений, подлинность которого проверяет TUF ([`update-index.md`](update-index.md), [`tuf.md`](tuf.md)).

## Манифест

`plugin.toml` — файл TOML. Неизвестные ключи — ошибка: манифест более новой версии формата не читается как более слабый.

```toml
id = "kz.example.echo"
version = "1.0.0"
min_core = "0.2.0"
modules = ["kz.example.Echo"]

[name]
ru = "Эхо"
kk = "Жаңғырық"
en = "Echo"

[description]
ru = "Возвращает запрос обратно"
kk = "Сұрауды кері қайтарады"
en = "Returns the request back"

[replaces]
symname = "kz.example.echo"
version = "1.2.1"

[capabilities]
keys = true
dialogs = true
files = true
http = ["https://tsp.pki.gov.kz/", "https://*.gov.kz/"]
origins = ["https://*.ecc.kz", "http://client2.kazynashylyk.kz"]
http_insecure = ["http://ncalayer.uchet.kz:8080/"]
key_files = true
page_files = true
page_files_ext = ["cms"]
settings = true
shared = true
```

| Поле | Обязательно | Правило |
|---|---|---|
| `id` | да | Строчные латинские буквы, цифры, `.` и `-`; от 3 до 64 символов; начинается и заканчивается буквой или цифрой; есть хотя бы одна точка (`^[a-z0-9][a-z0-9.-]{1,62}[a-z0-9]$`). Обычно — обратное доменное имя автора |
| `version` | да | Версия плагина, semver |
| `min_core` | да | Минимальная версия программы, semver |
| `modules` | да | От 1 до 32 `module`-имён, без повторов; каждое — латинские буквы, цифры, `.`, `_`, `-`, от 1 до 128 символов (`^[A-Za-z0-9._-]{1,128}$`) |
| `name` | да | Название в окне «Плагины»: `ru`, `kk` и `en`, каждое непустое и не длиннее 128 символов |
| `description` | нет | Описание: `ru`, `kk` и `en`, каждое не длиннее 2048 символов |
| `replaces` | нет | Бандл оригинала, который заменяет плагин: `symname` (`^[A-Za-z0-9._-]{1,128}$`) и `version` — версия оригинала как строка OSGi, не semver; непустая, не длиннее 64 символов |
| `capabilities` | нет | Возможности плагина. Всё, что не указано, выключено |
| `builtin` | нет | Зарезервировано для модулей ядра (см. [Встроенные модули](#встроенные-модули)). Пакет с `builtin = true` или с `id`, который начинается с `io.github.arynyklas.openncalayer.builtin.`, не устанавливается |

`replaces` нужен для `accessory`: `getBundles` показывает `symname` и `version` установленных и включённых плагинов (версия — в форме OSGi, `major.minor.micro`, как её печатает оригинал), а `installBundle` по `symname` находит порт.

### Возможности (`capabilities`)

Плагин получает только те функции программы, которые заявлены здесь. Функции каждой возможности описаны в разделе [Capabilities](#capabilities).

| Ключ | По умолчанию | Что разрешает |
|---|---|---|
| `keys` | `false` | Работа с ключами пользователя: открыть хранилище, подписать |
| `dialogs` | `false` | Показ диалогов |
| `files` | `false` | Чтение и запись файлов, которые пользователь выбрал в диалоге |
| `http` | `[]` | HTTPS-запросы по адресам с указанными префиксами, не больше 32 префиксов |
| `origins` | `[]` | `http_request_ex` к origin самой страницы, если он подходит под один из шаблонов (не больше 32); относительные адреса — только от него |
| `http_insecure` | `[]` | `http_request_ex` по HTTP без TLS под точными префиксами, не больше 8 |
| `key_files` | `false` | `keys_open` хранилища по пути, который назвала страница (нужен `keys`); каждый файл — только после согласия пользователя |
| `page_files` | `false` | `page_file_read` и `page_file_write`: файлы и каталоги, которые назвала страница; каждый файл (каталог) — только после согласия пользователя |
| `page_files_ext` | `[]` | Расширения файлов, которые пишет `page_file_write` (нужен `page_files`): до 16, латинские буквы и цифры, сравниваются без учёта регистра |
| `settings` | `false` | `settings_get`, `settings_put`: настройки плагина на диске |
| `shared` | `false` | `shared_get`, `shared_put`: данные, общие для всех экземпляров плагина (а значит, для всех сайтов) в процессе |
| `builtin` | `false` | Только для модулей ядра: функции возможности `builtin`. Манифест без `builtin = true` с этим ключом — ошибка |

Окно установки показывает каждую возможность отдельной строкой: префиксы `http`, сайты `origins`, префиксы `http_insecure` со словами «незащищённое соединение», `key_files`, `page_files` с расширениями записи, `settings` и `shared` («делить данные между сайтами»). Обновление, которое добавляет возможности (новые флаги, префиксы и шаблоны, не покрытые прежними, новые расширения), снова спрашивает пользователя.

### Адреса `http`

Префикс `http` должен соответствовать правилам:

- начинается с `https://` (строчными буквами);
- без имени пользователя и пароля (`@` до пути), без query (`?`) и fragment (`#`);
- без пробелов, управляющих символов и `\`;
- путь обязателен и заканчивается `/`: `https://a.kz/` и `https://a.kz/api/` подходят, `https://a.kz` и `https://a.kz/api` — нет;
- порт можно указать; без порта — 443;
- в пути нет `;`, `%2f` и `%5c` (в любом регистре): с ними префикс не пропустил бы ни одного адреса (см. ниже);
- хост может быть `*.` и доменом не меньше чем из двух меток (`https://*.gov.kz/`): тогда подходит любой хост под этим доменом по границе метки (`a.gov.kz`, `x.y.gov.kz`), но не сам `gov.kz`, не `evilgov.kz` и не `gov.kz.evil`. Запрещены `https://*.kz/`, `https://*/`, `https://a*.kz/` и `*.` перед IP-адресом.

Адрес запроса разрешён, если он тоже `https://` без имени пользователя и без `\`, пробелов и управляющих символов, а также:

- хост совпадает с хостом префикса без учёта регистра;
- порт совпадает с портом префикса; явный `:443` равен отсутствию порта;
- путь начинается с пути префикса;
- если путь префикса не `/`, в пути запроса нет `;`, `%2f` и `%5c` (в любом регистре).

Query и fragment запроса не проверяются. Адреса разбираются как в браузерах (стандарт WHATWG URL): сегменты `.` и `..` в пути (в том числе `%2e%2e`) раскрываются до сравнения. Поэтому `https://a.kz/api/../x` не проходит под префикс `https://a.kz/api/`, а `https://a.kz/apix` не проходит, потому что путь префикса заканчивается `/`.

Закодированные `/` и `\` (`%2f`, `%5c`) и параметры пути после `;` разборщик оставляет как есть, а серверы могут раскрыть их иначе: одни декодируют `%2f` до того, как раскрыть `..`, другие отбрасывают `;…`. Тогда `https://a.kz/api/..%2fsecret` или `https://a.kz/api/..;/secret` оказались бы за пределами `/api/`. Поэтому под префиксом с путём, отличным от `/`, такие адреса запрещены.

Запрос отправляется по адресу в той форме, в которой его проверили (после разбора и раскрытия сегментов, без fragment), а не по исходной строке. Перенаправлениям программа не следует: ответ 3xx возвращается плагину вместе с `Location`, и следующий запрос плагина по этому адресу снова проходит проверку.

Примеры для префикса `https://tsp.pki.gov.kz/`:

| Адрес | Результат |
|---|---|
| `https://tsp.pki.gov.kz/tsp` | разрешён |
| `https://TSP.pki.gov.kz/x` | разрешён |
| `https://tsp.pki.gov.kz:443/x` | разрешён |
| `https://tsp.pki.gov.kz.evil/` | запрещён: другой хост |
| `https://tsp.pki.gov.kz@evil/` | запрещён: имя пользователя, хост `evil` |
| `https://tsp.pki.gov.kz:8443/` | запрещён: другой порт |
| `http://tsp.pki.gov.kz/` | запрещён: не HTTPS |

Шаблон `origins` — `https://` или `http://`, хост (или `*.` и домен не меньше чем из двух меток, как в префиксе) и необязательный порт, без пути, query и fragment: `https://*.ecc.kz`, `https://a.kz:8443`. Порт без указания — 443 или 80 по схеме.

Префикс `http_insecure` — как префикс `http`, но `http://`, только точный хост (без `*.`), порт без указания — 80: `http://ncalayer.uchet.kz:8080/`.

### `[[operations]]`: действия для окна ручных инструментов

Эта необязательная таблица нужна, чтобы плагин был виден в окне ручных инструментов, на сервере и в командной строке. **Плагин без неё в этом окне не виден** (запрещено по умолчанию). Для сайтов он работает как обычно, через WSS. Модель разрешений — [manual-plugins.md](manual-plugins.md); код — `crates/oncl-plugin/src/operations.rs`.

*Операция* — это не просто имя. Это шаблон запроса, который строит программа, плюс список импортов, сеть и для каждого применения ключа **профиль**: вид подписи, откуда берётся содержимое и какие опции программа принудительно задаёт сама.

```toml
min_core = "0.1.0-alpha.7"          # не ниже: старая программа таблицу отвергает (deny_unknown_fields), новая — по min_core

[[operations]]
name    = "sign-file"               # ^[a-z][a-z0-9-]{0,31}$, уникально; до 32 операций
module  = "example.sign"            # из `modules`
manual  = true                      # показывать в ручном окне (по умолчанию false)
server  = false                     # допускать вызов с сервера и из CLI (по умолчанию false); оба false — ошибка
request = '{"module":"example.sign","method":"signFile","args":["{file:base64}"]}'
label   = { ru = "…", kk = "…", en = "…" }   # недоверенный текст автора: 1–80 символов, без управляющих, bidi и невидимых (Cf) символов, без пробелов по краям

[[operations.params]]               # до 16; ^[a-z][a-z0-9_]{0,31}$, уникальны, все используются в request
name = "file"
kind = "document"                   # document | text | choice | flag | locale
max_bytes = 16777216                # document: 1..=MAX_DOCUMENT_BYTES (около 192 МиБ; по умолчанию 16 МиБ); text: max_chars 1..=65536 (по умолчанию 256); choice: choices (1–32)

[operations.uses]
imports     = ["keys_select", "keys_sign_cms_ex", "hash"]   # известные имена импортов; возможности манифеста обязаны их объявлять
network     = "pki"                 # "none" (по умолчанию) | "pki" | ["https://…/"] (каждый под capabilities.http)
interactive = ["keys_select"]       # ⊆ {keys_select, keys_choose, keys_flow_open, keys_flow_pick} и ⊆ imports

[[operations.uses.key]]             # не больше одной: операция применяет ключ один раз
kind     = "cms_ex"                 # raw | cms | cms_ex | xml | xml_ex | xades
content  = "param:file"             # param:<имя> (bound) | "derived"
max_uses = 1                        # единственное допустимое значение (по умолчанию 1)
[operations.uses.key.profile]       # поля зависят от вида; неизвестное поле — отказ
timestamp = "basics"
```

**Шаблон `request`.**

- Любой JSON-объект (не массив и не строка в корне).
- Подстановка — строка-значение, которая целиком равна `"{имя}"` (text, choice, locale — строка JSON; flag — булево) или `"{имя:base64}"` (document, обязательно с `:base64`). Она может стоять в значении на любой глубине.
- Подстановки нельзя ставить в ключ, внутрь строки (`"x{имя}"`) и двойными (`"{a}{b}"`). Экранирования скобок нет.
- Если в корне есть `module`, это фиксированная строка, равная `module` операции (когда плагин обслуживает несколько `modules`, корневой `module` обязателен). Если есть `method` — фиксированный простой текст без скобок. `args` необязателен и может быть массивом, объектом или любым значением; ключи `module`/`method`/`args` не требуются.
- Числа только целые. Дубликаты ключей отвергаются на любой глубине.
- Пределы: не больше 16 КиБ, 2048 значений, глубина не больше 16 (корень = 1), не больше 64 ключей в объекте, ключ не длиннее 128 байт и без управляющих и невидимых символов.
- Каждый объявленный параметр должен использоваться, каждая подстановка — называть объявленный параметр.
- Программа строит запрос из разобранного JSON одним проходом (ключи по возрастанию, числа как записаны). Длина считается до подстановки и сверяется с `max_transfer`.

Три реальные формы:

```toml
# 1. Массив args (rating1c, dogovor24, qiwi)
request = '{"module":"x.y","method":"sign","args":["{doc:base64}"]}'
# 2. Объект args (fhs, energy)
request = '{"module":"x.y","method":"sign","args":{"data":"{doc:base64}","who":{"name":"{who}"}}}'
# 3. Ключи в корне, без module и args (esf-osdkz, eproc, efactoring, market)
request = '{"method":"signPlainData","storageName":"PKCS12","data":"{text}"}'
request = '{"type":"text","data":"{text}"}'
```

**Текст как содержимое.** `content = "param:<имя>"` может называть `text`-параметр для любого вида подписи. Тогда подписываются UTF-8-байты набранного текста, а разрешение пользователя привязано к ним. Пустой текст — не содержимое (`InvalidValue`).

- В тексте, который является содержимым, `InvalidValue` вызывает любой управляющий символ, кроме `\n` и `\t` (NUL, `\r`, ESC, DEL, C1), и любой невидимый или bidi-символ (U+202A–E, U+2066–9, U+200B–F, U+2028/9, U+FEFF, U+00AD и др.; проверка — `oncl_plugin::operations::signed_text_problem`).
- Окно заменяет CRLF на LF при снятии снимка формы. Дальше текст не обрезается и не нормализуется: и отображение, и подпись берут один и тот же текст.
- Двойники символов, NBSP, пробелы по краям и NFC/NFD допустимы: окно согласия показывает текст дословно, с длиной в символах и байтах и SHA-256, и помечает пробелы по краям и не-ASCII пробелы.
- `max_chars` — от 1 до 65536 символов (до 256 КиБ байтов).
- Для `raw` и `digest` содержимое может быть только bound (из параметра); `derived` для них отвергается.

**Сеть.** Операция с `[[operations.uses.key]]` обязана объявить `network = "pki"` (иначе `NetworkNeeded`): окно ручных инструментов подписывает только с хостами PKI. `none` и список адресов для ключевой операции не принимаются. Версия канонической записи объявления — `ONCLOP2`.

**Импорты.** Каждый импорт отнесён к одному из трёх классов (новый импорт не соберётся, пока его не отнесли):

- *Разрешены:* базовые функции, `keys_select/choose/flow_open/flow_pick/describe/chain/release/terminals`, `tokens_scan` (программа отвечает «токены выключены»), `http_request[_ex]`, `tsp_*`, `ocsp_fetch`, `crl_fetch`, `cms_verify`, `xml_verify`, `ca_*`, `pkix_path`.
- *Требуют профиль:* шесть `keys_sign_*`.
- *Запрещены:* `dialog_*`, `file_*`, `page_file_*`, `keystore_*`, `settings_*`, `shared_*`, `core_*`, `keys_open`, `tokens_id_card`, `data_*`.

Остальные правила:

- `network = "none"` несовместимо с импортами, которые шлют запросы (`http_request[_ex]`, `tsp_*`, `ocsp_fetch`, `crl_fetch`, `cms_verify`, `ca_issuer`, `pkix_path`) и с профилем, который ставит метку времени (`timestamp` у cms/cms_ex, `t` у xades).
- `interactive` должен входить в `imports`, но не наоборот.
- Адреса в `network` разрешены только под `capabilities.http` (не `origins` и не `http_insecure`).
- Каждый ключевой импорт (`keys_sign_*`) требует строки `[[operations.uses.key]]` того же вида, и наоборот. Применение ключа требует `capabilities.keys`.
- При компиляции пакета `uses.imports` обязан входить в импорты WASM (`LoadError::OperationImport`).

**`derived`.** Разбирается, но пока не выполняется: `Operation::runnable()` равно `false`. Запрещено для `raw` и для `content_form = "digest"`.

**Профили.** Значения по умолчанию задаёт программа. Незаданное поле значит значение по умолчанию, отклонение от него — отказ. Полей вне списка нет, задать их нельзя.

| Вид | Поля (по умолчанию) | Запрещено |
|---|---|---|
| `raw` | нет | любые опции |
| `cms` | `attached` (false), `timestamp` (`none`; `basics`) | `kalkan` |
| `cms_ex` | `encapsulate` (false), `cosign` (`never`), `content_form` (`data`; `digest` — только bound и без `encapsulate`), `timestamp` (`none`/`basics`/`kalkan`), `certificates` (`signer`/`chain`), `output` (`der`/`base64`/`pem`), `content_type`, `message_digest`, `signing_certificate_v2` (true), `signing_time` (`now`/`none`) | `cosign` кроме `never`, `attrs.extra`, `econtent_type`, `digest`, `timestamp = custom`, `certificates = extra` |
| `xml` | `element`, `parent` (только с `element`) | — |
| `xml_ex` | `element`, `parent`, `placement` (`document_element`/`first_child_of_document`/`parent`; `parent` ⇔ задан `parent`), `namespaces`, `other_prefix_uri`, `signature_method`, `digest_method` (из известных URI), `c14n`, `strip_whitespace`, `base64_line_breaks`, `output` (`as_is` / `{ serialize = { declaration, standalone_no, trim } }`), `transforms` (список `"enveloped"` / `{ c14n = "…" }`: `enveloped` первым, затем не больше одной каноникализации; пустой список отвергается, целый документ — только с `enveloped`) | `signature_id`, `signing_time_object`, чужие URI методов |
| `xades` | `level` (`b`/`t`; `lt`/`lta` отвергаются при разборе), `tsa` (`basics`/`kalkan`), `signature_method`, `digest_method` | `chain`, custom TSA, чужие URI |

`element` и `parent` — абсолютный XPath (начинается с `/`) либо `param:<имя>` (text-параметр: введённый пользователем текст показывается в согласии). XPath: не больше 1024 байт, без управляющих, bidi и невидимых символов; `param:` допустим только для text-параметра с `max_chars` не больше 256. Введённый текст проверяется до построения канонической записи профиля.

Профиль обязан покрывать все поля структур ABI подписи (`SignRawArgs`, `SignCmsArgs`, `SignCmsExArgs`, `SignedAttrs`, `SignXmlArgs`, `SignXmlExArgs`, `XadesArgs`). Тест разбирает эти структуры и не даёт добавить поле, пока его не отнесли к профилю или к «должно быть по умолчанию». Вызов с `cosign = auto` разбор не отвергает: профиль остаётся `never`, и программа приводит его к `never` на вызове.

**Каноническая запись профиля** нужна, чтобы подтверждение пользователя относилось именно к тому, что будет подписано (вход для `options_sha256` в билете `PluginUse`). Устройство: магия `ONCLOPT1\0`, вид (1 raw, 2 cms, 3 cms_ex, 4 xml, 5 xml_ex, 6 xades), затем поля вида в порядке таблицы: `id u8` и значение. Значения: bool — байт 0/1; перечисление — один байт с явным значением; строка — длина `u32` big-endian и UTF-8; необязательное — 0 или 1 и значение; список — счётчик `u32`. Записываются **все** поля, значения по умолчанию тоже, поэтому незаданное поле и явное значение по умолчанию кодируются одинаково, а двух разных профилей с одинаковой записью нет. Поле `param:<имя>` кодируется как фиксированный текст, который дал параметр (без значения — `None`). `Operation::canonical()` кодирует всё объявление, кроме `label`, для обнаружения изменений.

**Вызов объявленных операций.**

- Плагин, который объявляет `[[operations]]`, для сайтов по-прежнему работает через WSS, со старыми диалогами согласия и без билета. Объявления ограничивают только окно ручных инструментов, сервер и CLI.
- Через них (`Engine::plugin_call`) вызывается только объявленная операция. Каждое применение ключа получает билет, а без билета применение отклоняется до любой проверки. Импорты вызова ограничены импортами операции.
- Плагин, объявивший хотя бы одну операцию, вызывается через `plugin_call` только под объявленным именем (иначе `PermissionDenied` до запуска модуля).
- Сервер пропускает такой вызов с ошибкой в stderr, CLI отказывает: серверные и CLI-разрешения пока не реализованы.

**Обновления.** Обновление плагина требует нового явного согласия пользователя, если у операции появилось применение ключа (новый вид, содержимое или профиль), изменились `module`/`request`/параметры/`manual` у операции с ключом, добавлен импорт с возможностью, расширена сеть или включён `server`. Согласия не требуют: смена `label`, пробелы в `request` (JSON сравнивается как JSON) и сужение (меньшие лимиты параметров, меньше выбора, уже сеть, `manual` выключен, убранные импорты). Если установленный пакет не читается, всё, что объявляет новая версия, считается добавленным и ждёт согласия. Откат с отозванной версии проверяется так же.

**Как установленные плагины попадают в окно.** Из установленных плагинов (включённых, не отозванных, с читаемым пакетом — sha256 файла сверяется) строится реестр операций для окна. Для операции без `network = [urls]` разрешены хосты PKI (`NCA_PKI_HOSTS`) и, при `network = "pki"`, точные адреса службы меток времени (TSP) и OCSP НУЦ. Окну отдаётся список операций (в нём имя операции — слова программы, а `label` и название плагина — недоверенный текст автора) и список плагинов, у которых пакет не читается.

**Согласие при установке и обновлении.** Окно установки пакета с `[[operations]]` показывает на каждую операцию доверенный блок. Он строится только из проверенных полей: идентификатор операции, вид применения ключа, профиль подписи (показаны существенные и любые отличные от умолчания поля: `cosign=never`, вывод `cms_ex`, выключенные атрибуты, место и параметры XML, алгоритмы, уровень и TSA XAdES), сеть, признак `server` и для обновления — что именно новое или шире. Свободный текст манифеста (метка, XPath профиля) показывается отдельно, в рамке «Плагин называет это так», как обычный текст: метка не длиннее 60 знаков, XPath не длиннее 120, затем «…». Блок операций стоит перед списком возможностей. Обновление, удержанное ради согласия, спрашивается в том же окне (кнопка «Обновить»); ответ привязан к sha256 показанного пакета, и если на его место пришёл другой, обновление остаётся ждать и показывается заново. Тексты на казахском ждут проверки носителем языка.

### Как работает вызов в ручном окне

Страница «Плагины» окна ручных инструментов — пункт боковой панели рядом с «Подписать» и «Проверить». Шаги: список → форма → ключ → подтверждение → выполнение → результат.

- **Список.** Операции установленных плагинов. Название плагина и `label` показаны только в рамке «слова самого плагина». Операция без применения ключа показана, но не открывается: подтверждать нечего. У плагина без операций для окна одна строка с причиной, которую программа вычислила по манифесту (нет операций; нет операций для ручного окна; неподдерживаемая сеть; плагин не найден в реестре). Нечитаемый пакет — строка без причины (причина в журнале).
- **Форма.** Строится из `[[operations.params]]`: document (файл, читается один раз в память и сравнивается с пределом `max_bytes`), text (предел в символах), choice (выбор не подставляется по умолчанию), flag, locale.
- **Ключ.** Тот же поток, что на странице «Подписать»: файл хранилища, пароль, список сертификатов. Пароль убирается из поля при отправке, держится до выбора сертификата (страница ключа закрывается через 300 с простоя), затем обнуляется и в журнал не пишется.
- **Подтверждение.** Программа сама считает, что будет подписано, и показывает сводку: операцию, id и версию плагина, SHA-256 пакета, вид применения ключа и профиль словами, сеть с адресами, имя файла «выбран вами», размер и полный SHA-256, ключ (имя, серийный номер, CN, отпечаток, срок). Введённые значения идут отдельным блоком «не входит в то, что разрешается». Если сводка не совпадает с объявленной операцией, подтверждение не показывается. Кнопка называет действие («Подписать плагином {операция}»), включается после подготовки и 600 мс тишины, фокус при открытии — на «Отмена», Enter без Tab ничего не подтверждает, Escape отменяет с любого шага.
- **Выполнение.** Согласие действует 120 с и не запоминается: на каждый вызов — подтверждение заново. Перед запуском модуля программа заново выводит применение ключа из переданных параметров и сверяет с одобрением; если документ, текст, ключ, операция или вызов другие либо одобрение просрочено — отказ до запуска модуля. Предел выполнения — 300 с от подтверждения. Параллельно идёт один одобренный вызов.
- **Результат.** Успех показывается, только если ключ применён, нет отказов и ошибки; при этом сказано, что подпись в ответе программа не проверяла. Если ключ применён, но плагин упал — не успех. Если неизвестно, применён ли ключ, сказано считать, что применён. Ответ плагина показывается только в его рамке, без управляющих и bidi-символов, не больше 2000 символов. Ответ успешного вызова можно сохранить кнопкой «Сохранить ответ плагина (не проверен этой программой)»: в один `.json`-файл, весь как получен, без извлечения, очистки и обрезки. Программа не знает, где в ответе подпись (у каждого порта своя форма). Имя файла предлагает программа (из id операции и плагина, `[a-z0-9._-]`, не длиннее 96 знаков, всегда `.json`), место выбирает пользователь; запись атомарна и существующий файл не заменяет.

Для плагина слой ручного окна выглядит как обычный вызов:

- `keys_select`, `keys_choose`, `keys_flow_open`, `keys_flow_pick` отвечают про один и тот же ключ, который пользователь уже привязал в окне. Фильтр плагина проверяется по сертификату этого ключа; не подходит — `None`. Ответ `None` ключ у плагина не отнимает: фильтр лишь совещательный, а полномочие даёт только билет и одобрение пользователя. Фильтр считается не чаще раза на разный фильтр за вызов, не больше 16 разных фильтров за вызов (сверх — `limit`), ожидание ответчика OCSP — до 6 с.
- `keys_terminals` — `[]`, `tokens_scan` — `enabled = false`, `reply_drop` разрешён и безвреден.
- `keys_open` — trap `Denied`. `dialog_*`, `file_*`, `keystore_*`, `core_open_window` — trap `InteractionRequired`, как при вызове без интерфейса: плагин не отличает ручное окно от настоящего вызова.
- Все остальные импорты идут обычным путём. Сервер и CLI этот слой не используют.
- Плагин получает только handle — номер привязанного ключа; handle других ключей — отказ. `keys_release` привязанного handle ничего не делает.

## ABI

Версия ABI — `1` (`oncl_pdk::abi::ABI_VERSION`). Плагин — модуль WebAssembly для `wasm32`: 32-битная линейная память, без `start`-функции. Модуль экспортирует:

| Экспорт | Тип | Что делает |
|---|---|---|
| `memory` | память | Линейная память плагина |
| `oncl_abi_version` | `() -> i32` | Возвращает версию ABI; другая версия — плагин не загружается |
| `oncl_alloc` | `(len: i32) -> i32` | Выделяет `len` байт и возвращает адрес; `0` — выделить не удалось |
| `oncl_free` | `(ptr: i32, len: i32)` | Освобождает буфер, который вернул `oncl_alloc` |
| `oncl_process` | `(ptr: i32, len: i32) -> i64` | Отвечает на один запрос |

Экспорты проверяются при загрузке вместе с точными типами. Каждый импорт модуля должен быть функцией программы (host-функцией) из модуля `oncl` с типом `(ptr: i32, len: i32) -> i64`. Импорт функции, которой нет в ABI, — ошибка загрузки. Импорт функции возможности, которую манифест не заявил, — тоже. Программа связывает только функции заявленных возможностей.

Все значения передаются в CBOR, в той форме, в какой их пишет serde (крейт `ciborium`). Плагину на другом языке нужно знать её точно:

- структура — map с ключами-строками, равными именам полей (`{"request": …, "origin": …, "locale": …}`); поле со значением по умолчанию (в `oncl_pdk::abi` помечено `#[serde(default)]`) можно не передавать;
- байтовая строка — байтовая строка CBOR (major type 2), а не массив чисел;
- `()` и `None` — `null`, `Some(v)` — просто `v`;
- перечисление без данных (`ErrorCode`, `Level`, `Action`, `MessageKind`, `Method`) — текстовая строка с именем варианта в `snake_case`: `"denied"`, `"warn"`, `"key_info"`;
- результат host-функции `HostResult<T>` (`Result` в Rust) — map из одной пары: `{"Ok": значение}` или `{"Err": {"code": "invalid", "message": "…"}}`.

Результат типа `i64` — это `(ptr << 32) | len`: адрес и длина CBOR-байтов в памяти плагина.

Как проходит вызов `oncl_process`:

1. Программа кодирует `Input { request, origin, locale }`: запрос страницы, `Origin` соединения (если есть) и язык окон OpenNCALayer (`"ru"`, `"kk"` или `"en"`). Запрос — текст кадра до конца его первого объекта JSON, как его читает `new JSONObject` оригинала. Он может быть в нестрогой форме org.json: одинарные кавычки, слова без кавычек, `;` между парами, запятая перед `}`. Плагин, который читает запрос через `serde_json` (как `oncl_pdk::invoker::invoke`), отвечает на такой запрос `GENERAL_ERROR`.
2. Программа вызывает `oncl_alloc`, записывает `Input` в полученный буфер и вызывает `oncl_process(ptr, len)`. Буфер теперь принадлежит плагину.
3. Плагин возвращает `Output { response }` — ответ, который уйдёт странице как есть, — в буфере из своего `oncl_alloc`. Программа читает его и вызывает `oncl_free`.

Host-функция получает аргумент `(ptr, len)` в памяти плагина (буфер остаётся у плагина). Результат `HostResult<T>` — `Ok(T)` или `Err(HostError { code, message })` — записывается в буфер, который программа берёт у `oncl_alloc` плагина; этот буфер плагин освобождает сам. Host-функцию можно вызывать только из `oncl_process`. Вызов из `oncl_alloc` или `oncl_free`, пока их вызывает программа (в том числе пока она выделяет буфер под результат другой host-функции), — trap.

Программа читает и пишет память плагина только с проверкой границ. Буфер за пределами памяти, `0` из `oncl_alloc` и `Output`, который не разбирается, — ошибка плагина. Аргумент host-функции, который не разбирается, — не trap: функция отвечает `{"Err": {"code": "invalid", …}}`.

### Версии функций

У каждой host-функции есть версия программы, в которой она появилась (`Import::since`). Программа без функции не загрузит плагин, который её импортирует (неизвестный импорт — ошибка загрузки). Поэтому `min_core` плагина должен быть не ниже `since` всех его импортов.

Новые функции ABI добавляются новыми импортами со своими типами, `ABI_VERSION` остаётся `1`. Аргументы и результаты существующих функций расширяются только так, чтобы прежний плагин этого не заметил: новым полем, которое можно опустить (нет поля — значение по умолчанию), и новым вариантом, который бывает только в ответ на новое значение аргумента (`tsp_stamp`: `signers = of_cert` — `no_signer`).

| Функции | `since` |
|---|---|
| `log`, `now`, `random`, `cert_info`, `keys_choose`, `keys_sign_cms`, `keys_sign_raw`, `keys_sign_xml`, `keys_release`, `dialog_message`, `dialog_confirm`, `file_open`, `file_save`, `http_request` | `0.1.0-alpha.3` |

### Экземпляры

Экземпляр плагина создаётся на сессию — одно WebSocket-соединение или один виртуальный сокет моста — и живёт до её закрытия. Состояние плагина (глобальные переменные, выделенная память, ключи) сохраняется между запросами сессии, другие сессии его не видят. Сессия `0` (без сессии) получает экземпляр на один вызов.

В процессе живёт не больше 64 экземпляров, и их линейная память вместе (как она измерена при создании экземпляра и после каждого вызова) не больше бюджета памяти. При нехватке закрывается давно не использованный незанятый экземпляр, а если заняты все — запрос, которому нужен новый экземпляр, получает `PLUGIN_ERROR`. Память экземпляра WebAssembly не уменьшается, поэтому экземпляр, чья память после вызова больше порога, закрывается, и следующий запрос сессии получает новый.

## Ошибки

Если плагин не справился с запросом, страница получает:

```json
{"success":false,"errorCode":"PLUGIN_ERROR"}
```

Так бывает, если: плагин попал в trap (в том числе паника гостя), кончилось топливо, память выросла бы сверх лимита, буфер вышел за пределы памяти или за лимит, ответ не разбирается как `Output`.

Экземпляр после такой ошибки больше не вызывается: следующий запрос сессии получает новый экземпляр. Причина пишется в журнал.

**Обрыв без ответа.** Если плагин во время запроса вызвал `reply_drop`, ответ не отправляется, а соединение закрывается так же, как на запрос, который не является объектом JSON: TCP-соединение — без кадра Close, виртуальный сокет моста — кадром `close`, после которого расширение закрывает сокет страницы с кодом 1006. Так оригинальные модули отвечали на исключение, выброшенное до ответа. Флаг действует только на текущий вызов; `Output` плагин возвращает всё равно (если он не разбирается — `PLUGIN_ERROR`, обрыва нет). Встроенный модуль при сбое тоже обрывает соединение, см. [Встроенные модули](#встроенные-модули).

**Ошибка host-функции** — не ошибка плагина: плагин получает `HostError` и решает сам, что ответить странице.

| Код | Когда |
|---|---|
| `denied` | Не разрешено: адрес вне префиксов `http`, адрес TSA, OCSP или CRL вне хостов PKI |
| `invalid` | Неверные аргументы: CBOR не того типа, неизвестное хранилище, handle, за которым нет ключа |
| `limit` | Превышен лимит: размер, число ключей, длина текста |
| `failed` | Операция не удалась: ввод-вывод, сеть, подпись |

Отказ пользователя — не ошибка: выбор ключа и открытие файла возвращают `None`, вопрос — `false`, сохранение — `None`.

`HostError` может нести поле `cause` — стабильную строку `<область>.<вариант>` (константы `oncl_pdk::abi::cause`, весь список — `cause::ALL`). По ней плагин отличает сбои программы друг от друга так, как прежние модули различали варианты ошибок. Поле необязательно: программа без него его не пишет, плагин без него его не читает, а ошибка без причины кодируется теми же байтами, что и раньше. `message` у таких ошибок — текст ошибки программы.

| Область | Причины | Где |
|---|---|---|
| `cms` | `no_encapsulated_data`, `unknown_algorithm`, `malformed`, `cert_not_found`, `digest_mismatch`, `bad_signature`, `signing_certificate_mismatch`, `constraint` | `keys_sign_cms`, `keys_sign_cms_ex`, `tsp_stamp` (CMS не читается) |
| `xml` | `parse`, `doctype`, `too_large`, `too_deep`, `xpath`, `constraint`, `unsupported_algorithm`, `no_signature`, `bad_digest`, `bad_signature` | `keys_sign_xml`, `keys_sign_xml_ex`, `keys_sign_xades` |
| `key` | `malformed`, `unknown_key_algorithm`, `unsupported`, `mismatch`, `bad_signature`, `not_exportable`, `token` | `keys_sign_raw`; сбой ключа внутри CMS или XML — тоже причина `key.*` |
| `tsp` | `http`, `status`, `content_type`, `rejected`, `nonce_mismatch`, `imprint_mismatch`, `unsupported_imprint_algorithm`, `policy_mismatch`, `no_tsa_certificate`, `clock_skew`, `malformed` | метка времени `keys_sign_cms`; неверный CMS внутри — причина `cms.*` |

## Встроенные модули

Четыре модуля — `kz.gov.pki.knca.basics`, `kz.gov.pki.knca.commonUtils`, `kz.gov.pki.knca.applet.Applet` и `kz.gov.pki.ncalayerservices.accessory` — это такие же гости WebAssembly с тем же ABI, но вшитые в программу (`oncl_plugin::Builtins`). Нативного кода у них нет.

Для них ABI 1 расширен без нарушения совместимости (`since` 0.1.0-alpha.5):

- `call_locale` и `HostError.cause`;
- потоки выбора ключа `keys_flow_open`/`keys_flow_pick`, `keys_describe`, `tokens_scan`, `dialog_reader`, `file_choose_kind`, `pkix_path`, `SignerSel::OfCert` и `SignCmsExArgs.output` — их могут вызывать и обычные плагины с нужной возможностью;
- функции возможности `builtin` — только для встроенных модулей: ядро (`core_*`), окна и файлы ключей (`dialog_csr`, `dialog_import`, `keystore_*`), держатель удостоверения (`tokens_id_card`) и данные, которые программа держит за модуль (`data_*`).

Встроенный модуль:

- читается из `plugin.toml` с `builtin = true` и `id` под префиксом `io.github.arynyklas.openncalayer.builtin.` — только из самой программы, не из пакета;
- не устанавливается и не удаляется, его нет в окне «Плагины». Плагин не может занять имя его модуля (`ModuleTaken`, владелец `OpenNCALayer`);
- исполняется с доверием программы (`Trust::Builtin`): окна без строки источника (`detail` выбора ключа — без имени плагина), `page_file_read` читает файл без окна согласия, метки времени, OCSP и CRL идут через транспорт программы к любому адресу, как у прежних модулей, а TSA `basics` — та, что задана программе (`HostServices.tsa`). Доступны функции возможности `builtin`;
- обновляется только вместе с программой.

**Как вшиты.** Модули лежат в программе парами `plugin.toml` + `plugin.wasm` (не пакетами `.onclp`). Их собирает `build.rs` (`oncl-builtins-build`, профиль `builtin-wasm`, цель `wasm32-unknown-unknown`) или берёт готовыми из каталога `ONCL_BUILTINS_DIR` со сверкой `SHA256SUMS`, `SOURCE-SHA256` (исходники и тулчейн) и манифестов рабочего дерева. Путей машины в модулях нет: места паник без имён файлов (`-Zlocation-detail=none`), остальные пути — под переотображёнными префиксами. `version` и `min_core` манифеста равны версии программы. sha256 каждого модуля пишется в журнал при старте, а `openncalayer builtins` печатает строки `<id> <версия> <sha256 plugin.wasm> <sha256 plugin.toml>`. Модуль, который не загрузился при старте, — фатальная ошибка: код выхода 1, и новая версия откатывается проверкой здоровья обновления.

Модули и их крейты:

| Модуль | Крейт | Особенности |
|---|---|---|
| `kz.gov.pki.ncalayerservices.accessory` | `oncl-builtin-accessory` | не использует `data_*`, запросы получает как есть |
| `kz.gov.pki.knca.basics` | `oncl-builtin-basics` | — |
| `kz.gov.pki.knca.commonUtils` | `oncl-builtin-commonutils` | язык окон — общий для процесса ключ `locale` в `shared` |
| `kz.gov.pki.knca.applet.Applet` | `oncl-builtin-applet` | модуль по умолчанию; число оставшихся попыток PIN — общий для процесса ключ `try_count` в `shared`; документ `signXml` держит программа; токен получает только PIN, введённый в окне программы |

**Экземпляры.** Они не привязаны к сессии. Вызов берёт любой незанятый экземпляр модуля или создаёт новый; после вызова экземпляр отпускает ключи, пароли, согласия и PIN страниц и возвращается в пул. Незанятых экземпляров на модуль хранится не больше двух; экземпляр, чья память после вызова больше порога, закрывается. Живых экземпляров модуля (занятых и незанятых) не больше лимита; когда заняты все, вызов ждёт, пока один освободится, как нативный модуль ждал очереди окон. Встроенных модулей не больше четырёх. Пул отдельный от пула плагинов и не делит с ним лимит в 64 экземпляра. Общее для процесса состояние модуль держит в `shared_*`.

**32-битные системы** (Windows 7 x86: 2 ГиБ адресного пространства). Сборка проверяет, что вместе умещаются: экземпляры встроенных модулей при наибольшей памяти (4 × 4 × 16 МиБ), экземпляры плагинов (64 × 16 МиБ), копии аргумента и результата host-функции встроенного модуля, данные, которые держит программа (256 МиБ), один ответ со вставленными данными (не больше 128 МиБ), одно входящее сообщение WebSocket наибольшего размера (256 МиБ), куча чтения этого сообщения (16 МиБ) и запас 80 МиБ на код и кучу. Вне этой суммы остаются копии буферов host-функций плагинов, сообщения других соединений и кадр, в который ответ копируется после вызова. Документы держит программа, поэтому экземпляру хватает 16 МиБ, и живых экземпляров модуля четыре: пока одна страница держит окно модуля, вызовы других страниц без окон отвечают сразу.

**Сбой** встроенного модуля (trap, топливо, память, неверный `Output`, паника программы) — это не `PLUGIN_ERROR`: соединение обрывается без ответа, как при панике прежнего нативного модуля, причина пишется в журнал на уровне `error`. Экземпляр закрывается, следующий вызов получает новый.

**Чтение запроса.** Кадр читается так, как читает `new JSONObject` оригинала (`orgjson::scan`):

- вложенность не глубже 127 уровней;
- повтор ключа в любом объекте — ошибка;
- значение ключа `module` не строится (объект или массив в нём читается и отбрасывается);
- куча читателя ограничена (`orgjson::SCAN_BUDGET`: 16 МиБ на 32-битных системах, 256 МиБ на 64-битных). В неё входят ключи читаемых объектов (около 100 байт на ключ), текст ключей и слов, не взятых из кадра как есть (с escape-последовательностями или без кавычек), и значение `module`.

Кадр, которому нужно больше (на 32-битных системах — больше ста тысяч ключей в открытых объектах сразу), считается текстом, который org.json не прочитает: соединение обрывается без ответа. Модуль читает свою копию запроса отдельно, без этого предела, в пределах своей памяти. Запрос, который длиннее буфера между программой и модулем, до копирования и кодирования не доходит: соединение обрывается.

| Что | Лимит встроенного модуля |
|---|---|
| Линейная память экземпляра | 2 ГиБ на 64-битных системах, 16 МиБ на 32-битных (документы держит программа; пакет — до 35 000 документов длиной до 1 КиБ в запросе) |
| Память экземпляра, после которой он закрывается по окончании вызова | 64 МиБ на 64-битных системах, 8 МиБ на 32-битных |
| Незанятые экземпляры на модуль | 2 |
| Живые экземпляры на модуль | 32 на 64-битных системах, 4 на 32-битных |
| Топливо на вызов | 200 000 000 000 |
| Буфер между программой и модулем | 512 МиБ на 64-битных системах, на 32-битных — как память экземпляра |
| Данные, которые программа держит за модуль (`data_*`) | за вызов 2 ГиБ на 64-битных системах и 256 МиБ на 32-битных; за все вызовы процесса 8 ГиБ и 256 МиБ |
| Ответ со вставленными данными | 2 ГиБ на 64-битных системах, 128 МиБ на 32-битных; длиннее — обрыв соединения |

### Производительность

Замеры лежат в `crates/oncl-builtin-tests/tests/bench.rs` (тесты `#[ignore]`: `cargo test --release -p oncl-builtin-tests --test bench -- --ignored --test-threads=1`, результаты — в `target/builtins-bench.json`). Метод: медиана 7 прогонов после прогрева, окна по сценарию без задержек, фиксированные часы. «Нативный» — работа прежнего нативного `basics`, которую тест повторяет сам (выбор ключа, `oncl_pki`, разбор и запись JSON); второе сравнение — с прямыми вызовами `oncl_pki`. Пороги проверяет сам тест; в CI его гоняет job `bench` в `ci.yml` (только вручную, на `windows-2025`). Пределы — `tests/limits.rs` (64 и 32 бит; CI гоняет его и на `i686-pc-windows-msvc`).

Таблица снята не на CI, а на машине разработчика (Intel Core i9-14900KF, Windows 11 x64, сборка release). На машине, занятой другими сборками, отношения заметно хуже (у `cms` 64 МиБ — до 1,7 вместо 1,2), поэтому пороги рассчитаны на тихую машину.

|---|---|---|---|---|---|
| `basics` `cms`, RSA, присоединённая | 1,03 / 0,69 | 5,7 / 4,2 (1,35) | 68 / 55 (1,24) | 282 / 242 (1,17) | +15 мс; 1,5; 2,5; 2,5 |

Прочее: загрузка всех модулей — 10 мс (порог 250), вызов на новом экземпляре — 0,5 мс (порог 20), окно 32 ключей с живыми проверками OCSP — не позже нативного (разница −11 мс, порог +30), вшитые `plugin.wasm` вместе — меньше 1 МиБ (порог 4).

Документы держит программа (функции `data_*`, см. раздел [`builtin`](#builtin)), а модуль их не копирует. Поэтому его память — 1,1 МиБ при любом размере данных, а топливо на вызов от размера данных не зависит (около 1,7 млн единиц и при 1 КиБ, и при 64 МиБ). На 32-битных системах `basics` подписывает `cms` с данными 64 МиБ, а `commonUtils` — файл страницы 64 МиБ. Ответ с CMS данных самого большого сообщения больше 256 МиБ проходит на 64-битных системах. Программа сама кодирует CMS ответа (`SignCmsExArgs.output`), а PDK освобождает буфер `Input` до вызова обработчика.

**Как программа держит данные модуля (`data_*`).** Модуль не копирует большие документы через интерпретатор: данные держит программа, а модуль передаёт только маркеры.

- *Подмена на маркеры.* Перед вызовом программа сохраняет у себя и заменяет маркерами строки-значения запроса: не короче `DATA_KEPT_STRING_MIN` (1 КиБ), а в запросе длиннее `DATA_KEPT_LARGE` (1 МиБ) — не короче `DATA_KEPT_SHORT_MIN` (64 байта; ключи объектов — никогда), если вместе они не короче `DATA_KEPT_MIN` (16 КиБ). Длина строки — длина её JSON-текста между кавычками, escape-последовательности — как записаны. Маркер — префикс вызова `oncl-data:<32 случайные hex-цифры>:` (`Input.data_prefix`; странице он неизвестен) и номер. Так в программе остаётся и один длинный документ, и пакет коротких (`signXmls`, массивы `data`).
- *Пакеты.* На 32-битных системах экземпляру в 16 МиБ хватает пакета до 35 000 документов длиной до 1 КиБ; пакет подписывается целиком (измерено: 38 000 документов по 1000 байт, 39 000 — по 40 байт). Ответ с подписями не длиннее `BUILTIN_MAX_REPLY`, поэтому пакет более длинных документов короче. Короткие документы (меньше 64 байт) остаются в памяти модуля, и она, а не ответ, ограничивает их число.
- *Что отклоняется.* Запрос, который вместе с маркерами длиннее буфера между программой и модулем, и запрос, строки которого вместе с записью о каждой (`KEPT_ENTRY_COST`) не умещаются в то, что программа держит за вызов, отклоняются до копирования, ключей и кодирования: соединение обрывается.
- *Что переписывается.* Только запрос, который является корректным JSON (с проверкой каждой escape-последовательности: одиночный суррогат вроде `\ud800` делает запрос некорректным). Остальные байты запроса не меняются; некорректный запрос модуль получает как есть и отвечает на него, как на короткий. Запросы переписываются только модулю, который импортирует хотя бы одну функцию `data_*`.
- *Функции `data_*`.* Они принимают маркер этого вызова везде, где принимают данные (или сами данные), и сохраняют результат, возвращая его маркер. Чужой или неизвестный маркер — `invalid`.
- *Ответ.* После вызова каждая JSON-строка ответа, равная маркеру вызова, заменяется данными, записанными так, как org.json пишет строку в `JSONObject.quote` (`<\/`, как в ответах самих модулей; данные должны быть UTF-8, иначе сбой модуля — обрыв соединения). Ответ собирается в буфер ровно своей длины, не длиннее `BUILTIN_MAX_REPLY`.
- *Лимиты.* Все данные вызова отпускаются, когда вызов возвращается. За вызов программа держит не больше `BUILTIN_MAX_KEPT` байт (2 ГиБ на 64-битных системах, 256 МиБ на 32-битных), за все вызовы процесса — не больше `BUILTIN_KEPT_BUDGET` (8 ГиБ и 256 МиБ). Больше — `limit`, и соединение обрывается, когда бы лимит ни был превышен: при разборе запроса или во время подписи, что бы ни ответил модуль.
- Встроенные модули сами читают все длинные строки запроса, кроме данных подписи (`data_read`), поэтому их ответы те же, что без маркеров. Плагинам маркеров не дают: запрос плагина не переписывается, а функции `data_*` требуют возможности `builtin`.

Пароли — `Password::Text` от страницы или `Password::Secret` окна; пароли и пути в журнал не пишутся. Закрытый ключ не покидает программу.

## Capabilities

Окна плагина показывают сайт (`Origin` или `UNIDENTIFIED`) и название плагина на языке окон; текст плагина выводится как обычный текст, не как разметка. Первая host-функция, которая показывает окно, занимает общую для процесса очередь диалогов и держит её до конца `oncl_process` (после trap очередь отпускается). Поэтому окна плагина не перемешиваются с окнами basics и других модулей, а второй запрос ждёт, пока закончится первый.

**Выбор ключа.** `keys_choose` показывает те же окна, что `PKIExtras.sign`: выбор хранилища (PKCS#12 и JKS; по умолчанию оба), пароль, затем выбор ключа. В окнах видны сайт, название плагина и `detail`. `filter` — те же условия, что `signerParams` и `signingParams`: назначения ключа, ИИН, БИН, серийный номер, просроченные, цепочка CA (по умолчанию — CA НУЦ; пустая — без построения пути и OCSP) и проверка OCSP. Имена токенов в `storages` (`AKKaztokenStore`, `AKKZIDCardStore`, …) при включённой поддержке токенов ([`tokens.md`](tokens.md)) дают в окне хранилища считыватели с носителем и поле PIN; при выключенной эти строки неактивны, как в `PKIExtras.sign`.

`keys_select` добавляет к `filter` условия `more` (недоступный ключ виден в окне с причиной):

- `any_ext_key_usages` — хотя бы одно из назначений;
- `exclude_ext_key_usages` — ни одного из них;
- `knca_types` — хотя бы один тип Kalkan (`SIGNATURE`, `AUTHENTICATION`, …; неизвестное имя — `invalid`);
- `tin` — БИН сертификата, а если его нет — ИИН;
- `key_usage` — все биты из `digital_signature`, `non_repudiation`, `key_encipherment`, `key_agreement`;
- `obsolete_auth` — запрошенный clientAuth принимает и любой сертификат ГОСТ 2015-512, и sha256RSA с keyEncipherment.

`initial_path` подставляется в окно хранилища, если страница вправе назвать этот путь (локальный файл или сетевой путь, ранее выбранный пользователем в окне программы); иначе окно открывается как обычно. `order` — порядок ключей в окне по началу срока действия: `newest_first` (по умолчанию) или `oldest_first`.

**Открытие хранилища без окна (`keys_open`).** Хранилище называет плагин. `source` — `page_path` (путь от страницы), `bytes` (само хранилище) или `terminal` (считыватель токена); `password` — `text` или `secret` (id пароля из `dialog_password`, который плагин не видел).

Путь от страницы:

- разрешён только с `key_files = true` в манифесте, иначе `denied` (проверяется при вызове: функция одна и для байтов);
- читается по правилам путей страницы: устройства (`\\.\…`), каналы и каталоги — `not_found`, сетевой путь — только выбранный ранее в окне программы, файл больше 64 МиБ — `corrupt`; ничего не читается до согласия;
- пару (сайт, путь к файлу) пользователь разрешает в окне «Сайт … через плагин … просит открыть хранилище ключей: <путь>» — один раз за сессию; отказ или закрытое окно — `declined`.

Байты хранилища открываются без окна: они и пароль уже есть у страницы. Хранилища — PKCS#12 и JKS. PKCS#12 читается один раз; если в нём больше 16 ключей или больше 4 зашифрованных частей (safe), оно — `corrupt`, и это выясняется до проверки пароля и вывода ключей. Если все ключи хранилища не помещаются в свободные handle — `limit`, и не открывается ни один.

Токен (`terminal`) открывается в названном считывателе с PIN из `password`: все ключи носителя с сертификатом, по handle на каждый. PIN `text` пришёл от страницы (или плагина) и носителю уходит только с согласия пользователя. Окно называет сайт, плагин, носитель, считыватель и, если носитель их сообщает, оставшиеся попытки. Подробные правила согласия — в [tokens.md](tokens.md#pin-от-страницы). Ответы:

- поддержка токенов выключена, службы смарт-карт нет, в считывателе нет носителя этого хранилища или он извлечён, хранилище облачное — `no_device`;
- неверный PIN — `wrong_password { tries_left }`: число попыток сообщают Kaztoken, удостоверение личности и AKey; один вызов тратит не больше одной попытки;
- PIN, который носитель не примет (не ASCII; у удостоверения — не 4 символа), — `wrong_password { tries_left: None }` без единой команды носителю;
- PIN заблокирован — `blocked`; носитель без ключей с сертификатом — `no_keys`; ошибка носителя или службы — `failed`.

Handle ключа токена держит PIN в памяти программы до `keys_release` или конца экземпляра (затем память обнуляется). Каждая подпись — отдельное подключение к носителю с проверкой PIN, после которого карта сбрасывается. Если носитель отверг PIN, handle больше его не отправляет. Подпись носителя проверяется открытым ключом сертификата, прежде чем плагин её получит. Писать на токены (создавать ключи, записывать сертификаты) плагины не могут.

**Handle.** Закрытый ключ остаётся в программе: плагин получает только handle — номер ключа в своём экземпляре. Номера идут по возрастанию и не повторяются, поэтому handle после `keys_release` не может указать на другой ключ. Handle действует до `keys_release` или до конца экземпляра. Handle другого экземпляра, освобождённый или неизвестный — `invalid`.

**CMS с профилем плагина (`keys_sign_cms_ex`).** Собирает CMS по профилю плагина в одном месте с `keys_sign_cms`:

- `content` — `data` (подписываются данные) или `digest` (готовый хеш идёт в messageDigest как есть, в CMS не вкладывается);
- `cosign` — `auto` (подписанный CMS с вложенным контентом подписывается вторым подписантом, как `createCAdES`), `never` или `into` (новый подписант добавляется в данный CMS, подписывается `content`);
- `econtent_type` — OID типа содержимого (и атрибута contentType);
- `digest` — только хеш алгоритма подписи сертификата, другой — `invalid` (получатели НУЦ проверяют только эту пару);
- `attrs` — флаги contentType, messageDigest, signingCertificateV2 (SHA-256 сертификата), `signing_time { at: now | unix_ms, form: auto | utc | generalized }` и `extra` — атрибуты плагина: OID и значения готовым DER (значение, которое не разбирается как DER, и тип, который уже добавил флаг, — `invalid`). Атрибуты ложатся в DER SET в порядке сортировки. Без единого атрибута подписываются сами данные;
- `certificates` — `signer`, `chain` (цепочка `keys_chain`) или `extra` (сертификат подписанта и данные);
- `timestamp` — метка TSA на новом подписанте (как `tsp_stamp` с `replace`).

**Метки времени, OCSP и CRL.** Их запрашивает программа, а не плагин, и только у хостов PKI: `tsp.pki.gov.kz`, `ocsp.pki.gov.kz`, `crl.pki.gov.kz`, `pki.gov.kz`, `test.pki.gov.kz`, `crl.root.gov.kz`, `crl1.root.gov.kz` (на двух последних — CRL удостоверяющих центров НУЦ) и их поддоменов, по `http://` или `https://`.

- Адрес задаёт `PkiUrl`: `default` (`http://tsp.pki.gov.kz`, `http://ocsp.pki.gov.kz`), `fixed` (адрес) или `from_cert` (адрес из сертификата: OCSP — authorityInfoAccess, TSA — time-stamping в subjectInfoAccess или authorityInfoAccess; сертификат без адреса — `failed` с `other`). Адрес другого хоста, в том числе из сертификата и точки распространения CRL, — `denied`.
- Таймаут — от 1 мс до 60 с, повторов метки — не больше 10, иначе `invalid`.
- `PkiMethod`: `get` (base64 запроса после `/` как есть), `get_url_encoded` (base64 в кодировке URL, как NCALayer), `post { content_type }` (без типа — тип протокола), `post_with_path` (POST тела на адрес GET), `get_under(n)` (GET, пока закодированный запрос короче `n`, иначе POST).
- `Nonce`: `none`, `random(n)` или `value(bytes)`.
- Перенаправлениям программа при этих запросах не следует (3xx — это ответ), так что запрос не уходит с хостов PKI, даже если ответ указывает на другой адрес.
- Каждый запрос программы к хостам PKI (повтор метки, OCSP о каждом подписанте, скачивание каждого CRL) входит в лимит 64 HTTP-запросов за вызов (см. [Лимиты](#лимиты)). Сверх лимита запрос не отправляется, а результат — сетевой сбой с `kind = other`.

**Метка времени (`tsp_stamp`, `tsp_request`).**

- `TsaChoice` — `basics` (Стрибог-512, политика 1.2.398.3.3.2.6.4), `kalkan` (SHA-256, политика 1.2.398.3.3.2.6.2), оба — GET с кодировкой URL на `tsp.pki.gov.kz`, или `custom(TsaSpec { url, method, hash, policy, nonce, cert_req, retries, timeout_ms, check_skew_ms, require_tsa_eku })`.
- Ответ TSA проверяется всегда: HTTP 200 с `application/timestamp-reply`, статус granted, подпись токена, nonce, отпечаток и политика запроса (без политики — любая). С `require_tsa_eku` проверяется назначение timeStamping у подписанта токена, с `check_skew_ms` — что genTime не дальше от часов программы.
- `tsp_stamp` ставит метку на подписантов `signers` (`last`, `index(i)`, `all_unstamped` или `of_cert(сертификат)` — первого подписанта этого сертификата, как его находит Kalkan), заменяя прежнюю (`replace`) или добавляя ещё одну (`append`). В атрибут идёт токен (`token`) или весь `TimeStampResp` (`whole_response`).
- CMS, который не читается, — `invalid` с причиной `cms.*` и текстом ошибки программы.

**OCSP и CRL.**

- `ocsp_fetch` спрашивает о сертификате, издатель которого — `host_cas` (CA программы), `given` или первый из `verifies_cert`, чей ключ проверяет подпись сертификата (не найден — `invalid`). `cert_id_hash` — хеш CertID, `nonce` — расширение nonce запроса. Ответ — каким пришёл, с `BasicOCSPResponse` и статусом сертификата. С `check` ответ проверяется как проверки OCSP программы (ответчик по цепочке CA программы с OCSPSigning и nocheck, подпись, актуальность, CertID, эхо nonce), а то, что не так, — `problem` (`responder_unverified`, `ocsp_stale`, `nonce_mismatch`, `malformed`); тогда статус не сообщается.
- `crl_fetch` скачивает полный CRL из точек распространения сертификата и, если у сертификата есть FreshestCRL, дельта-CRL (без полного не используется). Статус по дельте (запись removeFromCRL — не отозван) решает поверх полного.

**Сетевой сбой** — не ошибка host-функции, а `NetFailure { stage, kind, address, detail }`: `stage` — `tsp`, `ocsp`, `crl`; `kind` — `unknown_host`, `connect`, `timeout`, `tls`, `http(status)`, `invalid_response`, `rejected(status)`, `clock_skew`, `other`; `address` — хост; `detail` — текст ошибки программы (у метки времени — как в сообщениях commonUtils).

**Проверка CMS (`cms_verify`).** Проверяет каждого подписанта отдельно и сообщает о каждой проверке `ok`, `skipped` или `fail(problem)`:

| Проверка | Что проверяет |
|---|---|
| `signature` | подпись над подписанными атрибутами и messageDigest над контентом (`data` — контент открепленной подписи; без него — `no_content`). Проблемы: `digest_mismatch`, `bad_signature`, `no_signer_cert` (в CMS нет сертификата подписанта), `malformed` (подписант не читается) |
| `ess_cert_id` | signingCertificateV2 против сертификата (`ess_cert_id_mismatch`; без атрибута — `skipped`) |
| `validity` | срок действия сертификата (`expired`, `not_yet_valid`) |
| `path` | путь через CA (`unknown_ca` — издатель не найден, `path_invalid` — путь не сходится) |
| `revocation` | статус отзыва (`revoked { at_ms, reason }`, `status_unknown` — ответчик не знает сертификат или ответ о другом, `responder_unverified`, `ocsp_stale`, `crl_invalid`, `malformed`, `net(NetFailure)`) |
| `tsp` | метка времени подписанта, если есть (`tsp_imprint_mismatch` — метка другой подписи, `tsp_invalid` — не проверяется или у сертификата TSA нет пути на её genTime) |

Параметры:

- `at` — время проверки: `now`, `signing_time` (атрибут signingTime) или `tsp_time` (genTime проверенной метки); без атрибута или метки — сейчас. Путь строится на это время, сдвинутое в срок действия сертификата (срок — отдельная проверка).
- `chain` — не задан: CA программы; `[]`: путь не строится; список: эти CA (они же доверенные для ответчиков OCSP).
- `revocation` — `none`; `embedded_ocsp` — только ответ OCSP из CMS (атрибут id-pkix-ocsp-basic `1.3.6.1.5.5.7.48.1.1` — `OCSPResponse` или `BasicOCSPResponse`, в OCTET STRING или без, подписанный или нет; или id-ri-ocsp-response в `crls`), проверенный на время `at`; `live_ocsp` — ответ из CMS, если есть, иначе ответчик сертификата (GET, CertID SHA-1); `live_ocsp_then_crl` — и CRL, если ответчик не дал проверенного ответа. Отзыв после времени проверки не считается: подпись сделана раньше.
- Ответчики и точки распространения из сертификатов спрашиваются только на хостах PKI, без перенаправлений; другой хост — `net` с `kind: other`.
- `require_key_usage` — из сертификатов, названных идентификатором подписанта, берётся первый со всеми указанными битами keyUsage. `first_signer_only` — только первый подписант.

**Как `cms_verify` работает в настольной программе.** Решения принимает единый валидатор SDK (`validate_cms`), а `cms_verify` лишь переводит его результат в `VerifyReport`. Из-за этого описание выше нужно читать с такими поправками:

1. `at` игнорируется (поле и `VerifyAt` оставлены ради совместимости проводного формата). Подписант проверяется на `genTime` проверенной заякоренной метки времени, иначе на «сейчас», но никогда на собственном `signingTime`. В профиле совместимости с NCALayer (`live_ocsp`, `live_ocsp_then_crl`) метка фиксирует время, даже если статус её TSA получить нельзя.
2. `live_ocsp` тоже обращается к CRL.
3. Недоступный статус в `live_*` — `fail(net{stage: ocsp, address: хост ответчика, kind: other})`, в режимах без сети — `fail(status_unknown)`. Ответ «unknown» неотличим от отсутствия ответа.
4. У `revoked` нет `reason` (CRLReason всегда `none`).
5. `unknown_ca` не выдаётся: ошибка пути всегда `path_invalid`.
6. `chain: []` значит «нет якорей»: `path` и `revocation` всегда `skipped`.
7. `tsp.check` остаётся `ok`, если валидатор лишь не может доказать статус TSA (`timestamp_unproven_ok`). Метка другой подписи или отозванный/неякорный TSA дают `fail`.

Из-за пункта 7 настольная программа мягче безголового режима SDK: там неподтверждённая метка — неизвестный статус, а вердикт `Valid` на этом основании невозможен. Плагин, читающий поля отчёта, увидит «всё хорошо». Плагин `k2sign` передаёт `at = signing_time`, `chain: []`, `revocation: none`: срок действия теперь проверяется на «сейчас», поэтому подпись сертификата, истёкшего после подписания, даёт `VALIDITY_EXPIRED` (раньше `ok`). Отзыв `k2sign` не проверяет.

**XML-подпись (`keys_sign_xml_ex`).** Подписывает XML так, как ждут получатели плагина. Незаданные поля дают алгоритмы, канонизацию и место подписи как у `keys_sign_xml`, но с переводами строк Santuario и байтами документа как есть. Форма `keys_sign_xml` — это `strip_whitespace` и `serialize { declaration: false, standalone_no: false, trim: true }`.

| Поле | Что значит |
|---|---|
| `placement` | `document_element` (последним ребёнком корня), `first_child_of_document` (последним ребёнком первого узла документа; если это комментарий или PI — ошибка, как у оригинала) или `parent` (в элемент XPath `parent`, только с ним) |
| `namespaces`, `other_prefix_uri` | `namespaces` (префикс → URI) и `other_prefix_uri` (URI любого другого префикса) переводят XPath на сравнение по пространствам имён: имя без префикса — без пространства имён, несвязанный префикс — ошибка. Без них имена сравниваются как написаны (и `SOAP-ENV:` — пространство SOAP 1.1) |
| `signature_method` | известный URI (RSA-SHA256 `xmldsig-more`, ГОСТ 2004 и 2015-512 Kalkan), подходящий ключу; подписи RSA-SHA1 не делаются — отказ |
| `digest_method` | URI дайджеста (по умолчанию — парный методу подписи) |
| `signed_info_c14n` | канонизация SignedInfo |
| `transforms` | `enveloped` первым, затем не больше одной канонизации; целый документ — только с `enveloped` |
| `signature_id` | атрибут `Id` подписи |
| `signing_time_object` | `ds:Object/ds:SignatureProperties/ds:SignatureProperty Id="<property_id>" Target="#<signature_id>"` с неквалифицированным `<timestamp>` и, при `target_ref`, вторая ссылка на него с теми же преобразованиями |
| `strip_whitespace` | без переводов строк между элементами подписи (без него — перевод строки после каждого элемента, как у Santuario) |
| `base64_line_breaks` | base64 строками по 76 символов с `&#13;` (`true`) или одной строкой (`false`); по умолчанию — как у Santuario: строками, если нет `strip_whitespace` |
| `output` | `as_is` (байты документа с вставленной подписью) или `serialize { declaration, standalone_no, trim }` — как запись JDK `Transformer`: своё объявление XML (`<?xml version="1.0" encoding="UTF-8"?>`, с `standalone="no"`) вместо исходного, без пробелов до первого узла, с `trim` — и по краям; остальное — исходные байты |

Ошибка подписи — `failed`.

`xml_verify` проверяет каждую подпись документа сертификатом её `KeyInfo` (более поздние подписи-дети корня не входят в то, что подписали более ранние) и возвращает их в порядке документа. Сертификат, который не читается, — пустые байты. Документ не разбирается — `invalid`.

**XAdES (`keys_sign_xades`).** Делает подпись XAdES-BASELINE (XAdES 1.3.2) всего документа: enveloped `ds:Signature` последним ребёнком корня, с `Id` и `ds:Object` с `xades:QualifyingProperties`.

- `SignedProperties` — `SigningTime` (время программы, UTC) и `SigningCertificateV2` (SHA-256 сертификата подписанта). Их подписывает вторая ссылка с `Type="http://uri.etsi.org/01903#SignedProperties"` и Exclusive XML Canonicalization.
- Уровень `t` добавляет `SignatureTimeStamp` над элементом `ds:SignatureValue` в Exclusive XML Canonicalization (TSA `tsa`, хеш — её).
- Уровень `lt` добавляет ещё `CertificateValues` (сертификаты `chain`, от издателя подписанта вверх) и `RevocationValues` о подписанте и о каждом сертификате `chain`, кроме самоподписанного корня (издатель берётся из `chain`; нет в `chain` — `invalid`). Это ответ OCSP от ответчика из AIA сертификата (`OCSPValues`), а у сертификата без адреса ответчика (как у промежуточных CA НУЦ) — CRL из его точек распространения, полный и, если есть FreshestCRL, дельта (`CRLValues`).
- Если у сертификата нет ни ответчика, ни точки распространения, CRL недоступен или не проверяется, подписи нет (`failed` со `stage = crl` или `invalid` с `crl_invalid`): пробела в данных об отзыве не бывает. Сертификат, отозванный по OCSP или CRL, — `invalid` с `revoked`.
- Метка времени, OCSP и CRL — только к хостам PKI, как у `tsp_*`, `ocsp_fetch` и `crl_fetch`.
- URI алгоритмов — по сертификату, как у `keys_sign_xml` (ГОСТ 2015-512, ГОСТ 2004, RSA-SHA256), или из `signature_method`/`digest_method`; подписи RSA-SHA1 не делаются.
- Подпись проходит `xml_verify`. Побайтное совпадение с другими реализациями XAdES не цель.

**Форма XAdES в настольной программе.** Она подписывает через историческое «проводное» API `oncl_xml::xades::sign`, а не через базовый построитель ядра (`SignRequest::xades_legacy`, `prepare_spec_source`). Поэтому её выход **не** является полным XAdES-BASELINE:

- нет обязательного `DataObjectFormat`;
- канонизация — Inclusive C14N 1.0 (`REC-xml-c14n-20010315`), а не Exclusive;
- другие `Id` подписи и ссылок.

Подписи проверяются тем же сертификатом и содержат `SignedProperties`/`SigningCertificateV2`, но байты у режимов разные. Описание выше (BASELINE, Exclusive C14N) верно для построителя ядра (безголовый режим), не для настольной программы. Различие закреплено тестом `oncl-core/tests/batch.rs::guarded_xades_legacy_b_and_the_desktop_wire_shape_differ_exactly_as_documented`.

#### Потоки выбора ключа

`keys_flow_open` и `keys_flow_pick` — окна выбора ключа по частям, с правилами, которыми различались встроенные модули. Поток живёт до конца вызова `oncl_process`; за вызов открывается не больше 4 потоков, отменённое окно хранилища тоже считается. Индикатор занятости показывается с ответа в окне хранилища до первого окна ключа потока (или до конца вызова). Правила `FlowArgs`:

- `storages` — хранилища окна в этом порядке, повторы остаются; пустой список — окно без хранилищ (в отличие от `keys_choose`, где пустой список — PKCS12 и JKS); неизвестное имя — `invalid`;
- `readers`: `live` — считыватели с носителем, найденные при открытии окна (при включённой поддержке токенов); `fixed([{ storage, reader }])` — эти, первым первый; каждый должен сейчас держать носитель своего хранилища, иначе `invalid`; `none` — строки токенов неактивны. После ошибки токена окно открывается снова с тем же считывателем (у `live` — только для ответа токеном), после ошибки файла — с тем же путём;
- `start`: `recent` — последний открытый файл, `page(путь)` — путь страницы, если страница вправе его назвать (иначе окно открывается пустым, а не с ошибкой; длина пути не ограничена), `empty`; `remember` — путь открытого файла становится последним (считыватель не запоминается);
- `detail` — строка обоих окон до 1 КиБ, у плагина с его названием впереди;
- `non_empty_password` — пустой пароль отвергается; `inner_password_policy` — пароль ключей внутренних систем: 8–32 символа, латинские заглавная и строчная, цифра и один из `#$^+=!*()@%&_-`; `same_storage` — ответ не предложенным хранилищем отвергается до чтения;
- `file`: `open` — любой файл, который открывает система; `chosen` — обычный файл на диске до 64 МиБ, в том числе на сетевом диске, но не устройство;
- `knca_types` — в окне только ключи этих типов Kalkan (неизвестный тип — `invalid`); `none` — ошибка окна хранилища, когда ключей не осталось (`no_keys`, `no_signing_keys`, `no_auth_keys`); `empty_is_none` — пустое хранилище тоже получает её;
- `order` — `store`, `newest_first`, `oldest_first` (по notBefore); `checks` — `settled` (любой ключ можно выбрать) или `live { filter, more }` (условия `keys_select` и OCSP, окно ключа следит за проверками, которые начинаются при первом выборе);
- `skip_blocked_reader` — считыватель, носитель которого ответил «PIN заблокирован», в этом потоке больше не пробуется.

### `dialogs`

| Функция | Аргумент | Результат |
|---|---|---|
| `dialog_message` | `MessageArgs { kind, text }`, `kind` — `info`, `warning`, `error` | `()` — когда пользователь закрыл окно |
| `dialog_confirm` | `ConfirmArgs { text }` | `bool`: `true` — «Да»; «Нет» и закрытое окно — `false`. Кнопка по умолчанию — «Нет» |
| `dialog_password` | `PasswordArgs { title, label, ok, cancel, allow_empty }` | `Option<SecretRef { id }>` — пароль остаётся в программе, плагин получает его номер для `keys_open`; отмена — `None` |
| `dialog_choice` | `ChoiceArgs { kind, title, text, buttons, default, options }` | `Option<u8>`: номер нажатой кнопки; со списком `options` — номер выбранного пункта, если нажата первая кнопка; закрытое окно, другая кнопка или ничего не выбрано — `None` |

Окно пароля показывает сайт, название плагина, заголовок, текст и кнопки плагина; без `allow_empty` «ОК» не принимает пустой пароль. Пароль живёт в экземпляре и годится только для `keys_open` этого экземпляра. Экземпляр держит 8 последних паролей: девятый вытесняет самый старый, и его номер дальше — `invalid`, как и неизвестный номер; номера не повторяются.

Окно выбора показывает сайт, название плагина, заголовок плагина (без него — вид сообщения), текст как обычный текст, от 1 до 3 кнопок слева направо (`default` — кнопка Enter) и список до 32 пунктов. Текст до 16 КиБ, заголовок, кнопки и пункты до 1 КиБ; иначе — `invalid`, окно не показывается.

### `files`

| Функция | Аргумент | Результат |
|---|---|---|
| `file_open` | `()` | `Option<OpenedFile { path, data }>` — файл, который пользователь выбрал в системном окне |
| `file_save` | `SaveArgs { suggested_name, data }` | `Option<String>` — путь, куда пользователь сохранил |
| `file_choose_kind` | `FileKindArgs { kind, directory }`, `kind` — имя `FileChooser.FileType` оригинала (`P12`, `XML`, `ALL`, …) или пустое для папки | `Option<String>` — путь существующего файла или папки, который выбрал пользователь, без чтения; путь, которого нет, и отмена — `None`; неизвестный тип (любой длины) — `invalid` с `cause = file.unknown_kind`. Начальная папка `directory` — только та, что страница вправе назвать; длина её не ограничена |
| `file_choose` | `ChooseFileArgs { mode, title, filters, initial_dir }`, `mode` — `open` или `directory` | `Option<ChosenPath { path, size }>` — путь, который выбрал пользователь, без чтения; `size` — размер файла, у каталога `None` |
| `file_open_ex` | `ChooseFileArgs` с `mode = open` | `Option<OpenedFile>` — как `file_open`, с заголовком, типами файлов и начальным каталогом плагина; `directory` — `invalid` |

Плагин не называет пути сам: файл выбирает пользователь. Читается только обычный файл на диске (не канал и не устройство), не больше 64 МиБ. Сохранение предлагает только имя файла из `suggested_name` (без каталогов) и пишет атомарно: через временный файл рядом и переименование. Типы файлов — до 16, у каждого до 16 расширений из латинских букв и цифр (приводятся к строчным). Начальный каталог берётся, только если страница могла бы его назвать (как для `page_files`) и это каталог. Выбранный сетевой путь (`file_choose`, `file_open_ex`) становится путём, который страница может назвать дальше.

### `page_files`

| Функция | Аргумент | Результат |
|---|---|---|
| `page_file_read` | `PagePathArgs { path }` | `PageRead`: `ok(OpenedFile)`, `not_found`, `too_large`, `declined` |
| `page_file_write` | `PageWriteArgs { dir, name, data }` | `PageWrite`: `written(path)`, `invalid`, `declined` |

Путь, который назвала страница, проходит те же правила, что у встроенных модулей: устройства (`\\.\`, `\\?\GLOBALROOT`) — никогда, сетевой путь — только выбранный ранее пользователем в окне программы. Читается только обычный файл не больше 64 МиБ (каталог, канал, устройство — `not_found`, больше — `too_large`), до согласия файл не читается. Программа спрашивает пользователя окном с сайтом, плагином и полным путём. Согласие запоминается в экземпляре (сессии) на пару (сайт, канонический путь), отказ — `declined`.

`page_file_write` пишет в существующий каталог, который назвала страница. `name` — имя без разделителей, `..`, управляющих и зарезервированных символов Windows, не начинается с `.` и не заканчивается `.` или пробелом, с расширением из `page_files_ext`; иначе — `invalid` без вопроса. Окно согласия показывает полный путь файла; согласие действует на каталог до конца сессии. Запись атомарная, существующий файл заменяется.

### `settings`

| Функция | Аргумент | Результат |
|---|---|---|
| `settings_get` | `()` | `BTreeMap<String, String>` — настройки; без файла или с повреждённым файлом — пустые (повреждение пишется в журнал) |
| `settings_put` | `BTreeMap<String, String>` | `()` — настройки заменяются целиком |

Настройки лежат в `<data>/plugins/settings/<id>.json`, пишутся атомарно, не больше 256 ключей и 64 КиБ JSON (иначе `limit`). Обновление плагина их сохраняет, удаление — удаляет.

### `shared`

| Функция | Аргумент | Результат |
|---|---|---|
| `shared_get` | `SharedKey { key }` | `Option<Bytes>` — значение, если оно есть и не истекло |
| `shared_put` | `SharedPut { key, value, ttl_ms }` | `()`; `value = None` удаляет ключ |

Значения живут в памяти процесса, общие для всех экземпляров одного загруженного поколения плагина, то есть для всех сессий и сайтов. Перезагрузка и обновление плагина начинают с пустого. Не больше 64 ключей и 64 КиБ ключей и значений вместе (иначе `limit`). Handle ключа через `shared` в другую сессию не переносится: таблица ключей — в экземпляре.

### `http`

| Функция | Аргумент | Результат |
|---|---|---|
| `http_request` | `HttpArgs { method, url, content_type, body }`, `method` — `get` или `post` | `HttpResponse { status, content_type, location, body }` |
| `http_request_ex` | `HttpExArgs { method, url, relative_to_origin, headers, content_type, body, timeout_ms }` | `HttpResponse` |

Адрес проверяется по префиксам манифеста (см. [«Адреса `http`»](#адреса-http)) и отправляется в проверенной форме. Вне префиксов — `denied`, ничего не отправляется. Запрос идёт через прокси из настроек OpenNCALayer, только по HTTPS, с лимитами 32 МиБ и 60 с и без следования перенаправлениям: 3xx возвращается плагину с `location`. У GET нет тела. За один вызов `oncl_process` уходит не больше 64 запросов вместе с запросами программы к хостам PKI; следующий получает `limit` и не отправляется.

`http_request_ex` отправляет запрос, если выполнено одно из условий:

- адрес под префиксом `http` (HTTPS, хост `*.` — по границе метки);
- `relative_to_origin` (адрес разрешается от origin текущего вызова) или абсолютный адрес с тем же origin (схема, хост, порт), и этот origin подходит под шаблон `origins`. HTTP — только если сам origin HTTP. Без origin или с origin, который не является адресом (`null`), — `denied`;
- адрес под префиксом `http_insecure` (HTTP, точный хост и порт).

Остальное, в том числе `file:`, `data:` и другие схемы, — `denied`. Заголовки — только `Cookie`, `User-Agent`, `Accept`, `Accept-Language`, `X-Requested-With` (без учёта регистра; другие — `denied`), не больше 16 и 8 КиБ вместе (иначе `limit`); CR, LF или NUL в заголовке или `content_type` — `invalid`. POST без `content_type` уходит без `Content-Type`. `timeout_ms` — от 1 до 60000. Перенаправлениям программа не следует, как у `http_request`.

## SDK

Плагин на Rust пишется с крейтом `oncl-pdk`. Под `wasm32` он даёт:

- Макрос `oncl_pdk::plugin!(handler)`. Обработчик `handler: fn(&Request) -> String` получает запрос (`text`, `origin`, `locale`) и возвращает ответ странице. Макрос экспортирует `oncl_abi_version`, `oncl_alloc`, `oncl_free`, `oncl_process`, а паника плагина перед trap пишется в журнал через `log`. Перед каждым вызовом обработчика макрос берёт 16 байт у `random` и засевает ими хеш, в котором `orgjson` держит ключи запроса (у гостя WebAssembly своего источника случайности нет, а известные странице ключи позволили бы ей подобрать ключи, которые все сталкиваются). Сам плагин `random` для этого вызывать не должен.
- Обёртки host-функций, которые возвращают `HostResult`: `host::{log, now, random, cert_info, reply_drop}`, `keys::{choose, flow_open, Flow, Key}` (`Flow::{keys, pick}`; `Key::{sign_cms, sign_raw, sign_xml, sign_xml_ex, sign_xades, describe, alias, certificate, handle}`; при удалении `Key` вызывается `keys_release`), `tokens::scan`, `dialogs::{message, confirm, password, choice, reader}`, `files::{open, save, choose, choose_kind, open_ex, page_read, page_write}`, `pki::path`, `http::{get, post, request_ex}`, `settings::{get, put}`, `shared::{get, put}`; для встроенных модулей — `core::{modules, bundles, install_bundle, open_window}` и `builtin::{dialog_csr, dialog_import, new_key, install_cert, change_password, id_card}`. Есть и `call_host` — вызов любой host-функции с типами ABI.
- `Request::add_info()` и реэкспорт `oncl_protocol::{invoker, orgjson}` и `serde_json`. Плагин, который отвечает в диалекте CommonInvoker (как `kz.gov.pki.knca.basics`), вызывает `invoker::invoke` (запрос читает `serde_json`, ключи объектов `body` идут в том порядке, в котором их положил метод) или `invoker::java::invoke_with` (через него отвечает сам модуль basics).
- Java-диалекты оригинала для плагинов, которые должны отвечать как оригинал байт в байт (реэкспорт из `oncl-protocol`):
  - `orgjson::{parse, reserialize}` — разбор org.json 20211205 с его текстами ошибок и позицией (`Duplicate key "a" at 11 [character 12 line 1]`);
  - `orgjson::{JObject, JValue, quote}` — запись, как пишет `JSONObject.toString()`: порядок ключей `HashMap` (`JObject::hash_map()` для `new JSONObject()` и бинов, `JObject::from_map(n)` для `new JSONObject(map)`, `JObject::stringer()` для `JSONStringer`), числа без хвостовых нулей, `<\/`, `\u2028`;
  - читатели `orgjson::{opt_boolean, get_boolean, opt_int, get_int, get_object, get_array, array_get_string, …}` с текстами `JSONException`;
  - `javamap` — порядок `HashMap` для любого набора ключей;
  - `javab64::{decode_java, decode_kalkan, encode_mime}`;
  - `javaexc::Throwable` — тексты исключений Java;
  - `legacy::dispatch` — рефлексивный диспетчер `commonUtils` и его клонов: поиск метода по имени и числу аргументов, преобразование массивов, тексты `NoSuchMethodException`/`IllegalAccessException`/`argument type mismatch`, `uuid` через org.json. `null` без `uuid` — обрыв соединения. Методы самого `commonUtils` `null` не возвращают: отмена у них — ответ `{"code":"500","message":"action.canceled"}` с `uuid` и без;
  - `invoker::java::invoke_with` — `CommonInvoker` оригинала: `details` с классом исключения (`java.lang.IllegalArgumentException: Supported apiVersion is 2`), порядок `{"body":…,"status":true}` и `{"code":…,"details":…,"message":…,"status":false}`, таблица методов с аннотациями и числом параметров, а для запроса, который не дошёл до `try` оригинала, — выбор `BadRequest::{Reply, Drop, CatchAll}`.
  - Модуль basics отвечает через `invoker::java::invoke_with` с `BadRequest::CatchAll` (запрос без строкового `method` — `GENERAL_ERROR` с `org.json.JSONException` в `details`, как у оригинала); `commonUtils` — через `legacy::dispatch`.

Импортируются только те host-функции, которые плагин вызывает, поэтому плагину без `keys` не нужно заявлять `keys`. `call_host` ссылается на все функции, и плагину с ним нужны все возможности.

**Пример.** `crates/oncl-pdk/example` — модуль `io.github.arynyklas.openncalayer.Example`, класс `Example` с методом на каждую возможность (`echo`, `count`, `origin`, `confirm`, `message`, `sign`, `signRaw`, `signXml`, `hold`, `release`, `rawSign`, `open`, `save`, `fetch`) и методами, которые нарочно ведут себя плохо (`spin`, `grow`, `panic`). Сборка:

```sh
cargo build --release --target wasm32-unknown-unknown --manifest-path crates/oncl-pdk/example/Cargo.toml
```

Модуль — `crates/oncl-pdk/example/target/wasm32-unknown-unknown/release/oncl_plugin_example.wasm`; вместе с `plugin.toml` примера он упаковывается в `.onclp`. Пример — отдельный workspace со своим `Cargo.lock`, в релизы он не входит. Тесты `oncl-plugin` собирают его сами в `target/plugin-example`.

## Жизненный цикл

Установленные плагины лежат в `<data>/plugins/`:

- `state.json` — установленные плагины (версия, sha256 пакета, источник, включён ли, отозван ли), версии, которые не загрузились, случайный `install_id` для раскатки и последний принятый `seq` каталога каждого канала;
- `packages/<id>-<version>.onclp` — пакеты;
- `catalog/<канал>.json` — каталог. Его подлинность задают метаданные TUF общего клиента в `<data>/update/tuf/` ([`tuf.md`](tuf.md)).

Каждый файл заменяется атомарно, состояние меняется под одной блокировкой и сохраняется до того, как изменение видно. Повреждённый `state.json` заменяется свежим (причина в журнале). Другая ошибка чтения выключает плагины — окно «Плагины» показывает её.

### Каталог

Каталог — записи `plugins` индекса обновлений канала из настроек (`updates.channel`, по умолчанию — канал версии OpenNCALayer); подлинность индекса проверяет TUF, см. [`update-index.md`](update-index.md).

- Скачивается через 10–60 с после старта, если действующего каталога нет, иначе через 2–10 минут; дальше раз в 6–24 часа, после сбоя загрузки — через 30 минут – 2 часа.
- Принятый каталог (метаданные TUF, `seq` и канал проверены при загрузке) сохраняется. Сохранённый каталог при чтении с диска проверяется заново без сети: подпись `targets` проверяется от встроенного корня, байты каталога должны совпасть с длиной и sha256 из этих `targets`, ни они, ни корень не должны истечь (до этого срока каталог и действует), а `seq` не должен быть меньше принятого. Загруженный в память каталог проверяется только по этому сроку.
- Каталог, скачанный по запросу при включённых обновлениях, сразу применяется в фоне.
- С выключенными обновлениями (`updates.enabled = false`) плановых загрузок и автообновлений плагинов нет. Каталог скачивается только по запросу: окно «Плагины», `installBundle`, «Проверить сейчас» в настройках и «Проверить обновления» в меню значка (проверка плагинов идёт в фоне по сохранённым настройкам).
- Сборка без зашитого корня доверия каталога не имеет: окно пишет «Каталог плагинов недоступен в этой сборке», плагины ставятся только из файла.

### Старт

Включённые и не отозванные плагины загружаются из своих пакетов; sha256 файла сверяется с записанным при установке. Плагин, который не загрузился (пакет изменён, нужен более новый OpenNCALayer, модуль занят), остаётся установленным в состоянии «ошибка» и не мешает остальным.

### Установка из каталога

Кнопка «Установить…» или `installBundle`. Порядок:

1. Пакет скачивается только по HTTPS; его размер и sha256 сверяются с индексом.
2. `Package::read`; совпадение `id`, `version`, `modules` и `replaces` манифеста с записью индекса; `min_core`; пробная компиляция с проверкой имён модулей (встроенный модуль или модуль другого плагина не занимается).
3. Пакет, не прошедший проверку, помечает версию плохой. Сбой сети версию плохой не делает: установку можно повторить, а обновление повторится при следующей проверке каталога. Не делает её плохой и модуль, который уже обслуживает другой установленный плагин: это зависит от установки, а не от пакета. Обновление на такую версию не повторяется, пока плагины не изменятся (удаление, выключение, установка или обновление плагина), а установку можно повторить сразу. При любом отказе ничего не ставится, значок сообщает об ошибке; установку, начатую из окна «Плагины», окно ещё и объясняет на языке интерфейса.
4. Окно «Установка плагина» показывает, кто просит (`origin` без управляющих символов, разделителей строк и символов направления текста, не длиннее 128 символов), имя, версию, что плагин заменяет и его возможности.
5. Кнопка «Установить» становится доступной через 1,5 с после появления окна, чтобы клик или Enter, предназначенные другому окну, не установили плагин. «Установить» загружает плагин, записывает пакет и состояние и сообщает «Плагин установлен». «Отмена» или закрытие окна ничего не меняет.

### Установка из файла

«Установить из файла…» (фильтр `*.onclp`). Проверки пакета, `min_core` и модулей те же, а окно содержит предупреждение: «Этого плагина нет в каталоге OpenNCALayer, его не проверял мейнтейнер…». Если плагин с тем же `id` уже установлен, окно называет его версию и откуда он — из каталога или локальный. Такой плагин помечается «локальный»: каталог его не обновляет и не отзывает.

### Обновление и отзыв

После каждого принятого каталога (плановой загрузки или «Проверить сейчас» при включённых обновлениях) для каждого плагина из каталога выбирается версия (`choose_plugin`): обновление — с раскаткой, только вверх; с отозванной версии — на лучшую неотозванную, в том числе вниз и без раскатки.

- Новая версия скачивается и проверяется как при установке, загружается новой «генерацией» и только потом записывается. Если что-то не прошло, версия попадает в плохие, а старая продолжает работать.
- Обновление, которое может не больше установленной версии, не спрашивает пользователя, значок сообщает «Плагин обновлён».
- Если новая версия может больше (новый флаг `keys`, `dialogs` или `files` либо адрес `http`, не покрытый префиксами установленной версии), она скачивается и проверяется, но не ставится. Установленная версия продолжает работать, окно «Плагины» показывает, что новая версия сможет сверх установленной, с кнопкой «Разрешить обновление», а значок один раз сообщает «Обновление плагина ждёт разрешения». Обновление ставится, когда пользователь его разрешит; если каталог за это время перестал его предлагать, ждать нечего.
- Отозванная версия без замены выгружается и помечается отозванной (уведомление один раз). Она не загружается, пока каталог её не вернёт.

### Во время работы

Вызов, который идёт, доигрывает на своём экземпляре. Следующий вызов той же сессии получает экземпляр новой генерации или `MODULE_NOT_FOUND`, если плагин выгружен. Сбой вызова выбрасывает только его экземпляр.

### Выключение и удаление

«Выключить» выгружает плагин, «Включить» загружает снова (кроме отозванного). «Удалить» (после вопроса) выгружает плагин и удаляет его пакет и запись.

### Нужный модуль

Запрос к модулю, которого никто не обслуживает, отвечает `MODULE_NOT_FOUND`, как раньше. Если действующий каталог (без скачивания) предлагает плагин с таким модулем, а он не установлен, значок сообщает «Сайту X нужен плагин «Y»» с кнопкой «Установить…». Кнопка открывает окно «Плагины» (не чаще раза в 10 минут), а окно отмечает плагин «Нужен сайту X». Сообщение (и новое чтение открытого окна) бывает, только когда эта отметка меняется: плагин стал нужен или нужен другому сайту.

## installBundle

`kz.gov.pki.ncalayerservices.accessory` `installBundle` повторяет порядок проверок оригинала:

1. Пустой `symname` — `SYMNAME_PARAMETER_IS_EMPTY`.
2. Без заголовка `Origin` — `org.json.JSONException: JSONObject["origin"] is not a string.`.
3. Затем программа ищет в каталоге неустановленный плагин, у которого `replaces.symname` равен `symname`. Если действующего каталога нет, она его скачивает; если скачивание уже идёт, дожидается его. Всё это — не дольше 10 с, после чего ответ без каталога. Если скачать каталог не удалось (сеть, индекс не опубликован или отвергнут), запросы страниц ещё 5 минут обходятся без каталога и не скачивают его снова. «Обновить каталог», «Установить…» в окне «Плагины» и «Проверить сейчас» скачивают его сразу.

Что отвечает:

- **Плагин найден** — ответ сразу `{"errorCode":"NONE"}`, а установка (скачивание, проверки, окно подтверждения) идёт в фоне: как и оригинал, ответ не ждёт пользователя. Пока установка идёт (в том числе ждёт ответа пользователя), повторный запрос отвечает так же и новую не начинает. О сбое установки, начатой страницей, значок сообщает не чаще раза в 10 минут для каждого плагина.
- **Не найден, уже установлен** (в том числе выключен или отозван) **или каталога нет** (сборка без корня доверия обновлений, офлайн, метаданные TUF истекли, не успел за 10 с) — `BUNDLE_NOT_FOUND_OR_ALREADY_INSTALLED`. Значок сообщает «Сайт {origin} запросил модуль {symname}. Каталог OpenNCALayer не предлагает его установить: его там нет или он уже установлен» с кнопкой «Реестр плагинов» (не чаще раза в 10 минут). `origin` и `symname` показываются без управляющих символов, разделителей строк и символов направления письма, не длиннее 128 символов.

`uuid` запроса возвращается, как раньше.

`getBundles` добавляет к бандлам оригинала `replaces.symname → replaces.version` включённых загруженных плагинов, `getServices` — модули плагинов. Оба списка живые и видят плагин сразу после установки. Версию бандла `getBundles` печатает как `Bundle.getVersion().toString()` у оригинала: `major.minor.micro` и `.qualifier`, если он есть (`1.2` → `1.2.0`, `2` → `2.0.0`, `1.2.0` и `1.2.3.rc1` остаются). Манифест остаётся как есть, он сверяется с манифестом оригинала и `registry.toml`. Строка, которая не версия OSGi (например, semver-пререлиз `1.0.0-beta.2`: оригинал такую не принимает и таких бандлов не имеет), уходит как написана. `showBundleManager` открывает окно «Плагины».

Порядок записей — намеренное отличие от оригинала: при установленных плагинах `getBundles` и `getServices` ставят модули плагинов после встроенных, по алфавиту. Порядок оригинала с плагинами зависит от его реестра OSGi и не воспроизводится.

## Порты

Порты сторонних плагинов оригинала лежат в `plugins/`: 35 каталогов `plugins/<short>`, по одному на плагин оригинала, и общие библиотеки в `plugins/common/`. Это отдельный workspace для `wasm32-unknown-unknown`: в workspace ядра и в его релизы он не входит. Один порт собирается в пакет командой `cargo xtask plugin pack plugins/<short>`; job `conformance` в `release.yml` собирает пакеты всех портов, но не публикует их (`docs/dev/release.md`).

В каталоге порта:

- `plugin.toml` — манифест (раздел [«Манифест»](#манифест)): `id` вида `io.github.arynyklas.openncalayer.port.<short>`, имена `module`, которые порт обслуживает, `replaces` — `symname` и версия бандла оригинала, и только нужные порту возможности;
- `registry.toml` — данные реестра: бандл оригинала (`symname`, версия, поставщик), состояние порта (`full` — всё, что делает оригинал; `partial` — с оговорками; `needs-tokens` — всё, но часть проверяется только на токенах), способ сверки с оригиналом и отличия от оригинала (`[[differences]]`), которые реестр показывает пользователю;
- исходники крейта `oncl-port-<short>`.

Порты по семействам:

| Группа | Семейство | Порты |
|---|---|---|
| 2 | ecc.kz | market, efactoring, nursign, k2sign |
| 3 | клоны commonUtils | rating1c, xdox, eot, ezsigner, uchet, arta, metadoc |
| 4 | CommonInvoker | idocs, fhs, doodocs, devart, thundercrypt |
| 5 | прочие средние | taxtech, energy, eproc, esf-osdkz, uchet-esf, qiwi, bas, eup, dogovor24, onaidocs, workspace, simourg, motiw |
| 6 | тяжёлые | buhta, acbank, knp, documentolog, qoltanba, skf |

Состояние `full` — у buhta, acbank и doodocs, у остальных `partial`.

Общие библиотеки:

- `oncl-port-kit` (`common/kit`) — то, что плагины оригинала собирали средствами Java: тела `multipart/form-data` байт в байт, `new URL(context, spec)` и origin, zip-архивы, `Properties.storeToXML`, шаблоны `SimpleDateFormat`, ответы семейства ecc.kz;
- `oncl-port-legacy` (`common/legacy`) — общее у клонов commonUtils (рефлексивный диспетчер `oncl_pdk::legacy`): бин `ResponseMessage`, проверки `StorageInfo`, типы ключей и выбор ключа, `KeyInfo`, Base64 Java, тексты сетевых исключений Java;
- `oncl-port-pki` (`common/pki`) — DER в госте (RustCrypto `der`, `x509-cert`, `cms`; без ключей и случайности — подписывает программа): подписанные атрибуты и имена из строк DN, чтение CMS, атрибуты и запрос OCSP ЕСЭДО, доверенные сертификаты Java KeyStore, тексты сертификатов Java и Kalkan.

Диалекты JSON (org.json, порядок `HashMap` Java, диспетчеры) — в `oncl-pdk`. Тесты портов — крейт `oncl-port-tests` (`crates/oncl-port-tests`): он грузит собранный `.wasm` в настоящую программу для плагинов с тестовым PKI и, где нужно, эмулятором токенов.

**Порядок `HashMap` Java.** У оригинала это бакеты `(h ^ h >>> 16) & (ёмкость − 1)` по порядку, а внутри бакета — порядок вставки. Бакеты одинаковы на всех ОС, но порядок вставки свойств бина (например, `KeyInfo` в `getKeyInfo` commonUtils) выбирает JVM, и он разный:

| ОС | Порядок |
|---|---|
| Windows 11 | `pem, keyId, alias` в бакете 9 и `subjectDn, algorithm` в бакете 15 |
| Linux | `pem, alias, keyId` и любой порядок второй пары (от запуска к запуску) |
| Windows 7 | `keyId, alias, pem` и `algorithm, subjectDn` |

Программа и порты пишут порядок Windows 11 на всех ОС. На Linux и Windows 7 ключи одного бакета могут идти иначе, чем у оригинала на той же ОС.

**Правила порта.**

- **Сохраняется** то, что видит страница: форма ответов, коды и тексты ошибок, порядок проверок, порядок полей (в том числе порядок `HashMap` Java), байты подписей и запросов к серверам.
- **Исправляется** то, что небезопасно или опирается на состояние вне песочницы: подписи на SHA-1 (sha1RSA) не создаются; HTTPS — только с проверкой сертификата и по адресам из манифеста; ключи и пароли не запоминаются между соединениями и не пишутся на диск (то, что порт сохраняет, например путь к хранилищу, идёт через возможность `settings`); файлы настроек и кэши оригинала не читаются; пути к файлам от страницы заменяются окнами программы. Каждое такое отличие записывается в `registry.toml`.
- Токены — только через экспериментальную поддержку ([`tokens.md`](tokens.md)); пока она выключена, хранилища токенов пусты.

Ожидаемые ответы в тестах выведены из поведения оригинала и сверены с работающим оригиналом (см. [«Сверка с оригиналом»](#сверка-с-оригиналом); исключение — onaidocs, у него `computed`).

**Схема `registry.toml`.** Её единственный читатель — `xtask::registry::ports`; `cargo xtask registry build` отказывается собирать сайт, если хоть один порт её нарушает, и называет все такие порты вместе.

| Поле | Правило |
|---|---|
| `id` | равен `id` из `plugin.toml`, а тот — `io.github.arynyklas.openncalayer.port.<short>`; `<short>` — `^[a-z0-9][a-z0-9-]{0,62}$` |
| `modules` | те же, что в `plugin.toml` |
| `[original]` `symname`, `version` | те же, что `[replaces]` в `plugin.toml`; `symname` — `^[A-Za-z0-9._-]{1,128}$` и не повторяется у двух портов |
| `[original]` `vendor` | 1–256 символов без управляющих |
| `[port]` `status` | `full`, `partial` или `needs-tokens` |
| `[port]` `conformance` | `computed` или `confirmed` (см. [«Сверка с оригиналом»](#сверка-с-оригиналом)); в канал `stable` `cargo xtask index add-plugin` пускает только `confirmed` |
| `[[differences]]` `ru` | до 64 отличий, каждое — 1–2048 символов без управляющих, кроме перевода строки; показываются как текст, на казахской и английской страницах — с пометкой «на русском» |

Лишние ключи — ошибка. Каждый порт получает на сайте проекта страницу `/plugins/<short>/` (и `/kk/…`, `/en/…`) и строку каталога `/plugins/#<symname>`; новый порт с `registry.toml` попадает на сайт при следующей сборке.

**Как добавить порт.** Создайте каталог `plugins/<short>` (имя не начинается с `c` — так workspace отделяет порты от `common/`), положите в него `plugin.toml` и `registry.toml`, добавьте тесты в `oncl-port-tests`. Если порт тянет новые зависимости — запустите `cargo xtask licenses --plugins`.

### Сверка с оригиналом

Поведение портов сверено с работающим оригиналом NCALayer 1.4 в изолированной лаборатории проекта: одни и те же запросы страницы идут оригиналу и нашей программе с портом, ответы сравниваются поле за полем, включая порядок ключей, байты подписей по форме и тексты ошибок.

Записи оригинала приватные, в публичный репозиторий они не попадают. Тесты `oncl-port-tests` содержат ожидания, написанные вручную на синтетических значениях. `cargo xtask privacy` всегда ищет файлы и заголовки записей, пути с буквой диска и сертификаты, выпущенные тестовыми УЦ НУЦ (DER и base64), а серийные номера, DN тестовых ключей и имена лаборатории — только по приватному списку (секрет `PRIVACY_DENYLIST`). Ссылки на лабораторию и на её записи в тексте он не находит, их проверяет ревью.

Каждое найденное расхождение получает одно из состояний:

- **исправлено** — порт изменён, и тест закрепляет наблюдённое правило;
- **принято отличием** — запись в `[[differences]]` порта с названной причиной (безопасность, состояние вне песочницы, порядок или предел, зависящие от ОС или ядра, либо осознанный выбор порта вместо поведения оригинала);
- **недостижимо** — у кода комментарий `// Not observable:` с причиной: для ветки нет ключа, устройства или сети, которыми её можно вызвать;
- **открыто**.

Место, где порт опирается на вывод из кода оригинала, пока оно не проверено на оригинале, помечается комментарием `// Unverified against the original:`; в портах сейчас такого места нет.

Поле `conformance` в `registry.toml` порта:

- `computed` — поведение выведено из кода оригинала (декомпиляция бандла); сверка с работающим оригиналом не закончена. Либо остались расхождения, не закрытые на оригинале, либо версия оригинала новее сверенной и сверена только по байткоду.
- `confirmed` — сверка закончена: каждое расхождение исправлено, принято отличием или недостижимо. Только такой порт пускает в канал `stable` команда `cargo xtask index add-plugin` (порт с `computed` она отвергает, см. раздел 7а `docs/dev/release.md`). Для `beta` поле не проверяется.

Сейчас `confirmed` у 32 портов из 35. У трёх `computed`:

- **simourg 2.4** и **ezsigner 1.2.2** — новую версию оригинала порт принял по сравнению байткода бандлов, а на работающем оригинале сверка не повторена; после повтора им вернут `confirmed`. У simourg различаются три класса окон ключа и списка запомненных ключей, которых порт не воспроизводит (у него общие окна программы); классы, обрабатывающие запросы и подписывающие, совпадают побайтно. У ezsigner различаются проверка локального пути (в 1.2.2 появилась ветка для macOS, которую порт не воспроизводит) и номер строки в одном классе; остальные классы, включая `CMSSignUtil`, совпадают побайтно.
- **onaidocs 1.1.0** — порт выведен из кода бандла (sha256 проверен, байткод разобран), но работающий оригинал в лаборатории не запускался. Не сверены ответы и тексты ошибок, состав CMS (только подписант или вся цепочка), параметры метки времени и окно ключа; список — в `[[differences]]` порта. В канал `stable` порт не пойдёт, пока не станет `confirmed`.

Итоговая сверка покрывает код каждого порта (simourg — на версии 2.2, ezsigner — на 1.2.1). Порты, кроме uchet, повторены на сборке до последних правок uchet и arta; после неё менялись только код uchet (его сценарии прогнаны на итоговой сборке), `registry.toml` arta и комментарии `oncl-pki`. Необъяснённых расхождений в повторе нет. Правки портов после этого повтора закреплены тестами, но на оригинале ещё не повторены.

Версия порта, поведение которого менялось, получает следующий `1.0.0-beta.N`. `min_core` порта — первая версия программы, у которой есть всё поведение, на которое порт опирается (fhs и nursign: текст разборщика JDK для текста перед первой разметкой, `0.1.0-alpha.6`). Начиная с `0.1.0-alpha.6` программа даёт плагину (не встроенному модулю) текст `SAXParseException` JDK и для текста перед первой разметкой (`Content is not allowed in prolog.`). Ответы портов, которые передают это сообщение (devart, eproc, клоны commonUtils, fhs V1, skf), для такого документа изменились; более старая программа даёт им прежний текст.

Саму программу сверяют так же: на теге job `conformance` в `release.yml` собирает артефакт для лаборатории (`docs/dev/release.md`, раздел 7б), агент сверяет сборку с оригиналом и ставит на коммит тега статус `conformance`. Без него новая версия не попадёт в `stable`.
