# Как защищены обновления (TUF)

Для тех, кто хочет понять, почему подмена обновления не пройдёт, и для владельца проекта, который подписывает выпуски. Здесь: из чего состоит защита, как клиент проверяет файлы, что делать при сбое и при потере ключа.

Клиент проверяет индекс обновлений только по схеме TUF. Подпись minisign больше не используется. Формат самого индекса описан в [`update-index.md`](update-index.md).

## Что такое TUF

[TUF](https://theupdateframework.github.io/specification/latest/) (The Update Framework) — набор подписанных файлов-метаданных. Они отвечают на четыре вопроса:

| Роль | Вопрос |
|---|---|
| `root` | Какие ключи вправе подписывать остальное? |
| `targets` | Какие файлы существуют и какие у них хеши? |
| `snapshot` | Какие версии метаданных актуальны вместе? |
| `timestamp` | Свежо ли всё это сейчас? |

Один ключ подписи этого не даёт. TUF позволяет заменить любой ключ без выпуска новой версии программы, разделяет роли между ключами и ограничивает срок, в который возможна подмена.

## Что защищено

Индекс обновлений (`updates/v1/{stable,beta}.json`) остался прежним, ни один байт не изменился. В TUF он — *цель* (target) с путём `indexes/stable.json` или `indexes/beta.json`. TUF — это слой проверки вокруг индекса.

Пакеты ядра, расширение и плагины целями TUF не являются. Они лежат в GitHub Releases, индекс ссылается на них, а клиент проверяет их по `sha256` и `size` из индекса.

Цепочка доверия клиента:

```
встроенный root.json (версия 1)
  → цепочка root N+1, N+2, … (опубликованные корни)
    → timestamp → snapshot → targets
      → индекс канала (цель) → пакет (sha256 + size из индекса)
```

## Роли, ключи, сроки

Используется только Ed25519 (`keytype` и `scheme` равны `ed25519`) и только хеш sha256.

| Роль | Что подписывает | Ключей / порог | Срок `expires` | Где ключ |
|---|---|---|---|---|
| `root` | открытые ключи всех четырёх ролей и порог каждой | 1 / 1 | 365 дней | офлайн у владельца |
| `targets` | пути, длины и sha256 индексов | 1 / 1 | 30 дней | офлайн у владельца |
| `snapshot` | версию `targets` | 1 / 1 | 30 дней | офлайн у владельца |
| `timestamp` | версию и sha256 `snapshot` | 1 / 1 | **7 дней** | **онлайн**: секрет окружения GitHub |

Все четыре ключа различны. Поле `consistent_snapshot` равно `true`. Делегирований, зеркал (`mirrors`), `path_hash_prefixes`, RSA и ECDSA нет.

Срок считается от момента подписи, формат RFC 3339 (`YYYY-MM-DDTHH:MM:SSZ`). Срок `timestamp` — 7 дней, он перевыпускается ежедневно (см. [«Подпись timestamp при публикации Pages»](#подпись-timestamp-при-публикации-pages)).

Ключ `root` один (порог 1): так владельцу не нужна церемония с несколькими носителями. Цена названа в разделе [«Ротация и компрометация»](#ротация-и-компрометация): потеря или утечка ключа `root` означает переустановку программы у всех.

### Идентификатор ключа

Ключ в `root.json` записывается так:

```json
{"keytype": "ed25519", "scheme": "ed25519", "keyval": {"public": "<64 hex>"}}
```

`keyid` — это sha256 канонического JSON (см. ниже) этого объекта, строчные hex-цифры. Клиент пересчитывает `keyid` каждого ключа в корне и отвергает корень, где ключ лежит под чужим идентификатором.

Подпись в метаданных имеет вид `{"keyid": "<hex>", "sig": "<128 hex>"}`. Порог считается по различным `keyid` из роли: подписи неизвестных ключей и повтор одного ключа в порог не входят.

### Канонический JSON и подпись

Подписывается не файл, а объект `signed`, приведённый к каноническому JSON OLPC ([spec §4.1](https://theupdateframework.github.io/specification/latest/#metaformat)): без пробелов, ключи отсортированы по байтам, в строках экранируются только `"` и `\`, числа только целые. Для клиента это значит:

- каноническая форма строится от произвольного `serde_json::Value`, а не от типизированной структуры. Неизвестные поля остаются в подписи, поэтому добавление поля в метаданные подпись не ломает;
- подпись — Ed25519 по этим байтам, проверяет `ring`;
- только после проверки подписи метаданные разбираются в типизированную модель.

Метаданные отвергаются, если в `signed` есть нецелое число или `_type` не соответствует имени роли.

## Где лежат файлы

Файлы лежат в репозитории и на сайте проекта в каталоге `tuf/v1/` (`https://arynyklas.github.io/OpenNCALayer/tuf/v1/`). GitHub Pages отдаёт их с `Cache-Control: max-age=600`, и это не изменить. Поэтому включён `consistent_snapshot`: каждая версия метаданных и каждая цель имеют своё имя, и в десятиминутном кэше не смешиваются разные снимки.

| Путь | Содержимое |
|---|---|
| `metadata/<N>.root.json` | корень версии N; хранятся все версии |
| `metadata/timestamp.json` | единственный файл без номера; в git не хранится, создаётся при публикации Pages |
| `metadata/<N>.snapshot.json` | снимок версии N |
| `metadata/<N>.targets.json` | метаданные целей версии N |
| `targets/indexes/<sha256>.<name>.json` | индекс: `<name>` — последняя часть пути цели (`stable.json`, `beta.json`), `<sha256>` — хеш содержимого; байты те же, что в `updates/v1/<name>.json` |

Клиент ходит только `GET` по HTTPS (перенаправление на `http://` отвергается). К API GitHub он не обращается.

## Как клиент проверяет

Это краткая сводка [клиентского процесса из спецификации (§5)](https://theupdateframework.github.io/specification/latest/#detailed-client-workflow). Какое подмножество реализовано, видно из раздела [«Что клиент отвергает»](#что-клиент-отвергает).

1. **Корень.** Доверенный корень — `crates/oncl-update/keys/root.json`, `build.rs` встраивает его в сборку.
   - Если проверка уже была, клиент берёт сохранённую цепочку корней и заново проверяет её от встроенного корня: оба порога на каждом шаге, версия ровно +1. Сохранённый корень сам по себе, подписанный собственными ключами, ничего не доказывает.
   - Затем клиент запрашивает `metadata/<N+1>.root.json`, пока не получит 404. Каждый следующий корень должен подходить по подписи и порогу и ключам предыдущего корня, и своим собственным; его `version` равна ровно N+1.
   - За один обход клиент проходит не больше `max_roots` корней (по умолчанию 128). Если следующий корень ещё есть, это ошибка «цепочка слишком длинна»; пройденные корни сохраняются, и следующий обход продолжается с них.
   - Последний корень в цепочке не должен быть истёкшим.
   - Если у новой версии корня изменился ключ или порог `timestamp`, `snapshot` или `targets`, сохранённые версии этих ролей удаляются. Иначе после смены ключа сработала бы защита «версия не уменьшается» и клиент застрял бы. (Спецификация, §5.3.11, называет первые две роли; `targets` добавлен, чтобы ротация его ключа тоже не блокировала клиента.)
2. **Timestamp.** `metadata/timestamp.json`: подпись ключом `timestamp` из актуального корня, `version` не меньше сохранённой, срок не истёк. Внутри — версия (а при наличии длина и хеш) `snapshot`.
3. **Snapshot.** `metadata/<N>.snapshot.json` по версии из timestamp: подпись, совпадение версии и хеша, срок. Версии в `meta` не меньше сохранённых.
4. **Targets.** `metadata/<N>.targets.json` по версии из snapshot: подпись, версия, срок. Если в нём есть поле `delegations`, это отказ с явной ошибкой.
5. **Цель.** Клиент ищет в `targets` путь `indexes/<channel>.json`, скачивает `targets/indexes/<sha256>.<channel>.json` и сверяет длину и sha256 с метаданными. Если записи канала в `targets` нет, канал считается пустым («В канале пока нет выпусков»).
6. **Индекс.** Дальше действуют правила индекса: схема, `channel` совпадает с каналом клиента, `seq` не меньше последнего принятого. Правило «30 дней с `generated`» при TUF не применяется: свежесть задают `expires` ролей, а `expires` индекса остаётся просто полем формата (см. [`update-index.md`](update-index.md)).
7. **Сохранение.** Цепочка корней и версии ролей записываются в состояние после своих проверок. Корни записываются одной записью с удалением версий из п. 1, даже если корень дальше по цепочке отвергнут. Запись всегда атомарна (`oncl_pki::fsutil`).

Истёк ли срок, решают часы клиента: при обновлении метаданных и при скачивании цели (набор метаданных, у которого что-то истекло, не используется). От неверных часов TUF не защищает ([spec §7.1](https://theupdateframework.github.io/specification/latest/#support-for-bogus-clocks)).

### Что клиент отвергает

- Метаданные с неверной подписью, ниже порога, с чужим `keyid`, с повтором `keyid` в роли или с ключом под неверным идентификатором.
- Корень, где один ключ служит двум ролям (ключ `timestamp` лежит онлайн и не должен давать права на `targets`).
- Файл одной роли на месте другой (отказ по подписи и по `_type`).
- Корень не версии N+1, корень без подписи порога прежних ключей, корень без подписи собственных ключей, истёкший последний корень.
- `timestamp`, `snapshot`, `targets` с версией ниже сохранённой или не той, что названа выше по цепочке; истёкшие метаданные.
- Цель с неверными длиной или sha256.
- `delegations` в `targets`.
- Ключ не `ed25519`, хеш не sha256.
- `consistent_snapshot`, не равный `true`.
- Индекс чужого канала и индекс с `seq` ниже последнего принятого.

Поля `mirrors` и `path_hash_prefixes` клиент не читает: они входят в подпись и ничего не значат (`path_hash_prefixes` бывает только в делегированиях, а они запрещены; зеркал в корне версии 1.x нет).

Любая из этих причин — отказ. К другому пути проверки клиент не переходит.

## Что клиент хранит

В каталоге `<данные>/update/tuf/` лежит один файл `state.json` и файл блокировки `lock`. В `state.json`:

- цепочка принятых корней (как скачаны, от встроенного корня);
- версии последних принятых `timestamp` (с тем, что он перечислил), `snapshot` и `targets`.

Сами файлы метаданных каждый раз скачиваются заново (имена несут версию и хеш). Исключение — последний принятый файл `targets`: он сохраняется как есть, чтобы индекс, сохранённый каталогом плагинов, можно было проверить без сети. При этом подпись `targets` проверяется заново по цепочке корней от встроенного, а срок `targets` и корня учитывается. Срок `timestamp` и `snapshot` при такой проверке не учитывается: они подтверждают только актуальность, и их срок — дни.

Запись атомарна (`oncl_pki::fsutil`), размер файла ограничен 1 МиБ и при чтении, и при записи. Последний принятый `seq` каждого канала лежит отдельно, в `<данные>/update/state.json` ([`update-index.md`](update-index.md)).

Индекс читают две части программы: апдейтер (`crates/openncalayer/src/update.rs`) и каталог плагинов (`crates/openncalayer/src/plugins.rs`, `crates/oncl-plugin/src/store.rs`). Они работают через один TUF-клиент и один каталог состояния. Так версии метаданных не расходятся, а `timestamp`, принятый одной частью, не отвергается другой как «откат». Каждая запись берёт блокировку каталога (файл `lock`) на время чтения, слияния и записи. Она сливает состояние на диске с сохраняемым, никогда не понижает версию роли и не заменяет корень более старым. Версии более новой эпохи ключей (после ротации) вытесняют версии прежней.

Если состояние повреждено (не JSON, другая схема, лишнее поле, файл больше лимита, сохранённый корень не корень, цепочка корней не проходит от встроенного), клиент начинает со встроенного корня, заменяет состояние и сообщает причину через `Trusted::state_was_reset()` (вызывающий код пишет её в журнал). Ошибка чтения другого рода (например, нет доступа) — это ошибка, а не сброс.

Если встроенный корень новее всего сохранённого, версии `timestamp`, `snapshot` и `targets` из состояния тоже забываются: ключи корней между ними неизвестны. Встроенный корень — единственное, что нельзя восстановить из сети: он поставляется вместе с программой.

## Подпись timestamp при публикации Pages

`timestamp.json` — единственный файл, который подписывается автоматически, и единственный секрет, который попадает в CI.

- Секрет — ключ `timestamp` в *environment* GitHub. Доступ к нему ограничен правилом окружения (только ветка `main`). Остальные три ключа CI не видит никогда.
- `pages.yml` публикует Pages раз в сутки (cron) и при каждом слиянии. На этом шаге job окружения сначала клиентским кодом проверяет, что `snapshot` подписан ключом из актуального корня и согласован с `targets` и индексами, и только потом подписывает `timestamp`. CI не может «благословить» чужой снимок: он подписывает лишь версию и хеш уже подписанного владельцем `snapshot`.
- `version` у timestamp — Unix-время в секундах в момент подписи, `expires` — через 7 дней. Версия растёт сама, без хранимого счётчика.
- Файл попадает только в артефакт Pages и **не коммитится в git**. Ежедневный коммит требовал бы права записи у CI и засорял бы историю, а он не нужен: `version` берётся из времени, и подпись не должна быть привязана к ревизии.

Следствие: если Pages не публикуется 7 дней, `timestamp` истекает и клиенты перестают принимать обновления (см. [«Сбои»](#сбои)).

## Ротация и компрометация

Любая роль заменяется новым `root.json` версии N+1, подписанным ключом root версии N (порог 1). Клиенты берут его при очередной проверке, выпуск новой версии программы не нужен.

| Ключ | Ротация | Что даёт украденный ключ | Чего не даёт |
|---|---|---|---|
| `timestamp` (онлайн) | новый root, новый ключ в окружении; клиенты удаляют сохранённые timestamp и snapshot | заморозку: тому, кто ещё и управляет выдачей Pages, — вечный перевыпуск старого снимка до `expires` у `snapshot` (30 дней) и откат на ещё не истёкший снимок | установки кода: `targets` и `snapshot` подписаны не им |
| `snapshot` | новый root | смесь версий `targets`, которые ещё действуют | нового содержимого индекса |
| `targets` | новый root | подмену индекса, то есть ссылок и sha256 пакетов, а значит произвольную установку. Нужны ещё `snapshot` и `timestamp`; первые два офлайн у одного владельца, один носитель — одна точка отказа | подписать новый корень |
| `root` | новый root, подписанный старым ключом root | всё: корень с новыми ключами всех ролей; клиенты, дошедшие до него, доверяют атакующему | — |

**Потеря или утечка ключа root — это переустановка.** Порог 1 означает единственный ключ без резерва. При потере ротировать root некому. При утечке атакующий выпустит корень N+1 раньше владельца или вместо него, и клиенты, дошедшие до него, перестанут доверять владельцу. Остальные три ключа это не затрагивает: их утечка закрывается ротацией через root.

Root нужно продлевать раз в год (срок 365 дней): истёкший корень клиент не принимает, а цепочка должна оставаться непрерывной.

Оговорка: ротация защищает клиентов, только пока атакующий не контролирует и хостинг. Если он отдаёт клиенту подложные метаданные вместо опубликованного нового корня, клиент не узнает о ротации ([spec §6.1](https://theupdateframework.github.io/specification/latest/#key-management-and-migration)).

## Что делает владелец

Порядок команд — [`docs/dev/release.md`](../dev/release.md), раздел 7г (`cargo xtask tuf …`).

1. Сгенерировать четыре различных ключа Ed25519 на своей машине. Секретные ключи шифруются паролем и не пишутся в рабочее дерево git (как у `cargo xtask sign keygen`).
2. Ключ `timestamp` внести как секрет окружения GitHub, остальные три хранить офлайн.
3. Подписать корень версии 1 (root, версия 1, 365 дней) и положить его в `crates/oncl-update/keys/root.json`.
4. Для каждого выпуска индекса подписать `targets` и `snapshot` своими ключами (срок 30 дней: подписывать нужно не реже раза в 30 дней, даже без выпуска, командой `refresh`). `timestamp` подпишет CI.
5. Раз в год выпускать новую версию `root`.

## Сбои

- **Истёк `timestamp`** (Pages не публиковался 7 дней). Клиент отвергает метаданные, обновлений нет, ошибка видна в журнале и в окне настроек. Установленная версия продолжает работать, ничего не откатывается. Лечится публикацией Pages.
- **Истёк `snapshot` или `targets`.** То же самое; лечится подписью владельца.
- **Сбой подписи или проверки `timestamp` при публикации Pages** (репозиторий не проходит проверку клиентским кодом, `snapshot` истёк, секрет отсутствует). Сайт не публикуется, запуск красный. Прежний сайт продолжает отдавать свой `timestamp`, действующий до 7 дней. Сайт без `metadata/timestamp.json` дал бы каждому клиенту 404, то есть ошибку проверки.
- **Сеть недоступна.** Повтор через 30–120 минут. Ошибка проверки — повтор в обычный срок (см. [`update-index.md`](update-index.md), «Обновление в программе»).
- **404 на `timestamp.json`, пока клиент не принял ни одного `timestamp`, или нет записи канала в принятых `targets`.** Это значит, что канал ещё не опубликован. В окне настроек: «В канале пока нет выпусков», в журнале — `info`, следующая проверка в обычный срок.
- **404 на `timestamp.json` после первой принятой публикации, на `snapshot`, `targets` или файл цели.** Это ошибка проверки: опубликованный репозиторий не теряет файлов, а подмена ответом 404 не должна тихо останавливать обновления. В журнале `warn`, повтор через 30–120 минут. (404 на корень N+1 — это просто конец цепочки корней.)
- **Корень N+1 подписан неверно.** Цепочка не принимается, клиент остаётся на последнем принятом корне и пишет ошибку.

## Почему нет запасного пути

Клиент не знает minisign: ни проверки, ни ключей `current/next`, ни ветки «если TUF не удался, попробовать старое». Запасной путь свёл бы защиту к самому слабому из двух. Атакующий, который мешает TUF (подменой ответа или блокировкой), откатил бы клиента на путь без ротации, порогов и разделения ролей.

Дорогая миграция с двойной публикацией не нужна: клиентская база — альфы и беты, канала `stable` ещё нет. Старые установки обновляются в выпуск «только TUF» обычным обновлением по minisign, а встроенный в него `root.json` становится корнем доверия.

## Почему нет делегирований

`delegations` в метаданных `targets` — отказ клиента. Сторонних авторов плагинов пока нет: все порты плагинов собирает проект. Когда появится первый, понадобится делегирование. Оно добавит:

- роль автора с путями `plugins/<префикс>*`, порог и ключи автора;
- обход делегирований клиентом (глубина и число посещённых ролей ограничены);
- запись верхней роли с `custom.revoked` для отзыва чужого плагина;
- реестр авторов с префиксами идентификаторов и имён модулей (пути не выражают владение именами модулей);
- правила проверки PR.

Доставка встроенных модулей ядра через индекс потребует ещё отдельной роли с порогом выше 1. До тех пор клиент, получивший метаданные с `delegations`, не пытается их понять.

## Ограничения платформы

Проверку реализует крейт `oncl-update` на `ring` (Ed25519), `serde_json`, `sha2` и `time`; новых зависимостей нет. TLS — только rustls на ring. Библиотеки `aws-lc-*` на Unix разрешены, но в крейт обновлений не входят: иначе нельзя собрать версию для Windows 7. Клиент блокирующий, работает поверх `oncl_pki::http::HttpTransport`.
