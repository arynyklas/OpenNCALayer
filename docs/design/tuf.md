# Аутентификация обновлений через TUF

**Статус: планируется в `0.1.0-rc.2`.** До неё клиент проверяет индекс подписью minisign (`update-index.md`, `roadmap.md`, D26). Начиная с rc.2 клиент проверяет индекс только по TUF; выпуск `0.1.0` — TUF-only. Этот документ описывает, как устроена схема, а решения владельца, из которых она следует, записаны в [`roadmap.md`](roadmap.md) (D8, D10, D26, P15).

[TUF](https://theupdateframework.github.io/specification/latest/) (The Update Framework) — это подписанные метаданные, которые отвечают на четыре вопроса: какие ключи имеют право подписывать (`root`), какие файлы существуют и какие у них хеши (`targets`), какие версии этих метаданных актуальны вместе (`snapshot`) и свежо ли всё это сейчас (`timestamp`). Схема даёт то, чего не даёт один ключ minisign: ротацию любого ключа без выпуска клиента, разделение ролей и ограниченный срок действия подмены.

## Слои

Индекс обновлений (`updates/v1/{stable,beta}.json`, формат — [`update-index.md`](update-index.md)) **не меняется ни на байт**. В TUF он — *цель* (target) с путём `indexes/stable.json` или `indexes/beta.json`. Всё новое — слой аутентификации вокруг него: метаданные, клиентский верификатор и инструменты выпуска. Пакеты ядра, расширение и плагины целями TUF **не** являются: они остаются ассетами GitHub Releases, на которые ссылается индекс, и проверяются, как раньше, по `sha256` и `size` из индекса.

Цепочка доверия клиента:

```
встроенный root.json (версия 1)
  → цепочка root N+1, N+2, … (опубликованные корни)
    → timestamp → snapshot → targets
      → индекс канала (цель) → пакет (sha256 + size из индекса)
```

## Роли, ключи, сроки

Только Ed25519: `keytype` и `scheme` равны `ed25519`. Других алгоритмов подписи и хешей, кроме sha256, нет.

| Роль | Что подписывает | Ключей / порог | Срок `expires` | Где ключ |
|---|---|---|---|---|
| `root` | открытые ключи всех четырёх ролей, порог каждой | 1 / **1** | 365 дней | офлайн у владельца |
| `targets` | пути, длины и sha256 индексов | 1 / 1 | 30 дней | офлайн у владельца |
| `snapshot` | версию `targets` | 1 / 1 | 30 дней | офлайн у владельца |
| `timestamp` | версию и sha256 `snapshot` | 1 / 1 | **7 дней** | **онлайн**: секрет окружения GitHub |

Все четыре ключа различны. `consistent_snapshot` равен `true`. Делегирований, зеркал (`mirrors`), `path_hash_prefixes`, RSA и ECDSA нет.

Сроки считаются от момента подписи в формате RFC 3339 (`YYYY-MM-DDTHH:MM:SSZ`). Срок `timestamp` — 7 дней, перевыпускается ежедневно (см. «Подпись timestamp»).

`root` с порогом 1 — решение владельца: единственный ключ root избавляет от церемонии с несколькими носителями. Цена названа в разделе «Ротация и компрометация»: потеря или утечка ключа root означает переустановку у всех.

### Идентификатор ключа

Объект ключа в `root.json`:

```json
{"keytype": "ed25519", "scheme": "ed25519", "keyval": {"public": "<64 hex>"}}
```

`keyid` — sha256 канонического JSON (см. ниже) этого объекта, строчные hex-цифры. Клиент **пересчитывает** `keyid` каждого ключа из `keys` корня и отвергает корень, где ключ лежит под чужим идентификатором. Подпись в метаданных — `{"keyid": "<hex>", "sig": "<128 hex>"}`; порог считается по различным `keyid` из роли, подписи неизвестных ключей и повтор одного ключа в порог не входят.

### Канонический JSON и подпись

Подписывается не файл, а объект `signed`, приведённый к каноническому JSON OLPC ([spec §4.1](https://theupdateframework.github.io/specification/latest/#metaformat)): без пробелов, ключи объектов отсортированы по байтам, в строках экранируются только `"` и `\`, числа — только целые. Правила для клиента:

- каноническая форма строится от **произвольного `serde_json::Value`**, а не от типизированной структуры: неизвестные поля остаются в подписи, и подпись не рвётся, когда в метаданные добавляют поле;
- подпись — Ed25519 по этим байтам, проверка — `ring`;
- после проверки подписи метаданные разбираются в типизированную модель.

Метаданные, где `signed` содержит нецелое число или `_type` не соответствует имени роли, отвергаются.

## Раскладка

Файлы лежат в репозитории и на сайте проекта под `tuf/v1/` (`https://arynyklas.github.io/OpenNCALayer/tuf/v1/`). GitHub Pages отдаёт файлы с `Cache-Control: max-age=600`; управлять заголовками нельзя. Поэтому `consistent_snapshot: true`: каждая версия метаданных и каждая цель имеет своё имя, и в 10-минутном кэше не смешиваются разные снимки.

| Путь | Содержимое |
|---|---|
| `metadata/<N>.root.json` | корень версии N; **хранятся все версии** |
| `metadata/timestamp.json` | единственный файл без номера; в git не хранится, создаётся при публикации Pages |
| `metadata/<N>.snapshot.json` | снимок версии N |
| `metadata/<N>.targets.json` | метаданные целей версии N |
| `targets/indexes/<sha256>.<name>.json` | индекс: `<name>` — последняя часть пути цели (`stable.json`, `beta.json`), `<sha256>` — хеш содержимого; байты те же, что в `updates/v1/<name>.json` |

Клиент ходит только `GET` по HTTPS (перенаправление на `http://` отвергается), к API GitHub он по-прежнему не обращается.

## Как клиент проверяет

Это краткая сводка [клиентского процесса спецификации (§5)](https://theupdateframework.github.io/specification/latest/#detailed-client-workflow); подмножество, которое реализует клиент, описано в «Что клиент отвергает».

1. **Корень.** Доверенный корень — `crates/oncl-update/keys/root.json` (встраивается `build.rs`). Если проверка уже была, то после него идёт цепочка принятых корней из состояния, и клиент **заново проверяет её от встроенного корня** (оба порога на каждом шаге, версия ровно +1): сохранённый корень сам по себе, подписанный собственными ключами, ничего не доказывает. Дальше клиент запрашивает `metadata/<N+1>.root.json`, пока не получит ответ 404. Каждый следующий корень должен подходить по подписи и порогу **и ключам предыдущего корня, и своим собственным**, его `version` равна ровно N+1. Если N+1 существует, а за один обход клиент уже прошёл `max_roots` (по умолчанию 128) корней, это ошибка «цепочка слишком длинна»; пройденные корни сохраняются, и следующий обход продолжает с них. Корень, дошедший до конца цепочки, должен быть не истёкшим. Если у новой версии изменился ключ или порог `timestamp`, `snapshot` или `targets`, сохранённые версии этих трёх ролей удаляются (spec §5.3.11 называет первые две; `targets` добавлен, иначе после fast-forward `targets` ротация его ключа не восстанавливает клиента): это снимает блокировку «версия назад» после ротации.
2. **Timestamp.** `metadata/timestamp.json`: подпись ключом `timestamp` из актуального корня, `version` не меньше сохранённой, срок не истёк. В нём — версия (и при наличии длина и хеш) `snapshot`.
3. **Snapshot.** `metadata/<N>.snapshot.json` по версии из timestamp: подпись, совпадение версии и хеша, срок. Версии в `meta` не меньше сохранённых.
4. **Targets.** `metadata/<N>.targets.json` по версии из snapshot: подпись, версия, срок. Поле `delegations` — отказ с явной ошибкой.
5. **Цель.** Путь `indexes/<channel>.json` ищется в `targets`. Файл `targets/indexes/<sha256>.<channel>.json` скачивается и сверяется по длине и sha256 из метаданных; при отсутствии записи канала в `targets` канал пуст («В канале пока нет выпусков»).
6. **Индекс.** Дальше работают правила индекса: схема, `channel` совпадает с каналом клиента, `seq` не меньше последнего принятого. Правило «30 дней с `generated`» в режиме TUF **не применяется**: свежесть задают `expires` ролей, а `expires` самого индекса остаётся полем формата (см. [`update-index.md`](update-index.md)).
7. **Сохранение.** Цепочка корней и версии ролей записываются в состояние после своих проверок (корни — одной записью с удалением версий из п. 1, даже если корень дальше по цепочке отвергнут), всегда атомарно (`oncl_pki::fsutil`).

Часы клиента определяют, истёк ли срок: при обновлении метаданных и при скачивании цели (`download_target` получает текущее время: набор, у которого что-то истекло, не используется). TUF от неверных часов не защищает ([spec §7.1](https://theupdateframework.github.io/specification/latest/#support-for-bogus-clocks)).

### Что клиент отвергает

- метаданные с неверной подписью, ниже порога, с чужим `keyid`, дубликатом `keyid` в роли или ключом под неверным идентификатором; корень, где один ключ служит двум ролям (ключ `timestamp` онлайн и не должен давать права на `targets`); файл одной роли на месте другого (отказ по подписи и по `_type`);
- корень не `N+1`, корень без подписи порога прежних ключей, корень без подписи собственных ключей, истёкший конечный корень;
- `timestamp`, `snapshot`, `targets` с версией ниже сохранённой или с версией, не совпадающей с названной выше по цепочке; истёкшие метаданные;
- цель с неверными длиной или sha256;
- `delegations` в `targets`;
- ключ не `ed25519`, хеш не sha256;
- поля `mirrors` и `path_hash_prefixes` клиент не читает: они входят в подпись и ничего не значат (`path_hash_prefixes` бывает только в делегированиях, а они запрещены; зеркал в корне версии 1.x нет);
- `consistent_snapshot` не `true`;
- индекс чужого канала и индекс с `seq` ниже последнего принятого.

Любая из этих причин — отказ без обращения к другому пути проверки.

## Состояние клиента

Каталог `<данные>/update/tuf/` содержит один файл `state.json` (и `lock`): цепочку принятых корней как скачаны (от встроенного корня) и **версии** последних принятых `timestamp` (с тем, что он перечислил), `snapshot` и `targets`; сами файлы метаданных каждый раз скачивают заново (имена несут версию и хеш), кроме последнего принятого файла `targets`: он сохраняется как скачан, чтобы индекс, сохранённый каталогом плагинов, проверялся без сети (подпись `targets` проверяется заново по цепочке корней от встроенного, срок `targets` и корня учитывается, а `timestamp` и `snapshot` нет: они подтверждают актуальность и их срок — дни). Запись атомарна (`oncl_pki::fsutil`), размер файла ограничен 1 МиБ и при чтении, и при записи. Последний принятый `seq` каждого канала лежит в `<данные>/update/state.json` ([`update-index.md`](update-index.md)).

Индекс читают два потребителя: апдейтер (`crates/openncalayer/src/update.rs`) и каталог плагинов (`crates/openncalayer/src/plugins.rs`, `crates/oncl-plugin/src/store.rs`). Они работают через **один** TUF-клиент и **один** каталог состояния. Так версии метаданных не расходятся, а `timestamp`, принятый одним потребителем, не отвергается как «откат» другим. Каждая запись берёт блокировку каталога (файл `lock`, на время чтения, слияния и записи), сливает состояние на диске с сохраняемым и **никогда не понижает версию** роли и не заменяет корень более старым; версии более новой эпохи ключей (после ротации) вытесняют версии прежней.

Если состояние повреждено (не JSON, другая схема, лишнее поле, файл больше лимита, сохранённый корень не корень, цепочка корней не проходит от встроенного), клиент начинает с встроенного корня, заменяет состояние и сообщает причину через `Trusted::state_was_reset()` (вызывающий код пишет её в журнал). Ошибка чтения другого рода (например, нет доступа) — это ошибка, не сброс. Если встроенный корень новее всего сохранённого, версии `timestamp`, `snapshot` и `targets` из состояния тоже забываются: ключи корней между ними неизвестны. Встроенный корень — единственное, что нельзя восстановить из сети: он доставляется самим пакетом.

## Подпись timestamp при публикации Pages

`timestamp.json` — единственный файл, который подписывается автоматически, и единственный секрет, который попадает в CI.

- Секрет — ключ `timestamp` в *environment* GitHub; доступ к нему ограничен правилом окружения (только `main`). Остальные три ключа CI не видят никогда.
- `pages.yml` публикует Pages раз в сутки (cron) и при каждом слиянии. На этом шаге job окружения: проверяет клиентским кодом, что `snapshot` подписан ключом из актуального корня и согласован с `targets` и индексами, и только потом подписывает `timestamp`. CI не может «благословить» чужой снимок: подписывать он умеет лишь версию и хеш уже подписанного владельцем `snapshot`.
- `version` timestamp — Unix-время в секундах в момент подписи, `expires` — через 7 дней. Версия монотонна без какого-либо хранимого счётчика.
- Файл попадает только в артефакт Pages. **В git он не коммитится:** ежедневный коммит ради подписи требовал бы права записи у CI, засорял бы историю и не нужен — `version` берётся из времени, а подпись не должна быть привязана к ревизии.

Следствие для эксплуатации: если Pages не публикуется 7 дней, `timestamp` истекает и клиенты перестают принимать обновления (см. «Сбои»).

## Ротация и компрометация

Любая роль заменяется новым `root.json` версии N+1, подписанным ключом root версии N (порог 1); клиенты берут его при очередной проверке, **выпуск клиента не нужен**.

| Ключ | Ротация | Что даёт украденный ключ | Что он не даёт |
|---|---|---|---|
| `timestamp` (онлайн) | новый root, новый ключ в окружении; клиенты удаляют сохранённые timestamp и snapshot | заморозку: тому, кто ещё и контролирует выдачу Pages, — вечный перевыпуск старого снимка вплоть до `expires` `snapshot` (30 дней), откат на ещё не истёкший снимок | установку кода: `targets` и `snapshot` подписаны не им |
| `snapshot` | новый root | смесь версий `targets`, которые ещё действуют | новое содержимое индекса |
| `targets` | новый root | подмену индекса, то есть ссылок и sha256 пакетов: произвольную установку; нужен ещё и `snapshot` с `timestamp` (все три офлайн у одного владельца, один носитель — одна точка отказа) | подписать новый корень |
| `root` | новый root, подписанный старым ключом root | всё: корень с новыми ключами всех ролей; клиенты, дошедшие до него, доверяют атакующему | — |

**Потеря или утечка ключа root — переустановка.** Порог 1 означает единственный ключ без резерва: при потере ротировать root некому, при утечке атакующий выпустит корень N+1 раньше владельца или вместо него, и клиенты, дошедшие до него, перестанут доверять владельцу. Остальные три ключа это не затрагивает: их утечка закрывается ротацией через root. Root продлевается раз в год (срок 365 дней): истёкший корень клиент не принимает, а цепочка должна оставаться непрерывной.

Оговорка: ротация защищает клиентов, только пока атакующий не контролирует и хостинг. Если он отдаёт клиенту подложные метаданные вместо опубликованного нового корня, клиент не узнает о ротации ([spec §6.1](https://theupdateframework.github.io/specification/latest/#key-management-and-migration)).

## Церемония владельца

На уровне дизайна; порядок команд появится в `docs/dev/release.md` вместе с инструментами (`cargo xtask tuf …`).

1. Сгенерировать четыре различных ключа Ed25519 на машине владельца; секретные ключи шифруются паролем и не пишутся в рабочее дерево git (как у `cargo xtask sign keygen`).
2. Ключ `timestamp` внести как секрет окружения GitHub, остальные три хранить офлайн.
3. Подписать корень версии 1 (root, версия 1, 365 дней) и положить в `crates/oncl-update/keys/root.json`, выпустить rc.2.
4. Для каждого выпуска индекса: подписать `targets` и `snapshot` ключами владельца (срок 30 дней: не реже раза в 30 дней, даже без выпуска, `refresh`); `timestamp` подписывает CI.
5. Раз в год — новая версия `root`.

## Сбои

- **Истёк `timestamp`** (Pages не публиковался 7 дней): клиент отвергает метаданные, обновлений нет, ошибка видна в журнале и окне настроек. Уже установленная версия продолжает работать, ничего не откатывается. Лечится публикацией Pages.
- **Истёк `snapshot` или `targets`**: то же, лечится подписью владельца.
- **Сеть недоступна**: повтор через 30–120 минут, как сегодня; ошибка проверки — обычный срок (`update-index.md`, «Обновление в демоне»).
- **Ответ 404 на `timestamp.json`, пока клиент не принял ни одного `timestamp`, и отсутствие записи канала в принятых `targets`**: репозиторий (канал) ещё не опубликован: в окне настроек «В канале пока нет выпусков», в журнале — `info`, следующая проверка в обычный срок. **Ответ 404 на `timestamp.json` после первой принятой публикации, на `snapshot`, `targets` или файл цели — ошибка проверки** (опубликованный репозиторий не теряет файлов; подмена ответом 404 не должна тихо останавливать обновления): `warn`, повтор через 30–120 минут. 404 на корень N+1 — конец цепочки корней.
- **Корень N+1 подписан неверно**: цепочка не принимается, клиент остаётся на последнем принятом корне и пишет ошибку.

## Почему нет запасного пути

Клиент rc.2 и `0.1.0` не знает minisign: ни проверки, ни ключей `current/next`, ни ветви «если TUF не удался, попробовать старое». Запасной путь свёл бы защиту к самому слабому из двух: атакующий, мешающий TUF (подмена ответа, блокировка), откатил бы клиента на путь без ротации, порогов и разделения ролей. Клиентская база — альфы и беты, а канала `stable` ещё нет, так что дорогой миграции с двойной публикацией не требуется: старые установки обновляются в TUF-only выпуск обычным обновлением по minisign, а встроенный в него `root.json` становится корнем доверия.

## Почему нет делегирований

`delegations` в метаданных `targets` — отказ клиента. Сторонних вендоров пока нет: все порты плагинов собирает проект. Делегирование (P15b) появится вместе с первым вендором и добавит: роль вендора с путями `plugins/<префикс>*`, порог и ключи вендора, обход делегирований клиентом (глубина и число посещённых ролей ограничены), запись верхней роли с `custom.revoked` для отзыва чужого плагина, реестр вендоров с префиксами идентификаторов и имён модулей (пути не выражают владение именами модулей) и правила проверки PR. Доставка встроенных модулей ядра через индекс (D8) потребует ещё отдельной роли с порогом выше 1 (P15c). До тех пор клиент, получивший метаданные с `delegations`, не пытается их понять.

## Ограничения платформы

Верификатор реализован в `oncl-update` на `ring` (Ed25519), `serde_json`, `sha2` и `time`; новых зависимостей нет. TLS — только rustls на ring; `aws-lc-*` на Unix разрешён и в крейт обновлений не входит: иначе нельзя собрать Windows 7 (см. D14 в [`roadmap.md`](roadmap.md)). Клиент блокирующий, поверх существующего `oncl_pki::http::HttpTransport`.
