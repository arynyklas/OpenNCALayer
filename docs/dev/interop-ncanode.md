# Проверка подписей в NCANode (Kalkan)

Для разработчиков: как убедиться, что наши подписи XMLDSig и CMS и наши файлы ключей принимает независимая программа — [NCANode](https://github.com/ncanode-kz/NCANode). Её сервер проверяет подписи через Kalkan — так делают сервисы, которые принимают подписи NCALayer.

Команда `cargo xtask interop-ncanode` работает только в Linux. В Windows она печатает «interop с NCANode запускается в Linux» и завершается с кодом 0 (это не значит, что проверка прошла).

## Как запустить

Нужен Docker. В Debian или Ubuntu (в том числе в WSL) его можно поставить и запустить от root:

```sh
apt-get install -y docker.io
service docker start
```

Ваш пользователь должен входить в группу `docker`. В CI на раннере `ubuntu-24.04` Docker уже есть. Дальше:

```sh
cargo xtask fetch-fixtures     # тестовые ключи NCANode → target/fixtures/ncanode/
cargo xtask interop-ncanode
```

Что происходит при запуске:
- Контейнер называется `oncl-ncanode-interop` и слушает случайный порт на `127.0.0.1`. Имя можно поменять переменной `ONCL_NCANODE_CONTAINER`, том с кэшем — `ONCL_NCANODE_CACHE_VOLUME`.
- Контейнер с таким же именем, оставшийся от прерванного запуска, удаляется перед стартом.
- После проверки контейнер удаляется, а образ и том с кэшем остаются (как их удалить — ниже).
- NCANode запускается с настройками по умолчанию: промышленные корни, CRL и OCSP НУЦ. При старте он скачивает сертификаты и CRL с `pki.gov.kz`, `root.gov.kz` и `crl.pki.gov.kz`/`crl.root.gov.kz`, поэтому нужна сеть.
- Если скачать сертификат НУЦ не удалось (`Cannot download file` — случается то с одним, то с другим), NCANode завершается. Тогда xtask печатает журнал контейнера и запускает его заново, всего до пяти попыток.
- Кэш NCANode (`/app/cache`) лежит в томе Docker `oncl-ncanode-cache` и сохраняется между запусками. Уже скачанные сертификаты НУЦ NCANode берёт из кэша, поэтому следующая попытка или следующий запуск качает меньше. Исключение — `nca_gost.crt`: он просрочен (`notAfter` 2025-06-25), и NCANode скачивает его заново при каждом старте.

Если `docker pull` падает с ошибкой `docker-credential-desktop.exe: executable file not found` (в WSL остался `~/.docker/config.json` от Docker Desktop), скачайте образ с пустым конфигом: `DOCKER_CONFIG=<пустой каталог> docker pull <образ>`. Сама команда после этого образ уже скачивать не будет.

В CI эта команда запускается только в job `live` (по расписанию и вручную), а не на каждый push. Сейчас проходят все 47 проверок.

Полная независимая матрица по NCANode OpenAPI (CMS/CAdES, XML/XAdES, PDF/PAdES и далее) — команда `cargo xtask platform-interop`, см. [`platform-interop.md`](platform-interop.md). Команда на этой странице проверяет только наши файлы ключей и подписи XMLDSig/CMS через Kalkan.

## Образ

| | |
|---|---|
| Образ | `malikzh/ncanode@sha256:052222f30ac73d9f0060a5c80c572723d25dd84e21073435795a10db254c02b8` |
| Версия | NCANode 3.5.1 (тег Docker Hub `3.5.1`, релиз GitHub `3.5.1`), KalkanCrypt 0.7.5 |

Digest образа закреплён в `xtask/src/ncanode/container.rs` (`IMAGE`). Тестовые файлы `cargo xtask fetch-fixtures` берёт с того же коммита NCANode (`NCANODE_COMMIT` в `xtask/src/fetch.rs`).

Как обновить образ:
1. Поменяйте digest в `xtask/src/ncanode/container.rs` и в этой таблице, а также `NCANODE_COMMIT` в `xtask/src/fetch.rs`.
2. Убедитесь, что «контроли» (см. ниже) по-прежнему получают `SIG_CRYPTO_FAILURE`, а хорошие подписи — ожидаемую оценку сертификата. Правило прохождения опирается на порядок проверок в `AdesVerificationService.grade()`: сначала значение подписи, потом сертификат.

### Где лежат образ и том

Образ (около 700 МБ) и том `oncl-ncanode-cache` лежат вне `target/`, в хранилище Docker. Так сделано по двум причинам:
- образ объявляет `VOLUME /app/cache`, и без именованного тома каждый запуск оставлял бы анонимный том;
- NCANode работает в контейнере от root, и каталог `target/`, подключённый как bind mount, получил бы файлы root, которые `cargo clean` не удалит.

Где именно они лежат, зависит от Docker: с `docker.io` внутри дистрибутива — в `/var/lib/docker`, с Docker Desktop — в его хранилище. Удалить их можно так:

```sh
docker volume rm oncl-ncanode-cache
docker image rm malikzh/ncanode@sha256:052222f30ac73d9f0060a5c80c572723d25dd84e21073435795a10db254c02b8
```

## Что проверяется

Мы подписываем в своём процессе (`oncl_xml`, `oncl_pki::cms`), а результат отправляем в HTTP API NCANode.

Ключи:
- придуманные `fixtures/synthetic/user-{gost2015,gost2004,rsa}-sign.p12`;
- тестовые ключи NCANode (из `WithTestData.groovy`, они приходят с `cargo xtask fetch-fixtures`):
  - `individual_valid_2015.p12` — ГОСТ 2015-512, пароль `Aa123456`, истёк 2023-07-28;
  - `ceo_sign_revoked_2004.p12` (`KEY_CEO_SIGN_REVOKED_2004`) — ГОСТ 34.310-2004, издатель `ҰКО 3.0 (GOST TEST)`, пароль `Qwerty12`, истёк 2023-01-18;
  - `individual_valid_sign_2004.p12` (`KEY_INDIVIDUAL_VALID_SIGN_2004`) — несмотря на имя, это RSA-2048 / sha256WithRSA, издатель `ҰКО 3.0 (RSA TEST)`, пароль `Qwerty12`, истёк 2022-01-18. В выводе называется «NCANode RSA».

| Проверка | Как |
|---|---|
| XML, весь документ | `sign_enveloped` → `/xml/verify`. Исходный документ неудобный: BOM, декларация, комментарии, CRLF, пространство имён по умолчанию, `xml:lang`, атрибуты не по порядку, пустой элемент, кириллица. Подписанный — в форме Kalkan, без BOM и декларации |
| XML, элемент `#payload` | `sign_element("//data")` → `/xml/verify` (с DTD, см. ниже) |
| CMS с данными внутри и без них | `cms::sign` → `/cms/verify` (для подписи без данных — с `data`) |
| XML, две подписи | придуманные ГОСТ 2015, затем RSA → `/xml/verify`. Проверяется число подписантов (2) и оценка **первой** подписи: вторую NCANode не оценивает (см. ниже) |
| CMS, соподпись | придуманные ГОСТ 2015, затем RSA → `/cms/verify`, 2 подписанта, оценка каждого |
| Контроли | NCANode обязан ответить `INVALID/SIG_CRYPTO_FAILURE` на: изменённый документ (ГОСТ 2015, придуманный ключ); изменённый элемент `#payload` с DTD (ГОСТ 2015, придуманный ключ); изменённый элемент `#e1` с DTD (ключ NCANode ГОСТ 2015); испорченный `DigestValue` (ключ NCANode ГОСТ 2004); изменённое значение подписи CMS (придуманный ГОСТ 2015 и ключ NCANode ГОСТ 2004) |
| Дайджест против Kalkan | Kalkan подписывает тот же вход тем же ключом (`/xml/sign`), и `DigestValue` новой ссылки должен совпасть с нашим. Входы: неудобный документ целиком (все три ключа NCANode); тот же документ с нашей подписью (вторая подпись покрывает первую); элемент `#e1` под двумя разными `xml:lang`. Затем наш `verify` должен принять документ, который подписал Kalkan |
| `#e1` под двумя `xml:lang` | наша подпись элемента → `/xml/verify` |
| Наш файл ключа: ключ без сертификата | Генерируем ключ (ГОСТ 2015, ГОСТ 2004, RSA; `oncl_pki::keygen`), строим на него запрос на сертификат (CSR, `oncl_pki::csr`) и пишем ключ в `<PREFIX><keyId>.p12` (`keystore::create_key_file`, пароль `Default1`) → `/pkcs12/aliases`. Kalkan должен открыть файл и увидеть ровно один alias — keyId |
| Наш файл ключа: сертификат установлен | Придуманный ключ того же алгоритма выпускает сертификат по CSR (субъект, ключ и расширения запроса, SKI = keyId). Затем `keystore::install_certificate` и `keystore::change_password` на `Interop12` — как в `importCertificate` → `/pkcs12/info`. Kalkan должен найти в файле сертификат с нашим серийным номером |
| Наш файл ключа: Kalkan подписывает CMS | `/cms/sign` с этим файлом → `/cms/verify`. Подпись Kalkan нашим ключом проверяется, подписант один, оценка `INDETERMINATE/CHAIN_INCOMPLETE` |

Подпись CSR в NCANode проверить нельзя: у него нет метода для PKCS#10, а `/x509/verify` принимает подписанные данные строкой UTF-8, которой `CertificationRequestInfo` не является. Подпись CSR проверяет сам xtask (нашим кодом, открытым ключом из запроса) перед выпуском сертификата. Что Kalkan читает сгенерированный ключ, показывает проверка «Kalkan подписывает CMS». Что Kalkan принимает подписи, которые делает `PrivateKey::sign` (им же подписывается CSR), показывают проверки придуманными ключами.

## Как читать результат

NCANode оценивает подпись по порядку (`AdesVerificationService.grade()`):
1. Сначала проверяется значение подписи и дайджесты ссылок. При неудаче оценка `INVALID/SIG_CRYPTO_FAILURE`.
2. Потом проверяется сертификат: срок, доверенный издатель, отзыв.

Ни один из наших ключей не строит цепочку до действующего корня НУЦ: у придуманных свои корни, а тестовые сертификаты NCANode просрочены. Поэтому `valid` всегда `false`.

Проверка пройдена, только если NCANode вернул ровно ожидаемую оценку и ожидаемое число подписантов:
- хорошая подпись придуманным ключом — `INDETERMINATE/CHAIN_INCOMPLETE`;
- хорошая подпись ключом NCANode — `INDETERMINATE/OUT_OF_BOUNDS_NO_POE` (срок истёк; у отозванного ГОСТ 2004 срок проверяется раньше отзыва);
- контроль — `INVALID/SIG_CRYPTO_FAILURE`.

До оценки сертификата NCANode доходит, только если значение подписи сошлось. Поэтому `OK` в колонке `signature` значит, что Kalkan принял подпись. Контроли показывают обратное на тех же путях: с DTD для элементов, на просроченных ключах NCANode, для XML и CMS.

Колонка `signature`:

| Значение | Что значит |
|---|---|
| `OK` | хорошая подпись с ожидаемой оценкой |
| `rejected, expected` | контроль отвергнут, как и должен |
| `UNEXPECTED` | любая другая оценка (в колонке оценки дописано, какая ожидалась) |
| `ERROR` | запрос не удался |
| `opened` | только для проверок «наш файл ключа»: ответ NCANode совпал с ожидаемым |

Для проверок «наш файл ключа» ожидаемое такое: для «ключ без сертификата» — список alias из одного keyId; для «сертификат установлен» — серийный номер выпущенного сертификата в том виде, как его печатает NCANode (`BigInteger.toString(16)`). При `UNEXPECTED` ожидаемое значение дописано в последнюю колонку. Проверка «Kalkan подписывает CMS» читается как остальные проверки CMS. Ключи генерируются заново при каждом запуске, поэтому keyId и серийные номера в выводе каждый раз другие.

### Особенности NCANode, которые учитывает команда

- `/xml/verify` не регистрирует атрибуты `Id`, поэтому не находит `URI="#id"` и отвечает `SIG_CRYPTO_FAILURE` даже на подпись элемента, которую сделал сам Kalkan через `/xml/sign` с `referenceUri`. Поэтому в начало подписанного документа, который уходит в `/xml/verify`, xtask вставляет внутреннее подмножество DTD `<!DOCTYPE root [<!ATTLIST data Id ID #IMPLIED>]>`. Каноническую форму оно не меняет. С таким DTD подпись Kalkan проверяется (`OUT_OF_BOUNDS_NO_POE`), и наша тоже, а изменённый элемент отвергается.
- `/xml/verify` ищет подпись как `ds:Signature` среди детей корня и снимает её через `root.removeChild`. Поэтому NCANode проверяет только подписи с префиксом `ds:`, вставленные в корень. Наши подписи именно такие.
- Для XML с несколькими подписями NCANode возвращает оценку только первой по документу подписи (проверяет он с последней), а `valid` считает по всем. Поэтому проверка «XML 2 signatures: count, 1st graded» сверяет число подписантов и оценку первой подписи, но не второй. Вторую подпись покрывают проверка «XML document» с придуманным RSA (Kalkan принимает нашу RSA-подпись) и проверка «Kalkan digest: over our signature» (наш дайджест документа, уже несущего подпись, совпадает с Kalkan).

Правило Kalkan для `xml:*` в Canonical XML: при наследовании от опущенных предков побеждает **внешнее** значение (`crates/oncl-xml/src/c14n.rs`). Это показывают проверки «#e1 under 2 xml:lang»: дайджест элемента `<e Id="e1">` под `<r xml:lang="ru">` → `<m xml:lang="kk">` совпадает с дайджестом Kalkan, и NCANode принимает нашу подпись этого элемента.
