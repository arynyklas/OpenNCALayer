# Установщик для WinGet (`oncl-winget-setup`)

Для разработчиков и мейнтейнера: что за программа `oncl-winget-setup`, зачем она нужна WinGet и как её проверять. О подаче пакета в WinGet — [`winget.md`](winget.md).

## Зачем это нужно

WinGet запускает установщик и верит его коду возврата. У обычного `Setup.exe` от Velopack (закреплённой версии) две проблемы:
- при переустановке он принудительно завершает установленную программу, даже посреди подписи;
- если не выполнены prerequisites, он выходит с кодом 0, ничего не поставив.

Поэтому в WinGet отдаётся не он, а маленькая программа `oncl-winget-setup`. Она несёт **неизменённый** `Setup.exe` и сама решает, можно ли его запускать.

Файл называется `openncalayer-<версия>-win-<x64|x86>-winget-setup.exe`. Он есть только для Windows 10 версии 1809 и новее. Варианты для Windows 7 установщика для WinGet не имеют и остаются с обычными установщиками.

## Что делает программа

1. Отказывается работать с повышенным токеном (установка идёт в профиль пользователя). Проверка выполняется до любых записей.
2. Читает свой payload (вложенный `Setup.exe`) из собственного файла и проверяет SHA-256, версию и архитектуру. Payload лежит сразу после последней секции PE-файла, перед таблицей сертификатов Authenticode; после таблицы данных быть не может (код — `payload.rs`).
3. Если программа OpenNCALayer уже запущена, просит её «замереть». Для этого есть **отдельный** канал управления для текущего пользователя (`oncl_ipc::maintenance`; это не WSS и не native messaging). Решение принимается так же, как у штатного обновления (`Host::hold`): сначала новые запросы удерживаются, потом проверяются активные операции, период тишины (QUIET) и открытые окна.
   - «Заморозка» (hold) живёт, пока жива связь с установщиком. Если установщик убили, программа не остаётся занятой навсегда (есть ещё предел `MAX_LEASE`).
   - Если программа занята дольше `--wait` (по умолчанию 180 с), установка не трогается, код выхода 4.
   - Если запущена старая версия программы без такого канала, код выхода 5. Ничего не завершается принудительно.
4. Распаковывает payload в приватный каталог и запускает `Setup.exe --silent` (без других ключей).
5. Код возврата `Setup.exe` ничего не доказывает, поэтому проверяется результат: манифест по локатору Velopack, установленная программа (`--version`) и запись в «Приложения и возможности» (HKCU: версия, расположение, деинсталлятор).
6. После доказанной установки снова запускает ту программу, которая работала до неё. При чистой установке окон не открывает.

### Коды выхода

| Код | Значение |
|---|---|
| 0 | успех (только он считается успехом) |
| 1 | прочий сбой |
| 2 | неверные аргументы |
| 3 | payload повреждён или отсутствует |
| **4** | **занято** |
| 5 | программу нельзя спросить (старая версия) |
| 6 | `Setup.exe` завершился ошибкой |
| 7 | `Setup.exe` завершился, но нужная версия не установлена |
| 8 | токен повышен |
| 9 | не Windows |

В манифесте WinGet успехом остаётся только код 0 (`InstallerSuccessCodes` не расширять).

## Манифест приложения

В PE-файле программы должен быть ресурс `RT_MANIFEST` с `requestedExecutionLevel level="asInvoker"` и идентификаторами `supportedOS` для Windows от Vista до 11. Без него Windows по имени файла (`…-winget-setup.exe`, в нём слово «setup») решает, что это старый установщик, и до запуска показывает запрос UAC «Разрешить этому приложению от неизвестного издателя…». Без интерактивного сеанса запуск тогда падает с ошибкой `ERROR_ELEVATION_REQUIRED` (740). Нажать «Да» бесполезно: токен станет повышенным, а программа по замыслу откажет с кодом 8.

Манифест самого `Setup.exe` лежит внутри payload и к этой программе не относится.

Файл манифеста — `crates/oncl-winget-setup/windows/oncl-winget-setup.manifest`. `build.rs` передаёт его компоновщику MSVC (`/MANIFEST:EMBED /MANIFESTINPUT /MANIFESTUAC:NO`): новых зависимостей и `rc.exe` не нужно, для x64 и x86 одинаково. Ресурс занимает отдельную секцию `.rsrc` до `.reloc`. Payload по-прежнему дописывается после **последней** секции и до таблицы сертификатов, поэтому `payload::append/read` и порядок подписи не меняются: сначала `package winget-setup`, потом Authenticode всего файла.

Защита от ошибки: `cargo xtask package winget-setup` отказывается собирать программу без манифеста `asInvoker` (`oncl_winget_setup::manifest`). Тесты `crates/oncl-winget-setup/tests/manifest.rs` читают ресурс из собранной программы и проверяют, что payload находится.

## Порядок выпуска (`release.yml`)

1. Собирается `oncl-winget-setup` (`--no-default-features`, без тестовой обвязки).
2. `vpk pack` собирает обычный установщик.
3. `Setup.exe` подписывается Authenticode (если SignPath настроен).
4. `cargo xtask package winget-setup` вкладывает **итоговый** `Setup.exe` в `oncl-winget-setup`.
5. Сам `oncl-winget-setup` подписывается Authenticode отдельным запросом SignPath (артефакт `signpath-unsigned-winget-setup-<вариант>`).
6. Публикуются именно эти файлы, их SHA-256 попадают в `SHA256SUMS` релиза.
7. Из них делается манифест WinGet (`cargo xtask winget manifest`, см. [`winget.md`](winget.md)).

Без SignPath программа публикуется неподписанной, в журнале остаётся notice. Подпись не подделывается.

## Как это проверяется

Тесты запускают настоящие процессы и настоящий канал управления: `cargo test -p oncl-winget-setup --test maintenance`. Они проверяют:
- активная операция не прерывается, `Setup.exe` не стартует;
- новые операции блокируются, пока действует «заморозка»;
- если установщик убит, программа освобождается;
- открытое окно или незавершённый период тишины дают «занято»;
- `Setup.exe` с кодом 0 без установки и неверная версия (манифест, запись в «Приложения и возможности», программа, расположение, архитектура) приводят к отказу.

Вместо настоящего `Setup.exe` Velopack в тестах работает **тестовая обвязка** `oncl-winget-harness`. Это поддельный рабочий стол, стоящий за настоящим `ActivityGate`, и поддельный `Setup.exe`, который пишет в одноразовый каталог и в одноразовый ключ реестра HKCU `OpenNCALayer-test-*`. Настоящий `Setup.exe` пишет настоящую запись в «Приложения и возможности» и на одноразовый корень не перенаправляется.

Три теста с настоящей программой помечены `#[ignore]` и требуют собранной обвязки (файл `crates/openncalayer/tests/maintenance_e2e.rs`):
- `real_idle_daemon_is_held_for_setup_and_released`;
- `real_signing_in_flight_gets_busy_and_completes_correctly`;
- `a_killed_installer_releases_the_real_daemon`.

Сборка и запуск:

```sh
cargo build -p oncl-winget-setup --bin oncl-winget-harness
cargo test -p openncalayer --features e2e-prompter --test maintenance_e2e -- --ignored
```

Окно Slint (`any_window_open`) в настоящей программе без экрана не проверяется.

CI (`ci.yml`, job `windows-package`) собирает программу без обвязки, запускает `cargo xtask package winget-setup` (проверку PE-файла) и `cargo test -p oncl-winget-setup --test maintenance`.

## Что сделать мейнтейнеру один раз

Репозиторий не меняет ни секреты, ни серверные настройки SignPath. Перед первым релизом с установщиком для WinGet мейнтейнер один раз добавляет в **проект SignPath** (не в этот репозиторий) то, что `release.yml` отправляет на подпись отдельным запросом. Это артефакт `signpath-unsigned-winget-setup-<вариант>` — zip с одним файлом `openncalayer-<версия>-win-<x64|x86>-winget-setup.exe`.

В настройки артефакта (`artifact-configuration` — ту, по которой подписывается `signpath-unsigned-setup-*`, либо отдельную, на которую указывает `SIGNPATH_SIGNING_POLICY_SLUG`) нужно добавить элемент `<pe-file path="*-winget-setup.exe">` с тем же шагом Authenticode.

Пока этого нет, SignPath отклонит запрос, и job `binaries` упадёт, а не выпустит неподписанный файл. Если секретов SignPath нет совсем, шаги подписи пропускаются, а установщик публикуется неподписанным с notice в журнале.

## Известное слабое место: программа запустилась, пока готовился `Setup.exe`

Последняя проверка (одна попытка, без повторов) делается **после** повторной проверки SHA-256 копии `Setup.exe` и прямо перед его запуском.
- Если при первой проверке программы не было, а теперь она есть, она получает обычную «заморозку».
- Любой процесс установки, о котором не спрашивали (другой `openncalayer.exe`, `Update.exe`, вторая копия программы), отменяет запуск с кодом 4. Причина: `Setup.exe` завершает **все** процессы под корнем установки (`nmhost.exe` не считается).

Остаётся окно в **несколько секунд**: от последней проверки до момента, когда `Setup.exe` (читает свой файл, проверяет prerequisites, место и ОС) дойдёт до принудительной остановки процессов. Программа, которая стартовала именно тогда (автозапуск при входе, relay расширения), не заморожена и может быть остановлена.

Закрыть это можно только двумя способами:
- изменить `Setup.exe` (но закреплённый Velopack не меняется);
- ввести маркер «идёт обновление» (именованный mutex или файл в каталоге данных), который установщик ставит до первой проверки, а программа и relay соблюдают при старте. Это поможет только версиям, которые о нём знают.

## Особые случаи

- Запущенная программа без канала управления (старая версия): код 5.
- Администратор при выключенном UAC: код 8, так задумано.
- Два установщика одновременно без запущенной программы: между ними нет общего замка, решает собственная блокировка `Setup.exe`.
- Страница, которая опрашивает NCALayer (`getActiveTokens`), продлевает период тишины. Поэтому код 4 в занятом браузере — нормальный исход.
- `winget install --interactive` запускает программу без `--silent`: код 2.
- Установка более старой версии поверх новой не отклоняется.
- Код 4 в манифесте WinGet — не успех. `Setup.exe`, который не завершился за 15 минут, не останавливается: «заморозка» при этом снимается, временная копия остаётся.

Намеренно не учитывается:
- `oncl-server` без окон, `oncl` и программы, встраивающие SDK: они не входят в десктопный пакет;
- сканирование токенов в окне «Инструменты» не идёт через движок (его покрывает признак открытого окна);
- новые окна во время «заморозки» не блокируются, их операции ждут в `begin`.

## Что считается операцией

Все учитываются в одном `ActivityGate`:

| Что начинается | Как учитывается |
|---|---|
| Запрос модуля со страницы по WSS и через мост расширения (в том числе вызовы плагинов: это те же модули) | `session::dispatch` берёт `ActivityLease` на время обработки |
| Операции окна «Инструменты» (подпись, хеш, сведения) | `Engine::with_activity`: lease привязан к `OperationLease` и живёт, пока последний владелец операции (контекст, нативный worker, ответ) не отпустит её |
| Открытое окно (подтверждение, настройки, мастер TLS, плагины) | `DaemonHost::hold` спрашивает `window_open` уже после «заморозки» |
| Штатное обновление, второй установщик | та же «заморозка» (исключительная) |

## Границы последней проверки (`last_look`) и запуск тестов

- Процессы, которые нельзя открыть (другой сеанс, защищённые), `last_look` пропускает: ошибка открытия не считается препятствием. Это тот же охват, что у принудительной остановки в самом `Setup.exe`. Препятствием считается только сбой при получении списка процессов.
- Тесты не для Windows (`tests/maintenance/main.rs`) запускаются только вручную (например, в WSL: `cargo +1.99.1 test -p oncl-winget-setup --test maintenance`). Три теста `#[ignore]` с настоящей программой требуют заранее собранной обвязки (`cargo build -p oncl-winget-setup --bin oncl-winget-harness`).
