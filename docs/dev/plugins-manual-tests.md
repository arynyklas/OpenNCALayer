# Порты плагинов в окне ручной подписи: как собрать wasm и прогнать тесты

Для разработчиков портов плагинов. Здесь описано, как проверить, что операции плагина (`[[operations]]` в `plugin.toml`) работают через окно «Плагины» (ручную подпись): как собрать модули, запустить тесты и добавить новый порт.

## Что проверяют тесты

Тесты `crates/oncl-core/tests/plugin_ports_manual.rs` берут **настоящие wasm-модули портов** (`plugins/<порт>`) и прогоняют их через **настоящий путь ручного вызова** в `oncl-core` с **настоящим придуманным ключом**. Устройство ручного вызова — в [`manual-plugins.md`](../design/manual-plugins.md), список операций и страниц — в [`manual-plugins-inventory.md`](../design/manual-plugins-inventory.md).

Для каждой объявленной операции тест проверяет три вещи:
- вызов завершился `Applied` (ключ применён);
- ответ порта разбирается так, как это описано в документации;
- подпись **верна по независимому оракулу** (программе, которая не использует наш код).

Если объявление в `plugin.toml` отличается от того, что модуль на самом деле передаёт ключевому вызову, ядро отвергает вызов (`options-mismatch`) до использования ключа. Поэтому прогон заодно доказывает, что объявление верное.

## Как запустить

Одна команда:

```text
cargo xtask plugin-ports-manual [--wasm-dir <каталог>] [--no-build] [фильтр…]
```

Она делает три шага:
1. Собирает порты: `cargo build --release --locked --target wasm32-unknown-unknown --workspace` в каталоге `plugins/` (результат — в `target/plugin-build`; сеть не нужна, если зависимости уже в кэше cargo; около 35 с).
2. Запускает `plugin-ops-check --require-wasm`: сверяет импорты каждой операции с импортами модуля.
3. Запускает `cargo test -p oncl-core --features plugins --test plugin_ports_manual -- --ignored [фильтр…]` с переменной `ONCL_PLUGIN_WASM_DIR`.

Фильтр — часть имени теста (например, `rating1c` или `network`).

Тесты помечены `#[ignore = "needs the built port wasm…"]`: без модулей они бессмысленны, а обычный `cargo test` не должен собирать 34 модуля. **В CI они не пропускаются.** Job `test` запускает `cargo test --workspace --all-features -- --include-ignored`. Если `ONCL_PLUGIN_WASM_DIR` не задан, тесты сами собирают `plugins/` в `target/plugin-ports` (как `oncl-port-tests`). Затем шаг «Plugin operations lint» проверяет импорты по этим модулям с `--require-wasm`. Если модулей нет, тест падает с сообщением, а не пропускается.

## Что нужно для запуска

Нужны OpenSSL 3 и отдельное окружение Python — по инструкции в [`development.md`](development.md), раздел «Что нужно для тестов».

| Переменная | Что это |
|---|---|
| `ONCL_PLUGIN_WASM_DIR` | Каталог с файлами `oncl_port_<порт>.wasm` (`-` в имени порта заменяется на `_`). Если не задана, тесты собирают `plugins/` сами (`oncl_testkit::plugin::ports_built`) |
| `ONCL_OPENSSL` | OpenSSL 3 с `cms`. Если не задана — `openssl` из `PATH`, а в Windows — OpenSSL из Git for Windows. Оракул CMS и сырой подписи |
| `ONCL_PYHANKO_PYTHON` | python отдельного окружения с `lxml` и `cryptography`. Если не задана — `python3` или `python` из `PATH`. Оракул XML-DSig (`tests/support/oracle/xmldsig_verify.py`). Если нужного окружения нет, тест падает, а не пропускается |

## Что проверяет оракул

- **CMS.**
  - `oncl_pki::cms::verify` над одобренным документом проверяет подпись, и она **не** должна подойти к другому документу.
  - `openssl cms -verify -binary -noverify` делает то же и тоже отказывает на другом документе.
  - Сертификат подписанта в CMS — это сертификат ключа.
  - Вложенное содержимое (attached) побайтно равно документу.
  - Метка времени проверяется по наличию `signatureTimeStampToken` в отчёте.
- **Сырая подпись (raw).** RSA PKCS#1 v1.5 SHA-256 проверяется открытым ключом сертификата из репозитория **и** командой `openssl pkeyutl -verify -rawin -digest sha256`.
- **XML.** Подпись проверяют `oncl_xml::verify` и `xmldsig_verify.py` (lxml: каноникализация, дайджест каждого `Reference` после его преобразований, подпись `SignedInfo` RSA-ключом сертификата, сертификат в `KeyInfo` — это сертификат ключа). Структура: какой элемент подписан, куда вставлена подпись, документ без подписи равен исходному. Оракул обязан отказать на изменённом документе. ГОСТ-подписи оракул не проверяет (`unsupported`): ключи ГОСТ проверяют только проверяющие из репозитория.

## Тестовая обвязка (`tests/support/ports.rs`)

Её используют все тесты портов. Подключается так: `#[path = "support/ports.rs"] mod ports;`.

```rust
run_port_operation(port, operation, params, &RunOptions) -> PortRun
try_run_port_operation(…) -> Result<PortRun, PluginPrepareError>
RunOptions { tamper: Option<Box<dyn Fn(&str) -> String>>, key: Option<&'static str> }   // RunOptions::tampered(op, from, to)
PortRun { call: ApprovedCall, summary: ConsentSummary, request: String, cert, applications, http_log }
assert_applied(&run) / assert_refused_before_the_key(&run) / reply_json(&run) / from_base64(..)
oracle::verify_cms(cms, content, &cert, attached) -> CmsFacts
oracle::verify_raw_rsa(&cert, data, signature)
oracle::verify_xml(signed, &cert, n) -> XmlFacts;  oracle::assert_xml_rejected(doc, &cert)
```

Что делает `run_port_operation`:
1. Читает `plugins/<порт>/plugin.toml` и модуль и ставит их в `PluginRegistry` (`PackageHash::Loose` через `loose_package_hash`) с лимитами `ManualLimits::desktop()`. Это то же определение, что у настоящей программы (см. раздел о лимитах ниже). Другие лимиты можно подставить через `RunOptions.limits`.
2. Регистрирует политику объявленных операций `allow_declared_with_pki` с адресами `oncl_plugin::NCA_PKI_ENDPOINTS` (одна константа и здесь, и в настоящей программе): GET и POST для OCSP и службы времени (`DEFAULT_OCSP`, `DEFAULT_TSA`).
3. Готовит ключ: фикстура `user-rsa-sign`, сертификат перевыпущен временным корнем, AIA указывает на OCSP-ответчик по умолчанию, ответчики OCSP и службы времени — подставные, под тем же корнем; часы — `NOW` из фикстур.
4. Проходит весь путь: `plugin_prepare` → `ConsentSummary` → `UserConfirmation::after_user_confirmed` (публичный конструктор: единственный способ, которым это делает интерфейс) → `approve` → `plugin_call_approved`.

Ничего со стороны плагина не подменяется.

**Негативный тест для порта:** `RunOptions::tampered(операция, "поле = значение", "поле = другое")` правит манифест (подмена), и вызов обязан быть отвергнут с `options-mismatch` (`TicketRefusal::Options`), `NotApplied`, ключ не применён.

## Как добавить порт

1. В `plugins/<порт>/plugin.toml` добавьте `[[operations]]` (форма описана в [`plugins.md`](../design/plugins.md)). `min_core` не ниже `operations_min_core()`. Поднимите версию плагина в `plugin.toml` и `Cargo.toml` (и в `plugins/Cargo.lock`). Хеши в `plugins/workspace/registry.toml` не трогайте: ими занимается выпуск.
2. Запрос в шаблоне должен быть **ровно** тем, что шлёт страница (см. инвентаризацию). Профиль — **ровно** тем, что порт передаёт ключевому вызову. В `imports` указывайте только те, что действительно вызываются: лишний отвергнет `plugin-ops-check`, недостающий даст `Denied` при вызове. У любой операции с ключом ставьте `network = "pki"`.
3. Создайте файл `tests/plugin_ports_manual/<порт>.rs` и добавьте `mod` в `plugin_ports_manual.rs`. По тесту на каждую операцию (положительный, с оракулом) и негативный с `tampered`.
4. Запустите `cargo xtask plugin-ports-manual <порт>`.

## Лимиты окна ручной подписи (`ManualLimits::desktop()`)

Одно определение лимитов для настоящей программы (`crates/openncalayer/src/plugins/manual.rs`: `ManualLimits::desktop().instance` при установке каждого плагина) и для тестовой обвязки: `oncl_core::plugins::ManualLimits`. Умолчания SDK не менялись: библиотека консервативна.

### Что показали настоящие порты

Измерения на отладочной сборке с запасом по лимитам; пики взяты из временной инструментации.

| Операция | Метаданные сверх `max_transfer` | Линейная память гостя | Ответ |
|---|---|---|---|
| `sign-xml`, `sign-xml-element` (1 КиБ…64 КиБ) | ≈ 65,0 МБ, от размера документа не зависит (XML ex и XAdES B/T/LT — то же) | 1,2–1,7 МБ | 3,5–67 КБ |
| CMS и raw: 1 КиБ | 2,4 МБ | 1,2 МБ | 2,2–5,7 КБ |
| CMS и raw: 1 МиБ | 135 МБ | без вложения 9–11 МБ, с вложением 14,5 МБ | вложенная CMS 1,33 × документ |
| CMS и raw: 4 МиБ | 539 МБ | 32–40 МБ, с вложением 53 МБ | |
| CMS и raw: 12 МиБ | 1,61 ГБ | 98–123 МБ, с вложением 153 МБ | 16,0 МиБ |

- Метаданные для CMS и raw = `max_transfer` + 128 × размер документа + 2,2 МБ: каждый ключевой вызов допускает свои аргументы по 128 байт метаданных на байт (`host_call_metadata`). Для XML ≈ 65 МБ уходит на проверку подписанного документа после подписи (`oncl_xml::verification_metadata_bound`); от размера документа это не зависит.
- Память гостя — не больше 12,1 байта на байт документа (для вложенной CMS) плюс 3 МиБ. Передача — документ в base64 (запрос) и 4/3 документа в ответе. **Передача в 16 МиБ не вмещает документ в 12 МиБ** (ответ получается 16,0 МиБ).
- Сверх этого вызов резервирует `8 × max_transfer + max_memory` памяти и `max_transfer` метаданных (`call_scratch`). Метаданные считаются ещё и в память.

`manual_call_budget(лимиты, вид, длина, длина_текстовых_параметров)` суммирует всё это с запасом:
- длина аргументов = документ + все текстовые параметры вызова + 4 КиБ. Параметр `param:` может взять значение из любого из них, включая сам подписываемый XML-текст, поэтому XML-текст считается и как документ, и как текстовый параметр;
- для CMS и raw добавляется 4 МиБ;
- для XML берётся граница `verification_metadata_bound` и 8 МиБ памяти.

`Engine::plugin_prepare` и `plugin_call_approved` берут эти резервы из бюджета контекста и сразу отдают. При нехватке они отказывают **до ключа и до согласия пользователя** с подкодом `resource-budget` (если нет временного хранилища для XML — `no-temporary-store`).

### Как выбран `max_document`

Бюджеты — это потолки учёта, а не выделенная память. Платформа обещает ограниченный объём памяти (контрольный процесс — 1 ГиБ). Измерено: пик рабочего набора процесса теста (psutil, отладочная сборка, весь тестовый стенд вместе с самим документом) при вложенной CMS документа максимального размера. Базовая линия (малый документ) — 20 МиБ.

| `max_document` | Передача | Линейная память | Бюджет метаданных | Бюджет памяти | Резерв по модели вложенной CMS (`CmsEx`): память / метаданные | Пик рабочего набора | Запас до 1 ГиБ по бюджету памяти |
|---|---|---|---|---|---|---|---|
| 2 МиБ | 5 МиБ | 60 МиБ | 384 МиБ | 512 МиБ | 374 / 266 МиБ | 62 МиБ | 2,0× |
| **4 МиБ** | 9 МиБ | 112 МиБ | **704 МиБ** | **896 МиБ** | 718 / 526 МиБ | 104 МиБ | 1,14× |
| 8 МиБ | 17 МиБ | 216 МиБ | 1280 МиБ | 1664 МиБ | 1406 / 1046 МиБ | 247 МиБ | бюджет 1,6 ГиБ > 1 ГиБ |
| 16 МиБ | 33 МиБ | 424 МиБ | 2368 МиБ | 3136 МиБ | 2782 / 2086 МиБ | 458 МиБ | бюджет 3,1 ГиБ — втрое выше |

(Бюджеты считаются по самому большому вызову — `XmlEx`, поэтому метаданных в них больше, чем в резерве `CmsEx`.)

**Выбор: для 64-битной сборки — 4 МиБ.** Реальный рабочий набор и при 16 МиБ (458 МиБ) укладывается в 1 ГиБ. Но потолки учёта при 8–16 МиБ (1,6–3,1 ГиБ) превышают бюджет машины, а модель «128 байт метаданных на байт» не нами выбрана. Меньший предел документа с ясным отказом (`resource-budget`, либо `RequestTooLarge` у самого шаблона — до согласия) лучше многогибибайтных потолков.

**Для 32-битной сборки — 512 КиБ.** `oncl_plugin::MAX_MEMORY` там 16 МиБ (память гостя 12,1 × 0,5 МиБ + 3 МиБ ≈ 9 МиБ), передача 2 МиБ, бюджеты метаданных и памяти по 192 МиБ.

Форма операции принимает документ до `max_bytes`, объявленного в манифесте (по умолчанию 16 МиБ), а рабочий стол отказывает выше своего предела.

**`max_document` — не жёсткий предел.** Это размер, под который считаются лимиты. Реально документ допускает проверка перед вызовом по бюджету: при 4 МиБ принимаются документы примерно до 5,3 МиБ (вложенная CMS на 5 МиБ подписывается по-настоящему). Форма в окне «Плагины» сужает объявленный в манифесте `max_bytes` до `ManualLimits::desktop().max_document`, чтобы отказ был ясным до выбора файла, а подпись под полем показывает действующий предел. Отказ по размеру документа — `InputLimit` (подкод `resource-budget`). Если бюджеты не вмещают даже модуль с пустым документом (движок настроен неверно), то `MemoryLimit` с тем же подкодом.

**Бюджеты 704/896 МиБ — это потолки учёта одного движка, а не выделенная память:** измеренный пик рабочего набора при 4 МиБ — около 104 МиБ. Движок документов держит свой бюджет в 1 ГиБ. Сумма потолков двух движков больше 1 ГиБ, но реальной памяти сверх измеренного они не добавляют, потому что потолки не выделяются.

**Движок окна «Плагины» обязан брать `ManualLimits::desktop().resources`** (со своим `operation_timeout`). С умолчаниями SDK любая XML-операция и любой документ CMS крупнее ≈ 0,4 МиБ отказываются с `resource-budget`. Страница «Плагины» (`oncl_ui::plugin_offer`, `engine_limits()`) так и делает. Движок документов (`main.rs`, `desktop_limits()`: 24 часа и умолчания бюджетов) плагинов не держит, ему они не нужны. Проверка перед вызовом не удерживает резерв после себя: что никто не займёт место между ней и применением ключа, обеспечивает `max_in_flight = 1`. В сумму `manual_call_budget` входит и ответ модуля (`max_transfer` памяти), поэтому узел с большой передачей и малым документом не проскочит.

Итоговые значения `ManualLimits::desktop()` для 64-битной сборки:
- `max_document` 4 МиБ, `max_transfer` 9 МиБ, `max_memory` 112 МиБ, `metadata_bytes` 704 МиБ, `memory_bytes` 896 МиБ;
- остальное — умолчания `ResourceLimits`. `operation_timeout` — 5 минут (хост, который ждёт пользователя внутри операции, продлевает его сам: `ResourceLimits { operation_timeout, ..ManualLimits::desktop().resources }`);
- `fuel` — умолчание SDK.

`ManualLimits::for_max_document` выводит всё из размера документа:
- передача = (4/3 документа + 16 КиБ) × 1,5;
- память = 2 × (13 × документ + 4 МиБ), но не выше `MAX_MEMORY`;
- бюджеты = `manual_call_budget` самого большого XML-вызова × 1,1, с округлением вверх.

### Тесты лимитов

- `limits::every_cms_and_raw_operation_signs_a_document_at_the_limit` — все четыре операции CMS и raw на документе в 4 МиБ, оракулы openssl и репозитория.
- `the_estimate_signs_and_one_byte_less_is_refused_before_the_key` — все 7 операций: ровно по модели подписывают, а на байт меньше метаданных или памяти получают `resource-budget` до ключа.
- `the_default_metadata_budget_refuses_an_xml_signature_before_the_key`.
- `a_document_over_the_limit_is_refused_before_the_key`.
- `an_engine_without_a_temporary_store_refuses_xml_before_the_key`.

### Прочие настройки, которые нужны окну ручной подписи

- `EngineServices::with_temporary_store` нужен для XML (без него — `no-temporary-store` до ключа). Также `with_validation` (проверка подписанта онлайн) и `with_plugin_keys`. Временное хранилище окна — `TemporaryStore::new(spool)` в том же каталоге `data/spool`, что у движка документов (`desktop_engine`: замок владельца и очистка устаревшего при старте).
- Адреса для `network = "pki"`: GET и POST для OCSP и службы времени (`oncl_plugin::NCA_PKI_ENDPOINTS`). Подписанта проверяют GET-запросом к OCSP из сертификата, а метку времени Kalkan берут GET-запросом.
- Операция с `uses.key` без `network = "pki"` не подписывает никогда (`network.rs`).

## Что оракулы НЕ доказывают

- **Метка времени.** Проверяется только наличие `signatureTimeStampToken` в CMS (отчёт `oncl_pki::cms::report`). Сам токен независимым инструментом не проверяется.
- **ГОСТ.** Ключи ГОСТ проверяют только наши проверяющие; `openssl` и `xmldsig_verify.py` знают только RSA. Объявленные профили не фиксируют алгоритм (ядро выбирает по ключу), поэтому ключи ГОСТ не отсекаются: ручной прогон показал, что операции с ними подписывают. Автоматического положительного теста с ключом ГОСТ в наборе нет, ГОСТ-подписи независимым инструментом не проверяются.
- **`create-raw-sign`** проверяет RSA PKCS#1 v1.5 SHA-256. Опций у неё нет, поэтому негативный тест подмены профиля для неё невозможен; остальные 6 операций им покрыты.
- **XML.** Оракул отвергает неизвестные преобразования, неоднозначный `Id` (два элемента с одним `Id`) и подпись без ссылок (`the_xml_oracle_rejects_wrapping_shapes`).
- **`sign-xml-element`.** Оба XPath (`tbs` и `parent`) абсолютные и вводятся текстом. Подписываемый элемент обязан иметь атрибут `Id`. Форма оригинала «tbs с пустым parent» не покрыта: родитель обязателен (профиль `placement = parent` значит, что `parent` задан). То же у `eproc.sign-xml-element` и (для `xml_ex`) у `rating1c`: сам порт принимает пустой родитель, а окно — нет. У `eproc` тип ключа зафиксирован шаблоном (`keyType = SIGNATURE`): привязанный ключ типа AUTHENTICATION закончится ответом порта «action.canceled».
- **Размер wasm.** `PluginRegistry::install` сам размер wasm не ограничивает (`MAX_WASM` = 16 МиБ проверяет только `Package::read`). Хост, который ставит модуль не из пакета, обязан проверить размер сам.
