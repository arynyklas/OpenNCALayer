# Выпуск версии и подпись индекса обновлений

Инструкция для мейнтейнера: как выпустить версию, подписать индекс обновлений и опубликовать его, чтобы установленные программы увидели обновление. Формат индекса, правила проверки и поведение программы — в [`../design/update-index.md`](../design/update-index.md).

Обычный выпуск — это разделы 3 (собрать релиз), 4 (подписать индекс) и 8 (проверить). Разделы 1, 2 и 7г описывают разовую настройку. Остальные — отдельные случаи: продление индекса (5), отзыв версии (6), ключи (7), плагины (7а), сайт (7в), приватность (9).

## Как это устроено в общем

1. Вы ставите тег `v<версия>`. Сборка делает релиз и открывает pull request (PR) с **неподписанными** индексами каналов. Канал — это список версий, на которые смотрит программа: `stable` (обычные версии) и `beta` (в него идут и предварительные).
2. Вы подписываете индексы у себя на машине и пушите подписи в этот PR.
3. После слияния PR индексы публикуются на GitHub Pages, и программы видят новую версию.

Секретный ключ в CI не попадает никогда. Исключение одно: ключ `timestamp` TUF. TUF — второй слой защиты индекса. Ключ `timestamp` лежит в секрете GitHub, подписывает только «свежесть» уже подписанного вами снимка и больше ничего не может (раздел 7г).

Репозиторий проекта — `arynyklas/OpenNCALayer`, сайт — `https://arynyklas.github.io/OpenNCALayer/`.

Варианты сборки в этом документе:

| Вариант | Что это |
|---|---|
| `win-x64`, `win-x86` | Windows 10 и новее, 64 и 32 бита |
| `win7-x64`, `win7-x86` | Windows 7 SP1, 64 и 32 бита |
| `linux-x64` | Linux |
| `osx` | macOS (одна сборка для Intel и Apple Silicon) |

## 1. Ключи minisign для индекса (устаревший путь, один раз)

Подпись minisign нужна только клиентам версии `0.1.0-rc.1` и старше: они знают лишь её. Клиент `0.1.0-rc.2` и новее проверяет индекс только по TUF и minisign не знает. Пока в мире есть такие старые установки, путь minisign остаётся (минимум до `0.2.0`). Он нужен и самому `xtask` (`sign`, `index check`).

```sh
cargo xtask sign keygen --out <каталог вне репозитория>
```

- Пароль вводится дважды, без эха. Пустой пароль не принимается.
- В каталоге появятся `oncl-index.key` (секретный ключ, зашифрован паролем; в macOS и Linux права `0600`) и `oncl-index.pub`.
- Каталог внутри рабочего дерева git команда отвергает, если его нет в `.gitignore`. Отвергается и файл, который git уже отслеживает. Поэтому `--out crates/oncl-update/keys` не сработает: в этом каталоге лежат открытые ключи, их коммитят.
- Путь проверяется честно: учитываются символические ссылки, junction и `..`, а рабочее дерево ищется по ближайшему каталогу с `.git`. Если git не может открыть репозиторий, команда отказывается писать ключ.
- Секретный ключ хранится офлайн у мейнтейнера (на зашифрованном носителе). Его не коммитят и не кладут в секреты GitHub.

Открытый ключ коммитится:

```sh
cp <каталог>/oncl-index.pub crates/oncl-update/keys/current.pub
```

Сборки `0.1.0-rc.1` и старше вшивают `crates/oncl-update/keys/current.pub` и `crates/oncl-update/keys/next.pub` (если файлы есть; это делает `crates/oncl-update/build.rs`). Без них обновления в такой сборке выключены.

Клиент `0.1.0-rc.2` и новее ключами minisign не пользуется. Его точка доверия — корень TUF `crates/oncl-update/keys/root.json` (раздел 7г). Сборка без `keys/root.json` обновляться не умеет: обновления выключены, а в журнале и в окне настроек написано, что корень не встроен. Такая сборка **не должна попадать в индексы**. Копии, установленные из сборок без корня доверия, придётся переустановить.

## 2. Настройки репозитория (один раз)

Их меняет только мейнтейнер: workflow этого сделать не может.

- Settings → Pages → Source: **GitHub Actions**. Иначе `pages.yml` не опубликует ни индекс, ни сайт: сайт соберётся и проверится, но не развернётся (в журнале будет `::notice::Pages is not enabled`).
- Settings → Actions → General → **Allow GitHub Actions to create and approve pull requests**. Иначе job `index` не откроет PR с индексом.
- Settings → Rules (или Branches) → правило для `main`: обязательная проверка **Index check / check** (`index-check.yml`).
  - Проверка запускается на каждый PR и на каждый пуш в `main` и всегда отчитывается. Если не менялись ни `updates/`, ни `crates/oncl-update/keys/`, шаг cargo пропускается, а проверка проходит, так что обычные PR она не задерживает.
  - Обязательная проверка должна стоять на коммите до того, как `main` сдвинется. Запуск на пуш в `main` отчитывается уже после пуша. Поэтому с этим правилом изменения попадают в `main` только через PR, а прямой пуш проходит, только если мейнтейнер есть в списке обхода (bypass list) правила. У классической защиты ветки администраторы по умолчанию освобождены.
  - Workflow не может включить это правило сам. Без него можно слить неподписанный PR индекса: Pages такой индекс не опубликует, но и все следующие публикации встанут, пока его не подпишут.
- Окружение `tuf-timestamp` с секретом `TUF_TIMESTAMP_KEY` (создаётся при церемонии, раздел 7г). Окружению разрешена только ветка `main` (Deployment branches and tags → Selected branches → `main`). Секрет — именно **секрет окружения, а не секрет репозитория**: иначе его мог бы прочитать любой workflow, в том числе из ветки PR того же репозитория.

Необязательно — секреты подписи кода. Без них шаги подписи пропускаются с уведомлением в журнале сборки, и релиз выходит неподписанным:

- Authenticode (подпись для Windows) через SignPath: секрет `SIGNPATH_API_TOKEN`, переменные `SIGNPATH_ORGANIZATION_ID`, `SIGNPATH_PROJECT_SLUG`, `SIGNPATH_SIGNING_POLICY_SLUG`;
- Apple: секреты `APPLE_CERTIFICATE_P12` (base64), `APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGN_IDENTITY`, `APPLE_ID`, `APPLE_TEAM_ID`, `APPLE_APP_PASSWORD` подписывают и нотаризуют `.app` (пакет обновления, `.zip`, содержимое `.pkg`). Сам `.pkg` подписывается и нотаризуется, только если есть ещё `APPLE_INSTALL_IDENTITY` — идентичность «Developer ID Installer» из того же `APPLE_CERTIFICATE_P12`.

Необязательно — секрет `PRIVACY_DENYLIST` для проверки приватности в `privacy.yml` (раздел 9).

## 3. Выпуск версии

1. **Поднимите версию.**
   - В `[workspace.package]` файла `Cargo.toml`.
   - В одиннадцати пинах `version = "=<версия>"` у цепочки SDK: `oncl-flows`, `oncl-gost`, `oncl-pki`, `oncl-pdf`, `oncl-pdk`, `oncl-plugin`, `oncl-protocol`, `oncl-registry`, `oncl-token`, `oncl-update`, `oncl-xml` (в `[workspace.dependencies]`; без этого workspace не разрешится).
   - В четырёх `plugin.toml` встроенных модулей и в lock-файлах (подробно — [`sdk.md`](sdk.md), раздел 6).
   - Обновите `Cargo.lock` (`cargo check --workspace`), прогоните проверки из раздела «Перед отправкой изменений» в [`development.md`](development.md) и закоммитьте.

2. **Поставьте подписанный тег, проверьте подпись и запушьте его:**

   ```sh
   git tag -s v<версия> -m "OpenNCALayer <версия>"
   git tag -v v<версия>
   git push origin v<версия>
   ```

   Тег аннотированный и подписан вашим ключом (`user.signingkey`, тем же, что подписывает коммиты). `git tag -v` должен сообщить о верной подписи. Если подписи нет или она не сходится, а тег ещё не отправлен, удалите его (`git tag -d v<версия>`) и поставьте заново.

   Первым делом job `version` сверяет тег с версией в `Cargo.toml` и останавливает сборку при расхождении. Версия с суффиксом (`0.1.0-alpha.1`) выходит как pre-release и попадает только в канал `beta`. Версия без суффикса выходит как обычный релиз и попадает в оба канала, `stable` и `beta`.

3. **`release.yml` собирает релиз.** Для каждого варианта сборки (таблица выше) он делает архивы, установщики и пакеты Velopack (инструмент упаковки и обновления) с дельтами — то есть с файлами, которые содержат только отличия от прошлой версии. Команды: `cargo xtask package windows|macos|linux`. Linux собирается в контейнере со старой системной библиотекой glibc 2.28, чтобы программа шла и на старых дистрибутивах (`cargo xtask package linux-build`). Кроме того, он собирает расширение браузера, список состава SBOM и `SHA256SUMS`, выпускает подтверждение происхождения (attestation) на каждый файл и создаёт релиз.

   Установщики:
   - `openncalayer-<версия>-<вариант>-setup.exe` — четыре варианта Windows;
   - `openncalayer-<версия>-osx.pkg` и `openncalayer-<версия>-osx.zip`;
   - `openncalayer-<версия>-linux-x64.AppImage`;
   - для `win-x64` и `win-x86` ещё `openncalayer-<версия>-<вариант>-winget-setup.exe` — установщик для WinGet ([`winget-installer.md`](winget-installer.md)). Манифест WinGet делает `cargo xtask winget manifest` из этих файлов и `SHA256SUMS` релиза, и только для релиза без суффикса. Порядок подачи — [`winget.md`](winget.md).

   Варианты `win7-*` собираются командой `cargo xtask win7`. Содержимое их пакетов (вместе с `Squirrel.exe` и заглушкой Velopack) и их `Setup.exe` проходят проверку импортов Windows 7 (см. [`development.md`](development.md), «Сборка для Windows 7»).

   **Пакет для Arch Linux.** Job `arch` берёт архив `linux-x64` этого же прогона и делает из него пакет `openncalayer-bin-<pkgver>-1-x86_64.pkg.tar.zst` (`cargo xtask package arch`). `pkgver` — версия без дефиса: `0.1.0-rc.4` → `0.1.0rc.4`. Затем в контейнере Arch Linux он собирает пакет `makepkg`, ставит, запускает `openncalayer --version` и удаляет. Пакет — артефакт `release-arch`: он попадает в релиз, в `SHA256SUMS` и в подтверждение происхождения, как остальные файлы. Собирается и для pre-release.

   **Встроенные модули** (WebAssembly) job `builtins` собирает один раз (`cargo xtask builtins build`, каталог `target/builtins` с `SHA256SUMS`) и выкладывает артефактом. Каждый вариант сборки скачивает его и задаёт `ONCL_BUILTINS_DIR`, поэтому все шесть вариантов вшивают одинаковые байты. (`cargo xtask win7` и `cargo xtask package linux-build` берут модули из этой переменной, а без неё собирают сами.) После сборки `cargo xtask builtins check --bin <программа>` сверяет вывод `openncalayer builtins` с `SHA256SUMS`. Контрольные суммы модулей публикуются файлом `builtins-SHA256SUMS`.

   **Проверка перед публикацией черновика.** Сверьте встроенные модули хотя бы одного варианта Windows и `linux-x64`:
   1. Положите файл `builtins-SHA256SUMS` в пустой каталог под именем `SHA256SUMS`.
   2. Распакуйте программу варианта.
   3. Запустите `cargo xtask builtins check --bin <программа> --dir <каталог>`.

   Команда должна сообщить, что вшиты все четыре модуля в том виде, в каком их собрал job `builtins`. Если она находит расхождение, черновик не публикуется.

   **Релиз сначала создаётся черновиком.** С флагом `--prerelease` — только версия с суффиксом. Дальше:
   - приватная лаборатория проекта (отдельные виртуальные машины) ставит установщики этого прогона на чистые Windows 7, Windows 11 и Linux и пишет статус коммита `vm-smoke`;
   - workflow `mac-smoke.yml` проверяет `.pkg` на Mac (раздел 8);
   - когда `vm-smoke` и `mac-smoke.yml` зелёные, допишите описание и опубликуйте черновик: `gh release edit v<версия> --draft=false`;
   - если красный любой из них, черновик не публикуется;
   - PR индекса для черновика пройдёт `index check` только после публикации: ссылки на файлы черновика не открываются.

   **Проверка на совместимость с оригиналом.** После `vm-smoke` агент лаборатории сверяет сборку этого тега с оригиналом NCALayer (артефакт `conformance-<вариант>`, раздел 7б) и пишет на коммит тега второй статус — `conformance`. Без зелёного `conformance` новая версия не попадёт в `stable`: его требует проверка PR индекса (раздел 4, шаг 3). Предварительной версии, которая идёт только в `beta`, он не нужен.

4. **Job `index` готовит PR с индексами.** Он скачивает файлы релиза и для каждого канала версии выполняет `cargo xtask index add --channel <канал> --tag v<версия>`: для pre-release это `beta`, для релиза — `stable` и `beta`. У каждого индекса свой следующий номер `seq`, прежние записи сохраняются. Затем job открывает PR «chore(updates): add …» с веткой `updates/v<версия>`. Вариант `osx` идёт в индексы наравне с остальными: универсальную сборку проверяет `mac-smoke.yml` на Mac с Apple Silicon и с Intel (раздел 8). Индексы в PR **не подписаны**, и `index check` не пропустит PR, пока не подписан каждый из них.

## 4. Подпись индекса в PR

На ветке PR, у себя на машине:

```sh
git fetch origin
git switch updates/v<версия>
```

1. **При необходимости уменьшите `rollout`** новой версии в индексах PR (`updates/v1/<канал>.json`, значение от 0 до 100). Это доля установок, которым версия предлагается. Руками меняются только значения полей. Переформатировать файл нельзя: он публикуется байт в байт, и `.gitattributes` запрещает git менять в нём концы строк.

2. **Подпишите каждый индекс PR** (для релиза — оба):

   ```sh
   cargo xtask sign updates/v1/stable.json --key <каталог>/oncl-index.key
   cargo xtask sign updates/v1/beta.json --key <каталог>/oncl-index.key
   ```

   Пароль вводится без эха. Перед записью `.minisig` команда проверяет формат и срок индекса, правило URL и саму подпись — открытым ключом той же пары, а не ключами из `crates/oncl-update/keys/`. Неверный, истёкший или ссылающийся не на релизы проекта индекс не подписывается. Подпись не тем ключом, что в `current.pub`, поймает только `index check` (шаг 3).

   **Шаг 2а: метаданные TUF.** Если репозиторий TUF уже создан (в дереве есть `tuf/v1`, раздел 7г), подпишите метаданные TUF над этими индексами. Делайте это **после** `cargo xtask sign`: `.minisig` нужен клиентам `rc.1`, а цель TUF — те же самые байты индекса. Поэтому после этого индексы не правятся.

   ```sh
   cargo xtask tuf update --keys <каталог ключей TUF>
   cargo xtask tuf check --no-timestamp --base origin/main
   ```

   Пароль ключей (один на root, targets и snapshot) вводится без эха и только если есть что подписывать. Команда:
   - копирует индексы в `tuf/v1/targets/indexes/<sha256>.<канал>.json`;
   - пишет `tuf/v1/metadata/<N+1>.targets.json` и `<N+1>.snapshot.json` (версии строго на 1 выше, срок 30 дней);
   - проверяет результат кодом клиента.

   Если индексы не менялись, она пишет «up to date» и ничего не меняет. `timestamp.json` она не трогает. До церемонии (когда нет `tuf/v1`) этот шаг пропускается.

3. **Проверьте так же, как это сделает CI** (нужен свежий `origin/main`):

   ```sh
   cargo xtask index check updates/v1 --base origin/main --vm-smoke --conformance
   ```

   Что проверяется:
   - подпись ключом `crates/oncl-update/keys/current.pub` (только им, не `next.pub`);
   - срок индекса и правило URL;
   - рост `seq` относительно базовой ветки;
   - ключ обновлений в теге каждой версии, которая новая относительно базы или с заменёнными пакетами (`crates/oncl-update/keys/current.pub` в теге должен быть равен `current.pub` или `next.pub` дерева);
   - ответ `HEAD` 200 на каждый URL пакета и расширения;
   - статусы коммита на теге каждой новой версии ядра: `vm-smoke = success` — у каждой, `conformance = success` — у новой версии в `stable` (для `beta` не нужен).

   Без сети используйте `--offline` без `--vm-smoke` и `--conformance`: тогда не проверяются ни `HEAD`, ни статусы.

   Если лаборатория ещё не поставила статус, проверка PR падает с сообщением «v<версия> has no successful … status». Когда статус станет зелёным, перезапустите проверку (Actions → Index check → Re-run). Красный статус значит, что версия в этот канал не выйдет.

4. **Закоммитьте индексы вместе с их `.minisig` и запушьте.** PR, открытый workflow, сам проверок не запускает, поэтому `index-check.yml` сработает именно на этот пуш. Коммитятся и файлы `tuf/v1`: без них `tuf check` откажет («index-mismatch: run `cargo xtask tuf update`»), как `index check` отказывает неподписанному индексу.

5. **Слейте PR.** После слияния `pages.yml` ещё раз проверяет индексы против коммита до пуша (`--base <github.event.before>`; на самом первом пуше — `--no-base`: подписи, срок и URL проверяются, а ключ в тегах нет, его проверили при добавлении версий). Затем он публикует каталог `updates/` на GitHub Pages вместе с сайтом проекта (раздел 7в). Клиенты читают `https://arynyklas.github.io/OpenNCALayer/updates/v1/<канал>.json`. Туда же, в `/tuf/v1/`, уезжает репозиторий TUF с `timestamp.json`, подписанным в этот день (раздел 7г).

**Если до слияния этого PR вышла ещё одна версия.** У второго PR тот же следующий `seq` на тех же файлах, и после слияния первого он конфликтует. Не разрешайте конфликт руками и не берите файлы своей ветки: `index check` сравнивает `seq` и пропавшие файлы, а не пропавшие версии, и такая правка молча потеряет версию из первого PR. Вместо этого перезапустите job `index` релиза второй версии (Actions → Release → Re-run job `index`), когда первый PR уже в `main`. Он соберёт индексы заново от свежего `main`, с обеими версиями и следующим `seq`. Затем подпишите, как выше.

Программы увидят новую версию при очередной проверке: первая — через 2–10 минут после запуска, дальше раз в 6–24 часа.

**Расширить раскатку позже** (вплоть до 100):
1. Поднимите `rollout` версии в `updates/v1/<канал>.json`. Для релиза — в обоих каналах.
2. `cargo xtask index refresh --channel <канал>` (изменённому индексу нужен новый `seq`, иначе проверка откажет).
3. Подпишите, откройте PR в `main` и слейте — как в разделах 5 и 6.

## 5. Продление индекса

Клиент отвергает индекс, которому больше 30 дней с момента `generated`, даже если в `expires` стоит более поздняя дата. Срок у каждого канала свой: каждый индекс, который не менялся 30 дней, надо продлить и подписать заново. Предварительные версии меняют только `beta.json`, поэтому уже опубликованный `stable.json` нужно продлевать и тогда, когда выходят одни пререлизы.

```sh
cargo xtask index refresh --channel <канал>
cargo xtask sign updates/v1/<канал>.json --key <каталог>/oncl-index.key
```

`refresh` меняет только `seq` (+1), `generated` и `expires` и удаляет устаревшую подпись. Список версий остаётся прежним. Дальше — PR в `main`, проверка и слияние, как в разделе 4 (в том числе шаг 2а, если есть `tuf/v1`).

## 6. Отзыв версии

Сломанную версию отзывают правкой индекса: в её записи ставят `"revoked": true`. Клиент читает только индекс своего канала, а релиз без суффикса записан и в `stable.json`, и в `beta.json`. Поэтому отзывать его нужно **в каждом индексе, где он есть, одним PR**. Если отозвать только в одном, установки другого канала останутся на этой версии и будут её получать.

Отозванная во всех индексах версия больше не предлагается. Установки, которые уже на ней, получают самую новую неотозванную версию своего канала, даже если она старше.

Порядок для релиза (для пререлиза — только `beta`):

```sh
# в updates/v1/stable.json и updates/v1/beta.json: "revoked": true у версии
cargo xtask index refresh --channel stable
cargo xtask sign updates/v1/stable.json --key <каталог>/oncl-index.key
cargo xtask index refresh --channel beta
cargo xtask sign updates/v1/beta.json --key <каталог>/oncl-index.key
cargo xtask index check updates/v1 --base origin/main
```

`refresh` нужен ради нового `seq`, иначе проверка откажет. Затем откройте PR и слейте. Если исправленная версия уже выпущена, достаточно отозвать сломанную: клиенты перейдут на исправленную как на обычное обновление.

## 7. Смена ключа minisign (устаревший путь)

Это касается только клиентов `0.1.0-rc.1` и старше. Клиент `rc.2` и новее доверяет корню TUF; ротация его ключей — в разделе 7г.

Старый клиент доверяет только ключам minisign, зашитым в его сборку: `current.pub` и, если есть, `next.pub`. `index check` (в PR и перед публикацией на Pages) проверяет подпись каждого индекса в `updates/v1/` ключом `current.pub` того же коммита. А тег каждой новой версии он проверяет на ключ `current.pub` или `next.pub` этого коммита. Версии, опубликованные до смены ключа, не перепроверяются: их теги хранят старый ключ.

Поэтому ключ меняют в три шага, и между ними есть период, когда сборки доверяют обоим ключам:

| Шаг | `current.pub` | `next.pub` | Чем подписаны индексы | Какие установки принимают индексы |
|---|---|---|---|---|
| до смены | старый | — | старым ключом | все |
| 1–2, переход | старый | новый | старым ключом | все; версии с двумя ключами примут и новый |
| 3, после переключения | новый | — | новым ключом | только версии с двумя ключами и более новые |

1. **Подготовка.**
   - `cargo xtask sign keygen --out <новый каталог>`.
   - Новый открытый ключ положите в `crates/oncl-update/keys/next.pub`, закоммитьте и выпустите версию **без суффикса** (релиз, а не пререлиз): пререлиз идёт только в `beta.json`, и установки на `stable` не получили бы сборку с двумя ключами.
   - Раскатайте её лучше на 100 %: установка, которая её не получит, после шага 3 обновляться перестанет.
   - Все индексы пока подписываются **старым** ключом: его знают и прежние сборки, и новая. `index check` принимает только подпись ключом `current.pub`, так что подпись новым ключом на этом шаге не пройдёт.
   - После переключения отзыв версии может откатить установку на сборку старше этой, а такая сборка новых индексов уже не примет.
2. **Ожидание.** Подождите, пока установки обновятся до версии с двумя ключами. Всё это время индексы подписываются старым ключом, их продления (раздел 5) тоже. Статистики установок у проекта нет, поэтому срок выбираете вы: клиенты проверяют индекс раз в 6–24 часа, но выключенные компьютеры и установки с выключенным автообновлением отстают.
3. **Переключение — одним PR в `main`:** замена ключей и переподпись **каждого** индекса. После замены `current.pub` `index check` отвергает индекс со старой подписью, поэтому ни этот PR, ни публикация на Pages не пройдут, пока со старой подписью остаётся хоть один канал. Для каждого файла `updates/v1/<канал>.json`, который есть (сейчас `stable` и `beta`):

   ```sh
   cp <новый каталог>/oncl-index.pub crates/oncl-update/keys/current.pub
   git rm crates/oncl-update/keys/next.pub
   cargo xtask index refresh --channel stable
   cargo xtask sign updates/v1/stable.json --key <новый каталог>/oncl-index.key
   cargo xtask index refresh --channel beta
   cargo xtask sign updates/v1/beta.json --key <новый каталог>/oncl-index.key
   cargo xtask index check updates/v1 --base origin/main
   ```

   `refresh` даёт каждому индексу следующий `seq`: без него изменённый индекс проверка не пропустит. Последняя команда проверяет все каналы сразу — подпись новым ключом из `current.pub`, срок, правило URL, рост `seq` и `HEAD` 200 по каждому URL. Она должна пройти до слияния: после слияния `pages.yml` проверяет те же индексы теми же ключами и только потом публикует. Закоммитьте ключи, индексы и их `.minisig` одним коммитом, откройте PR и после зелёного `index-check.yml` слейте. Открытые в это время PR с индексами (например, `updates/v<версия>` нового релиза) после этого надо обновить от `main` и подписать новым ключом.

Старый ключ в `next.pub` не остаётся: версии, собранные после переключения, ему не доверяют, и утёкший старый ключ для них бесполезен. Тем установкам, которые знают только старый ключ, это не поможет: если старый секретный ключ скомпрометирован, их защищает только переустановка.

Порядок важен: индекс, подписанный ключом, которого у клиента нет, отвергается как подделка, и обновления встают до переустановки.

## 7а. Выпуск плагинов

Плагины выходят отдельно от ядра, пачками. Релиз плагинов получает тег `plugins-ГГГГММДД` (второй за день — `plugins-ГГГГММДД.1` и так далее) и выходит как pre-release без флага Latest, чтобы «последним релизом» оставалось ядро. Выпускает его workflow `.github/workflows/plugins.yml`.

1. **Поднимите версию порта** в его `Cargo.toml` и `plugin.toml` (они должны совпадать) и слейте в `main`. Какие порты выйдут, видно заранее:

   ```sh
   cargo xtask plugin pending --channel beta
   ```

   Команда печатает каталоги `plugins/<порт>`, чьей пары `(id, version)` ещё нет в индексе `beta`. Пустой вывод значит, что выпускать нечего. Проверка, что версию не забыли поднять, — [`plugin-version-check.md`](plugin-version-check.md).

2. **Поставьте тег на `main` и отправьте его:**

   ```sh
   git tag plugins-ГГГГММДД && git push origin plugins-ГГГГММДД
   ```

   Workflow:
   - проверяет имя тега;
   - собирает каждый порт из `pending` дважды (`cargo xtask plugin pack`) и сравнивает пакеты байт в байт: пакеты детерминированы, и пути машины сборки в модуль не попадают;
   - проверяет, что `plugins/THIRD-PARTY.txt` свежий (`cargo xtask licenses --plugins --check`), и кладёт его рядом с пакетами. В нём лежат лицензии крейтов портов и шрифтов, которые порты встраивают в модуль (`plugins/<порт>/fonts/`: файл шрифта, источник из `fonts/README.md` и текст `OFL.txt`);
   - делает `SHA256SUMS`, подтверждение происхождения всех файлов и релиз.

   Если выпускать нечего, workflow заканчивается с notice и без релиза. Новый шрифт в порте кладут вместе с `OFL.txt` и `README.md` со строкой `Источник: <URL>`, иначе `cargo xtask licenses --plugins` откажется.

3. **Подпишите индекс.** Workflow открывает PR `updates/<тег>` с пакетами в индексе `beta` (`cargo xtask index add-plugin --channel beta`), неподписанным. На ветке PR:

   ```sh
   cargo xtask sign updates/v1/beta.json --key <каталог>/oncl-index.key
   cargo xtask index check updates/v1 --base origin/main
   ```

   Закоммитьте индекс с `.minisig` (и метаданные TUF — шаг 2а раздела 4), отправьте, дождитесь зелёного `index-check.yml` и слейте. Программы подхватят плагин при следующей проверке индекса и перезагрузят его без перезапуска ядра. Ключ подписи в CI не попадает.

4. **`stable`.** В `stable` workflow сам не пишет. Готовую версию плагина (без суффикса), проверенную в `beta`, вы добавляете вручную тем же порядком:

   ```sh
   cargo xtask index add-plugin --channel stable --tag <тег релиза> --package <пакет из релиза>
   ```

   Дальше — подпись `stable.json`, проверка, PR. Предварительную версию (`1.0.0-beta.1`) команда в `stable` не добавит.

   В `stable` выходит только порт с `conformance = "confirmed"` в `plugins/<порт>/registry.toml`. Это значит, что поведение порта сверено с работающим оригиналом, а принятые отличия записаны в `[[differences]]`. Порт с `computed` команда отвергает («`<id>`: conformance with the original is not confirmed (conformance = computed)»), так же как пакет, `id` которого нет ни у одного порта. Порты команда читает из `--plugins <каталог>` (по умолчанию `plugins/` рабочего дерева), поэтому запускайте её на коммите, где `registry.toml` порта уже говорит `confirmed`. Для `beta` порты не читаются.

**Собрать пакет локально:** `cargo xtask plugin pack <каталог крейта плагина>` — получится `target/plugins/<id>-<версия>.onclp`.

**Проверить объявленные операции плагинов.** `[[operations]]` в `plugin.toml` описывают, что плагин умеет подписывать в окне ручной подписи. Проверка:

```sh
cargo xtask plugin-ops-check [путь…] [--wasm-dir <каталог>] [--require-wasm] [--json]
```

- Без путей проверяются все `plugins/*/plugin.toml`.
- Правила схемы (имена, плейсхолдеры, подписи, профили, `max_uses = 1`, флаги `manual` и `server`) проверяет тот же разбор манифеста, что и в ядре.
- Команда сверяет объявленные `imports` операции с импортами собранного модуля (`target/plugin-build/wasm32-unknown-unknown/release/<крейт>.wasm`, он появляется после `plugin pack`) и печатает сводную таблицу: плагин, операции, запускаемые, derived, статус.
- Операции с `content = "derived"` помечаются «blocked until MP3b» (код 0): окно такие операции не запускает, и поставляемых операций с `derived` нет.
- Код выхода 1 — есть ошибки. Если модуля нет, это предупреждение и строка NOTICE (правило импортов пропущено); с `--require-wasm` — ошибка.
- Команда работает офлайн и быстро, поэтому выполняется в CI.

**Отзыв версии плагина** — как у ядра (раздел 6): `"revoked": true` у записи в каждом индексе, где она есть, затем `refresh`, подпись, проверка и PR. Установки на отозванной версии переходят на самую новую неотозванную, а если её нет — плагин выключается.

## 7б. Сборка для проверки совместимости

Тег версии собирает ещё и job `conformance` в `release.yml`. Он делает:
- ядро с тестовыми возможностями (`--features e2e-prompter`) для `linux-x64` и `win-x64`;
- пакеты всех портов (`dist/plugins/*.onclp`) с `SHA256SUMS`.

Это артефакт workflow `conformance-<вариант>`: он хранится 30 дней и **никогда не публикуется** (`publish` берёт только артефакты `release-*`). Им сверяют поведение с оригиналом в изолированной лаборатории.

Только в этой сборке есть:
- команда `openncalayer e2e install-plugin <пакет>` — ставит пакет как локальный плагин, включённым, и печатает `<id> <версия>`;
- переменная `ONCL_E2E_EXTRA_CA=<pem>` — исходящий HTTPS ядра и плагинов начинает доверять этому CA в дополнение к корням webpki.

В релизной сборке команды нет, а переменная ничего не меняет; CI это проверяет.

## 7б-2. Пакеты `oncl` и `oncl-server`

Тег версии собирает ещё и jobs `platform` (по вариантам `win-x64`, `win-x86`, `win7-x64`, `win7-x86`, `linux-x64`, `osx`) и `platform-sbom` в `release.yml`. Они делают самостоятельные программы SDK отдельными архивами `oncl-<версия>-<вариант>` и `oncl-server-<версия>-<вариант>` (`.zip` для Windows, `.tar.gz` для остальных; без Velopack и без файлов десктопа), `SHA256SUMS` и список состава CycloneDX (SBOM) для каждой программы.

Архивы делает `cargo xtask package platform --flavor <вариант> --bin <каталог> --version <версия> --dist <каталог>` (шаги описывает `--help`). Что при этом проверяется:
- сам вариант сборки: статический CRT, список импортов, которых нет в Windows 7, glibc 2.28, оба среза macOS;
- состав архива: ровно ожидаемые файлы, ни ключа, ни токена, ни тестовых данных;
- работа **распакованных** архивов, если хост может их запустить: `hash` и `verify`; `oncl-server` с примером конфигурации без слушающего сокета; подпись через сервер, включённый явно на loopback; чистая остановка.

Сборки для Windows 7 и Linux делает `cargo xtask package platform-build` (на закреплённом nightly Rust; Linux — в контейнере glibc 2.28), остальные — обычный `cargo build`.

Это артефакты workflow `platform-<вариант>` и `platform-sbom` (30 дней). Они **не** `release-*`: `publish` их не берёт, ничего не подписывается и не уходит в реестры и магазины браузеров. Архивы вы добавляете к релизу вручную после проверки.

## 7в. Сайт проекта на Pages

`pages.yml` публикует одним артефактом сайт проекта (`site/`, `cargo xtask registry build`: каталог портов, загрузка, история оригинала) и рядом с ним каталог `updates/`. Индексы копируются в артефакт после сборки сайта байт в байт. У сайта нет своего пути `updates`: workflow проверяет, что его нет, и сверяет копию (`diff -r updates _site/updates`).

Когда запускается:
- пуш в `main`, который меняет индексы, ключи, `tuf/`, `site/`, `plugins/*/plugin.toml` или `registry.toml`, `xtask/`, тексты возможностей плагинов, бандлы ядра или данные сайта;
- раз в сутки — подхватить новые релизы и факты из ветки `upstream`. GitHub отключает расписание после 60 дней без активности в репозитории; тогда включите его заново в Actions;
- после того как наблюдатель за оригиналом опубликовал факты (`repository_dispatch` с типом `upstream`, см. [`upstream-watch.md`](upstream-watch.md));
- после каждого запуска workflow Release (`workflow_run`). Релиз создаёт его job `publish` токеном `GITHUB_TOKEN`, а события от этого токена других workflow не запускают, поэтому событие `release` на такой релиз не приходит;
- когда вы публикуете черновик релиза, правите или удаляете релиз (событие `release`). Само это событие не деплоит (окружение `github-pages` пускает только ветку по умолчанию), а запускает `pages.yml` заново на `main`. Пока релиз — черновик, список релизов сайта его пропускает;
- вручную: Actions → Pages → Run workflow.

Вне пуша база проверки индексов — коммит, который сейчас развёрнут на Pages (последний успешный деплой окружения `github-pages`). Поэтому запуск по расписанию, после релиза или вручную не опубликует индекс, который не прошёл бы проверку пуша. Если деплоев ещё не было, проверка идёт с `--no-base`.

Каталог `updates/v1` нельзя «потерять» случайно. Сайт публикуется без него, только если его нет ни в базе, ни в коммите, развёрнутом на Pages. Если индексы есть хоть в одном из них, workflow падает, а не снимает их с Pages.

Список релизов и ветка `upstream` — внешние входы. Если их нет или они битые, в журнале будет предупреждение, а на сайте — «данных пока нет»; сборка идёт дальше. Битый `registry.toml` или битый индекс останавливает сборку.

## 7г. TUF: ключи, церемония, повседневная работа

TUF — схема, по которой программа проверяет, что индекс обновлений настоящий и свежий. Роли, сроки и поведение клиента описаны в [`../design/tuf.md`](../design/tuf.md). Здесь — что делает мейнтейнер. Команды — `cargo xtask tuf …` (справка: `cargo xtask tuf <команда> --help`). Они используют тот же код `oncl_update::tuf`, что и клиент, и проверяют каждый результат клиентом до завершения.

### Порядок выпуска: две подписи

- Сейчас индекс публикуется **двумя способами одновременно**: индекс minisign `updates/v1/<канал>.json` с `.minisig` (для клиентов `rc.1`, которые знают только minisign) **и** репозиторий TUF `tuf/v1` (для `rc.2` и новее). Клиент `rc.2` не знает minisign, клиент `rc.1` не знает TUF.
- Путь minisign (`updates/v1/*.minisig`, `crates/oncl-update/keys/current.pub`, `cargo xtask sign`, `cargo xtask index check`) остаётся в репозитории и на Pages минимум до `0.2.0`.
- Один PR индекса — две подписи по порядку. Сначала `cargo xtask sign` (`.minisig` для клиентов `rc.1`), затем `cargo xtask tuf update` (раздел 4, шаг 2а). Цель TUF — те же байты индекса, поэтому менять индекс после `tuf update` нельзя. Индексы, `.minisig` и `tuf/v1` коммитятся вместе. `index-check.yml` и `pages.yml` отказывают индексу, которого `tuf/v1` не перечисляет.
- Тег `v0.1.0` ставится только после того, как обновление `rc.2` → `rc.3` по TUF пройдено в лаборатории на **опубликованных** файлах. Клиент `rc.2`, поставленный из релиза, обновляется с Pages на `rc.3`: цепочка встроенный root → timestamp → snapshot → targets → индекс → пакет.
- Версия `rc.2` (клиент TUF) не выпускается, пока не выполнено оба условия: (1) пройдена церемония (`tuf init`, `crates/oncl-update/keys/root.json` в дереве, окружение `tuf-timestamp` и секрет `TUF_TIMESTAMP_KEY`); (2) `tuf/v1` опубликован на Pages, и команда `cargo xtask tuf verify-published --url https://arynyklas.github.io/OpenNCALayer/tuf/v1/` проходит (так же её запускает job `verify`). Сборка без `keys/root.json` обновляться не умеет и в индексы не попадает (критерий `keyed` в `release.yml` смотрит на `root.json`).

### Что где лежит

| Файл | Что это | Где хранить |
|---|---|---|
| `<ключи>/root.key`, `targets.key`, `snapshot.key` | секретные ключи Ed25519, зашифрованы паролем (формат секретного ключа minisign: scrypt и контрольная сумма; неверный пароль отвергается) | офлайн, на зашифрованном носителе; не в git |
| `<ключи>/timestamp.key` | ключ timestamp, **не зашифрован**, одна строка `oncl-tuf-ed25519-seed-v1:<64 hex>` | только как секрет GitHub; после установки секрета файл удалить (потеря ключа лечится ротацией: `tuf root --rotate-timestamp`) |
| `tuf/v1/metadata/<N>.root.json`, `<N>.targets.json`, `<N>.snapshot.json` | метаданные, **хранятся все версии** | git |
| `tuf/v1/targets/indexes/<sha256>.<канал>.json` | копия индекса под своим хешем | git |
| `crates/oncl-update/keys/root.json` | корень доверия клиента: копия `metadata/1.root.json` байт в байт (клиент встраивает его при сборке) | git |
| `metadata/timestamp.json` | его подписывает CI при публикации Pages | **не в git**; только в артефакте Pages |

Каталог ключей не должен лежать там, где git его закоммитит. `tuf init` проверяет это так же, как `sign keygen`, и не перезаписывает существующие файлы. В macOS и Linux файлы ключей получают права `0600`. **В Windows права владельца не выставляются**: файлы наследуют права каталога (`tuf init` печатает об этом предупреждение). Поэтому в Windows держите каталог ключей в папке, доступной только вам, на зашифрованном томе. Ключи шифруются scrypt с параметрами minisign (32 МиБ памяти); защита держится на длине пароля, так что берите длинную фразу.

### Церемония (один раз)

1. **Ключи, корень версии 1 и якорь:**

   ```sh
   cargo xtask tuf init --keys <каталог вне репозитория>
   ```

   Пароль (не короче 12 символов) вводится дважды, без эха. Один пароль на все три зашифрованных ключа: команды открывают root, targets и snapshot одним паролем, а ключи с разными паролями не откроют. Команда печатает идентификаторы ключей, пишет четыре файла ключей, `tuf/v1/metadata/1.root.json` (подписан ключом root, срок 365 дней, `consistent_snapshot: true`, четыре различных ключа, пороги 1) и копию `crates/oncl-update/keys/root.json`. Существующее она не перезаписывает.

2. **Окружение GitHub и секрет.** Через веб: Settings → Environments → New environment `tuf-timestamp` → Deployment branches and tags → Selected branches and tags → Add `main`. Или так:

   ```sh
   gh api -X PUT repos/arynyklas/OpenNCALayer/environments/tuf-timestamp \
     -F 'deployment_branch_policy[protected_branches]=false' \
     -F 'deployment_branch_policy[custom_branch_policies]=true'
   gh api -X POST repos/arynyklas/OpenNCALayer/environments/tuf-timestamp/deployment-branch-policies \
     -f name=main -f type=branch
   gh secret set TUF_TIMESTAMP_KEY --env tuf-timestamp < <каталог>/timestamp.key
   ```

   В PowerShell перенаправление `<` не работает, там так: `Get-Content -Raw <каталог>\timestamp.key | gh secret set --env tuf-timestamp TUF_TIMESTAMP_KEY`.

   Сразу после этого **удалите `timestamp.key`** (`rm <каталог>/timestamp.key`; в PowerShell — `Remove-Item`). Другой копии ключа быть не должно: потерянный секрет заменяется ротацией (`tuf root --rotate-timestamp`).

   Правило репозитория: окружение `tuf-timestamp` пускает **только `main`**, а секрет `TUF_TIMESTAMP_KEY` существует **только в нём**. `gh secret list` без `--env` его не показывает. Если такой секрет есть среди секретов репозитория, удалите его: `gh secret delete TUF_TIMESTAMP_KEY`. Проверяющих у окружения быть не должно: job подписывает по расписанию, без человека.

3. **Закоммитьте** `tuf/v1/metadata/1.root.json` и `crates/oncl-update/keys/root.json` вместе с первым `cargo xtask tuf update` (шаг 2а раздела 4) в ближайший PR индекса и слейте его **до тега `rc.2`**: сборка тега встраивает якорь из своего дерева, и без него `rc.2` не обновляется. Первая публикация Pages подпишет timestamp, а дальше это делается ежедневно.

4. **Проверьте.** После деплоя job `verify` workflow Pages зелёный, а адрес `https://arynyklas.github.io/OpenNCALayer/tuf/v1/metadata/timestamp.json` отдаёт файл.

До церемонии (нет `tuf/v1` и якоря) всё работает как раньше: `tuf check` пишет «no TUF repository yet» и проходит, Pages не публикует `/tuf/`, job `timestamp` ничего не делает. **После** церемонии пустой или отсутствующий секрет — ошибка: запуск Pages красный, ничего не деплоится (старый сайт с ещё действующим timestamp продолжает отдаваться до 7 дней). «Без timestamp» допустимо только пока нет `tuf/v1` (и в форках, где job `timestamp` не запускается: `github.repository` должен быть `arynyklas/OpenNCALayer`).

### Повседневно и по расписанию

- **Каждый выпуск индекса:** раздел 4, шаг 2а.
- **Раз в месяц (не реже чем раз в 30 дней, даже без выпуска):** `cargo xtask tuf update --keys <каталог> --refresh`. Появятся новые версии `targets` и `snapshot` с теми же целями и новым сроком. Дальше PR, `index-check.yml`, слияние. Раз в неделю `tuf-expiry.yml` проверяет `main` и падает (GitHub присылает письмо о падении запуска по расписанию), когда targets или snapshot истекают меньше чем через 10 дней или root — меньше чем через 45.
- **Раз в год:** `cargo xtask tuf root --keys <каталог>` — продление root (версия N+1, 365 дней, те же ключи), подписанное ключом root. Просроченный root клиент не принимает, а `tuf update` и `tuf timestamp` отказывают.
- Старые версии метаданных не удаляются: `tuf check --base` отвергает удаление и правку опубликованных файлов.

### Что делает CI каждый день

`pages.yml` работает раз в сутки и при каждом слиянии, меняющем `tuf/` или индексы. Четыре job-а:

1. **`timestamp`.** Окружение `tuf-timestamp`; только `main`, только репозиторий `arynyklas/OpenNCALayer`, только события `push`, `schedule`, `workflow_run`, `workflow_dispatch`, `repository_dispatch`; права `contents: read`; все действия закреплены по SHA коммита. Job собирает xtask **до** того, как секрет попадает в окружение. Последним шагом, где секрет есть только в `env` этого шага, он выполняет `cargo xtask tuf timestamp` над **копией** `tuf/v1`.

   Сначала команда проверяет репозиторий клиентским кодом без timestamp: цепочка root от встроенного якоря `crates/oncl-update/keys/root.json`, подписи, версии, хеши всех файлов, цели равны `updates/v1/*.json`, до конца срока root, targets и snapshot осталось не меньше суток. При любой ошибке файл не создаётся, код выхода не нулевой, а сообщение не содержит ключа. Подписанный файл (он не секретный) передаётся в `build` выходом job: артефактов и действий после секрета нет. Пустой секрет при существующем `tuf/v1` — ошибка.
2. **`build`.** Всегда проверяет закоммиченное дерево (`cargo xtask tuf check --no-timestamp --base …`: якорь без `tuf/v1` или наоборот — красный; ни того, ни другого — зелёный). Кладёт `tuf/v1` и `metadata/timestamp.json` в `/tuf/v1/` артефакта Pages (в git файл не попадает) и проверяет копию: `cargo xtask tuf check --fail-on-expiring --min-days 3 --min-root-days 3`.
3. **`oracle`** (без секретов и без права записи). Читает собранный артефакт python-tuf'ом (`xtask/assets/tuf-oracle/verify_repo.py`; зависимости закреплены хешами в `requirements.txt`, ставятся `pip install --require-hashes`). Независимая реализация должна принять репозиторий в том виде, в каком он будет отдаваться. Её согласие необходимо, но не достаточно: python-tuf принимает то, что Rust-клиент отвергает. Главным остаётся проверка на Rust. `deploy` ждёт `build` и `oracle`.
4. **`verify`.** После деплоя запускает настоящий клиент по HTTPS против опубликованного сайта (`cargo xtask tuf verify-published --url …/tuf/v1/`, до четырёх попыток: Pages кэширует файлы на 10 минут).

Любая из этих ошибок делает запуск **красным**, и GitHub присылает письмо о падении запуска по расписанию.

**Если job `timestamp` падает** (репозиторий не проходит проверку, snapshot истёк, секрета нет), **сайт не деплоится вовсе**. Сайт без `metadata/timestamp.json` дал бы каждому клиенту 404, то есть ошибку проверки, а прежний сайт ещё отдаёт timestamp, действующий до 7 дней. Побочное следствие: пока TUF красный, не публикуются ни индексы minisign, ни остальной сайт. Чинить надо сразу (раздел ниже).

Ручной запуск Pages (`workflow_dispatch`) **с ветки, отличной от `main`**, при существующем `tuf/v1` всегда красный: job `timestamp` на такой ветке не запускается, и без timestamp `build` останавливается с ошибкой. Запускайте Pages только с `main`: `gh workflow run pages.yml --ref main`.

### Если timestamp истёк (запуск красный, клиенты не обновляются)

1. Откройте красный запуск Pages и прочитайте сообщение:
   - `expired` или `expiring` у `snapshot` либо `targets` — продлите: `cargo xtask tuf update --keys <каталог> --refresh`, откройте PR и слейте (после слияния Pages подпишет timestamp);
   - `expired` у `root` — `cargo xtask tuf root --keys <каталог>`;
   - `no TUF repository` или `does not verify` — исправьте репозиторий по коду из таблицы ниже;
   - «the environment variable TUF_TIMESTAMP_KEY is not set» — секрет пропал: восстановите его командой `gh secret set` из `timestamp.key` или сделайте ротацию.
2. Пока запуск красный, Pages отдаёт прежний сайт: его timestamp действует до 7 дней, потом клиенты перестают принимать обновления (`docs/design/tuf.md`, «Сбои»). Установленные версии продолжают работать, ничего не откатывается. Клиенты берут обновления, как только Pages снова публикует свежий timestamp.
3. Если Pages не публикуется потому, что отключено расписание (GitHub отключает его после 60 дней без активности), включите его в Actions заново.

### Ротация ключей

| Что | Команда | Что делать потом |
|---|---|---|
| timestamp | `cargo xtask tuf root --keys <каталог> --rotate-timestamp` | (1) слить PR с новым root; (2) **после** слияния положить `<каталог>/timestamp.v<N>.key` в секрет (`gh secret set TUF_TIMESTAMP_KEY --env tuf-timestamp < <файл>`) и удалить файл; (3) запустить Pages вручную: `gh workflow run pages.yml --ref main`. Между (1) и (3) запуск Pages красный: новый root называет новый ключ, а в секрете ещё старый (и наоборот до слияния: старый root не знает нового ключа). `tuf timestamp` отказывает, и сайт не деплоится. Клиенты всё это время получают прежний сайт с ещё действующим timestamp (до 7 дней), так что окно надо уложить в эти дни |
| snapshot или targets | `cargo xtask tuf root --keys <каталог> --rotate-snapshot` или `… --rotate-targets` | `cargo xtask tuf update --keys <каталог>`: targets и snapshot, подписанные старыми ключами, больше не действуют, команда сама подпишет новые версии. `root` и новые метаданные коммитятся одним PR |
| root | `cargo xtask tuf root --keys <каталог> --rotate-root` | новый корень подписан и старым, и новым ключом root. Новый файл `root.v<N>.key` храните как root, старый удалите после публикации |
| продление root | `cargo xtask tuf root --keys <каталог>` (без флагов) | раз в год |

Пароль новых зашифрованных ключей — тот же, которым открыты старые (не короче 12 символов). Новые ключи пишутся рядом со старыми с суффиксом `.v<N>.key` (N — версия нового root), старые файлы остаются. Клиент для ротации выпускать не нужно.

Если ключ root потерян или утёк, придётся переустанавливать программу у всех пользователей (`docs/design/tuf.md`, «Ротация и компрометация»). Так выбрано сознательно: один ключ root с порогом 1 и без резерва (`docs/design/tuf.md`). Храните его так, чтобы его нельзя было ни потерять, ни отдать.

### Что проверяет `cargo xtask tuf check`

```sh
cargo xtask tuf check [--dir tuf/v1] [--index updates/v1] [--anchor crates/oncl-update/keys/root.json] \
  [--base <ref>] [--no-timestamp] [--fail-on-expiring] [--min-days 10] [--min-root-days 45] [--now <время>]
```

- Без каталога и без якоря команда пишет `tuf check: no TUF repository yet` и завершается с кодом 0 (так выглядит состояние до церемонии).
- Без `--no-timestamp` timestamp обязателен и проверяется (так проверяется репозиторий, который публикуется). С `--no-timestamp` timestamp в дереве запрещён.
- Часы проверки подписей удерживаются внутри срока файлов, так что подписи и цепочка проверяются и у просроченного репозитория. Сроки проверяются отдельно.

Коды выхода:
- **0** — всё проверено (предупреждения код не меняют) или репозитория ещё нет;
- **1** — найдены проблемы или команда не смогла выполниться;
- **2** — ошибка командной строки.

Каждая находка — строка `tuf check: error[<код>]: <сообщение>` в stderr или `tuf check: warning[<код>]: <сообщение>` в stdout. В конце — `tuf check: ok` либо `tuf check: failed with N problem(s)`.

| Код | Что значит |
|---|---|
| `stray-file` | файл вне раскладки или файл цели, на который не ссылается ни один targets |
| `timestamp-committed` | `metadata/timestamp.json` лежит в дереве (при `--no-timestamp`) |
| `no-timestamp` | timestamp обязателен, но его нет |
| `no-root`, `root-gap`, `no-snapshot`, `no-targets` | нет `<N>.root.json`, пропущена версия root, нет snapshot или targets |
| `anchor-missing`, `anchor-mismatch`, `anchor` | нет якоря при существующем репозитории; якорь не равен `metadata/<его версия>.root.json` байт в байт; якорь не читается как root |
| `repository-missing`, `repository-removed` | якорь есть, а каталога нет; репозиторий был в `--base` и пропал |
| `client` | клиент отвергает репозиторий (в сообщении — текст ошибки клиента): цепочка root, подписи, версии |
| `signature`, `malformed`, `unreadable` | подпись ниже порога; файл не разбирается; файл не читается |
| `stale-snapshot`, `stale-targets`, `version-mismatch` | timestamp или snapshot указывают не на самую новую версию; версия в файле не равна версии в имени |
| `missing-file`, `hash-mismatch` | файл, на который ссылаются метаданные, отсутствует или не совпадает по длине или хешу |
| `index-mismatch`, `index-not-listed`, `index-missing`, `unexpected-target` | цель не равна байтам `updates/v1/<канал>.json` (лечится `cargo xtask tuf update`); индекс не перечислен в targets; targets перечисляют индекс, которого нет; цель не является индексом |
| `file-modified`, `file-removed`, `version-rollback`, `no-version-bump` | относительно `--base`: опубликованный файл изменён или удалён, версия упала, файлы добавлены без роста версии |
| `expired`, `expiring` | срок истёк или осталось меньше `--min-days` (targets, snapshot) либо `--min-root-days` (root) дней. С `--fail-on-expiring` это ошибка, иначе предупреждение |

Остальные команды:
- `tuf init`;
- `tuf update [--refresh]`;
- `tuf timestamp --out <каталог> [--key-env ИМЯ | --key-file ФАЙЛ] [--anchor] [--index]`;
- `tuf root [--rotate-timestamp] [--rotate-snapshot] [--rotate-targets] [--rotate-root]`;
- `tuf verify-published --url <база> [--anchor] [--allow-missing]` (`--allow-missing` терпит ещё не опубликованный репозиторий).

Для автоматизации и тестов пароль можно читать из файла: `--passphrase-file`; время подписи задаёт `--now`.

## 8. После выпуска

- **Проверьте происхождение файлов релиза:** `gh attestation verify <файл> --repo arynyklas/OpenNCALayer`.
- **Убедитесь, что индекс опубликован:** `curl -fsS https://arynyklas.github.io/OpenNCALayer/updates/v1/<канал>.json.minisig`.
- **Проверка установки на macOS** — workflow `mac-smoke.yml`.
  - Он запускается после каждого Release тега (`workflow_run`) и вручную: Actions → Mac smoke → Run workflow, вход `tag` (для запуска вручную файл должен лежать на ветке по умолчанию).
  - Он ставит `.pkg` тега командой `installer -pkg … -target CurrentUserHomeDirectory` на `macos-15` (Apple Silicon) и `macos-15-intel` (Intel) и печатает каждую проверку строкой `PASS|FAIL <имя> <подробности>`. Любой `FAIL` роняет job. Журнал каждого Mac — артефакт `mac-smoke-<runner>-<тег>`.
  - Условием индекса он не служит (job `index` его не ждёт). Поэтому **не подписывайте индексы PR (раздел 4), пока оба прогона не зелёные**: в индексах уже есть вариант `osx`.
  - Список проверок — в самом workflow, сводка — в [`docs/user/install.md`](../user/install.md#установка).
  - Черновик pre-release workflow с токеном только на чтение не видит. Тогда `.pkg` берётся из артефакта `release-packages-osx` запуска Release, а вместо `SHA256SUMS` проверяется подтверждение происхождения. После Release это происходит само. При запуске вручную для черновика укажите ещё вход `run_id` — номер запуска Release этого тега (из адреса запуска в Actions → Release). Для опубликованного релиза `run_id` не нужен.
  - Метки раннеров — по [списку образов GitHub](https://github.com/actions/runner-images#available-images). Intel-раннеры GitHub поддерживает до вывода из эксплуатации образа macOS 15 осенью 2027 ([объявление](https://github.blog/changelog/2025-09-19-github-actions-macos-13-runner-image-is-closing-down)); после этого матрицу надо сократить.
  - Workflow не проверяет Gatekeeper, самообновление, работу в браузерах и значок в строке меню (программа запускается с `--no-tray`).
- **Самообновление на macOS** — workflow `mac-selfupdate.yml`. Он запускается только вручную: Actions → Mac self-update → Run workflow, входы `from` и `to` (по умолчанию `v0.1.0-rc.4` и `v0.1.0`).
  - Он ставит опубликованный `.pkg` версии `from`, запускает программу и до 60 минут ждёт, пока она сама обновится до `to` по опубликованному индексу. Потом проверяет строку `the update is healthy` в журнале и порт `127.0.0.1:13579`.
  - Версия `from` должна быть опубликована (не черновик), а индекс `beta` на Pages должен уже перечислять `to`.
  - Запуск идёт на `macos-15` и `macos-15-intel`, каждая проверка — строка `PASS|FAIL <имя> <подробности>`, журналы — артефакт `mac-selfupdate-<runner>-<from>-to-<to>`.
- **Кто обновляется сам.** Сам себя обновляет только копия, установленная установщиком (`Setup.exe`, `.pkg`, `.zip`, AppImage). Из архива программа работает, но обновления у неё выключены. Пакет `openncalayer-bin` для pacman пользователь обновляет вручную (самообновление в нём тоже выключено).
- **Пакет Arch Linux вручную не публикуется.** Исправление самого пакета — это новая версия программы.

## 9. Приватность

Оригинальный NCALayer запускается только в приватной лаборатории проекта. То, что видно только там, в публичный репозиторий не попадает:
- записи обмена с оригиналом;
- серийные номера и имена тестовых сертификатов НУЦ;
- пути машин, имена приватных хостов, сетей и репозиториев.

Ожидания публичных тестов пишутся по правилу на синтетических данных, а не копируются из записей. Это проверяет `cargo xtask privacy`; в CI — workflow `privacy.yml` на каждый пуш и PR.

### Что проверяется всегда

- Нет файлов `*.jsonl` и `*.jsonl.zst` вне `target/`. Файлы с таким расширением, которые не являются записями (это тестовые данные), перечислены в `TRANSCRIPT_FILE_EXCEPTIONS` в `xtask/src/privacy.rs`.
- Нет текста с заголовком записи рекордера (`"recorded_at"` вместе с именем инструмента записи или кадром сервера `"dir":"s2c"`), в том числе с экранированными кавычками внутри строкового литерала.
- Нет путей с буквой диска (`[A-Z]:\`, `[A-Z]:/`) ни в коде, ни в документах. Тестовые литералы, которые нужны коду (например, пути установки под Windows), перечислены по файлам в `MACHINE_PATH_EXCEPTIONS`: файл, буква диска и начало остатка пути. Новый литерал добавляется туда в том же PR.
- Нет сертификатов, выпущенных тестовым УЦ НУЦ, ни в DER, ни в base64 (PEM, строки JSON и литералы, разбитые на строки). Издателя узнают по имени: это субъекты сертификатов из `fixtures/nca/test/`. Сами эти сертификаты УЦ, синтетические тестовые данные, публичные сертификаты НУЦ и данные OpenSSL проходят. Записанный ответ публичного тестового OCSP НУЦ (`fixtures/nca-ocsp/`) разрешён по хешу содержимого (`TEST_CA_EXCEPTIONS`).

### Что именно просматривается

Отслеживаемые файлы рабочего дерева (`git ls-files`) — целиком. С `--range <base>..<head>` ещё и то, что добавляет каждый коммит диапазона относительно своего родителя (у слияния — первого), и сообщения этих коммитов.

- У текстового файла проверяются только строки, добавленные коммитом (`+` в диффе; номер строки — в версии файла, которую делает коммит). Текст, который уже был в базе или в предыдущем коммите диапазона, повторно не срабатывает, когда коммит лишь правит файл рядом, сдвигает или переставляет эту строку. (Строка, которую дифф и удаляет, и добавляет, добавленной не считается.)
- Бинарный файл (поиск сертификатов) проверяется целиком, но только когда коммит его добавляет или меняет. Путь файла проверяется, когда коммит его создаёт.
- Версия файла, совпадающая с версией рабочего дерева, проверена выше целиком и отдельно не повторяется. Строка, добавленная и затем удалённая в диапазоне, всё равно находится в коммите, который её добавил.
- С пустым деревом `4b825dc642cb6eb9a060e54bf8d69288fbee4904` вместо базы проверяется вся история.
- Workflow берёт диапазон PR (`base..head`), пуша (`before..sha`) или новой ветки (от общего предка с веткой по умолчанию).

### Denylist (приватный список запретного)

Denylist — приватный список того, что нельзя публиковать. В репозиторий он не попадает.

- Запуск: `cargo xtask privacy --denylist <файл>`. В файле по строке на запись: подстрока без учёта регистра или `re:<выражение>` (синтаксис крейта `regex`). Пробелы по краям отбрасываются, пустые строки и строки, начинающиеся с `#`, пропускаются.
- Проверяются строки файлов (бинарный файл — целиком, без номера строки), пути файлов и строки сообщений коммитов.
- Находка печатается как `файл:строка: denylist entry`. У сообщения коммита — `commit <id>:строка`, у версии файла из истории — `файл@<blob>:строка`. Ни запись, ни совпавший текст не печатаются, а ошибка в записи называет только номер строки списка.
- В CI список — секрет `PRIVACY_DENYLIST`, base64 файла (`base64 -w0 <файл>` → Settings → Secrets and variables → Actions). Шаг denylist раскодирует его во временный файл и запускает уже собранный xtask. Без секрета (форк, PR из форка) шаг оставляет `::notice::` и проходит, а структура проверяется и там.
- У мейнтейнера тот же список перед каждым пушем проверяет хук `pre-push` публичного checkout. Хук и список хранятся вне репозитория.

Находку исправляют до пуша (`git commit --amend`, `git rebase -i`). Пушить коммит, который нашла проверка, нельзя, даже если следующий коммит её убирает: с `--range` проверка видит и его.
