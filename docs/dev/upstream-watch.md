# Наблюдатель за оригиналом

Для мейнтейнера: как проект узнаёт, что оригинальный NCALayer изменился, и что делать, когда приходит оповещение.

Наблюдатель следит за оригиналом: версией и полями манифеста `ncalayer.der`, его подписантом, дистрибутивами, составом и содержимым бандлов ядра и плагинов, сертификатами в keystore, программным интерфейсом из байткода. Любое изменение не позже чем через 6 часов становится коммитом с фактами в ветке `upstream` этого репозитория и issue с меткой `upstream`, `upstream-plugin` или `upstream-alert`.

Что делать, если пришло оповещение `upstream-alert`, — в разделе 6. Если сайты НУЦ недоступны с серверов GitHub — раздел 7.

## 1. Что публикуется и что нет

Публикуются только **факты**:

- поля манифеста НУЦ (`version`, `info`, `updurl`, `syspkgs`, `disturls`, бандлы со всеми полями, включая неизвестные новые), его sha256, размер, время подписи и подписант (sha256, серийный номер, субъект, издатель, срок);
- для каждого дистрибутива и бандла: адрес (без одноразового ключа страницы загрузок), имя файла, размер, sha256, SHA-1, опубликованный на странице, формат, состав файлов (путь, размер, sha256, вид), сведения о JRE (версия, поставщик, архитектура, число файлов, хеш дерева), метаданные установщиков (ключи `[Setup]` из разрешённого списка, значения реестра, файлы `[Run]`, `Info.plist`, смещение payload в `.sh`, версия Go и хеш вложенной программы лёгкого установщика, версии `tzdb.dat`);
- для каждого JAR: заголовки `MANIFEST.MF` из разрешённого списка, подписанты блоков подписи, хеш содержимого без файлов подписи, публичные и защищённые классы, методы и поля с дескрипторами, методы с аннотацией `NCALayerMethod`, имена модулей, строковые константы (коды ошибок и адреса, номера портов), счётчики классов сторонних библиотек, нативные файлы, алиасы и сертификаты keystore, сведения о вложенных манифестах.

Никогда не публикуются:
- файлы оригинала и их части: бинарники, извлечённые файлы, декомпилированный код, дословные фрагменты кода, тексты скриптов установщиков, тексты страниц сайтов НУЦ;
- закрытые ключи и зашифрованные блоки ключей keystore;
- пароли.

## 2. Как это устроено

Код — `cargo xtask upstream` (`xtask/src/upstream/`). Запускает его workflow [`upstream.yml`](../../.github/workflows/upstream.yml): по расписанию каждые 6 часов и вручную. Запуски не пересекаются (`concurrency: upstream`). Используется только `GITHUB_TOKEN`, других секретов нет.

Workflow состоит из двух job-ов:

- **`collect`** (windows-2025, права только `contents: read`) собирает факты:
  - `cargo xtask upstream tools` закрепляет внешние распаковщики;
  - `cargo xtask upstream run --dry-run` опрашивает источники, скачивает изменившееся во временный каталог `$RUNNER_TEMP`, распаковывает, собирает факты и пишет каталог emit, в котором только `*.json` (это проверяет и сам `run`, и отдельный шаг);
  - каталог уходит артефактом `upstream-facts` на 3 дня; скачанные оригиналы удаляются вместе с временным каталогом.
- **`publish`** (ubuntu-24.04, права `contents: write` и `issues: write`, без кэшей) публикует:
  - `cargo xtask upstream publish --from out` заново и строго проверяет артефакт: только ожидаемые пути, только JSON до 64 MiB, схемы с отказом на неизвестные поля, история совпадает с `latest/facts.json`, `key8` сходится;
  - сам формирует issues из `diff.json`, коммитит в ветку `upstream`, пушит без force и шлёт `repository_dispatch` с типом `upstream`;
  - если `collect` упал, создаётся issue `upstream-alert` вида `collect_failed`.

### Как опрашиваются источники

- **Манифест** скачивается и проверяется всегда. Проверяется CMS-подпись, подписант должен быть ровно один (`CN=NCALayer`), а его сертификат должен быть подписан корнем НУЦ (`oncl_pki::roots::nca_production`).
- **Дистрибутивы и фиксированные файлы** опрашиваются запросом HEAD (размер, `ETag`, `Last-Modified`) и сверяются с `hash` манифеста.
- **Ссылки со страницы загрузок** сверяются по SHA-1, опубликованному рядом со ссылкой. Одноразовый ключ `download.php?key=` в идентичность источника не входит.
- **Бандлы** сверяются по `hash` манифеста, без запросов.
- Источник считается исчезнувшим только после 3 неудачных опросов подряд; успешный опрос сбрасывает счётчик.
- HTML-страница вместо файла или манифеста (ошибка или капча со статусом 200) — это сбой опроса, а не новая версия и не `bad_signature`.
- Если не загрузилась сама страница загрузок, её ссылки остаются в фактах и тоже считают неудачи.

Ссылки страницы загрузок устроены сложнее:
- Ключ `download.php?key=` обслуживает ровно один запрос (даже HEAD; дальше — перенаправление 302 на HTML-страницу `404.php`) и только с cookie сессии страницы и заголовком `Referer`. Поэтому опрос саму ссылку не запрашивает: `run` перед каждой её загрузкой заново читает страницу в новой сессии и берёт ссылку с тем же slug и свежим ключом.
- Статус ссылки меняют только такие загрузки. Новая или вернувшаяся ссылка начинает со статуса `ok`. Неудачная (`failing`) или отвергнутая (`refused`) скачивается снова каждым запуском, пока загрузка не удастся.
- Счётчик неудач ссылки считает только опросы подряд, в которых её не нашли (страница не загрузилась или ссылки на ней нет). Только он убирает ссылку после 3 таких опросов. Опрос, нашедший ссылку, обнуляет счётчик, а неудачные загрузки его не трогают.
- Если изменение замечено, а скачать файл не удалось, опрос его «не запоминает»: следующий запуск увидит изменение снова и повторит загрузку. Исключение — отвергнутая (`refused`) ссылка страницы: следующий опрос об изменении не сообщает, но запуск всё равно скачивает её снова и сверяет с опубликованным SHA-1.
- Файл, оставленный как «содержимое не изменилось», тоже сверяется с `hash` манифеста и опубликованным SHA-1.

### Безопасность

**Оригиналы не запускаются никогда.**
- ZIP, JAR, `.sh` (заголовок и ZIP-payload) и лёгкий установщик Windows (программа на Go с gzip-потоком настоящего установщика) разбирает наш код. Записи ZIP читаются в памяти и на диск не пишутся.
- Inno Setup распаковывает innounp 2.71.2. Он скачивается с закреплённого коммита репозитория InnoUnpacker, архив и программа сверяются по sha256.
- MSI с кабинетами и DMG распаковывает 7-Zip из образа runner'а, только версии 25.01 и новее: они по умолчанию отказываются создавать символические ссылки за пределами каталога распаковки. Более старые версии не используются, такие дистрибутивы получают статус `skipped`.
- Вывод инструментов пишется в файл в рабочем каталоге, в журнал попадает только код выхода. Обход каталога после работы инструмента пропускает символические ссылки и reparse point.

**Лимиты.** Манифест — 1 MiB, страница — 2 MiB, бандл — 256 MiB, дистрибутив — 1 GiB. Распаковка: 4 GiB всего, 200 000 файлов, 512 MiB на файл, вложенность архивов 4. Превышение лимита — ошибка, а не обрезка. Перенаправления обрабатываются вручную, не больше 5, каждый адрес проверяется.

**Срок запуска.** `collect` останавливается через 120 минут, поэтому у `run` свой срок — 90 минут от старта (`--deadline-minutes`, по умолчанию `RUN_DEADLINE`; `0` — без срока). Когда срок истёк:
- ещё не начатые загрузки пропускаются, а идущая прерывается (запросу не дают больше оставшегося времени);
- в журнал пишется строка `fetch: <id> skipped: run deadline passed, left for the next run`;
- источник возвращается в состояние, которое было до запуска (источник, которого там не было, следующий опрос снова назовёт новым);
- сбой не засчитывается;
- запуск завершается обычным образом: факты и записи того, что успело скачаться, публикуются.

**Куда можно соединяться.** Только на публичные адреса. Loopback, частные сети, link-local, CGNAT 100.64/10, ULA, multicast, unspecified, адреса документации и IPv4-mapped такие же отвергаются до соединения (у бандлов НУЦ есть адреса из частных сетей — они получают статус `refused`).
- Имя разрешается один раз на запрос, проверяются все его адреса, и соединение идёт только на них — без повторного разрешения и без прокси из окружения. Поэтому подмена DNS-ответа (DNS rebinding) соединение никуда не уведёт.
- Запрос без сессии может пойти на любой проверенный адрес (если один не отвечает — на следующий).
- Сессия — это одна загрузка ссылки страницы. Чтение страницы и запрос ссылки идут на адрес, на который сессия попала первым. (Пока адрес не закреплён, следующий пробуется, только если к предыдущему не удалось подключиться.) Это нужно потому, что у `ncl.pki.gov.kz` несколько адресов A, а PHP-сессия живёт на одном сервере, и ссылка, запрошенная у другого, отвечает `404.php`.
- Каждая ссылка получает свою сессию: сервер, который перестал принимать соединения, стоит неудачи одной ссылки, а не всех. Сервер, который принимает соединение и зависает, задерживает каждую закреплённую за ним загрузку до тайм-аута запроса: 10 минут у ссылок страницы (`PAGE_DOWNLOAD_TIMEOUT`; их пять, у каждой своя сессия), 30 минут у остальных.
- TLS сайтов `*.pki.gov.kz` выпущен публичным WebPKI-центром, поэтому для всех хостов используются корни WebPKI. Таблица `TLS_ROOTS` в `xtask/src/upstream/http.rs` позволяет назначить хосту корни НУЦ.

## 3. Ветка `upstream`

Это отдельная ветка без общей истории с `main`, в ней только JSON (проверяется перед каждым коммитом):

```
state.json                         состояние опроса (внутреннее)
latest/facts.json                  последние факты
index.json                         история
history/<id>/facts.json            факты записи
history/<id>/diff.json             разница с предыдущей записью
history/<id>/changes.json          изменения источников по опросу
```

- `id` имеет вид `<YYYY-MM-DD>-<version>-<key8>`. В `version` всё вне `[A-Za-z0-9._-]` заменено на `_`; `key8` — первые 8 hex-символов sha256 от байтов `facts.json`. Шаблон: `^[0-9]{4}-[0-9]{2}-[0-9]{2}-[A-Za-z0-9._-]+$`.
- Все файлы — `serde_json` с отступами и переводом строки в конце, коллекции отсортированы. В фактах нет времени запуска, `ETag` и `Last-Modified`. Поэтому одинаковый мир даёт одинаковые байты и одинаковый `key8`.
- Новая запись истории появляется только при изменении разобранных фактов. Пробелы, порядок ключей JSON и переводы строк после публикации или checkout изменением не считаются, в том числе на следующий день. Хеши файлов и подписи остаются частью сравнения: перепаковка и переподпись сохраняют записи `repack`. Счётчики неудач источников в `state.json` обновляются независимо от истории.
- `latest/facts.json` имеет вид `{schema: 1, manifest, bundles{symname: {name, version, required, …, fetch, jar, signer_matches}}, distributions{source id: {url, page, label, filename, size, sha256, published_sha1, format, status, unpack, files, jre, jars, embedded_manifests, meta}}, jars{sha256: {…, content_sha256, manifest_mf, signers, api, libraries, natives, keystores, embedded_manifests}}}`. Поля `fetch` и `status` принимают значения `ok`, `pending`, `unreachable`, `refused`, `hash_mismatch`.
- `signers[путь блока]` — сертификат, названный первым `SignerInfo` блока по издателю и серийному номеру. Записи нет, если `SignerInfo` назван по `subjectKeyIdentifier` или его сертификата нет в блоке.
- `index.json` имеет вид `{schema: 1, entries: [{id, date, observed, version, key8, path, kind, summary{core[], plugins[{symname, from, to, change}], distributions[], notes[]}, issues[{key, number, label}]}]}`, записи идут по возрастанию `observed`. Строки `summary` — простой текст.
- `kind` — вид записи:
  - `baseline` — первые факты;
  - `change` — изменение;
  - `repack` — изменились только байты (перепакованный или переподписанный JAR с теми же содержимым, API и заголовками, переподписанный манифест с тем же JSON).
- Идентификаторы источников: `manifest`, `dist:<type>` (`disturls` с непустым адресом), `page:<slug подписи ссылки>`, `fixed:ncalayer.zip`, `fixed:tzdb.dat`, `bundle:<symname>`.

## 4. Issues

Какие бывают:

| Метка | Когда создаётся |
|---|---|
| `upstream` | ядро: изменились поля манифеста (кроме переподписи), бандл ядра (`required`, кроме перепаковки) или содержимое дистрибутива. Смена подписанта манифеста — предупреждение в issue, не сбой |
| `upstream-plugin` | по одному на изменившийся плагин (кроме перепаковки), со строкой о порте из `plugins/<short>/registry.toml` |
| `upstream-alert` | сбой: `bad_signature`, `manifest_unreachable`, `collect_failed`. Одно issue на вид в день: его создаёт первый запуск дня, следующие его не меняют |

Последняя строка тела issue — `<!-- upstream-key: <key> -->`. Ключ бывает такой: `core:<version>:<key8>`, `plugin:<symname>:<version>` (`plugin:<symname>:removed:<key8>`), `alert:<kind>:<date>`. По нему повторный запуск находит своё issue:
- тело то же — ничего не происходит;
- тело другое, issue открыто — тело заменяется и добавляется комментарий;
- issue закрыто — только комментарий, оно не переоткрывается.

Номера issues записываются в `index.json` в том же коммите.

Когда issue не создаётся:
- Первый запуск даёт запись `baseline` без issues.
- Перепаковка, смена доступности источника и первая успешная загрузка уже известного источника (дистрибутива, ссылки страницы или бандла, который до этого был `pending`) — только строка в `summary.notes` («первая загрузка известного источника»).
- А источник, который опрос видит впервые (`added` в `changes.json`), и новый sha256 у уже загружавшегося дистрибутива issue открывают.

## 5. Ручной запуск

```sh
gh workflow run upstream.yml -f mode=run           # сбор и публикация
gh workflow run upstream.yml -f mode=issues-only   # issues последней записи ветки
```

Локально, без публикации:

```sh
cargo xtask upstream run --dry-run --emit target/upstream/emit
```

Подробности:
- Без `--dry-run` `run` сначала открывает ветку `upstream` (её рабочая копия и есть состояние, поэтому `--state` тогда запрещён), затем публикует каталог emit тем же кодом, что и `upstream publish`. Для этого нужны `GITHUB_TOKEN` и `GITHUB_REPOSITORY`.
- `publish` отказывается от каталога emit, в `index.json` которого нет какой-либо записи ветки: такой каталог собран не из её состояния и стёр бы историю.
- MSI и DMG распаковывает 7-Zip 25.01 или новее (путь — `ONCL_7Z`). Пакет `7zip` из Ubuntu 24.04 старее: с ним MSI и DMG получают `skipped`.
- Без innounp установщики Inno Setup получают статус `skipped`.
- `cargo xtask upstream poll` печатает только изменения источников.

## 6. Разбор `upstream-alert`

- **`bad_signature`** — манифест не прошёл проверку: другая подпись, неизвестный издатель или CN не `NCALayer`. Факты не обновлены. Скачайте `ncalayer.der` вручную и сверьте подписанта с опубликованными сертификатами НУЦ. Если НУЦ сменил корень, обновите `oncl_pki::roots`.
- **`manifest_unreachable`** — манифест недоступен (сетевая ошибка, статус не 2xx, HTML или другой файл вместо DER) 3 опроса подряд или с первого запуска. Проверьте по журналу `collect`, доступны ли сайты НУЦ с серверов GitHub. Если их блокируют, см. раздел 7.
- **`collect_failed`** — job `collect` упал. Журнал прогона — по ссылке в issue.

## 7. Резервный путь, если сайты НУЦ недоступны с серверов GitHub

1. Задайте переменную репозитория `UPSTREAM_SOURCE=lab`: плановые запуски `collect` выключатся.
2. На машине с прямым доступом к сайтам (приватная лаборатория), в checkout `main`, выполните команды ниже. Наблюдатель соединяется только напрямую: переменные прокси (`HTTPS_PROXY`, `ALL_PROXY` и другие) он не использует, потому что через прокси соединение ушло бы мимо проверенных адресов. Если они заданы, `run`, `poll` и `tools` пишут об этом строку.

   ```sh
   git fetch origin upstream
   git worktree add --detach ../upstream-state origin/upstream
   cargo xtask upstream run --dry-run --state ../upstream-state --emit <dir>
   cargo xtask upstream publish --from <dir> --branch-dir ../upstream-lab --no-push --no-issues
   git -C ../upstream-lab push origin HEAD:refs/heads/upstream-lab-<дата>
   ```

   `publish` с `--no-push --no-issues` токена не требует: он проверяет каталог emit, создаёт рабочую копию ветки `upstream` в `../upstream-lab` и коммитит факты. Затем откройте PR из `upstream-lab-<дата>` в `upstream`.
3. После слияния выполните `gh workflow run upstream.yml -f mode=issues-only`.
4. Когда доступ вернётся, удалите переменную `UPSTREAM_SOURCE`.

## 8. Кто читает эти данные

- **Реестр плагинов** (сайт проекта): берёт `index.json` и `latest/facts.json` (`manifest.version`, `bundles{symname: {version, required}}`). Страницы пересобираются по `repository_dispatch: upstream`.
  - Для сайта `latest/facts.json` читается потоком (`BufReader`) с лимитом 64 MiB — тем же, что у `publish`. Большие `distributions` и `jars` проверяются как JSON, но не сохраняются в памяти.
  - `index.json`, индексы каналов и список релизов по-прежнему ограничены 8 MiB каждый.
  - Некорректный или слишком большой файл остаётся ошибкой, а не частичными данными.
- **Приватная лаборатория**: читает ветку без токена (по sha коммита), скачивает изменившиеся оригиналы со сверкой sha256 из `latest/facts.json`, декомпилирует изменившиеся JAR в песочнице без сети и учётных данных и хранит всё у себя.

## 9. Известные ограничения

- Имена файлов MSI в фактах — это ключи таблицы File, как их выдаёт 7-Zip, а не имена при установке.
- Порты, вставленные в байткод инструкцией `sipush`, в пул констант не попадают и в `ports` не видны.
- Ссылки страницы загрузок без опубликованного SHA-1 скачиваются целиком на каждом опросе (сейчас SHA-1 публикуется для всех ссылок). Ссылка в статусе `failing` или `refused` скачивается на каждом запуске, пока загрузка не удастся.
- Первый бандл, JAR которого не скачался, получает API-diff только при следующем изменении. Появление JAR после сбоя отражается только строкой в `notes`.
