# Rust SDK: как встроить `oncl-core` в свою программу

Страница для разработчика на Rust, который хочет подписывать и проверять файлы из своей программы. Здесь: как подключить библиотеку, что в неё входит, какие у неё лимиты и что обещано по стабильности.

`oncl-core` — библиотека OpenNCALayer. Она подписывает, проверяет, хеширует и инспектирует файлы и потоки байт, а также ставит метки времени. Всё, чему можно доверять, задаёте вы: сертификаты, ключи, часы, сеть, журнал аудита и лимиты ресурсов. Вашу программу, которая встраивает SDK, ниже называем «хост».

В библиотеке нет окон, демона, открытого порта, установщика и самообновления; графическая сессия не нужна. Команда `oncl` и HTTP-сервис `oncl-server` — отдельные программы на том же движке, в SDK они не входят.

Устройство библиотеки описано в [`../design/platform.md`](../design/platform.md). Короткое введение — в [`README` крейта](../../crates/oncl-core/README.md).

## 1. Как подключить

Пока ничего не опубликовано в crates.io, поэтому `cargo add` не подойдёт. Подключайте проверенный тег или коммит по path или по git.

SDK использует два изменённых крейта RustCrypto из наших форков: `streebog` и `hmac` (в них добавлены варианты для секретного ввода). Поэтому в вашем проекте нужен такой же `[patch.crates-io]`, с теми же `rev`, что в корневом `Cargo.toml`:

```toml
[dependencies]
oncl-core = { path = "OpenNCALayer/crates/oncl-core", features = ["full"] }

[patch.crates-io]
streebog = { git = "https://github.com/arynyklas/hashes", rev = "7f67647379b26e89068874cfe8cf3bf0c8e72b69" }
hmac = { git = "https://github.com/arynyklas/MACs", rev = "062e38d40e71236dcf49275ab7f9bd491b033c1c" }
```

Если подключаете по git, у каждой записи должны быть одинаковые `git` и `rev`. Проверка `cargo xtask sdk smoke` (раздел 7) собирает проект-потребитель именно так, но из распакованных пакетов.

### Шифрование

Шифрования и расшифрования CMS в фасаде SDK, CLI и HTTP нет. Для получателей с RSA они есть только в библиотеке `oncl-pki` (`oncl_pki::cms::envelope`, см. [`platform-interop.md`](platform-interop.md)). Казахстанского ГОСТ-профиля шифрования нет: Kalkan не умеет ни согласования ключа, ни ГОСТ-шифра в CMS, профиль не доказан, и мы его не придумываем. RSA его не заменяет.

При расшифровании открытый текст попадает в приёмник (`StagingSink`) кусками **до** проверки тега GCM: тег стоит в конце сообщения, а 1 ГиБ в память не поместить. При любой ошибке вызывается `discard`, а результат считается успешным только после `Ok`. Значит, всё, что пришло до `Ok`, предварительное. Чтобы данные не уходили дальше до проверки, нужен настоящий приёмник: временный файл в каталоге только для владельца, который после `Ok` переименовывается в итоговое имя, а в `discard` удаляется. Готового файлового приёмника в библиотеке пока нет — его нужно написать в хосте.

## 3. Как устроено встраивание

Хост строит один `Engine` и для каждой операции открывает отдельный контекст:

```text
EngineServices::hash_only(limits)            // host services, nothing global
    .with_keys(provider, guard)              // key sources + the audit guard
    .with_validation(ValidationServices)     // trust anchors, status transport, clock
    .with_temporary_store(store)             // only for operations that must stage bytes
    .with_cades(...) / .with_plugins(...)    // optional
Engine::new(services)?
engine.begin(ExecutionGrant, OperationPolicy, Arc<dyn OperationControl>)? -> OperationContext
engine.sign / verify / hash / inspect / extend / stamp / ... (request, Source, output, &mut ctx)
```

SDK сам ничего не берёт из сети, окон или настроек десктопа. Всё, что ему нужно, хост передаёт через эти объекты:

| что передаёт хост | тип | примечания |
|---|---|---|
| разрешение на операцию | `ExecutionGrant` | действия и id ключей; выдаётся только доверенным кодом хоста |
| ключи | `KeyProvider` (`keys::KeySources` для файлов, встроенных ключей, ключей с именем и токенов) | секрет берётся на время работы и затирается (zeroize), во временное хранилище не попадает |
| журнал применения ключа | `KeyUseGuard` | `before_use` обязан надёжно записать событие **до** применения закрытого ключа; если запись не удалась, ключ применять нельзя; `finish` записывает исход |
| доверие и статус отзыва | `ValidationServices` (корневые и промежуточные сертификаты, `HttpTransport`, `NetworkPolicy`, часы) | строгая проверка без статуса отзыва заканчивается отказом |
| сетевой транспорт | `oncl_pki::http::HttpTransport` | CRL, OCSP, RFC 3161; `UreqTransport` — всего лишь вариант по умолчанию; свой транспорт показывает пример `custom_transport` |
| часы | `Arc<dyn Fn() -> OffsetDateTime>` | задаются снаружи, чтобы вердикты можно было воспроизвести |
| отмена и прогресс | `OperationControl` | точки проверки; блокирующий ввод-вывод хост должен уметь прерывать |
| временное хранилище | `TemporaryStore` | ограниченное и приватное; ключи и пароли в нём не хранятся |

Запускаемые примеры (`cargo run -p oncl-core --example <имя>`). Они на лету выпускают одноразовую RSA PKI, не ходят в сеть и не оставляют ключей в репозитории:

- `sign_file [КАТАЛОГ [ФАЙЛ]]` и `verify_file КАТАЛОГ ФАЙЛ` — отсоединённая подпись CMS при строгой проверке; `verify_file` завершается с кодом 1, если документ изменён;
- `custom_transport` — свой `HttpTransport`, подключённый к проверке; если сети нет, строгая подпись отклоняется с `NotApplied`.

`tests/examples.rs` запускает примеры как настоящие процессы, поэтому они не устареют.

## 4. Результаты и ошибки

**Вердикт.** `Verdict::{Valid, Invalid, Indeterminate}` — это ответ о подписи, а не ошибка выполнения. Отчёт раздельно показывает: целостность подписи, цепочку до корня, срок действия, отзыв, доказательство метки времени и заявленное время подписания. У каждого пункта свой статус: `CheckStatus::{Passed, Failed, Unavailable, NotApplicable}`. Нет доказательств — это `Unavailable` или `Indeterminate`, но не `Valid`. Отмена, истёкший срок и нехватка ресурсов — ошибки, а не вердикты.

**Профили CAdES и PAdES.** Если запросить профиль (`cades-b`, `pades-t` и т. д.), проверка требует больше, чем целостность. Допустим, сама подпись верна, но в CMS нет нужного для профиля атрибута. Тогда у подписанта остаётся `signature = Passed`, а в причинах появляется `ValidationReason::Profile(ProfileViolation)`. Нарушения такие:

- в подписи CAdES нет signing-time;
- в подписи PAdES signing-time есть (EN 319 142-1, таблица 1; Kalkan его пишет);
- тип содержимого не id-data;
- нет атрибута signing-certificate.

Такой подписант на этом профиле `Invalid` и не получает `ades_level`. Ошибки digest, ESS и значения подписи остаются отказами `Signature(..)` и сообщаются рядом. Общие профили `pdf` и `cms` baseline не требуют: они судят те же байты только по целостности и доверию.

**AppliedState.** Если операция с закрытым ключом могла начаться, каждый отказ после этого несёт `NotApplied`, `Applied` или `Unknown` (`OperationError::applied_state`). SDK не обещает ни отката, ни повтора, ни «ровно один раз»: метка времени, уже выданная удалённо, и подпись, посчитанная до отказа приёмника вывода, остаются как есть. Если `KeyUseGuard` отказал в `finish` уже после применения ключа, сообщается `Applied`.

**Коды ошибок.** `OperationError` — типизированная ошибка. `ErrorCode` (`OperationError::code`) — стабильные машинные категории; они никогда не выводятся из текста сообщений. Оба типа публичные.

Пока SDK в альфе, хосту нужно сопоставлять `ErrorCode` с веткой «всё остальное». Сейчас ни `ErrorCode`, ни `ValidationReason`, ни `ProfileViolation` не помечены `#[non_exhaustive]`. Поэтому новый вариант (как `ValidationReason::Profile`) ломает сборку у потребителей, и такое изменение указывается в заметках о миграции (раздел 6). Пометить их `#[non_exhaustive]` запланировано в первом выпуске, которому понадобится новый код; сейчас этого нет, потому что придётся менять сопоставления у всех потребителей в workspace. Текст `Display` у вариантов предназначен для логов; по нему нельзя управлять логикой.

**Результаты держат свои резервы.** Результаты, которые хост хранит у себя (`ScopedSigners`, промежуточный вывод, результаты пакетов), продолжают держать зарезервированную память и метаданные и исходную область операции. Освобождайте их до следующей операции, если бюджет одной операции остался по умолчанию (примеры так и делают).

## 5. Лимиты

Значения `ResourceLimits::default()` (хост может их менять):

| лимит | по умолчанию |
|---|---|
| операций одновременно | 1 |
| входной документ | 1_073_741_824 байт (1 ГиБ) |
| контейнер (структура CMS/XML/PDF) | 1_073_741_824 |
| обрамление (framing) | 67_108_864 |
| вывод | 2_214_592_512 (входной документ + контейнер + обрамление) |
| учитываемая живая память | 1_073_741_824 (1 ГиБ) |
| временное хранилище (scratch) | 8_589_934_592 |
| метаданные | 67_108_864 |
| срок операции | 300 с от начала, не перезапускается |

Документ больше 1 ГиБ отклоняется ошибкой `InputLimit`. Хост может поднять `input_bytes`, но гарантирован только 1 ГиБ. Это лимиты учёта, а не измерение RSS процесса. Приёмочный прогон «1 ГиБ / 1 ГиБ» (`cargo xtask platform-proof`) выполнен: 70/70 на `9a1f0181`, см. [`platform-acceptance.md`](platform-acceptance.md).

Пределы отдельных форматов (пакет — 1024 элемента, 8 подписей на JOSE-токен, 10_000 итераций KDF при инспекции и т. д.) описаны в самих модулях. Методы плагинов, унаследованные от NCALayer, сохраняют свои пределы на строки и Base64; лимиты SDK на них не действуют.

### Подписанные результаты и `container_bytes`

`input_bytes` ограничивает документ, а не подпись. Подписанный результат для документа ровно в `input_bytes` может быть больше только на байты контейнера (структуры подписи), но не больше `container_bytes` и не больше предела формата. SDK читает такой результат повторно из любого `Source`: файла, сокета, HTTP-загрузки.

Сервер должен принять всю загрузку до начала работы, поэтому он действует так:

1. Кладёт загрузку во временное хранилище через `FrozenInput::capture_wire`. Этот вызов не списывает ни один из двух лимитов. Он держит не больше остатка лимита документа плюс остатка `container_bytes` (можно сузить необязательным максимумом).
2. Отдаёт движку `FrozenInput::wire_reader` — внешний источник с известной длиной. Движок учитывает и классифицирует байты так же, как для файла, поэтому учёт у SDK, CLI и сервера одинаковый.

Допущенный снимок таких байт движку не передаётся: `FrozenInput::reader` их отклоняет, а `wire_inspection_reader` нужен для повторного чтения в той же операции, когда хосту надо что-то проверить самому. Данные, которые вообще не документ (например, свидетельства проверки со своими границами), можно складывать так же с максимумом.

Ключ сервера `container_bytes` (по умолчанию 1 ГиБ) — это `ResourceLimits::container_bytes` движка. Предел размера запроса с подписанным `input` равен `input_bytes + container_bytes + framing_bytes + 64 КиБ` (см. [`http-api.md`](../user/http-api.md)).

### Приём ввода без занятия слота

Пока хост ждёт медленного клиента, он не должен держать за это время один из слотов `max_in_flight` (или поток). Для этого есть `Engine::admit_intake` — то же, что `Engine::admit`, но без слота. Память, временный диск, метаданные, лимиты документа, контейнера и обрамления, срок и управление списываются так же, как при обычном допуске. Слот занимает `OperationAdmission::occupy_slot` (или, самое позднее, `Engine::begin_admitted`), когда ввод получен. Если все слоты заняты, он отказывает тем же `CapacityExceeded`: ничего не меняется, вызов можно повторить. Число таких операций хост ограничивает сам.

Байты можно подавать по частям:

- `oncl_pki::io::InputSpool`: `document` — для `FrozenInput::capture`, `wire` — для `FrozenInput::capture_wire`; `push` на каждую часть, `finish` отдаёт `FrozenInput`;
- `oncl_pki::digest::HashStream` (`hash_source`).

Каждая часть учитывается, проверяется на предел (проба N+1, `InputLimit`) и на управление и срок операции — как при вызове «одним куском». Отличие только в памяти: вызов «одним куском» списывает буфер чанка 256 КиБ, а `InputSpool` буфера не держит и памяти не списывает (часть пишется напрямую, не больше `IO_CHUNK_BYTES` за запись). Если хост сам копит части перед `push`, буфер его, и списывать его тоже ему. `oncl-server` один раз на запрос резервирует `IO_CHUNK_BYTES` через `ResourceScope::reserve_memory`, пушит по 256 КиБ и сбрасывает накопленное на диск перед ожиданием клиента, чтобы время записи на диск не считалось временем клиента. Все три способа сервер использует при загрузке (см. [`server.md`](../user/server.md)).

### Учёт CAdES

Проверка, продление и со-подпись в `cms::ades` (и простая со-подпись CMS) читают подпись один раз классифицирующим CMS-парсером, пока складывают её во временное хранилище:

- структура SignedData (заголовки, сертификаты, данные об отзыве, signer infos и токены меток времени) — это контейнер, он ограничен `container_bytes`;
- документом считается только содержимое;
- отсоединённое содержимое читается отдельно и списывается с `input_bytes`;
- отсоединённый документ, который хост уже допустил (читатель `FrozenInput`, как у сервера), воспроизводится и повторно не списывается — одинаково для проверки, продления и со-подписи.

Присоединённый результат CAdES — это документ плюс подпись. Документ размером ровно `input_bytes` можно снова проверять, продлевать и со-подписывать; на один байт больше — `InputLimit`. Структура подписи, не влезающая в `container_bytes`, даёт `ContainerLimit` (или `InputLimit`, если весь присоединённый поток уже при приёме больше `input_bytes + container_bytes`). Оба отказа происходят до любого применения ключа.

Свидетельства, которые движок копирует из подписи (сертификаты, статусы, токены меток), снова списываются с `container_bytes`. Продление и со-подпись списывают ещё и записываемую структуру (замер: проверка — 7081 байт контейнера, продление до LT — 17429). Поэтому лимит контейнера должен вмещать структуру, эти свидетельства и выходную структуру. Свидетельства дополнительно ограничены `EvidenceLimits`. Временное хранилище (`TempLimit`) нужно до `input_bytes + container_bytes` плюс один чанк. Простой профиль `cms` (`cms::stream::verify` и `extract`) всегда читал подпись именно так.

### Надбавка контейнера для подписанных PDF

Читая PDF, который уже подписан, SDK может превысить лимит документа на ограниченную надбавку. Предел:

`min(container_bytes, (max_revisions - 1) * 4 * max_object_bytes + PdfLimits::max_evidence_bytes)`

(`crates/oncl-pdf/src/verify.rs`, `lib.rs`). По умолчанию это около 188 МиБ: `max_revisions` = 16, `max_object_bytes` = 1 МиБ, `PdfLimits::max_evidence_bytes` = 128 МиБ. `max_evidence_bytes` — поле слоя PDF. Ни один поставляемый хост (CLI, сервер, десктоп) пока не выводит его из `EvidenceLimits.max_total_bytes`, поэтому у всех остаётся 128 МиБ.

## Плагины (feature `plugins`)

Этот раздел нужен хосту, который запускает плагины WebAssembly. Главная идея: плагин сам ничего не решает. Какую операцию вызвать, каким ключом и для каких данных, определяет хост, а подписать плагин может только после согласия пользователя или оператора.

### Реестр и объявленные операции

`PluginRegistry::install(manifest, package, wasm, limits, policy)` записывает вместе с плагином `PackageHash`. Он бывает двух видов:

- `PackageHash::File` — SHA-256 всего файла пакета, прочитанного `oncl_plugin::Package::read`;
- `PackageHash::Loose` (`plugins::loose_package_hash(manifest_toml, wasm)`) — хеш манифеста и модуля вместе, с разделением по доменам. Его используют CLI и сервер, которые загружают манифест и модуль раздельно.

Виды никогда не равны и кодируются разными тегами (`PackageHash::canonical`). Хеш `Loose` — не хеш файла пакета. Реестр принимает значение как есть и ничего не сверяет с модулем. Хост, который грузит плагины через `oncl_plugin::Store` (feature `distribution`, этот крейт её не включает), обязан брать манифест, модуль и `File(package.sha256)` из одного значения `Package`. `BuiltinInfo::sha256` (только модуль) не относится ни к одному из видов. В аудите плагин опознаётся по `PluginIdentity { id, package, version }`, а не по имени из манифеста (`Engine::plugin_identity`).

Плагин без `[[operations]]` работает как раньше: его права и `PluginPermission::with_keys` жёстко задают ключ. Для плагина с объявленными операциями `PluginRegistry::allow_declared` (и `allow_declared_with_pki`) добавляет политику реестра, построенную только из манифеста: объявленные импорты для одной тройки `(plugin, operation, caller)` и **любой** ключ. Выбранный ключ проверяется при разрешении конкретного вызова (там работает `PluginPermission::with_keys`); объявленная политика сама ключом не считается.

Объявленная сеть (`network`) соблюдается так:

- `none` — ни одного адреса;
- `pki` — только адреса на PKI-хостах, которые передаёт хост (обычно `oncl_plugin::NCA_PKI_HOSTS`, поддомены включены);
- `network = [urls]` — такие операции в этом выпуске не запускаются в ручном окне (`PluginRequestError::NetworkUnsupported`) и в списке не показываются.

Вправе ли вызывающий данного вида использовать вариант операции `manual` или `server`, проверяет хост, который всё связывает.

`Engine::plugin_operations` перечисляет `Manifest::manual_operations` (без URL-сетей). `Engine::plugin_request` строит точный текст запроса, который получит модуль. Он берёт разобранный JSON-шаблон и типизированные значения `PluginParam` и не склеивает строки:

- в шаблоне любой JSON-объект; заменяется каждое строковое значение-плейсхолдер целиком, на любой глубине (ключ и часть строки не заменяются);
- итоговая длина считается заранее и сверяется с `max_transfer` плагина (`ErrorCode::InputLimit`) до подстановки, затем запрос пишется один раз в буфер этого размера;
- документы — стандартный base64, не пустые;
- текст считается в символах, как его объявленный лимит; если профиль ключа читает его как XPath, он проверяется через `Source::check_value`;
- в тексте, который подписывается, нет управляющих символов, кроме `\n` и `\t`, а также двунаправленных и невидимых (`InvalidValue`; окно показывает ровно тот же `&str`);
- операция с ключом обязана объявлять `network = "pki"`; текстовый параметр может быть содержимым ключа любого вида (его байты UTF-8); текст не нормализуется;
- вывод — компактный JSON с отсортированными ключами объектов (порядок ключей шаблона не сохраняется), целые числа как записаны; число шаблона, которое не `i64`/`u64`, отклоняется (`InvalidTemplate`).

Необъявленные, не-manual, `derived` и URL-сетевые операции и неверные параметры отклоняются как `PluginRequestError`: всегда `NotApplied`, до использования любого ключа. Согласие в этот API не входит; оно описано ниже.

### Билет на использование ключа и `PluginConsentGuard`

Если манифест плагина объявляет `[[operations]]`, вызвать его через `plugin_call` можно только под объявленным именем операции — кто бы ни выбрал имя (ручное окно, grant сервера, флаг CLI). Любое другое имя отклоняется до запуска модуля: `PermissionDenied`, `NotApplied`, `OperationContext::plugin_refusal() == Some(TicketRefusal::UndeclaredOperation)`. Сервер пропускает такой grant (и пишет ошибку в журнал), CLI отклоняет вызов. Плагины без объявлений не затронуты.

Вызов под объявленным именем получает **билет** использования ключа. Для каждой из операций `keys_sign_raw`, `keys_sign_cms`, `keys_sign_cms_ex`, `keys_sign_xml`, `keys_sign_xml_ex`, `keys_sign_xades` Core один раз декодирует аргументы, строит из этого значения `plugins::PluginUse` и кладёт его в контекст операции. `AuthorizedSigner::sign_digest` переносит его в `KeyUseEvent` (`KeyUseEvent::plugin()`; `None` для использования документом и для плагинов без объявлений).

В билете записано:

- кто: идентичность плагина (`id`, `PackageHash`, версия) и вызывающий;
- что: объявленная операция, вид подписи, handle и `KeyId` единственного привязанного ключа;
- над чем: `ContentBinding` — SHA-256 и длина подписываемых байт (`prehashed` для входа CMS `Digest`);
- с какими опциями: `options_sha256`. Это SHA-256 от `oncl_plugin::operations::Profile::encode` по профилю, построенному из фактических аргументов, тем же кодировщиком, что у `KeyUse::options_sha256` для объявленного профиля.

Билет допускает ровно одно использование (`max_uses = 1`). Объявленная операция привязывает не больше одного ключа; любой импорт, принимающий ключ (`keys_describe`, `keys_chain`, `keys_release`, импорты подписи), на другой handle отвечает `PermissionDenied`, а `keys_release` привязанного handle можно повторять.

Что отклоняется до открытия ключа:

- аргументы, которые профилем выразить нельзя: CMS с со-подписью, `attrs.extra`, `econtent_type`, выбор `digest`, сертификаты `Extra`, свой TSA, signingTime не по умолчанию, XML `signature_id` и объект signing-time, XML `transforms` не в виде проверяемого списка, цепочка XAdES;
- импорт, вид которого операция не объявляет, и операция, чьё содержимое объявлено как `derived`.

XML `transforms` принимаются только в виде списка: сначала `enveloped`, затем не больше одной канонизации. Пустой список и любой другой порядок отклоняются; список входит в хеш опций. `cosign = Auto` принудительно становится `Never`, поэтому содержимое билета равно тому, что реально подписывается.

`KeyUseEvent::plugin()` есть только с feature `plugins` крейта `oncl-core`. `KeyUseEvent::is_plugin()` доступен всегда и говорит, несёт ли событие билет (без feature всегда `false`). **`KeyUseGuard` хоста, который регистрирует плагины с объявленными операциями, обязан отклонять любое событие с `is_plugin() == true`, если это не охранник плагинов.** Иначе охранник документов, не глядя на билет, разрешил бы использование ключа плагином как использование документом. `oncl-server`, `oncl-cli` и `ConsentGuard` из `oncl-ui` так и делают.

`PluginConsentGuard` — это `KeyUseGuard` движка плагинов. Его `before_use` отклоняет использование (`PermissionDenied`, ключ не применён), если не выполнены оба условия:

1. событие несёт билет;
2. у охранника есть непросроченный `PluginApproval` для того же вызова, плагина, операции, вызывающего, ключа и handle, с одним неистраченным `ApprovedUse`, у которого вид, содержимое и хеш опций равны билету.

Тогда использование тратится. Без одобрения охранник отклоняет всё, в том числе использование ключа документом (без билета): документам нужен свой движок. Причина отказа пишется по `OperationId` в ограниченный журнал на `REFUSAL_LOG` (64) записей: `refusals(id)`, `take_refusals(id)`, `refusal_log()`.

`PluginApproval` нельзя клонировать и десериализовать, публичного конструктора нет: его выдаёт Core (см. ниже), nonce принимается один раз. Охранники сервера (`DurableAuditGuard`) и CLI (`Authority`) отклоняют каждое использование по билету, пока у них нет собственных grants (`plugin_bytes`). Плагины без объявлений не затронуты.

### Ручное окно: сводка, согласие и одобренный вызов

Ручное окно работает в три шага Core, в таком порядке (подробнее — `docs/design/manual-plugins.md`, 4.2, 4.3, 4.8). И `plugin_prepare`, и `plugin_call_approved` принимают один и тот же `ManualCall { plugin_id, operation, params, key: &PluginKeyBinding, caller: &CallerContext }`.

**Шаг 1. `Engine::plugin_prepare(&ManualCall, &mut OperationContext)`.** Возвращает `PluginPrepared` или `PluginPrepareError` (всегда `NotApplied`). Что он делает:

- один раз открывает ключ. Вход в токен или расшифровка хранилища происходят здесь и ещё раз при вызове, поэтому хост собирает секрет **до** показа согласия и кладёт его в запрос ключа в привязке; неудачное открытие — это `KeyUnavailable` без причины;
- проверяет параметры так же, как `plugin_request`;
- замораживает то, что будет подписано: байты привязанного параметра, их SHA-256 и длину. Для профиля `cms_ex` с `content_form = digest` это дайджест, который Core сам считает хеш-алгоритмом подписи привязанного ключа (ГОСТ 34.311, Стрибог или SHA-2 — по сертификату и политике контекста), той же функцией, что позже использует подписант. Дайджест, названный плагином, не принимается никогда;
- считает хеш опций (`KeyUse::options_sha256`; источники `param:` профиля заполнены из типизированных текстовых параметров тем же кодировщиком, что на стороне билета);
- требует, чтобы `caller` был `CallerContext::LocalOperator` (у ручного окна нет origin), а привязка ключа несла публичные метаданные (`with_public_metadata`: alias и сертификат). Метаданные — заявление хоста о ключе, которым подписывают. Core показывает их, отдаёт плагину (`BoundKey`, `keys_describe`), а `plugin_prepare` сверяет их сертификат с тем, что хранилище держит для ключа (`CertificateMismatch`).

`PluginPrepared::summary()` возвращает `ConsentSummary` — **доверенное** описание для показа пользователю: идентичность `{id, PackageHash, version}`, имя операции, вид, число использований, объявленный профиль с подставленным текстом пользователя, хеш опций, имя параметра содержимого, длина, SHA-256 и prehashed-дайджест, alias ключа, серийный номер, subject CN, отпечаток SHA-256 и `not_after`, а также PKI-адреса, которые зарегистрировал хост. Текста плагина в сводке нет (`name`, `description`, `label` остаются в собственном кадре плагина). `key.alias` и `key.subject_cn` — строки хоста и сертификата, поэтому отрисовщик обязан их экранировать.

**Шаг 2. `UserConfirmation::after_user_confirmed(&ConsentSummary)`.** Только так можно получить токен, который принимает `PluginPrepared::approve(confirmation, ttl)`. Обязанность хоста: вызывать его только из обработчика действия пользователя на кнопке подтверждения, после того как отрисована именно эта сводка. Автоматически, заранее или по сохранённому ответу подтверждать нельзя (ничего не сохраняется). Токен называет SHA-256 показанной сводки, так что подтверждение одной сводки не одобряет другую; его нельзя клонировать и копировать.

`approve` возвращает `PluginApproval`. В нём: вид, привязка содержимого и хеш опций из `prepare`, одно использование (`max_uses = 1`), вызов того контекста, с которым он подготовлен, срок `ttl` по монотонным часам от текущего момента и nonce из 16 байт CSPRNG операционной системы (при сбое генератора ничего не выдаётся). `ttl = None` — это `APPROVAL_TTL`, 120 с; больший запрос обрезается до него, ноль отклоняется.

**Шаг 3. `Engine::plugin_call_approved(&ManualCall, PluginApproval, &ManualHost, &mut OperationContext) -> ApprovedCall`.** Запускает модуль в ручном окне. Перед запуском он заново выводит использование из параметров, переданных **сейчас**, и отклоняет одобрение, выданное не ровно для них (другой документ, текст, ключ, handle, вызывающий, операция, вызов; просрочка). Поэтому модуль никогда не видит документа, который пользователь не одобрял. Дальше он строит запрос (`plugin_request`), передаёт одобрение `PluginConsentGuard` и запускает `oncl_plugin::Compiled::call_manual` со свежим `BoundInteraction`:

- `BoundKey` строится из того же `PluginKeyBinding`, которым подписывает бэкенд;
- часы — часы проверки, считанные в момент вызова;
- транспорт и `OcspCache` — хоста, из `ManualHost`;
- origin нет.

Окончательную проверку при использовании ключа всё равно делает охранник. Одобрение отзывается, когда вызов закончился (`Drop`: и при trap, и при ошибке, и при панике).

Требования к движку:

- он должен быть построен через `EngineServices::with_plugin_keys(provider, Arc<PluginConsentGuard>)` — это его единственный охранник ключей. `with_keys` его сбрасывает, и одобренный вызов тогда отклоняется с `TicketRefusal::NoGuard`;
- одновременно идёт один одобренный вызов (`Busy`);
- документы держите на другом движке: `ConsentGuard` десктопа отклоняет событие с билетом, а охранник плагинов — событие без билета.

**Сертификат подписанта.** Одобрение привязывает SHA-256 сертификата: его несут `ApprovedUse` и `PluginUse`, его показывает `ConsentSummary.key.fingerprint_sha256`. `plugin_prepare` открывает ключ один раз и отклоняет (`CertificateMismatch`), если сертификат хранилища не совпадает с метаданными привязки. В точке подписи `AuthorizedSigner` ставит в билет отпечаток сертификата, который держит аренда ключа; охранник (и быстрая проверка `plugin_call_approved`) отклоняют другой отпечаток с `TicketRefusal::CertificateChanged`, ключ не применён. Alias нужен только для показа и не сверяется. Алгоритм prehash выбирается по тому же строгому правилу, что у подписанта.

Практические замечания:

- давайте каждому движку свой `PluginConsentGuard` (у него один слот одобрения);
- вызов, отклонённый как `Busy`, расходует своё одобрение: пользователю придётся подтвердить снова;
- хосты **обязаны** задавать срок в контексте, который передают в `plugin_call_approved`: плагин держит слот операции, пока не истечёт срок или топливо;
- срок одобрения — монотонный `Instant`, он может не идти, пока система приостановлена.

`ApprovedCall` описывает исход честно:

- `result()` / `response()` — строка ответа модуля;
- `applied()` — `Applied` (в том числе когда модуль упал после использования ключа), `Unknown` (когда само приложение не сообщило) или `NotApplied` при любом отказе;
- `refusals()` — типизированные `TicketRefusal` этого вызова (от охранника или от проверок до запуска модуля), плюс `NoGuard`, `Busy`, `Replayed`, `UndeclaredOperation`, `Caller`.

### Коды отказов и аудит

`ErrorCode` не меняется. Рядом с ним у каждого отказа плагина есть `PluginRefusalCode` (стабильный, `#[non_exhaustive]`):

- `id()` — строка в kebab-case (`content-mismatch`, `package-changed`, `approval-expired`, `not-declared`, `not-granted`, ...). Она **никогда не переиспользуется и не перенумеровывается**;
- `ALL` перечисляет все коды в порядке «только добавлять»; тест фиксирует полный список id, поэтому любое изменение сделано намеренно;
- `error_code()` — `ErrorCode`, с которым сообщается отказ (тот же, что даёт `OperationError::code`): `PermissionDenied` для отказов по билету, вызывающему и объявлению; `InputLimit` или `InvalidInput` для параметров; `UnsupportedAlgorithm`, `MissingKeyProvider`, `Io`.

Код есть у каждой причины: `From<TicketRefusal>`, `From<&PluginRequestError>`, `From<&PluginPrepareError>`, `From<ApprovalIssueError>`, `From<ApprovalRejected>` и метод `subcode()` у каждой. Два особых случая:

- `TicketRefusal::NotGranted` — сервер или CLI использует ключ, а ни один grant оператора это не покрывает;
- `TicketRefusal::AuditFactTooLong` — версию или id grant нельзя записать в аудит (больше 255 байт); отказ происходит до обращения к журналу.

`DurableAuditGuard::with_plugin_policy` возвращает `io::Result<Self>` (ошибка, если охранник уже разделён).

Где хост это читает:

- `ApprovedCall::subcode()` — первый отказ охранника, иначе причина, по которой вызов нельзя было подготовить; `None`, когда ничего не отклонено (в том числе после ошибки, случившейся после применения ключа);
- `OperationContext::plugin_refusal_code()` — необъявленное имя, отклонённое в `plugin_call`;
- для сервера с `DurableAuditGuard` — `take_plugin_refusals(operation_id)`, отображается через `PluginRefusalCode::from`.

Сам плагин код никогда не видит: его ошибка — голый `PermissionDenied` без текста причины.

`PluginAuditRecord::from_ticket(&PluginUse, nonce, grant_id)` — то, что записывает аудит использования:

- плагин `{id, вид пакета + sha256, version}` и операция;
- `PluginUse::digest()` — дайджест билета;
- SHA-256 nonce одобрения с разделением по доменам (сам nonce не пишется никогда);
- SHA-256 и длина содержимого и признак, что содержимое — prehashed-дайджест;
- SHA-256 опций;
- вид вызывающего (не его имя), `declared` и `grant_id` оператора.

Ни байтов документа, ни параметров, ни секретов в записи нет. `PluginConsentGuard` выдаёт запись событием `tracing` (`target = "oncl::plugin_audit"`), когда использование разрешено; отказ с его `subcode` и дайджестом билета — событием `warn`. Отказы, которые до охранника не доходят (ошибка запроса или `prepare`, одобрение, отклонённое вызовом), — тоже события `warn` с тем же target и `subcode`. Долговременная форма аудита — в [`server.md`](../user/server.md).

### Подделки для тестов

`PluginApproval::new`, `ApprovedUse::new` и остальные конструкторы непубличны. Feature `testing` крейта `oncl-core` (в выпуск не входит никогда) добавляет `PluginApproval::for_tests`, `ApprovedUse::for_tests`, `PluginUse::for_tests` и `KeyUseEvent::with_plugin_ticket_for_tests`: они подделывают то, чего Core никогда бы не сделал, — только для тестов охранников.

Программы выпуска собираются с `-p`, но `cargo build --workspace --all-targets` и `cargo test` склеивают `testing` из dev-зависимостей в те же бинарники. Поэтому CI запускает `cargo xtask check-release-features`: он читает `cargo tree -p <openncalayer|oncl-cli|oncl-server|oncl-ui> -e normal -f "{p} [{f}]"` (features обычного дерева, без dev-зависимостей) и падает, если у какого-либо крейта виден `testing`.

## 6. Версии и миграция

Здесь написано, как нумеруются версии и что менялось в публичном API между выпусками.

- Версия общая для всех крейтов SDK и приложений (`[workspace.package]`). У плагинов свои версии.
- До 1.0 (`0.1.0-alpha.N`) любая альфа может сломать публичный API любого крейта SDK. Каждая поломка требует повысить версию и добавить строку в таблицу миграции ниже. Модули не становятся стабильным контрактом только потому, что они `pub` внутри workspace.
- Версия SDK — **следующая невыпущенная** на момент изменения, читается из тегов и манифестов, а
  не угадывается. Версия `[workspace.package]` в этом дереве — `0.1.1`; предыдущий
  выпущенный тег — `v0.1.0`.

## 7. Готовность к публикации

Короткий итог: проверить, что SDK собирается и работает из упакованных исходников, можно офлайн; сама публикация в реестр заблокирована и не выполнялась.

Цепочка крейтов SDK в порядке публикации (каждый крейт идёт после тех, от которых зависит):

`oncl-gost` → `oncl-registry` → `oncl-pki` → `oncl-pdf` → `oncl-protocol` → `oncl-pdk` →
`oncl-xml` → `oncl-token` → `oncl-flows` → `oncl-update` → `oncl-plugin` → `oncl-core`

Это все крейты, достижимые из `oncl-core` со всеми features плюс `distribution` крейта `oncl-plugin` (`oncl-update`). У них есть `description`, `license` (Apache-2.0), `repository`, `rust-version`, `keywords`, `categories`, список `include` и `publish = true`. В `include` входят исходники, данные, которые встраивает сборка, `LICENSE` и `NOTICE`; тестов, fixtures, корпусов, скриптов и оракулов там нет. `oncl-core` дополнительно поставляет `README.md`, три примера и `THIRD-PARTY.txt`.

Всё остальное остаётся `publish = false`: `oncl-ui`, `oncl-desktop`, `oncl-api`, `oncl-server`, `oncl-cli`, `openncalayer`, `oncl-nmhost`, `oncl-tls`, `oncl-trust`, `oncl-ipc`, встроенные модули и их сборочные и тестовые крейты, прослойки для Windows 7, `oncl-testkit`, `oncl-port-tests`, плагины.

### Что проверяет `cargo xtask sdk smoke`

Проверка не требует ни реестра, ни загрузки:

1. `cargo package --offline` для всей цепочки **с** верификацией: каждый крейт собирается из своего упакованного архива, а соседние крейты берутся из локального набора архивов cargo. Нужны `--config patch.crates-io.hmac.git=…` / `.rev=…` и то же для `streebog`; форки должны быть в кэше cargo (`cargo fetch --locked`), загрузки во время проверки нет.
2. Файлы `.crate` распаковываются; внутри не должно быть `tests/`, `fixtures/` и `target/`, а `LICENSE` и `NOTICE` должны быть.
3. Отдельный крейт (свой `[workspace]` и свой lock-файл) зависит по path от `oncl-core` (`full`) и `oncl-pki` из распакованных исходников; на остальные распакованные крейты и на изменённые `hmac` и `streebog` указывает `[patch.crates-io]`. Его `cargo metadata` не должен показывать ни одного локального пакета вне распакованных исходников, а `cargo tree` — ни одного запрещённого крейта (UI, десктоп, обновление, сервер, рантайм). Затем он собирается и запускается: настоящие подпись и проверка CMS, изменённый документ отклонён, офлайн-подпись отклонена с `NotApplied`. В этом процессе нет ни дисплея, ни демона, ни сборщика метрик, ни слушающего порта.

Команды: `cargo xtask sdk closure`, `cargo xtask sdk smoke [--keep]`, `cargo xtask sdk licenses [--check]`.

Тяжёлая проверка запускается вручную (для владельца релиза или CI; ни в одном workflow здесь не подключена). Из корня workspace, на машине с заполненным кэшем реестра (`cargo fetch --locked`), запустите `cargo run -p xtask -- sdk smoke`. Успех: код 0 и последняя строка `SDK-CONSUMER-OK`; `--keep` оставляет `target/sdk-smoke` для разбора. Нужен `tar` в `PATH` (GNU или bsdtar). Сборка занимает минуты (генерируются RSA-ключи, собирается `oncl-core` с `full`).

Автоматический тест `cargo test -p xtask --test sdk_delivery` (без сети и сборки, только `cargo metadata` и `cargo tree`) следит, чтобы:

- набор крейтов с включённым `publish` совпадал с `xtask::sdk_delivery::CHAIN`, а цепочка шла в порядке зависимостей;
- ни одно сочетание features `oncl-core` не тянуло Slint, winit, tokio, axum, hyper, velopack и другие запрещённые крейты;
- `THIRD-PARTY.txt` был актуален;
- крейт из набора зависимостей, которого нет в карте реестра, вызывал ошибку с его именем, а не тихий пропуск.

### Что не проверено и не заявляется

- **Публикация заблокирована.** `oncl-gost` и `oncl-pki` нужна дополнительная feature `secret-input` у изменённых `streebog` и `hmac`. В версиях из crates.io её нет, поэтому `cargo package` крейта `oncl-gost` без настроек patch падает («`hmac` does not have that feature»). `cargo publish` сначала пакует, так что остановится он там же (не запускали: здесь ничего не публикуется). Перед любым выпуском эти форки нужно либо опубликовать под именами, которыми мы владеем, либо предложить upstream, и изменить манифесты. Это отдельное решение, в эту поставку оно не входит.
- Свободны ли имена крейтов в реестре и не заняты ли они кем-то, не проверялось.
- `cargo publish --dry-run` против настоящего реестра, загрузка и проверки после неё остаются за отдельно разрешённой публикацией.
- Проверка потребителя (`sdk smoke`) работает только на платформе хоста. Матрица Linux, macOS и Windows 7 — отдельные проверки (приёмочный прогон «1 ГиБ / 1 ГиБ» выполнен, см. раздел 5).

## 8. Лицензии и уведомления

Каждый крейт цепочки поставляет `LICENSE` (Apache-2.0) и `NOTICE`.

- `oncl-pki/roots/` встраивает сертификаты промышленных УЦ НУЦ. Это публичные документы; права на сертификаты принадлежат их эмитенту и не лицензируются под Apache-2.0 (см. `fixtures/README.md`). `testing-data/` — синтетический ключ.
- `crates/oncl-core/THIRD-PARTY.txt` перечисляет сторонние крейты SDK (из crates.io и git-форки из `[patch.crates-io]`, каждая поставляемая платформа, включая `distribution` плагинов) с текстами лицензий. Файл генерируется командой `cargo xtask sdk licenses`, актуальность проверяет `--check`.
- Отдельная опись лицензий программ — `cargo xtask licenses`.

## Лимиты свидетельств и большие CRL, встроенные в подпись

«Свидетельства» здесь — сертификаты, ответы OCSP, CRL и токены меток времени, которые лежат внутри подписи или передаются вместе с ней.

В `oncl_pki::evidence::EvidenceLimits` есть три публичных поля. Они ломают сборку у тех, кто создаёт структуру литералом (все литералы в дереве исправлены):

| Поле | Смысл |
|---|---|
| `max_crl_bytes` | сколько всего CRL можно принять во временное хранилище |
| `max_crl_item_bytes` | сколько на один CRL; не выше `crl::MAX_CRL_LEN` (64 МиБ) |
| `max_total_bytes` | сумма по всем видам свидетельств, включая CRL |

`EvidenceLimits::validate` отклоняет нулевые `max_crl_bytes`, `max_crl_item_bytes` и `max_total_bytes` ошибкой `EvidenceError::InvalidLimits` (как и нулевой `max_bytes`). Порядок трёх значений не навязывается: при приёме берётся минимум из предела элемента, суммы по CRL и общей суммы, а предел элемента ещё ограничивается `MAX_CRL_LEN`. Если одно значение выше другого, оно просто не определяет предел. `EvidenceLimits::intersect` — единственный поэлементный минимум двух наборов; им пользуются `oncl-core` и `oncl-xml`.

`max_bytes` и `max_item_bytes` теперь относятся только к свидетельствам, которые не CRL. Чтобы сохранить прежний допуск, задайте `max_crl_bytes = max_total_bytes = max_bytes` и `max_crl_item_bytes = max_item_bytes`.

Как принимается CRL:

- CRL больше `crl::MAX_BER_CRL_LEN` (1 МиБ) должен быть в DER. Он сканируется на месте через `crl::serial_status` и списывается один раз;
- меньший CRL может быть в BER; он приводится к дереву и списывается усиленно, как сертификаты, ответы OCSP и токены;
- `EvidenceStore::collect_base64` принимает свидетельство из текста base64 с квотами на декодированный размер (для XML).

### Пределы в поставляемых программах

| Программа | Что принимает |
|---|---|
| CLI | CRL до 32 МиБ (прочие свидетельства — 16 и 1 МиБ, всего 48 МиБ) при проверке; потолок покрытия — размер документа (потолок вывода) |
| `oncl-server` | тот же потолок покрытия: `max_coverage_bytes` — это потолок вывода операции, а не `input_bytes` (метка PAdES LT → LTA покрывает весь подписанный документ, а он при полном допуске уже больше `input_bytes`) |
| `oncl-server`, `oncl-ui` | прежние границы: подпись и продление с полным CRL НУЦ (около 20 МБ) отклоняются |

Подробности:

- Решение владельца: эти лимиты остаются.
- У сервера часть запроса со свидетельством — не больше 1 МиБ (`EVIDENCE_ITEM_BYTES`, читается раньше), а 2 МиБ на CRL — квота движка для свидетельств внутри проверяемого контейнера. У `oncl-ui` — 1 МиБ.
- Квота CLI в 32 МиБ на CRL (48 МиБ всего, `args.rs`) относится к проверке. При подписи файлы `--evidence-*` ограничены 256 КиБ каждый и 8 МиБ всего (`evidence.rs`), а для XAdES-LT/LTA потолок ещё ниже.
- Хост, которому нужно другое, задаёт `max_crl_*` сам.
- Хост, который отдельно ограничивает PDF-свидетельства, должен выводить границу из `EvidenceLimits.max_total_bytes` (ни один поставляемый хост так пока не делает; см. надбавку контейнера в разделе 5). Потоки свидетельств DSS в PDF читаются областями и больше не ограничены `PdfLimits::max_object_bytes` — только учётом контейнера и памяти и квотами свидетельств.

### Что покрыто, а что нет

Покрыто: офлайн-проверка CMS/CAdES и XAdES со встроенным полным CRL. Не покрыто:

- загрузка CRL по сети (`crl::fetch_for`: он по-прежнему декодируется целиком, с усиленным списанием 128×);
- файлы CRL оператора (`--evidence-crl`, не больше 256 КиБ на файл);
- загрузка по сети для PAdES-LT;
- сторона подписи для XAdES (ниже).

Структурные защиты PAdES (`/ID` trailer, свободная голова объекта 0) исправлены. Проверка PAdES-LT настоящих файлов NCANode ограничена чтением областей DSS и пределом надбавки контейнера (раздел 5).

### XAdES с полным CRL: проверка

NCANode и Kalkan пишут в XAdES-LT полный CRL НУЦ (около 20 МБ, 27 МБ в base64 с `&#13;` в конце строк) в `xades:EncapsulatedCRLValue`. Как проверка с этим справляется:

- `XmlVerifyProfile::max_metadata_bytes` теперь ограничивает только структурную разметку. Текст листьев `EncapsulatedX509Certificate`, `OCSPValue` и `CRLValue` сканер записывает как исходные диапазоны, вычитает из свойства, в котором они лежат, и потоком пропускает через `EvidenceStore::collect_base64` (ссылки на сущности и CDATA декодируются на лету, буферы по 16 КиБ);
- декодированные байты списываются с `max_crl_item_bytes`, `max_crl_bytes` и `max_total_bytes` до сохранения. `String`, DOM и `Vec` с base64 для листа не создаются;
- `validate_unsigned_layout` решает по структуре, записанной сканером. Для архивной метки времени канонические текстовые отрезки каждого листа берутся у канонического рендерера (`canonical_stream::stage_with_leaves`), а не из разбора отрендеренных байт;
- текст корректного листа ограничен только квотами свидетельств на его декодированные байты. Лист из пробелов декодируется в ничто и ограничен лишь размером входа (он идёт потоком и никогда не удерживается);
- XAdES внутри WS-Security сохраняет прежнюю границу (`70 × max_metadata_bytes` на `Signature`): CRL больше примерно 17 МБ внутри SOAP-конверта по-прежнему отклоняется.

Что изменилось для хоста:

- заданные хостом `EvidenceLimits` больше не обрезаются лимитом метаданных. `effective_limits` лишь масштабирует значения по умолчанию у хоста, который ничего не настраивал, на путях подписи и продления (функция общая). Ненастроенный хост SDK по-прежнему отклоняет CRL больше 256 КиБ ошибкой `EvidenceError::Limit`;
- `VerifyRequest::xades_with_limits` — аналог `cades` и `pades` для XAdES; CLI использует его со своей квотой CRL 32 МиБ;
- обратное чтение просканированного CRL (DER, больше 1 МиБ) списывается только как память, но не ещё и как метаданные (допуск XML-индекса — 56 МиБ из 64 МиБ бюджета метаданных по умолчанию);
- `oncl-server` и `oncl-ui` лимиты XAdES не передают и продолжают отклонять.

### XAdES с полным CRL: подпись

Не покрыто. `xades::source::material_xml`, `complete_signature`, `sign.rs`, `xades.rs` и `references/extension.rs` по-прежнему строят неподписанные свойства как `String`, ограниченную `max_metadata_bytes`. Поэтому потолок подписи и продления XAdES-LT/LTA такой:

- у хоста без настроенных `EvidenceLimits` один CRL — не больше 256 КиБ (`max_metadata_bytes` по умолчанию 262144). CRL ровно в 256 КиБ проходит предварительную проверку, на байт больше — `EvidenceError::Limit` до чтения документа (тест `default_signing_limits_refuse_a_crl_one_byte_over_the_markup_cap`);
- сумма всех сертификатов, ответов OCSP и CRL (в сыром виде) и готовый текст свойств (base64, ×4/3) тоже не больше `max_metadata_bytes`, иначе `MetadataLimit`. По этим проверкам CRL в подписи не больше примерно 190 КиБ (256 КиБ × 3/4; значение вычислено по коду, не измерено), и он делит это место с сертификатами и ответами OCSP;
- `max_metadata_bytes` не может быть больше 1 МиБ (профили это отвергают), поэтому даже при максимальной настройке потолок на всё свидетельство — около 768 КиБ.

Полный CRL НУЦ (около 20 МБ) поэтому нельзя ни подписать, ни продлить в XAdES-LT/LTA ни на одном хосте. Решение владельца: оставить лимиты и описать это здесь. Если понадобится снять ограничение, замысел такой: писать сгенерированные свойства в промежуточный артефакт (при exclusive C14N их каноническая форма равна тексту, которым они генерируются, так что покрытие архива и отрезки листьев не требуют разбора; доказать дифференциальным тестом против `canonical_stream`) и собирать голову, промежуточные неподписанные части и хвост.

## Статус отзыва внутри LT/LTA оценивается на момент доказательства

Ответы OCSP и CRL, которые лежат внутри подписи (CAdES, PAdES, XAdES уровней `LT` и `LTA`), нужны, чтобы проверять подпись долго после выпуска. Раньше они оценивались по часам проверяющего (`nextUpdate`, `ALLOWED_PERIOD`, срок сертификата ответчика на `now`). Из-за этого документ, который при подписании давал `Valid`, через несколько минут становился `Indeterminate`, при любом размере.

Теперь правило одно, оно живёт в `oncl-pki` (`ocsp::check_embedded_at_proof`, `crl::serial_status_at_proof`; выбираются через `validation::offline_revocation`, переключатель — `pkix::Currency`) и общее для CAdES, XAdES и PAdES.

### Правило

Пусть `P` — время доказательства. Встроенный ответ OCSP или CRL о сертификате пути принимается, если все прежние проверки по-прежнему проходят (CertID, привязка эмитента, подпись, цепочка ответчика и OCSPSigning/no-check; `unknown` отклоняется; CRL должен быть полным CRL эмитента) и дополнительно:

- **ответ свеж на `P`** (EN 319 102-1 5.2.5.4: максимальная свежесть — `nextUpdate - thisUpdate`, если ограничение не говорит иное). Если есть `nextUpdate` (у каждого CRL и у ответа OCSP, который его содержит), ответ свеж тогда и только тогда, когда `P < nextUpdate`. Поэтому 35-дневный CRL УЦ, выпущенный за несколько часов до доказательства, годится. Если `nextUpdate` нет (OCSP НУЦ), ответ свеж тогда и только тогда, когда `P - CLOCK_SKEW < thisUpdate` (300 с, строго);
- `thisUpdate <= now + CLOCK_SKEW` (для CRL: `thisUpdate <= now`): ответ не может быть из будущего проверяющего;
- сертификат ответчика строит цепочку **на момент `thisUpdate`**, а не `now`;
- `nextUpdate` и `ALLOWED_PERIOD` с `now` не сравниваются.

Что считается `P`:

- для `T` и `LT` — genTime метки времени подписи (для документной метки PAdES это первое доказательство);
- для `LTA` — тот же genTime метки времени подписи. Архивные метки защищают свидетельства, но `P` не двигают (статус, добавленный после метки подписи и до архивной, должен оставаться допустимым);
- встроенный статус сертификата самой службы меток времени оценивается так же, с genTime того токена в роли `P`;
- если времени доказательства нет (уровень `B`, метки нет или она недействительна), `at` равен `now` и действует прежнее правило. Статус, полученный онлайн, всегда оценивается как актуальный на `now`.

Без изменений: сертификаты подписанта и цепочки оцениваются как действительные **на `P`** (так было и раньше). Отозван в `P` или раньше — `Invalid`. Отозван после `P` — подпись остаётся действительной и сообщается `RevokedAfterProvenTime`.

### Какие статусы учитываются

Для одного сертификата оценивается каждый встроенный ответ OCSP и CRL, прошедший проверки выше, в произвольном порядке (их число ограничено лимитами хранилища свидетельств).

- Любой приемлемый `revoked` отзывает. Сообщается самое раннее время отзыва среди них: в `P` или раньше — `Invalid`/`Revoked`, после `P` — `RevokedAfterProvenTime`.
- `Good` требует хотя бы одного приемлемого `good` и ни одного `revoked`; иначе статус остаётся `Unavailable`.
- Неприемлемый статус (устарел, не тот эмитент или ответчик, другой сертификат, `unknown`) по-прежнему игнорируется и никогда не превращает `Unavailable` в `Good`. Ответ `good`, стоящий первым, больше не скрывает последующий `revoked`.

Слабое место, которое остаётся: статус, полученный онлайн (`check_path_revocation`), использует ОДИН источник на сертификат. CRL загружается, только если OCSP не дал ни `good`, ни `revoked`. Поэтому `good` от OCSP-ответчика принимается, хотя CRL мог бы сказать `revoked`. EN 319 102-1 требует приемлемой информации о статусе, а не всех доступных источников, так что это выбор политики; он зафиксирован как открытый. Кроме того, внутри цикла по статусам в `offline_revocation` нет контрольной точки работы или срока (граница — только лимиты хранилища свидетельств; худший случай равен прежнему случаю без приемлемого статуса).

### Откуда это в стандарте

ETSI EN 319 102-1 V1.3.1 (прочитано по опубликованному тексту):

- 5.2.5.4 (проверка свежести отзыва): статус свеж, когда `issuance time > validation time - maximum accepted freshness`;
- 5.5.4 шаг 6 повторяет проверку со *временем лучшей подписи*, если статус не был свеж относительно текущего времени;
- 5.5.4 шаг 4a: время отзыва после времени лучшей подписи подпись не делает недействительной; в этот момент или раньше — `INDETERMINATE/REVOKED_NO_POE`;
- 5.2.6.4 (проверка сертификата X.509) запускает проверку со временем проверки и не сверяет с ним сертификат подписи CRL эмитента;
- умолчание `nextUpdate - thisUpdate` из шага 1 5.2.5.4 применяется к ответам с `nextUpdate`. Для ответов OCSP НУЦ без него свежесть задаёт ограничение `CLOCK_SKEW` (стандарт для таких случаев говорит FAILED, пока ограничение не задано).

### Окно повторного использования

Злоумышленник, у которого есть ответ «good» до отзыва, может использовать его в течение срока действия самого ответа, `nextUpdate - thisUpdate`: до 35 дней для CRL НУЦ и 300 с для ответа без `nextUpdate`. Архивная метка времени (доказательство существования `LTA`) это окно не сужает: `P` — genTime метки подписи, а архивные метки лишь защищают встроенное. Это умолчание стандарта и окно прежнего правила на момент подписания.

### Что не проверено и чем намеренно отличается

0. Доказательства на настоящей PKI нет. Закреплённые fixtures NCANode LT никогда не доходят до времени доказательства, поэтому каденция НУЦ (35-дневный CRL корня, выпущенный за часы до метки времени) проверена записанным производственным CRL (`tests/crl.rs`) и синтетическим 35-дневным CRL, а не `Valid`-документом настоящей PKI. Простой CMS офлайн покрыт тестом `oncl-core` `offline_cms_status_is_judged_at_the_proof_time_not_the_host_clock`. `P` — ПОСЛЕДНЯЯ прошедшая метка времени подписи, а стандарт (5.5.4 шаг 3b) берёт самую раннюю (так было и раньше, это консервативнее).
1. 5.6.2.2.4 шаг 2a также просит доказательство существования информации об отзыве не позже контрольного времени. Для `LTA` это архивная метка времени, связывающая свидетельства; её проверяет граф свидетельств. Для `LT` оно не запрашивается (кроме метки подписи ничего нет), как и в 5.5.4.
2. Строгое `>` и свежесть 300 с — выбор в пределах ограничения, которое стандарт оставляет политике проверки; стандарт не предписывает эти значения.
3. Отозван в `P` или раньше — здесь `Invalid`; стандарт говорит `INDETERMINATE/REVOKED_NO_POE` (мы строже, без изменений).
4. Правило модели цепочки стандарта о компрометации ключа при отзыве УЦ после `P` не моделируется.

## Плотные PDF: бюджет перекрёстных ссылок

`PdfLimits::max_objects` (по умолчанию 4096) ограничивает только обходы графа объектов: число полей AcroForm, элементы свидетельств DSS, члены одного потока объектов, обход представления подписи. Потолком размера документа он больше не служит. Размер документа в объектах ограничен `PdfLimits::max_xref_entries` (по умолчанию 4 Mi записей по ВСЕМ ревизиям), и за каждую запись платится:

| Что | Стоимость |
|---|---|
| строка перекрёстных ссылок (любой ревизии) | 16 байт памяти операции; резервируется по мере чтения строк (шагами не более 65 536 строк), а не заранее |
| серия последовательных номеров объектов | 32 байта (в худшем случае по одной на запись) |
| классическая таблица xref / поток xref | читается чанками по 64 КиБ / инкрементально разжимается (включая предиктор PNG) прямо в строки; декодированная таблица не удерживается, `max_object_bytes` и `max_decoded_bytes` на неё не действуют, размер после разжатия ограничен объявленными строками и `max_decode_work` |

До выделения любой строки отклоняется объявленное число сверх оставшегося бюджета и число, которое остаток файла вместить не может (для классической таблицы). Лишние или недостающие данные потока xref обнаруживаются только после того, как имеющиеся строки прочитаны и списаны: такой документ некорректен и всё равно отклоняется до использования ключа.

Ошибки:

- сверх бюджета — `PdfError::Limit("xref entries")` (ровно limit+1, по всем ревизиям);
- квота памяти, не вмещающая строки, — `MemoryLimit`;
- обе возникают при чтении, до любого использования закрытого ключа (`NotApplied`).

Классическая таблица принимается независимо от того, где падают границы чанков по 64 КиБ. Заголовок подраздела или запись, разрезанные концом чанка, перечитываются из свежего чанка (в том числе когда последний токен упирается в конец чанка и число может быть разрезано). Единица, которая начинается с начала чанка, принимается, если заканчивается раньше этого чанка по 64 КиБ, и отклоняется иначе. Заголовок подраздела, окружённый пробелами длиннее чанка, всё ещё может быть отклонён в зависимости от выравнивания (это отказ «закрытием»; в настоящих документах так не бывает).

Не списывается (ограниченные временные буферы): чанк чтения 64 КиБ, буферы строк разжатия и предиктора (`RowReader`, одна строка предиктора не больше `max_object_bytes`) и копия при росте вектора строк (не больше одного шага, 1 МиБ, сверх списанной ёмкости).

Хосты, которые делают предварительную проверку продления PAdES, добавляют строки через `budget::PriorSignatures::xref_entries` → `budget::PlanInputs::xref_entries` (`budget::xref_memory` — верхняя оценка, которую использует `plan_memory`); сервер так и делает. `budget::reader` больше не масштабируется с `max_revisions`.

Замеры (отладочная сборка, настоящий процесс `oncl`, `scripts/pdf-dense/gen_dense_pdf.py`, три ревизии, перепроверено pyHanko; подпись выходного файла цела на всём файле):
